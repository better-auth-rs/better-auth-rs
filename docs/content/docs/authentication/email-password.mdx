---
title: Email & Password
description: Sign up and sign in with email, password, and optional username.
---

The `EmailPasswordPlugin` handles user registration and authentication via email/password or username/password.

`POST /sign-in/email` and `POST /sign-up/email` accept `application/json` and `application/x-www-form-urlencoded`. Form values remain strings: omit `rememberMe` for its default rather than sending the string `false`. HTTP media and syntax errors occur before origin checks; endpoint field validation occurs before form CSRF checks. Native API input keeps its typed boolean values and bypasses HTTP parsing.

## Setup

These examples assume you've already defined `AppAuthSchema`. If you want a complete setup from entity definitions through Axum mounting, start with the [Axum integration guide](/docs/integrations/axum).

```rust
use better_auth::plugins::EmailPasswordPlugin;

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(
        EmailPasswordPlugin::new()
            .enable_signup(true)
            .username(true)
            .password_min_length(8)
            .require_email_verification(false)
    )
    .build()
    .await?;
```

### Plugin Options

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `enable_signup` | `bool` | `true` | Allow new user registration |
| `username` | `bool` | `false` | Enable username behavior; requires `username` and `display_username` fields |
| `require_email_verification` | `bool` | `false` | Require verified email before sign-in |
| `password_min_length` | `usize` | `8` | Minimum password length in UTF-16 code units |

Username behavior is opt-in. Call `.username(true)` for defaults, or register the standalone [Username plugin](/docs/plugins/username) for validators, normalization, validation order, immutability, and display-name options. Without either form, username routes are absent and registration or update requests ignore username fields.

Email signup derives a missing `username` from a valid `displayUsername` and fills an empty display name from `username`. The admission callback receives the parsed endpoint fields. Database hooks and adapter field policies then apply their configured normalization. Updates change only supplied fields, so changing a username preserves the existing display name.

The configured hasher and password limits also apply to password reset, password changes, and other credential operations. Configure one password policy for the application.

### Password storage and migration

The default hasher matches Better Auth 1.7.6: scrypt with `N = 16384`, `r = 16`, `p = 1`, and a 64-byte derived key. Passwords are normalized with NFKC. A random 16-byte salt is encoded as hexadecimal; that hexadecimal text is the scrypt salt. The stored format is `salt:hash`, with 32 lowercase hexadecimal salt characters and 128 lowercase hexadecimal hash characters. Hashing runs on Tokio's blocking pool.

Existing Better Auth scrypt credentials can be used directly. Earlier better-auth-rs releases created Argon2 PHC strings. The default hasher does not silently accept those strings. To retain that format explicitly, configure `.password_hasher(Arc::new(Argon2PasswordHasher))`. Both `ScryptPasswordHasher` and `Argon2PasswordHasher` implement `PasswordHasher`.

For a migration, implement an explicit `PasswordHasher` that writes scrypt and recognizes the legacy Argon2 format during verification. Then replace legacy credentials through the authenticated password-change or password-reset flow. Login does not automatically rewrite stored hashes. Applications that retain the legacy hasher keep writing Argon2 until the configuration changes.

Install [`HaveIBeenPwnedPlugin`](/docs/plugins/have-i-been-pwned) to reject compromised passwords before the selected hasher runs.

## Sign Up

Setting `.auto_sign_in(false)` or `.require_email_verification(true)` returns `token: null` for registration. Repeating registration for an existing email returns a fresh synthetic user and preserves the stored account and password. A synthetic response applies schema defaults and `returned` restrictions; it does not run database transforms. With both defaults unchanged, duplicates return `422 USER_ALREADY_EXISTS_USE_ANOTHER_EMAIL`.

`.on_existing_user_sign_up(Arc<dyn OnExistingUserSignUp>)` receives the existing user and signup request after the duplicate's password is hashed. `.custom_synthetic_user(Arc<CustomSyntheticUser>)` receives `SyntheticUserInput` containing submitted core fields, parsed application fields, and a fresh identifier. Return the synthetic field map; the public schema removes hidden and unknown fields.

When email verification is required, registration creates no session and password sign-in returns `403 EMAIL_NOT_VERIFIED` until verification succeeds. Install `EmailVerificationPlugin` with its sender to deliver verification links. Its configuration is shared automatically; an explicit `.with_email_verification(...)` attachment remains available.

```http
POST /sign-up/email
Content-Type: application/json
```

### Request

```json
{
  "name": "Alice",
  "email": "alice@example.com",
  "password": "secure_password",
  "username": "alice",
  "displayUsername": "Alice"
}
```

| Field | Required | Description |
|-------|----------|-------------|
| `name` | Yes | Display name |
| `email` | Yes | Valid email address |
| `password` | Yes | Must meet minimum length |
| `username` | No | Unique username for username-based sign-in |
| `displayUsername` | No | Case-preserved display version of username |
| `callbackURL` | No | Redirect URL after sign-up |
| `rememberMe` | No | Boolean; `false` creates a one-day session with browser-session cookies |

Omitting `rememberMe` or setting it to `true` uses the configured session lifetime and persistent cookie. Explicit `null` and non-boolean values return a validation error before creating a user. The option does not create a session when automatic sign-in is disabled. Signup writes session cookies inside its transaction before committed database after hooks run, matching the upstream failure ordering.

### Response

```json
{
  "token": "session_abc123...",
  "user": {
    "id": "uuid",
    "name": "Alice",
    "email": "alice@example.com",
    "emailVerified": false,
    "username": "alice",
    "displayUsername": "Alice",
    "createdAt": "2024-01-01T00:00:00Z",
    "updatedAt": "2024-01-01T00:00:00Z"
  }
}
```

### Errors

| Status | Condition |
|--------|-----------|
| 400 | Invalid email format, password too short, or `USERNAME_IS_ALREADY_TAKEN` |
| 422 | `USER_ALREADY_EXISTS_USE_ANOTHER_EMAIL` when enumeration protection is disabled |

## Sign In with Email

```http
POST /sign-in/email
Content-Type: application/json
```

### Request

```json
{
  "email": "alice@example.com",
  "password": "secure_password"
}
```

| Field | Required | Description |
|-------|----------|-------------|
| `email` | Yes | Registered email address |
| `password` | Yes | Account password |
| `callbackURL` | No | Redirect URL after sign-in |
| `rememberMe` | No | Defaults to `true`. Set `false` for a 24-hour session and a browser-session cookie. |

### Response

```json
{
  "redirect": false,
  "token": "session_abc123...",
  "url": null,
  "user": { ... }
}
```

### Errors

| Status | Condition |
|--------|-----------|
| 400 | Missing or invalid email format |
| 401 | Invalid credentials |

## Sign In with Username

```http
POST /sign-in/username
Content-Type: application/json
```

### Request

```json
{
  "username": "alice",
  "password": "secure_password"
}
```

### Response

Same format as email sign-in, including `redirect` and `url`.

### Errors

| Status | Condition |
|--------|-----------|
| 400 | Missing username or password |
| 401 | Invalid credentials |
