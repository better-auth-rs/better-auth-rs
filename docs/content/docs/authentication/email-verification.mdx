The `EmailVerificationPlugin` handles sending verification emails and validating tokens.

## Setup

These examples assume you've already defined `AppAuthSchema`. If you want a complete setup from entity definitions through Axum mounting, start with the [Axum integration guide](/docs/integrations/axum).

```rust
use std::sync::Arc;
use better_auth::{AuthError, AuthResult, BetterAuth};
use better_auth::email::{ConsoleEmailProvider, EmailProvider};
use better_auth::plugins::{EmailVerificationPlugin, SendVerificationEmail};
use better_auth::prelude::UserView;

struct VerificationEmail;

#[async_trait::async_trait]
impl SendVerificationEmail for VerificationEmail {
    async fn send(&self, user: &UserView, url: &str, _token: &str) -> AuthResult<()> {
        let email = user.email.as_deref().ok_or_else(|| AuthError::bad_request("Email is required"))?;
        ConsoleEmailProvider
            .send(email, "Verify your email", "", url)
            .await
    }
}

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(
        EmailVerificationPlugin::new()
            .custom_send_verification_email(Arc::new(VerificationEmail))
    )
    .build()
    .await?;
```

Configure a `SendVerificationEmail` callback for `/send-verification-email`. Setting only the global `EmailProvider` does not enable that endpoint. The example uses `ConsoleEmailProvider` inside the callback for local development.

Direct `EmailVerificationConfig.verification_token_expiry` assignments use `Some(duration)`. Omission resolves to one hour through `verification_token_expiry()`. The plugin builder still accepts a `Duration`.

### Plugin Options

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `verification_token_expiry` | `Option<chrono::Duration>` | `None` (one hour) | How long verification tokens stay valid |
| `send_email_notifications` | `bool` | `true` | Use the default email provider for sign-in notifications; custom callbacks are independent |
| `require_verification_for_signin` | `bool` | `false` | Require verification for username sign-in when attached with `with_email_verification` |
| `send_on_sign_in` | `bool` | `false` | Send to unverified users when attached with `EmailPasswordPlugin::with_email_verification` |
| `send_on_sign_up` | `Option<bool>` | `None` | Send for new unverified OAuth users; `None` follows the provider's `require_email_verification` |
| `auto_sign_in_after_verification` | `bool` | `false` | Create a session after verification |

## Send Verification Email

```http
POST /send-verification-email
Authorization: Bearer <token>
Content-Type: application/json
```

```json
{
  "email": "alice@example.com",
  "callbackURL": "https://example.com/verify"
}
```

### Response

```json
{
  "status": true
}
```

## Verify Email

Called when the user clicks the link in the verification email.

```http
GET /verify-email?token=<verification_token>
```

### Response

```json
{
  "user": {
    "id": "uuid",
    "email": "alice@example.com",
    "emailVerified": true,
    ...
  },
  "status": true
}
```

| Status | Condition |
|--------|-----------|
| 400 | Token missing, expired, or invalid |

## Sending After Sign-Up

Set `.send_on_sign_up(true)` to send verification mail during email signup. With this option omitted, signup follows `EmailPasswordConfig::require_email_verification`. Delivery starts after account creation and before session creation, inside the signup transaction. Users become verified only after completing the verification flow.

Register `.callbacks(EmailVerificationCallbacks::<AppAuthSchema>::send(callback))` for verification notifications that need the full endpoint context. The callback receives `VerificationEmail` and `EndpointContext`. Return `Err` for a synchronous callback failure, `Ok(None)` for synchronous completion, or `Ok(Some(BackgroundFuture))` for asynchronous delivery. A synchronous failure propagates to the calling endpoint. Automatic signup, signin, change-email and verification-continuation notifications log asynchronous delivery failures and continue, matching the upstream notification boundary.

Use `EndpointContext::to_owned()` when delivery must retain the endpoint. Call `as_endpoint()` inside the future to access the same resolved runtime and transaction. Do not substitute the normal store for the retained transaction: SQL transactions reject operations after finalization, while the memory adapter preserves its isolated transaction rows.

Set `config.advanced.background_tasks = Some(BackgroundTasks::new(handler))` to let automatic verification delivery continue after the response. The handler receives an already-running `BackgroundTask`; dropping this handle does not cancel delivery. Without a handler, signup awaits delivery. The task retains request and logger scope. Transaction after hooks still run after commit, in their existing order, and rollback discards them.

The direct `/send-verification-email` endpoint uses the same callback factory but awaits delivery without the background handler. Both synchronous and asynchronous sender errors propagate from this direct endpoint. The `/verify-email` confirmation and legacy email-change branches use background scheduling. The legacy branch writes the new address before delivery and issues its session cookie after scheduling completes. Delivery failure does not undo a completed database write.

The same scheduler covers [password reset](/docs/authentication/password-management#reset-callbacks), [Phone OTP notifications](/docs/plugins/phone-number#typed-callback-context), and [user email-change and deletion notifications](/docs/concepts/users-accounts). Database lifecycle hooks and `before_delete` / `after_delete` remain awaited operations.

For Generic OAuth, attach the verification plugin with `OAuthPlugin::with_email_verification`. New unverified users follow `send_on_sign_up`; subsequent sign-ins send only when the provider requires email verification and `send_on_sign_in` is enabled. Sender failures are logged and preserve the verification decision, matching upstream. See [Generic OAuth / OIDC](/docs/plugins/oauth#generic-oauth--oidc).

Use [SeaORM hooks](/docs/concepts/hooks) for application database operations associated with user creation.

## Email Provider

The `ConsoleEmailProvider` logs emails to stderr and is useful for development:

```
[EMAIL] To: alice@example.com | Subject: Verify your email | Body: ...
```

For production, implement `EmailProvider` and call that provider from your `SendVerificationEmail` callback:

```rust
use better_auth::email::EmailProvider;

struct SmtpProvider { /* ... */ }

#[async_trait::async_trait]
impl EmailProvider for SmtpProvider {
    async fn send(
        &self, to: &str, subject: &str, html: &str, text: &str
    ) -> better_auth::error::AuthResult<()> {
        // Send via SMTP, SendGrid, etc.
        Ok(())
    }
}
```
