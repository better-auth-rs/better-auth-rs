The `SessionManagementPlugin` provides endpoints for querying, listing, and revoking sessions. Sessions are created automatically during sign-up, sign-in, passkey authentication, and successful 2FA completion.

## Setup

These examples assume you've already defined `AppAuthSchema`. If you want a complete setup from entity definitions through Axum mounting, start with the [Axum integration guide](/docs/integrations/axum).

```rust
use better_auth::plugins::SessionManagementPlugin;

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(SessionManagementPlugin::new())
    .build()
    .await?;
```

### Plugin Options

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `enable_session_listing` | `bool` | `true` | Allow `GET /list-sessions` |
| `enable_session_revocation` | `bool` | `true` | Allow revocation endpoints |
| `require_authentication` | `bool` | `true` | Require a valid session for plugin endpoints |

## Opaque Session Tokens

Better Auth stores opaque session tokens in the configured session storage. The database is the default. Browser cookies contain the token and an HMAC-SHA256 signature:

```http
Cookie: better-auth.session_token=session_abc123.signature
```

Enable Bearer transport explicitly for mobile apps or API clients:

```rust
use better_auth::config::BearerConfig;

config.session.bearer = Some(BearerConfig::default());
```

Bearer transport accepts the raw token returned by sign-in or the signed token from `set-auth-token`. Set `require_signature: true` to accept only signed Bearer tokens. An accepted Bearer token takes precedence over the session cookie.

## Endpoints

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/get-session` | Return the current session and user |
| `POST` | `/get-session` | Refresh an eligible session; requires `session.defer_session_refresh`, otherwise 405 |
| `POST` | `/update-session` | Update configured writable session fields |
| `POST` | `/sign-out` | Revoke the current session and clear cookies |
| `GET` | `/list-sessions` | List all active sessions for the current user |
| `POST` | `/revoke-session` | Revoke one specific session by token |
| `POST` | `/revoke-sessions` | Revoke all sessions for the current user |
| `POST` | `/revoke-other-sessions` | Revoke every session except the current one |

Session lists preserve the storage adapter's result order, matching upstream. Clients that need a specific order should sort the returned sessions.

## Session Lifecycle

1. A session is created after successful authentication.
2. The opaque token and session metadata are stored in the database or configured secondary backend.
3. The token is returned to the client and usually set as a cookie.
4. Authenticated requests resolve the token through a valid cookie cache or the configured session storage.
5. Session storage reads reject expired or revoked sessions. A valid cookie cache remains usable until its cache or session expiry.

## Refresh Behavior

Session refresh is controlled by `SessionConfig`:

```rust
use better_auth::AuthConfig;
use better_auth::config::SameSite;
use chrono::Duration;

let mut config = AuthConfig::new("secret...")
    .base_url("https://auth.example.com");
config.session.expires_in = Some(Duration::days(7));
config.session.update_age = Some(Duration::days(1));
config.session.disable_session_refresh = Some(false);
config.session.defer_session_refresh = false;
config.session.fresh_age = Some(Duration::minutes(10));
config.advanced.cookie_prefix = Some("better-auth".into());
config.advanced.use_secure_cookies = Some(true);
config.advanced.default_cookie_attributes.http_only = Some(true);
config.advanced.default_cookie_attributes.same_site = Some(SameSite::Lax);
```

- `update_age = Some(duration)`: refresh when the remaining lifetime falls below `expires_in - duration`.
- `update_age = None`: use the one-day default. Use `Some(Duration::zero())` to refresh on every authoritative read.
- `disable_session_refresh = Some(true)`: never refresh automatically.
- `defer_session_refresh = true`: `GET /get-session` reports `needsRefresh` without updating the stored expiry. `POST /get-session` performs the refresh.
- `fresh_age`: optional window for treating a session as "fresh" for sensitive actions.

A `disableRefresh=true` query parameter prevents refresh for the request. Sessions created with `rememberMe: false` expire in the database after 24 hours. These sessions use browser-session cookies and a signed `dont_remember` marker; requests with this marker do not refresh the session automatically. Remembered sessions use the configured `expires_in` lifetime. `/get-session` responses include `Cache-Control: no-store` and `Pragma: no-cache`.

## Secondary Storage

`BetterAuth::secondary_storage` installs a backend for server-side session and user snapshots. Sessions use that backend by default. Set `session.store_session_in_database = Some(true)` to retain database rows and permit fallback on a missing cache entry. Set `session.preserve_session_in_database = Some(true)` to keep expired audit rows after revocation and disable that fallback. Malformed cached JSON never restores a session through database fallback.

Session creation publishes its cache snapshot immediately by default. Explicitly deferred transaction creation, used by Passkey registration, publishes after commit; rollback discards that deferred write. User updates through the authentication store refresh cached user snapshots. See [Secondary Storage](/docs/concepts/secondary-storage) for backend methods, atomic verification consumption, and model hydration requirements.

`AuthRequest::new_session()` and `EndpointContext::new_session()` return `better_auth::NativeSessionData`, the exact snapshot supplied to the cookie writer. Its `user` is a `FieldValue`, so an array selected by an Account/User relationship stays an array. Cookie version callbacks receive the same native snapshot. Read named properties with `user_field("id")`; array properties return `Undefined`. HTTP and cache output use `public_user` to filter fields. Authenticated session reads continue to return typed `better_auth::SessionData`; an issuance snapshot does not establish an authenticated user.

## Cookie Cache

Enable a signed or encrypted session cache to avoid a database read on each request:

```rust
use better_auth::config::{CookieCacheConfig, CookieCacheStrategy};

config.session.cookie_cache = Some(CookieCacheConfig {
    enabled: Some(true),
    max_age: Some(Duration::minutes(5)),
    strategy: Some(CookieCacheStrategy::Jwe),
    version: "1".into(),
    ..Default::default()
});
```

`Compact` uses HMAC-SHA256, `Jwt` uses HS256, and `Jwe` uses A256CBC-HS512 encryption. Register `JwtPlugin::new().session_cookie_cache(true)` with the `Jwt` strategy to use the plugin's asymmetric signing keys instead of HS256. See [JWT](../plugins/jwt) for the cache token's issuer, audience, and purpose checks. Each cache is bound to its signed session token and configuration version. Large values use numbered cookie chunks. Authentication writes the cache, and sign-out clears its chunks.

Use `disableCookieCache=true` to read the authoritative session storage immediately. Session listing and revocation also use that storage. Changing `version` invalidates previously issued caches. With a database or secondary storage, sensitive session reads bypass the cookie cache. Without either backend, those reads can use the encrypted session snapshot.

Set `version` to a string with `.into()` or use `CookieCacheVersion::dynamic` for an asynchronous callback:

```rust
use better_auth::config::CookieCacheVersion;

config.session.cookie_cache.as_mut().unwrap().version =
    CookieCacheVersion::dynamic(|data| async move {
        Ok(format!("v2:{}", data.user.email_verified))
    });
```

The callback receives the snapshot at the cache write or read boundary. New sessions include hidden application fields before cookie filtering. Session lookups and signed cookie reads already contain filtered fields. Hidden fields stay out of the cookie and response. A version mismatch reads the session store; a callback error aborts the request. Compact, JWT, JWE, and plugin-signed JWT caches use the same callback.

## Stateless Sessions

Use `BetterAuth::stateless(config)` to build authentication without an application database schema or an explicit store:

```rust
use better_auth::{AuthConfig, BetterAuth};
use better_auth::plugins::{EmailPasswordPlugin, SessionManagementPlugin};

let auth = BetterAuth::stateless(AuthConfig::new("a-random-secret-of-at-least-32-characters"))
    .plugin(EmailPasswordPlugin::new())
    .plugin(SessionManagementPlugin::new())
    .build()
    .await?;
```

The builder uses `StatelessSchema` and a process-local `EphemeralStore`. Users, accounts, verification values, and plugin records disappear when that adapter is dropped. A valid encrypted session cookie remains readable after restart. This mode does not make password credentials or organization data durable.

When both database and secondary storage are absent, omitted settings enable JWE session cookies, use the session lifetime as their maximum age, refresh the cache during its final 20%, and store OAuth state and account data in encrypted cookies. Explicit `Some(false)`, strategy, duration, and refresh settings take precedence. A cookie refresh preserves the original session expiry; the refresh does not extend authentication indefinitely.

Configure cache refresh with `CookieCacheRefresh::Disabled`, `Enabled`, or `After(duration)`. `After` specifies the remaining cookie lifetime that triggers renewal. A configured database or secondary backend disables cookie-only renewal. Secondary storage alone keeps account cookies enabled, but stores OAuth state and sessions on the server.

Server-side revocation cannot invalidate an already issued stateless session cookie. Sign-out clears the client's cookies. Use a database or secondary storage when the application requires centralized session revocation. `disableCookieCache=true` forces an adapter read and cannot restore an expired or missing process-local session after restart.

Register process-local database hooks with `.database_hooks(Vec<Arc<dyn DatabaseHooks<StatelessSchema>>>)`. `EphemeralStore` also exposes `.with_hooks(...)` for explicit store use. Transactions isolate uncommitted changes, preserve concurrent unrelated writes, and run queued after-hooks only after commit. After-hook errors propagate after data has committed. Explicitly passing an `EphemeralStore` through `.store(...)` opts into server-store behavior; the builder does not infer durability from the adapter's concrete type.

## Using Sessions in Axum Handlers

With the `axum` feature, use the `CurrentSession` extractor to access the authenticated user directly in your handler:

```rust
use axum::Json;
use better_auth::integrations::axum::CurrentSession;
use better_auth::prelude::{AuthSession, AuthUser};

async fn profile(session: CurrentSession<AppAuthSchema>) -> Json<serde_json::Value> {
    Json(serde_json::json!({
        "user_id": session.user.id(),
        "session_token": session.session.token(),
    }))
}
```

Use `OptionalSession<AppAuthSchema>` for routes that should work for both authenticated and anonymous users.

## Application Session Fields

`POST /update-session` updates configured application fields on the authenticated session. HTTP and native endpoints require an object body and validate the body before checking the session. Unknown fields and built-in credentials are not writable. An empty update returns 400. Fields with `input: Some(false)` reject truthy input; `returned: Some(false)` excludes a field from session responses.

The request body must be a JSON object with `Content-Type: application/json`. Body validation runs before session authentication. A body with a missing or unsupported media type returns 415.

Add columns to the application-owned session entity and migrate the database before configuring those fields. `AuthEntity` generates the storage mapping. `AuthConfig.session.fields_mut()` configures the optional field map. `None` and `Some(IndexMap::new())` retain distinct configuration presence. `SessionFieldConfig` is an alias of `UserFieldConfig`; session fields support constant defaults, default factories, validators, input/output transforms, and `on_update`.

```rust
use better_auth::config::SessionFieldConfig;

config.session.fields_mut().insert("label".into(), SessionFieldConfig {
    field_name: Some("display_label".into()),
    ..Default::default()
});
```

`field_name` identifies the field in the model's serialized representation. The public field name is the map key. For manually implemented `SeaOrmSessionModel` types, implement `apply_fields` to persist the configured fields.

Custom `SessionStore` implementations return the updated model from `update_session_expiry`. The runtime uses that result for the refresh response so database transforms run once even when secondary storage is enabled.

Session creation removes caller-supplied `id` values and evaluates configured defaults before database hooks. Initial defaults use the input schema: plugin declarations replace application declarations while retaining field order. Adapter defaults and transforms retain application precedence. A configured ID default remains available to the hook. With secondary storage alone, ID generation precedes defaults and hooks, including when a hook cancels creation. Database writes can evaluate a field default again when the hook returns Undefined or returns Null for a required field. Secondary-only writes preserve the hook value without that second default evaluation.

A public update runs the validator, or the input transform when no validator exists. A database write then applies the adapter input transform and `on_update`; database reads apply the output transform. A cached session already contains its public field values, so cache reads do not repeat adapter transforms. With secondary storage alone, updates use the route parser without database transforms. With both storage modes enabled, an update response reflects the database result, while subsequent cache reads reflect the cached update, matching Better Auth 1.7.6.

Memory session fields use the [Memory JSON and array representation](/docs/concepts/users-accounts#memory-json-and-arrays). JSON output callbacks receive stored text before decoding; declared string and number arrays remain native arrays. This conversion applies to database-backed Memory rows, not secondary-only session caches.

Direct Memory store updates resolve supplied IDs at the configured ID position. A supplied `SessionUpdate.additional_fields["id"]` takes precedence over `SessionUpdate.id`, including explicit `Undefined`. Secondary writes use the same ID input precedence. Fields mapped to `id` share the final primary-key value according to schema order. An omitted value does not erase an earlier alias write. Aliased ID outputs run their configured callback, preserve `Null` and `Undefined`, and convert other values to strings.

Memory and SQL session updates suspend once after before-hooks and any secondary write, before adapter field conversion and persistence. The continuation wakes the callback queue directly, preserving the upstream adapter-lookup boundary without Tokio's reverse deferred wake order. Cancelled updates and secondary-only writes retain their existing control flow. This boundary does not establish complete JavaScript Promise scheduling equivalence.

## Two-Factor Interaction

When 2FA is enabled, sign-in verifies the primary credential first and then pauses on a pending verification flow. A full session is only created after `verify-totp`, `verify-otp`, or `verify-backup-code` succeeds.

## Security Notes

- Session tokens are generated with `OsRng`.
- Cookie transport should normally keep `Secure`, `HttpOnly`, and `SameSite` enabled.
- Session records can retain audit metadata such as IP address and user-agent.
- Users can hold multiple sessions across devices and revoke them selectively.

## Session Issuance in Plugins

Call `SessionManager::set_session_cookie(request, data, dont_remember)` when an endpoint issues session credentials. `data` is the exact `SessionData` snapshot for the user and session; `internal_data` constructs that snapshot from adapter records without removing hidden fields. The writer sets credential and cache cookies, then records the snapshot for `AuthRequest::new_session()` and `EndpointContext::new_session()`.

Pass `None` to inherit the request's signed `dont_remember` cookie, or an explicit boolean to select persistence. Creating a database session, refreshing a cache, or appending a cookie directly does not establish a newly issued snapshot. Response finalization merges already queued cookies without rereading the database or inferring session issuance from response headers.

Inside a database transaction, use `set_session_cookie_in_transaction` and pass the active `AuthTransaction<S>`. The signer receives that transaction through `SessionCookieContext<S>` so key generation cannot re-enter the global connection. Custom transaction adapters implement `JwksStore` on their transaction with the same connection or snapshot.
