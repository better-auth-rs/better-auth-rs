---
title: Email OTP
description: Sign in, verify email, reset passwords, and change email with one-time codes.
---

The Email OTP plugin implements Better Auth 1.7.6's nine public email OTP routes. Register an application sender to deliver each code. The plugin logs asynchronous delivery errors and retains the endpoint's success response, matching upstream background-task behavior. Sender factory errors, database errors, and OTP protection errors propagate on direct OTP endpoints.

```rust
use std::sync::Arc;
use async_trait::async_trait;
use better_auth::{AuthResult, plugins::email_otp::{EmailOtpMessage, EmailOtpPlugin, SendEmailOtp}};

struct Mailer;

#[async_trait]
impl SendEmailOtp for Mailer {
    async fn send(&self, message: &EmailOtpMessage) -> AuthResult<()> {
        send_mail(&message.email, &message.otp).await
    }
}

let plugin = EmailOtpPlugin::new().sender(Arc::new(Mailer));
```

Replace `send_mail` with your mail provider. Add `plugin` to the auth builder. Never return codes from a public endpoint or log codes.

| Method | Path | Purpose |
| --- | --- | --- |
| POST | `/email-otp/send-verification-otp` | Send an OTP for `sign-in`, `email-verification`, or `forget-password`. |
| POST | `/email-otp/check-verification-otp` | Check a code without consuming a successful code. |
| POST | `/email-otp/verify-email` | Consume the verification code and mark the email verified. |
| POST | `/sign-in/email-otp` | Consume a sign-in code and create a session. |
| POST | `/email-otp/request-password-reset` | Send a password-reset code. |
| POST | `/forget-password/email-otp` | Deprecated alias for the reset request. |
| POST | `/email-otp/reset-password` | Consume the reset code and update the credential password. |
| POST | `/email-otp/request-email-change` | Authenticate the user and send a code to the new email. |
| POST | `/email-otp/change-email` | Consume the address-bound code and update the user's email. |

Public body schemas run after endpoint before hooks and before authentication. Before and after hooks retain raw input and original Request bytes. Handlers and database callbacks receive the validated projection. Sign-in preserves additional fields; the other public routes remove unknown fields.

The upstream `createVerificationOTP` and `getVerificationOTP` helpers are server-only APIs. The plugin does not expose corresponding HTTP routes.

Codes contain six digits and expire after five minutes by default. Three wrong attempts are allowed; the next check returns `TOO_MANY_ATTEMPTS` and removes the code. Verification, sign-in, password reset, and email changes consume valid codes atomically. A code cannot authenticate two concurrent requests.

Use `.storage(EmailOtpStorage::Hashed)` to persist SHA-256 digests or `.storage(EmailOtpStorage::Encrypted)` to persist encrypted codes. `.reuse_otp(true)` resends an unexpired recoverable code and extends its expiry without resetting attempts. Hashed codes cannot be recovered, so resends generate a new code.

Use `EmailOtpStorage::CustomHash` for an asynchronous application hash. Use `CustomEncryption` with an `EmailOtpCodec` for reversible protection; `encode` and `decode` return strings and propagate failures. `generate_otp` accepts an application generator, with `None` selecting the default generator.

Enable `.send_verification_on_sign_up(true)` to send a verification code after email registration. Enable `.override_default_email_verification(true)` to supply OTP delivery when no explicit verification-email sender is configured. An explicit sender takes precedence, matching upstream plugin-option merging. Email verification hooks and automatic sign-in use the existing `EmailVerificationPlugin` configuration. Password reset uses the existing password hasher, reset callback, length limits, and session-revocation policy.

Use `.disable_sign_up(true)` to restrict sign-in to existing users. Unknown-user verification and password-reset requests return success without sending a code. When OTP sign-in proves an existing unverified email, the store removes the user's previous password, OAuth accounts, and sessions before issuing the owner's session. Already verified users retain their existing access.

New-user sign-in accepts the enabled username plugin's `username` and `displayUsername` fields, and the enabled phone plugin's `phoneNumber` field. Username creation applies normalization, validation, uniqueness checks, and the display-name default. A display name alone does not create a username. Protected fields such as `role` and `phoneNumberVerified` cannot grant privileges or establish proof. Application-defined fields use the shared [user schema](/docs/concepts/users-accounts), including required fields, input restrictions, defaults, validators, transforms, and public visibility.

Email changes are disabled by default. Enable `.change_email(true)` and, if required, `.verify_current_email(true)`. Current-email verification uses an `email-verification` code. The new-email code is bound to both addresses and requires an authoritative session.

Each public route supplies a default rate limit of three requests per sixty seconds. Application rate-limit overrides take precedence. Global rate limiting must be enabled for these limits to apply.

## Typed callback context

Call `.callbacks::<AppSchema>(EmailOtpCallbacks::default().generate(...).send(...))` after configuring the plugin. `AppSchema` is the schema supplied to the auth builder. Each callback receives `EndpointContext`, which exposes the parsed `body`, endpoint `path`, original optional `request`, and the complete `AuthContext<AppSchema>` through `auth`. The signup after hook also supplies the completed `response`.

```rust
use better_auth::plugins::email_otp::{EmailOtpCallbacks, EmailOtpPlugin};

let plugin = EmailOtpPlugin::new().callbacks::<AppSchema>(
    EmailOtpCallbacks::default().send(|message, endpoint| {
        let message = message.clone();
        let endpoint = endpoint.to_owned();
        Ok(Some(Box::pin(async move {
            let endpoint = endpoint.as_endpoint();
            let user = match endpoint.transaction {
                Some(transaction) => transaction.get_user_by_email(&message.email).await?,
                None => endpoint.auth.database.get_user_by_email(&message.email).await?,
            };
            send_mail(&message.email, &message.otp, user).await
        })))
    }),
);
```

The generator returns `AuthResult<Option<String>>`; generator errors propagate on direct OTP endpoints. The sender factory returns `AuthResult<Option<BackgroundFuture>>`. `Err` propagates immediately, `Ok(None)` schedules no work, and `Ok(Some(task))` uses the configured background handler or awaits delivery. Retain the endpoint with `to_owned()` before returning a task that uses its runtime. Context callbacks override their corresponding legacy callbacks. The legacy sender and generator remain available when context is unnecessary.

The default-email override keeps the original request and active transaction but supplies the OTP endpoint's synthetic `{ email, type }` input. Creation, lookup, reuse updates, and unknown-user deletion use that transaction. Upstream invokes the entire overridden endpoint as a background notification, so errors from that dispatch are logged. This policy does not suppress database errors on direct OTP endpoints. A scheduled SQL operation that resumes after commit or rollback receives the database's closed-transaction error; the runtime does not replace the retained transaction with a new connection.

## Trusted server operations

`auth.email_otp()?.create(email, kind).await?` implements upstream `createVerificationOTP`. Creation lowercases the input, always generates a new code, stores its protected value with zero failed attempts, and returns the plaintext code. Creation accepts any string and does not require an existing user or a sender. The generator receives the complete typed endpoint context with no HTTP request.

`auth.email_otp()?.get(email, kind).await?` implements upstream `getVerificationOTP` as `Option<String>`. Missing or expired records return `None`. A live hash returns a 400 error without calling the application hash function. Plaintext and encrypted records return the recovered code without consuming the record or resetting its failed attempts. These operations are available only through the Rust server API; no HTTP routes expose the codes.

Inside an application callback, use `endpoint.email_otp()?` or `EmailOtpApi::from_endpoint(endpoint)?`. Both operations use the callback's active database transaction. A native read sees codes created earlier in that transaction, and a rejected admission rolls back database OTP writes. The configured verification identifier policy applies to these operations. `auth.email_otp()` remains available for independent server calls. Both native endpoints run shared endpoint hooks, validation and instrumentation. Before patches can change the stored or queried address; callbacks receive validated input and after hooks retain raw patched input. `.with_request(NativeRequest { request, headers })` preserves an explicit native Request and header presence.

A dynamic base URL requires a configured fallback for independent server calls. Endpoint-bound calls retain the resolved URL and transaction without running URL resolvers again.

Verification after hooks run after a successful transaction commit. Secondary storage writes execute immediately, matching upstream, so a database rollback does not undo a secondary storage write.
