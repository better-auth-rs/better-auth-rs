The `OAuthPlugin` supports OAuth 2.0 and OpenID Connect (OIDC). It handles authorization code exchange, provider profiles, account linking, and provider logout.

## Setup

These examples assume you've already defined `AppAuthSchema`. If you want a complete setup from entity definitions through Axum mounting, start with the [Axum integration guide](/docs/integrations/axum).

```rust
use better_auth::plugins::OAuthPlugin;
use better_auth::plugins::oauth::OAuthProvider;

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(
        OAuthPlugin::new()
            .add_provider("google", OAuthProvider::google(
                "GOOGLE_CLIENT_ID",
                "GOOGLE_CLIENT_SECRET",
            ))
            .add_provider("github", OAuthProvider::github(
                "GITHUB_CLIENT_ID",
                "GITHUB_CLIENT_SECRET",
            ))
    )
    .build()
    .await?;
```

### Social provider inputs

Construct social providers with the built-in constructors or `OAuthProvider::custom(client_id, client_secret, auth_url, token_url)`. Direct struct literals are replaced by these constructors because built-in defaults remain private runtime state. The custom constructor requires an explicit profile decoder or `get_user_info` handler. Generic OAuth continues to use `GenericOAuthConfig`.

```rust
let mut google = OAuthProvider::google("GOOGLE_CLIENT_ID", "GOOGLE_CLIENT_SECRET");
google.scopes = Some(vec!["calendar.readonly".into()]);
google.prompt = Some("consent".into());
google.disable_implicit_sign_up = Some(true);
let oauth = OAuthPlugin::new().add_provider("google", google);
```

Social `scopes`, `disable_implicit_sign_up`, and `disable_sign_up` retain omission through `Option`. Omitted sign-up switches resolve to false. Except for Zoom, built-in providers add their default scopes, configured scopes, and request scopes; Discord places request scopes before configured scopes. Explicit empty lists retain the defaults. Set `disable_default_scope = true` to request only the configured and request scopes. To migrate an old complete scope override, wrap the list in `Some` and enable `disable_default_scope`. Custom social providers retain request-scope replacement semantics. Generic OAuth options keep their existing types and merge behavior.

`OAuthProvider::client_key` defaults to `None`. A nonempty value adds `client_key` to the authorization-code form for built-in providers that pass the common options upstream. PayPal, Reddit, WeChat, and custom providers ignore this field. The shared refresh flow and Generic OAuth do not consume this option. Configure `client_id` and `client_secret` separately.

`OAuthConfig.providers` uses an insertion-ordered map. `add_provider` preserves registration order, and replacing a name keeps its position. A custom provider map can be built with `[(name, provider)].into_iter().collect()`.

Set `require_email_verification` to `Some(true)` to require a verified user email before issuing a session. Omitted and false values disable this requirement. Social and Generic providers use the same verification policy and configured verification-email sender.

Register social providers in one `OAuthPlugin` for the verified upstream configuration mapping. The same plugin may contain Generic OAuth providers. Multiple `OAuthPlugin` instances keep separate runtime configurations and have no unique upstream provider-map equivalent.

Set `map_profile_to_user` to an `Arc<dyn OAuthProfileMapper>` to override local profile fields after built-in decoding. TikTok ignores this callback, matching its pinned provider behavior. Omitted mapper fields preserve the provider value. `Some(None.into())` clears the name, `Some(None)` clears the image, and `additional_fields` adds configured application fields. The mapper cannot change the account subject. A custom `get_user_info` handler takes precedence and skips this mapper. Callback errors propagate through the existing OAuth error path. `map_user_info` remains the base JSON decoder for custom providers; it is distinct from the local-field mapper.

`OAuthUserInfoHandler::get_user_info` returns `AuthResult<Option<OAuthUserInfoResponse>>`. Return `Ok(Some(profile))` for a profile or `Ok(None)` for a missing profile. Both results skip default HTTP lookup and the mapper. Missing profiles retain each endpoint’s existing redirect or `FAILED_TO_GET_USER_INFO` response. Return an application `AuthError` unchanged to preserve its HTTP status, error body, and headers through Social callback, OAuth Proxy, and account-info. Use `AuthError::internal(message)` for an ordinary implementation failure. Construct dynamic API errors with `AuthResponse::json(...)` and convert the response into `AuthError`.

To migrate a handler, use `AuthResult<Option<OAuthUserInfoResponse>>`, wrap successful profiles with `Some`, and wrap former string errors with `AuthError::internal`. `OAuthUserInfo.email` uses `SchemaValue<Option<String>>`: `Undefined` omits email, `Typed(None)` represents null, and `Typed(Some(email))` represents a string. For example, use `email: Some("owner@example.test".to_owned()).into()` for a supplied address. `OAuthProfile.email` adds an outer `Option`: `None` preserves the provider value, while `Some(SchemaValue::Undefined)` removes the field. Social decoders pass missing or null email to the mapper; sign-in and linking still enforce their existing required-email rules afterward. Account-info preserves email presence without changing stored users or accounts. Default Social profiles omit the public `user.id`; custom user-info handlers and active custom decoders retain their supplied ID. The internal account subject is unchanged. Non-string, non-null values remain errors. Generic raw-profile handlers use `AuthResult<Option<serde_json::Value>>`: return `Some(profile)` for success, `None` for an unavailable profile, or `Err` for an application error. `OAuthRefreshTokenHandler` and `OAuthIdTokenVerifier` retain their signatures and error rules.

Social and Generic sign-in normalize an omitted or null mapped name to an empty string before user creation, profile updates, and admission callbacks. Empty and nonempty strings are retained. Profile results, account-info responses, and the raw profile supplied to admission callbacks preserve their original name values. Explicit account linking retains its separate profile behavior.

Social `override_user_info_on_sign_in` and Generic `override_user_info` update an existing user's profile only during the normal OAuth callback. Direct ID-token sign-in, OAuth Proxy completion, and One Tap do not inherit that setting. All entry points retain their existing identity, account, email-verification, and session behavior.

`OAuthUserInfo.email_verified` uses `SchemaValue<Option<bool>>`: `Undefined` omits the field, `Typed(None)` preserves null, and `Typed(Some(value))` preserves a boolean. `OAuthProfile.email_verified` adds an outer `Option`: `None` leaves the provider value unchanged, while `Some(SchemaValue::Undefined)` explicitly omits it. Migrate a previous `true` field to `Some(true).into()` and a mapper `Some(true)` to `Some(Some(true).into())`. The account-info response and OAuth proxy preserve these states. Verification decisions require boolean true; false, null, and omission do not verify an email. Non-boolean, non-null values are rejected at the shared field boundary.

Provider defaults remain separate from mapped values. Discord, Google, and Slack preserve the provider flag; providers with a false default retain that default before mapping. Reddit also applies its false default after a null or undefined mapper flag. Generic HTTP profile normalization retains its existing false default. The upstream mapper declaration permits optional booleans; null preservation follows its runtime object-spread behavior, not a broader JavaScript truthiness API. The database user verification field remains boolean.

Discord prepares `image_url` before invoking the mapper. The default decoder reuses that value for PNG, animated GIF, and default avatars. Display names use `global_name`, then `username`, then an empty string.

Discord omits PKCE, the code verifier, standalone login hints and nonces, and callback device IDs. Code exchange and refresh use client-secret-post. Configure bot permissions with a decimal string in `authorization_params`, for example `("permissions".into(), "8".into())`. The configured entry is sent only when the combined default, request, and configured scopes contain `bot`. Request `additionalParams.permissions` overrides the configured value and remains effective without the bot scope. Request `additionalParams.login_hint` and `additionalParams.prompt` remain effective even though standalone login hints are omitted.

Set `disable_id_token_sign_in = true` to reject direct ID-token sign-in and linking before invoking verification or user-info callbacks. Authorization-code flow remains available. Google, GitHub, Discord, Polar, Atlassian, Cognito, Microsoft, Paybin, PayPal, and custom providers forward the configured `prompt`. GitLab, Spotify, Hugging Face, Vercel, Figma, Dropbox, Kick, Cloudflare, LinkedIn, Slack, Naver, Notion, LINE, Linear, Reddit, Salesforce, Railway, Twitch, Kakao, Zoom, Twitter, VK, WeChat, TikTok, Facebook, and Apple ignore this option. Roblox forwards a nonempty prompt and otherwise uses `select_account consent`. Omitted or empty prompts retain Discord’s `none` default. Additional authorization parameters retain their existing precedence.

Set `redirect_uri` when the provider callback URI differs from the route URI. Authorization and code exchange use the same configured value. Omitted or empty values use the route URI. Register the configured URI with the provider and route the callback to Better Auth; the option does not create another HTTP route.

Google direct ID-token sign-in and authorization-code callbacks map claims returned by the shared Google verifier used by One Tap. The verifier checks the signature, issuer, audience, token age and time claims. A supplied nonce is checked, and the configured `hd` authorization parameter restricts the hosted domain. Direct sign-in verifies once before mapping. Code callbacks and OAuth Proxy verify the token endpoint's ID token before mapping, retaining the existing callback error path. The production verifier uses Google's fixed public-key endpoint.

Use `OAuthProvider::google_with_options` to accept additional Google client IDs:

```rust
use better_auth::plugins::oauth::{GoogleOptions, OAuthProvider};

let google = OAuthProvider::google_with_options(
    "web-client-id",
    "client-secret",
    GoogleOptions {
        additional_client_ids: vec!["native-client-id".into()],
    },
);
```

The existing `OAuthProvider::google` constructor accepts one client ID. Additional IDs extend the accepted audiences for direct sign-in, code callbacks, OAuth Proxy, and One Tap's default Google configuration. Explicit One Tap client IDs replace the inherited list. Authorization and token requests use the current primary `client_id`. Google omits callback device IDs from code exchange.

For direct ID-token sign-in, a configured `verify_id_token` retains its application trust policy: only a successful result permits the default Google profile to parse that token's claims. Code callbacks use the shared Google verifier. A configured `get_user_info` retains precedence over the default profile and mapper. `/account-info` keeps the existing access-token/userinfo lookup, so stored-account reads do not acquire the sign-in token-age limit. Normal signed-flow fixtures cover both sign-in paths and callback precedence; complete provider parity is not claimed.

Figma uses PKCE and HTTP Basic client authentication for code exchange and refresh. Both credentials must be nonempty when authorization starts. GitHub keeps its default HTTP profile lookup separate from application callbacks. Use the existing authorization parameters to request Dropbox offline access. This represents upstream's `accessType` option; request-level additional parameters can override it.

let mut dropbox = OAuthProvider::dropbox("DROPBOX_CLIENT_ID", "DROPBOX_CLIENT_SECRET");

Ordinary pinned and SQLite contracts cover successful code/refresh flows, callback URI selection, optional fields, and callback/proxy/account-info error responses. The constructor adds no ID-token verifier. Strict JSON field types, JavaScript coercion, and untested network-error timing remain explicit boundaries.

Kakao uses client-secret-post for code exchange and refresh. Its default scopes are `account_email`, `profile_image`, and `profile_nickname`, followed by configured scopes and request scopes without deduplication. The fixed protocol omits PKCE, standalone hints/nonces, configured prompt, and callback device IDs. Ordinary additional parameters and configured callback URIs remain effective.

Kakao profile lookup uses GET/Bearer and passes the complete profile to the async mapper and returned data. The default decoder converts the documented numeric ID to the existing string account key, selects profile nickname before account name, and selects the main profile image before the thumbnail. Missing names become empty strings. Omitted and null email/image values retain their normal JSON shape. The default `emailVerified` is true only when both documented email flags are true. Pinned cases confirm false, omitted, and null flags produce false; Kakao emits a concrete boolean for these cases. Other providers retain their own verification-field presence and defaults. Arbitrary JavaScript truthiness coercion remains outside the shared field boundary.

Custom user-info and refresh handlers retain precedence. HTTP failures and null profiles return the shared missing-profile result; application mapper and custom-handler errors propagate unchanged. Ordinary pinned and SQLite contracts cover authorization, code/refresh encoding, callback URIs, profile fallbacks, mapper order, persistence, and callback/proxy/account-info errors. The constructor adds no ID-token verifier. Typed fields and untested malformed shapes or network/JSON failure timing remain explicit boundaries.

## Generic OAuth / OIDC

Use `GenericOAuthConfig` for providers with explicit OAuth endpoints or OIDC discovery. Register the callback URL `{base_url}{base_path}/callback/{id}` with the identity provider. The `id` is the provider identifier. For example, a provider named `oidc` uses `/auth/callback/oidc` when the auth base path is `/auth`.

```rust
use better_auth::plugins::oauth::{GenericOAuthConfig, OAuthPlugin};

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(OAuthPlugin::new().add_generic_provider("oidc", GenericOAuthConfig {
        client_id: std::env::var("OIDC_CLIENT_ID")?,
        client_secret: Some(std::env::var("OIDC_CLIENT_SECRET")?),
        discovery_url: Some(std::env::var("OIDC_DISCOVERY_URL")?),
        require_id_token_verification: true,
        scopes: vec!["email".to_string(), "profile".to_string()],
        ..Default::default()
    }))
    .build()
    .await?;
```

`GenericOAuthConfig::auth0(client_id, client_secret, domain)`, `::keycloak(client_id, client_secret, issuer)`, and `::okta(client_id, client_secret, issuer)` configure discovery and the default `openid`, `profile`, and `email` scopes. The Auth0 constructor returns `AuthResult` because the domain must parse as a URL. Auth0 forces HTTPS and uses the parsed host and port; Keycloak and Okta remove one trailing slash from the issuer. Change the returned configuration fields to customize scopes, token authentication, redirects, logout, PKCE, and sign-up policy. These constructors use the same discovery and verification path as explicit Generic OAuth configuration.

```rust
let mut provider = GenericOAuthConfig::auth0("client-id", "client-secret", "tenant.example.com")?;
provider.require_id_token_verification = true;
let oauth = OAuthPlugin::new().add_generic_provider("auth0", provider);
```

`GenericOAuthConfig::microsoft_entra_id(client_id, client_secret, tenant_id)` requires a concrete tenant GUID and returns `AuthResult`. The constructor lowercases the GUID, configures tenant discovery and endpoints, enables required ID-token verification, and selects the `openid`, `profile`, and `email` scopes. Register the result as `microsoft-entra-id`.

```rust
let provider = GenericOAuthConfig::microsoft_entra_id(
    "client-id",
    "client-secret",
    "aabbccdd-1122-3344-5566-778899aabbcc",
)?;
let oauth = OAuthPlugin::new().add_generic_provider("microsoft-entra-id", provider);
```

Entra reads the account subject from the verified `oid` claim. Verified claims take precedence over Graph profile fields. Display names assembled from given/family name aliases use JavaScript whitespace trimming. If the provider omits email, the profile uses a stable address under `microsoft-entra-id.placeholder.invalid` with `emailVerified: false`. With an access token, the handler reads the configured `user_info_url`; matching `sub` values allow Graph fields to fill missing token fields. A Graph HTTP error or a nonmatching subject retains the verified token profile, matching the upstream helper's explicit fallback. Transport and JSON errors propagate with context. Normal signed fixtures cover direct and code sign-in, profile mapping, Graph success, and HTTP 503 fallback; they do not establish live-provider or complete error-timing parity.

Use the same client routes as built-in providers:

```typescript
await authClient.signIn.social({ provider: "oidc", callbackURL: "/dashboard" });
await authClient.linkSocial({ provider: "oidc", callbackURL: "/settings" });
```

Discovery runs when the auth instance initializes. Explicit `authorization_url`, `token_url`, `user_info_url`, and `end_session_endpoint` values override discovered endpoints. OIDC providers also request `openid`. For an OAuth provider without discovery, configure the endpoints directly.

Discovery failures can skip a provider while allowing the auth instance to initialize, matching upstream. If a provider is required, check the configured plugin before registering it:

```rust
let oauth = OAuthPlugin::new().add_generic_provider("oidc", provider_config);
if !oauth.has_provider("oidc").await? {
    return Err(better_auth::AuthError::config("Required OIDC provider is unavailable").into());
}
let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(oauth)
    .build()
    .await?;
```

`has_provider` resolves and caches discovery. Auth initialization reuses the result. The method reports the available provider set, propagates invalid static configuration, and does not contact token, userinfo, or JWKS endpoints. Finish configuring the plugin before checking; subsequent configuration changes invalidate the cached result.

Set `require_id_token_verification: true` when using ID tokens for identity. Discovery must supply an issuer and a JWKS URI. Received ID tokens are checked for signature, issuer, audience, expiration, and the authorization request's nonce. Without discovery verification, Generic OAuth retains upstream's unverified ID-token decoding behavior. This option requires verification capability; a provider may still return an access token and use its userinfo endpoint without an ID token.

OIDC signature verification requires OpenSSL 3.0 or newer. OpenSSL 3.5 or newer is required for the complete ML-DSA algorithm set. The development shell supplies the native dependencies.

Zoom uses client-secret-post for code exchange and refresh, and GET/Bearer userinfo. `OAuthProvider::zoom(client_id, client_secret)` enables authorization PKCE by default. Use `OAuthProvider::zoom_without_pkce(client_id, client_secret)` to represent the pinned `pkce: false` option. That option removes the authorization challenge; code exchange still forwards its supplied verifier. Both constructors use the same state and callback validation.

Zoom ignores configured/request scopes, `disable_default_scope`, configured prompt, and standalone hints/nonces. Ordinary additional authorization parameters remain effective. The decoder reads `display_name`, `pic_url`, and email, and applies the shared truthiness rule to the documented numeric `verified` field. The async mapper receives the original profile; custom user-info handlers retain precedence. The ordinary contracts cover verified values 0/1, null pictures, mapper errors, HTTP 503, and both PKCE configurations through local HTTP and SQLite. Arbitrary JavaScript response shapes and provider-specific transport/error timing are outside this slice.


### Profile helpers

`GenericOAuthConfig::gumroad`, `::hubspot`, `::patreon`, `::slack`, and `::yandex` each accept a client ID and client secret. Register the returned configuration under the corresponding provider name. These constructors configure endpoints, default scopes, profile lookup, and the account subject. Customize the existing configuration fields before registration to change scopes, token authentication, redirects, logout, PKCE, and sign-up policy.

The helpers map each provider response before calling the configured `map_profile_to_user`. Slack selects `sub` as its account subject; the other four helpers select `id`. HubSpot selects POST client authentication by default. Profile callbacks receive JSON values, so a JavaScript own property with `undefined` remains indistinguishable from a missing property. Complete helper-object semantics are not aligned by these constructors.

### Token endpoint authentication

`token_endpoint_auth` applies to both authorization-code exchange and token refresh:

| Value | Configuration |
| --- | --- |
| `TokenEndpointAuth::ClientSecretPost` | Send `client_id` and `client_secret` in the form body |
| `TokenEndpointAuth::ClientSecretBasic` | Send form-encoded credentials in the Basic authorization header |
| `TokenEndpointAuth::None` | Send `client_id` without a client secret |
| `TokenEndpointAuth::PrivateKeyJwt(handler)` | Implement `ClientAssertion` to sign a fresh assertion for each request |
| `TokenEndpointAuth::Custom(handler)` | Implement `TokenRequestHook` to modify authentication headers and form parameters |

When `token_endpoint_auth` is omitted, a configured secret selects `ClientSecretPost`; otherwise the public-client method is used. Set the method required by the provider. `None` and `PrivateKeyJwt` cannot be combined with `client_secret`.

Use `authorization_url_params` for additional authorization parameters, `token_url_params` and `authorization_headers` for code exchange, and `refresh_token_params` for token refresh. Refresh parameters may be static or implement `OAuthRefreshParameters` to use the authenticated request. Reserved grant and authorization parameters cannot be replaced by these extra parameters. Implement `OAuthTokenHandler` through `get_token` when the provider needs a custom code exchange.

### Profiles and account identity

Generic OAuth reads an ID-token profile when it contains `sub` and `email`, then falls back to the userinfo endpoint. `get_user_info` accepts a `GenericOAuthUserInfoHandler` for a custom raw profile. `map_profile_to_user` accepts an `OAuthProfileMapper` to return local user fields independently of account identity. A missing userinfo endpoint, a non-success HTTP response, an empty response body, or JSON null produces no profile and does not call the mapper or account-subject resolver. Transport, response-body, JSON decoding, custom handler, and mapper errors propagate. Arbitrary non-JSON text and non-object JSON profile shapes are outside the supported profile contract. Verification and account-subject errors retain their authentication-denial mapping; application errors are not converted to profile absence.

The runtime calls `GenericOAuthUserInfoHandler::get_user_info_with_context` with the token set and a borrowed `GenericOAuthProfileContext`. The context exposes the resolved `client_id`, the current flow’s expected nonce, the resolved userinfo endpoint, and any completed OIDC verification through read-only getters. The context and `VerifiedOAuthClaims` have no public constructors. The default method calls `get_user_info`. Both methods return `AuthResult<Option<serde_json::Value>>`; migrate successful raw-profile results to `Ok(Some(profile))` and unavailable results to `Ok(None)`. The earlier alpha `get_user_info_with_verified_claims` method is replaced by this single context method. Migrate claims-dependent handlers to `context.verified_claims()` and endpoint reads to `context.user_info_url()`. The Entra preset requires verified claims and returns no profile when verified claims or a usable object ID are unavailable. Direct ID-token sign-in passes successful verification to profile lookup; code callbacks and stored-account reads verify at their existing profile boundary. Each OIDC flow validates the received token once before the profile handler and local mapper.

Set `OAuthProfile.additional_fields` to supply configured application user fields. Sign-up and profile updates apply the shared user schema, including input transforms, defaults, and protected-field filtering. OAuth Proxy preserves these mapped fields through its encrypted callback. Raw provider claims remain separate from mapped application fields.

For `OAuthProfile.name`, `None` preserves the provider value, `Some(SchemaValue::Undefined)` omits the mapped name, `Some(None.into())` supplies null, and `Some(Some(value).into())` supplies a string. For `OAuthProfile.image`, `None` preserves the provider value, `Some(None)` clears the mapped provider value, and `Some(Some(value))` replaces it. Generic OAuth then normalizes a null image to omission, so an existing local image remains unchanged. Other optional mapper fields preserve the provider value when omitted. Set `override_user_info: true` to update an existing user's profile during the normal OAuth callback.

`OAuthUserInfo.name` uses `SchemaValue<Option<String>>`: `Undefined` omits the name, `Typed(None)` preserves null, and `Typed(Some(value))` preserves a string. Migrate `name: None` to `name: SchemaValue::Undefined` and `name: Some(value)` to `name: Some(value).into()`. Generic profiles and account-info preserve these states. Provider-specific name fallbacks remain in place. OAuth Proxy uses the upstream empty-string fallback for absent or null names. Sign-in still uses email for an absent or null new-user name, skips absent or null name updates, and omits these names from user admission; those sign-in differences remain outside this profile representation change.

For a social provider's `OAuthUserInfo.image`, `None` omits the field, `Some(None)` supplies explicit null, and `Some(Some(url))` supplies a string. Profile updates preserve the local image when omitted and clear it for explicit null. New-user creation, user admission, `/account-info`, and OAuth Proxy retain this distinction. Raw JSON mappers must preserve key presence before decoding a nullable image.

The account subject comes from the original profile's `sub` for OIDC or `id` for OAuth. Implement `OAuthAccountSubject` through `account_subject` for providers with another stable identifier. Mapped user fields cannot change that identifier. `/account-info` fetches the profile for an existing linked account and keeps the stored account subject.

### Sign-up and email verification

Set `disable_sign_up: true` to reject new users through this provider. Existing users can continue signing in. `disable_implicit_sign_up: true` instead requires `requestSignUp: true` for new users. These settings apply to the configured provider; configure other sign-up mechanisms separately.

Set `require_email_verification: true` to withhold sessions from users whose email remains unverified. Attach an email verification plugin to send verification messages:

```rust
use std::sync::Arc;
use better_auth::plugins::email_verification::{EmailVerificationConfig, EmailVerificationPlugin};

let verification = Arc::new(EmailVerificationPlugin::with_config(EmailVerificationConfig {
    send_on_sign_up: None,
    send_on_sign_in: true,
    send_verification_email: Some(verification_sender),
    ..Default::default()
}));
let oauth = OAuthPlugin::new()
    .with_email_verification(verification)
    .add_generic_provider("oidc", provider_config);
```

`verification_sender` is an `Arc` implementing `SendVerificationEmail`; see the [email verification guide](/docs/authentication/email-verification). Register a separate `EmailVerificationPlugin` with the same sender and token expiry configuration to expose `/verify-email`.

`EmailVerificationConfig.send_on_sign_up` is `Option<bool>`. `None` follows the provider's `require_email_verification`, `Some(true)` sends for new unverified users, and `Some(false)` disables that send. Existing unverified users receive a message only when the provider requires email verification and `send_on_sign_in` is enabled. Sender failures are logged and do not change the verification decision, matching upstream.

## Provider Logout

When `end_session_endpoint` is configured, `POST /sign-out` also returns the provider logout `url` and a `redirect` flag. The endpoint includes the linked account's ID token as `id_token_hint`. A request `callbackURL` overrides `post_logout_redirect_uri`. A post-logout redirect also includes `client_id` and an optional request `state`. Without a redirect or ID token, the URL includes `client_id` only.

Set `disableRedirect: true` in the sign-out request to omit the `Location` header. Local logout completes even if the provider endpoint cannot be used. The most recently updated linked account with a configured logout endpoint takes precedence.

The sign-out body is optional. When present, send a JSON object with `Content-Type: application/json`. `callbackURL` and `state` must be strings; `disableRedirect` must be a boolean. Invalid bodies leave the session active.

`errorCallbackURL` may be an absolute URL or a root-relative path. OAuth errors preserve existing query parameters and append `error` and `error_description` with URL form encoding. Root-relative error callbacks remain relative. Redirect targets must pass the configured origin check.

`/sign-in/social` and `/link-social` validate JSON bodies before endpoint authentication. Hooks retain raw input; provider callbacks receive the schema projection. Unknown object fields are removed. `additionalData` preserves record fields except `__proto__`; `additionalParams` requires string values and rejects reserved OAuth parameters. ## Provider Account Info

Use `GET /account-info` to fetch provider-specific user info for a linked account. The response preserves the provider user ID and mapped additional fields. Generic OAuth includes an ID only when the profile mapper supplies one.
Pass the local account `id` returned by `/list-accounts` as the `accountId` query parameter.

```http
GET /account-info?accountId=local-account-id
Authorization: Bearer <token>
```

The response includes provider user info and an `account` object with `id`, `providerId`, and the provider's `accountId`. The example's Authorization header requires explicit `SessionConfig.bearer` configuration; browser clients may use signed session cookies.

For `POST /get-access-token` and `POST /refresh-token`, send `{ "accountId": "local-account-id" }`. When `account.store_account_cookie` is enabled, these POST endpoints also accept `{ "useAccountCookie": true }` to select the encrypted account cookie. The cookie uses upstream's JWE format and the `better-auth-account` purpose. Large values use numbered cookie chunks; replacing the cookie or signing out clears stale chunks. Select exactly one source. The authenticated session determines the user.

Set `account.encrypt_oauth_tokens = Some(true)` to encrypt stored access and refresh tokens with the shared XChaCha20-Poly1305 codec. Existing plaintext tokens remain readable; subsequent token writes use encryption. ID tokens remain unencrypted, matching upstream. Versioned encryption keys and migration from a legacy secret are described in [Security](/docs/reference/security#secret-rotation).

`/get-access-token` decrypts a refresh token only when the access token needs renewal. Decryption, provider refresh, and persistence failures return `400 FAILED_TO_GET_ACCESS_TOKEN`; `/refresh-token` uses `400 FAILED_TO_REFRESH_ACCESS_TOKEN` for those failures. A missing refresh token retains `REFRESH_TOKEN_NOT_FOUND`. Empty refresh and ID tokens returned by a provider preserve the existing stored values; `/get-access-token` can still return an explicitly empty provider ID token. Stored account scopes are comma-delimited and trimmed, including scopes containing spaces.

For `POST /unlink-account`, send `{ "accountId": "local-account-id" }`. Access-token, refresh-token, and account-info routes check the current database session even when a session cookie cache is enabled. A revoked session cannot read or refresh provider credentials through a cached session.

## How It Works

### PKCE Flow

Social authorization-code flows use PKCE (Proof Key for Code Exchange), except for Facebook, Discord, LinkedIn, Slack, Naver, Linear, Reddit, Roblox, Notion, Kakao, WeChat, TikTok, and Twitch. Zoom enables authorization PKCE by default and exposes `zoom_without_pkce` for its provider option. Generic OAuth enables PKCE by default; set `GenericOAuthConfig.pkce: false` for a provider that does not support it. Direct ID-token sign-in does not perform a code exchange.

1. A random `code_verifier` is generated
2. A `code_challenge` is derived using SHA-256
3. The challenge is sent in the authorization URL
4. The verifier is stored in a verification record
5. During token exchange, the verifier proves the request originated from the same client

### Account Linking Behavior

When the OAuth callback completes:

- **Existing account for provider**: Updates the stored tokens and creates a new session
- **New provider, existing email**: Links the provider when account-linking policy permits it
- **New provider, new email**: Creates a user and links the provider when sign-up policy permits it

Direct ID-token `/link-social` requests refresh an account already owned by the session user, including when new account linking is disabled. Omitted access and refresh tokens preserve stored values; explicit empty strings clear them. Another owner's account returns `409 SOCIAL_ACCOUNT_ALREADY_LINKED`. New links enforce the verified-email and matching-email policies before writing the account.

Authorization-code callbacks merge scopes when linking an existing account. Stored scopes retain their order; new scopes append after trimming and removing duplicates. A provider response without scopes preserves the stored grants. New accounts retain an empty scope string when the token exchange returns no scopes.

With `account.account_linking.update_user_info_on_link`, direct linking also updates the name, image, and permitted additional user fields. The provider cannot replace the user's email or verification status. Better Auth 1.7.6 logs and ignores errors from this profile synchronization after the account write; account write errors still propagate. Account creation errors return `417 LINKING_FAILED`, including an after-create hook error after the row was written. Direct linking does not wrap these operations in a transaction or invoke `validate_user_info`.

A before-create or before-update account hook can cancel its own write. Direct linking still synchronizes the user profile and returns success, matching upstream's null account result. Errors from nested hook operations remain errors.

### State Management

OAuth state expires after 10 minutes. `account.store_state_strategy` selects database storage or an encrypted cookie. State includes the callback URLs, PKCE verifier, link target, sign-up intent, and OIDC nonce when nonce binding is enabled. Database storage uses the raw state identifier and a signed state cookie. Cookie storage encrypts the full payload and binds its `oauthState` to the callback parameter.

An invalid state binding preserves the stored state and redirects to its configured error URL. A validated state is consumed before expiry or provider errors are returned. Malformed database state redirects with `internal_server_error`; malformed encrypted cookie state redirects with `state_invalid`.

With `allow_idp_initiated: true`, a callback without state starts a fresh authorization request. The new request establishes state and nonce binding before a session is issued.


### Twitch

Use `OAuthProvider::twitch(client_id, client_secret, TwitchOptions::default())` with `OAuthPlugin::add_provider("twitch", provider)`. The default scopes are `user:read:email` and `openid`; configured scopes precede request scopes without deduplication. Set `disable_default_scope` to exclude the defaults. The provider omits PKCE, the code verifier, standalone login hints and nonces, configured prompt, and callback device IDs. Code exchange and refresh use client-secret-post. The existing endpoint and callback URI fields remain effective.

`TwitchOptions.claims` requests additional ID-token fields. `None` requests `email`, `email_verified`, `preferred_username`, and `picture`. `Some(vec![])` retains only the shared helper's `email` and `email_verified` claims. Other lists replace the default list while retaining these two claims. Request `additionalParams.claims` overrides the generated JSON value.

The default profile reads the token endpoint's ID-token claims without a userinfo request. The account subject is `sub`; display fields are `preferred_username`, `email`, `picture`, and `email_verified`. Missing and null display values retain their presence. The mapper receives the complete claims and applies its fields last without changing raw `data`. Custom user-info handlers bypass the default decoder and mapper. A missing ID token logs a diagnostic and returns no profile. The constructor does not install a direct ID-token verifier.

The paired contracts cover ordinary authorization, profile mapping, custom handler precedence, and local code/refresh requests. Live Twitch acceptance, route persistence, arbitrary JavaScript value coercion, and exact token-decoding error metadata require separate validation.

### Notion

Use `OAuthProvider::notion(client_id, client_secret)` with `OAuthPlugin::add_provider("notion", provider)`. Notion has no default scopes; configured scopes precede request scopes. Authorization forwards login hints and fixes `owner=user` after additional parameters. The provider omits PKCE, the code verifier, standalone nonces, configured prompt, and callback device IDs. Code exchange uses HTTP Basic authentication; refresh uses client-secret-post. The shared configured callback URI remains effective.

Userinfo sends a Bearer request with `Notion-Version: 2022-06-28`. The default profile is `bot.owner.user`; an absent owner user produces a missing profile. Its `id` supplies the account subject. Mapping uses the owner profile, defaults an absent or null name to an empty string, maps missing or empty `person.email` to null, preserves avatar presence, and defaults `emailVerified` to false. Custom user-info and refresh handlers retain precedence. The constructor does not install an ID-token verifier. Live-provider acceptance and complete error timing require separate validation.

### LINE Social OAuth

Use `OAuthProvider::line(client_id, client_secret)` with `OAuthPlugin::add_provider("line", provider)`. Social LINE uses PKCE, client-secret-post grants, and `openid profile email` before configured and request scopes. Login hints are forwarded; standalone nonces, configured prompt, and callback device IDs are omitted.

Direct ID-token login uses LINE's verification endpoint through the existing verifier path. The default profile handler reads ID-token claims or uses GET/Bearer userinfo when claims are unavailable. The profile uses `sub`, defaults a missing or null name to an empty string, preserves email and picture presence, and sets `emailVerified` to false. The existing profile mapper and custom user-info handler retain their precedence. Social LINE is separate from the Generic helper below. Dedicated local contracts exercise ordinary configuration, profiles, direct/code sign-in, and code/refresh request and token fields. Live-provider acceptance and complete error timing require separate validation.

### LINE Generic OAuth

Use `GenericOAuthConfig::line(client_id, client_secret)` for LINE authorization-code login. Register each channel through the existing provider name:

```rust
use better_auth::plugins::oauth::{GenericOAuthConfig, OAuthPlugin};

let oauth = OAuthPlugin::new().add_generic_provider(
    "line-jp",
    GenericOAuthConfig::line("channel-id", "channel-secret"),
);
```

The constructor requests `openid`, `profile`, and `email`. Configure the existing `GenericOAuthConfig` fields before registration to override scopes or other common options. The profile handler reads the resolved client ID at each lookup. The stable account subject is `sub`. The profile contains only `sub`, `name`, `email`, `image` from `picture`, and `emailVerified: false`; the existing profile mapper runs afterward.

LINE Web ID tokens use HS256. The LINE handler posts a received ID token and client ID to LINE’s fixed verification endpoint, then reads the verified response claims. A flow nonce is included when the caller supplied one. Existing OIDC verification results are reused when present. The handler does not decode an unverified JWT. A missing ID token selects the configured userinfo endpoint. Verification, transport, and JSON errors propagate; a failed verification does not select userinfo. Request errors retain their causes without including the request URL.

This differs from Better Auth 1.7.6’s Generic LINE helper, which decodes the ID token in its profile handler: the Rust default adds one verification HTTP round trip. The default constructor retains Generic LINE’s authorization-code scope, with no generated ID-token nonce or direct ID-token login. Stored-account profile reads use the same handler and can therefore fail when LINE rejects a stored token. Complete error, network-timing, and stored-token behavior parity is not claimed.

LINE’s documented userinfo response has no email field. Applications that use an access-token-only profile need their existing profile mapper to supply an application email before signup; the constructor does not invent an email. Ordinary local fixtures cover signed Web-token profiles, nullable and absent fields, access-token userinfo with an explicit application mapper, and request form encoding. The fixtures do not establish live-provider acceptance or native/LIFF token behavior. See LINE’s [ID-token guide](https://developers.line.biz/en/docs/line-login/verify-id-token/) and [API reference](https://developers.line.biz/en/reference/line-login/#verify-id-token).

Salesforce uses PKCE, client-secret-post for code exchange and refresh, and a GET/Bearer user-info request. Authorization requires a nonempty client ID and secret. Default scopes precede configured scopes and request scopes without deduplication. Request-level additional parameters remain effective; standalone login hints, nonces, callback device IDs, and configured prompt are ignored by this provider helper. The constructor does not install an ID-token verifier.

Salesforce reads the internal account subject from `user_id`. Display fields use `name`, nullable or omitted `email`, and the nonempty `photos.picture` or `photos.thumbnail`. The selected thumbnail retains omission, null, or an empty string. An omitted or null `email_verified` defaults to false. The async mapper sees the original profile and overrides these display fields.
