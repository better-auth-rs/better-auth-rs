title: Organization

The `OrganizationPlugin` provides multi-tenancy support with organizations, membership management, invitation workflows, and role-based access control (RBAC).

## Setup

These examples assume you've already defined `AppAuthSchema`. If you want a complete setup from entity definitions through Axum mounting, start with the [Axum integration guide](/docs/integrations/axum).

```rust
use better_auth::plugins::OrganizationPlugin;

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(OrganizationPlugin::new())
    .build()
    .await?;
```

### Configuration

```rust
use better_auth::plugins::organization::OrganizationConfig;

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(
        OrganizationPlugin::new()
            .allow_user_to_create_organization(true)
            .organization_limit(5)
            .membership_limit(50)
            .creator_role("owner")
            .invitation_expires_in(172800) // 48 hours
            .invitation_limit(100)
    )
    .build()
    .await?;
```

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `allow_user_to_create_organization` | `bool` | `true` | Allow users to create organizations |
| `organization_limit` | `Option<usize>` | `None` | Max organizations per user |
| `membership_limit` | `Option<usize>` | `Some(100)` | Max members per organization |
| `creator_role` | `String` | `"owner"` | Role assigned to organization creator |
| `invitation_expires_in` | `u64` | `172800` (48h) | Invitation expiration in seconds |
| `invitation_limit` | `Option<usize>` | `Some(100)` | Max pending invitations per org |
| `cancel_pending_invitations_on_re_invite` | `bool` | `false` | Cancel the old pending invitation before creating a replacement |
| `require_email_verification_on_invitation` | `bool` | `false` | Require a verified recipient email for lookup, acceptance, and rejection |
| `disable_organization_deletion` | `bool` | `false` | Prevent organization deletion |
| `teams` | `OrganizationTeamsConfig` | Disabled | Team creation, membership, and limits |
| `dynamic_access_control` | `bool` | `false` | Enable persisted organization roles |
| `ac` | `Option<HashMap<String, Vec<String>>>` | `None` | Allowed resource statements for dynamic roles |
| `roles` | `Option<HashMap<String, RolePermissions>>` | `None` | `None` uses default roles; `Some` replaces them, including an empty map that grants no static permissions |
| `maximum_roles_per_organization` | `Option<usize>` | `None` | Maximum persisted roles per organization |

Configure invitation delivery with `OrganizationPlugin::custom_send_invitation_email(Arc<dyn SendInvitationEmail>)`. Implement `SendInvitationEmail::send` using the invitation, organization, member, inviter, and optional HTTP request in `InvitationEmail`. The plugin logs delivery failures and still returns the stored invitation, matching upstream behavior.

Use `.callbacks(OrganizationCallbacks::invitation_email(...))` for a synchronous factory with the complete `EndpointContext`. Return `Err` to propagate a synchronous failure, `Ok(None)` for synchronous completion, or `Ok(Some(BackgroundFuture))` for asynchronous work. The invitation is stored before the factory runs. New invitations run `after_create_invitation` after scheduling; resends omit this hook. Asynchronous delivery failures are logged. Configure `advanced.background_tasks` to retain running work outside the endpoint; without a handler, the endpoint awaits delivery.

Inviting an email with a pending invitation returns `USER_IS_ALREADY_INVITED_TO_THIS_ORGANIZATION`. Send `resend: true` to renew that invitation and send the email again. Resending preserves the invitation ID, role, and original inviter.

Organization metadata uses nullable text in the default Rust storage. SQL `NULL` represents an omitted value; the text `null` remains a stored value. Creation and update responses decode metadata; read/list/delete responses retain its stored text. Raw adapter operations preserve strings without JSON parsing. Applications migrating from the former `Option<Json>` model must migrate their column to nullable text; explicitly declared JSON models retain their native JSON contract. See the [database migration guidance](/docs/concepts/database#organization-models). A metadata field policy can replace creation input validation and receives the adapter's serialized JSON text before storage. Update input retains its base object validation. A trusted before-update hook can store the text `null`; a before-create hook's null value is omitted.

For fields declared `Json`, SQLite converts objects to JSON text after the application input transform. The application output transform receives that text before the adapter parses JSON. PostgreSQL preserves native JSON at these boundaries. These conversions also apply to the built-in `metadata` and dynamic-role `permission` fields. Routes retain their upstream decoding rules: for example, a `Json` permission policy can produce an object that a later role route fails to parse again. The create-role response keeps the original requested permissions even when a field policy changes the stored permissions.

Organization body schemas run after endpoint before hooks and before authentication or endpoint middleware. Callbacks in the handler receive the validated projection; endpoint before and after hooks retain raw input. Organization creation lets configured fields replace base fields, while organization update keeps its base fields. Team and dynamic-role routes retain their own upstream schema precedence and union rules.

Trusted native calls to `/organization/create` can omit both headers and a Request and supply `userId`. The plugin loads that user and applies organization limits, while bypassing a false `allow_user_to_create_organization` result for this server action. Explicit empty headers or a supplied Request still require an authenticated session. Native `/organization/check-slug` also permits omitted headers and Request. These rules do not grant an HTTP caller permission to act as another user.

Trusted native `/organization/create-team` and `/organization/remove-team` calls can supply `organizationId` without headers or a Request. Their lifecycle hooks receive `user: None`, and the team-limit policy receives `session: None`. Calls with a session retain membership and permission checks and can use the active organization. HTTP calls, explicit empty headers, and supplied Requests require authentication. Other team routes retain their required-headers and session rules. Team capacity checks use accurate database counts, independent of the default list limit.

## Additional fields

Set `OrganizationConfig::schema` to an `OrganizationFields` value. The `organization`, `member`, `invitation`, `team`, and `organization_role` members each use `UserConfig::additional_fields`. Define the corresponding typed SeaORM columns and select the application's organization models as described in the [database guide](/docs/concepts/database). The plugin configures the store during initialization.

```rust
use better_auth::plugins::organization::{OrganizationConfig, OrganizationFields};
use better_auth::config::{UserConfig, UserFieldConfig};

let config = OrganizationConfig {
    schema: OrganizationFields {
        organization: UserConfig {
            additional_fields: Some([("department".to_owned(), UserFieldConfig {
                required: Some(false),
                default_value: Some(serde_json::json!("general")),
                ..Default::default()
            })].into()),
        },
        ..Default::default()
    },
    ..Default::default()
};
let plugin = OrganizationPlugin::with_config(config);
```

Organization field validation follows the pinned upstream schema. `required: None` and `Some(true)` require a field during creation; `Some(false)` permits omission and null. A default does not make a required HTTP field optional. Updates permit omission. `input: Some(false)` excludes a field from the additional input schema; an existing base route field remains accepted. Field definitions retain insertion order. Validation reports every issue in the final route schema order, with replacements retaining the base field position. Organization routes validate declared types but do not invoke `validator`; the adapter applies `transform.input` once. HTTP date strings do not satisfy a date field, while typed storage defaults can supply dates. Enum fields retain upstream's unrestricted Organization input behavior.

Member creation and invitation creation let additional field schemas replace base input validation. `AddMemberInput` retains replacement values through `SchemaValue`; member roles can remain numbers, objects, null, or omitted values, while arrays use upstream string joining. Invitation creation still calls string operations on email and role after validation. Incompatible replacement values produce the upstream empty `500` response before persistence. Invitation request fields can replace status, creation time, expiration time, and inviter defaults; the before-create hook observes the authenticated inviter. Upstream field definitions replace attributes as a whole, so a TypeScript configuration that overrides a reference field must retain its `references` attribute when joins need that relationship. Rust applications express those relationships in their storage models.

Invitation team checks run only when teams are enabled and the supplied `teamId` is truthy. The before-create hook retains replacement values in `team_ids: SchemaValue<Vec<String>>`; `team_id: SchemaValue<String>` is the informational first-team alias. The adapter joins destination arrays after the hook, matching upstream coercion and runtime errors.

Adapter writes apply creation defaults and `on_update`, including implicit owner/default-team creation, invitation acceptance, and pending-invitation changes during team deletion. Adapter reads apply `transform.output` and `field_name` mapping once. Organization and team responses hide `returned: Some(false)` fields. Member, invitation, and dynamic-role responses retain those fields; full-organization responses hide them in their nested lists. Hooks receive the same entity visibility as the corresponding upstream adapter operation.

Use `UserFieldTransform::new_async` for awaited Organization input and output callbacks. Each row retains field order; asynchronous list projections can complete out of order while results retain query order. An input error prevents the write. An ordinary output error follows the write and leaves the stored row. Compound team and invitation operations retain their transaction and compensation boundaries.

The Memory adapter releases its state lock before awaiting field callbacks. Compound operations prepare field deltas, then check the latest membership, invitation state, capacity, and staged Serial allocation before publishing. A full team retains the existing capacity rejection. Another concurrent change that invalidates a prepared calculation returns `AuthError::Conflict`; callbacks are not replayed and completed output projections remain intact. Unrelated row updates remain intact. This explicit conflict is a Rust concurrency boundary, not an exact reproduction of JavaScript scheduling. Mutation guards retain accurate counts even when list queries have a default limit.

Dynamic-role creation accepts an optional outer `additionalFields` object. When supplied, that object uses the configured creation requirements. Upstream initializes the role update schema eagerly, which makes adapter role fields optional from initialization; the creation endpoint retains its original validation schema. Role updates return the old record merged with raw request fields, while subsequent reads expose the persisted transforms and `on_update` values. Invitation resend similarly returns the old record with the new expiration time, while storing `on_update` values.

Built-in fields accept replacement types, nullability, defaults, transforms, `on_update`, and visibility policies. Use public camelCase names such as `createdAt`. `SchemaValue<T>` preserves the default typed value, a replacement JSON value, or an omitted value. An explicit `null` differs from omission; an output transform can return `None` to omit a field. A `field_name` may name an alias of the same model column; mappings to another field or an unknown column fail initialization. Generate application-owned models from the configured schema so their storage types match the policies. A replacement timestamp policy removes the original adapter update generator and can preserve a plain string without date normalization.

Creation schemas let additional field definitions replace base definitions. Organization updates retain their base field validation. The adapter ignores custom `id` defaults, transforms, and storage mappings; Organization, Team, and Invitation creation retain an explicitly accepted ID.

The `metadata` and `permission` fields and the internal team counter `memberCount` accept policies. Ordinary team responses omit `memberCount`; full-organization joins expose the stored adapter value. Rust stores its private organization timestamp separately as `auth_updated_at`, leaving the public `updatedAt` name available for an application field. Replacing a field's type does not change the downstream operation: an operation that requires a string can still fail after its replacement input schema accepts another type, matching upstream behavior.

## Application hooks and dynamic options

`OrganizationPlugin::hooks(Arc<dyn OrganizationHooks>)` configures the 30 upstream lifecycle hooks. Implement only the methods your application uses. Before hooks receive mutable typed inputs. Changes replace the corresponding values before persistence. Creation drafts omit generated timestamps until the hook returns. Return an `AuthError` to stop the operation. After hooks receive stored records; an after-hook error does not undo writes that upstream already committed.

```rust
use async_trait::async_trait;
use better_auth::{AuthResult, plugins::organization::hooks::OrganizationHooks};
use better_auth::types::CreateOrganization;
use better_auth::wire::UserView;

struct OrganizationRules;

#[async_trait]
impl OrganizationHooks for OrganizationRules {
    async fn before_create_organization(
        &self,
        organization: &mut CreateOrganization,
        user: &UserView,
    ) -> AuthResult<()> {
        let name = user.name.typed()?.as_deref().unwrap_or("User");
        organization.name = format!("{name}'s organization");
        Ok(())
    }
}

let plugin = OrganizationPlugin::new().hooks(std::sync::Arc::new(OrganizationRules));
```

Hooks cover organization creation/update/deletion, member addition/removal/role changes, invitation creation/acceptance/rejection/cancellation, team creation/update/deletion, and team member addition/removal. Owner and default-team creation invoke their corresponding hooks. Invitation acceptance does not invoke member-add hooks, and leaving an organization does not invoke member-remove hooks. Resending an invitation invokes delivery without rerunning invitation creation hooks. Upstream ignores the return data from `beforeAddTeamMember`, so the Rust hook exposes a read-only target.

An organization ID override follows the database constraints. A database with foreign keys can reject changing an ID referenced by members or teams; the plugin propagates that error. The plugin does not disable constraints to imitate an adapter that has foreign keys disabled.

Configure asynchronous options with these interfaces:

| Interface | Options |
| --- | --- |
| `OrganizationPolicy` through `.policy(...)` | Creation permission, organization limit, invitation limit, team limit, dynamic role limit, custom default-team creation |
| `MembershipLimitPolicy` through `.membership_limit_callback(...)` | Organization capacity for the user being added or accepting an invitation |
| `TeamMemberLimitPolicy` through `teams.maximum_members_per_team_callback` | Team capacity for the authenticated actor and destination team |

Optional `OrganizationPolicy` methods return `None` to retain the static setting. The organization-limit callback returns `true` when the limit has been reached. Membership and team member callbacks return numeric limits. Static `membership_limit: Some(0)` uses the default of 100; a callback returning zero rejects admission. A dynamic membership limit does not change the default list size of 100. A zero invitation limit rejects new invitations, while `invitation_expires_in: 0` uses 48 hours. A zero maximum-team limit disables that limit.

Endpoint-aware hooks and policies receive `OrganizationEndpoint`, which exposes the request, global configuration, and organization persistence. A custom default-team callback must persist its team and return that record. Returning `None` uses normal team creation, including the before-hook changes. The returned team's identity controls owner membership and the active team.

`auth.organization()?.add_member(Some(body)).await` is a trusted server-only API, matching upstream `auth.api.addMember`. There is no public HTTP route. The API uses the installed Organization configuration, global before/after hooks, member input validation, and Organization lifecycle hooks. The JSON result preserves global hook replacements. Use `.with_request(NativeRequest { request, headers })` to supply a Request and headers independently. Inside an endpoint callback, `endpoint.organization()?` retains the resolved runtime and active transaction. The typed `OrganizationPlugin::add_member(input, request, context)` convenience method uses the same dispatcher and requires a member-shaped result.

Membership capacity uses a database count, independent of the default list limit. When a dynamic team capacity callback is configured, adding a team member requires an authenticated request. A failure during team addition removes the newly created organization membership and cleans team memberships for the original user and organization, even when `before_add_member` changes the saved member. Compensation errors propagate. Stores must implement `delete_member_for_user` and the Organization operations on `AuthTransaction` to support these paths.

The member table has separate, non-unique organization and user indexes. The endpoint rejects an existing membership before the creation hook; a hook may override the new member's user. If an existing application database contains the former `idx_member_org_user_unique` index, remove that index through an application migration. For CLI-generated models, remove the corresponding combined unique index using the application's mapped table and index names. This library does not drop indexes in existing databases automatically.

Dynamic team limits during invitation acceptance execute per team in the same transaction as member creation; a callback error rolls back every reserved seat. The invitation is claimed before that transaction. If the transaction fails, a conditional update restores the invitation to pending and runs its `on_update` callbacks again. Claim-output failures stop before the member transaction, and compensation failures propagate.
Set `cancel_pending_invitations_on_re_invite: true` to cancel the old invitation and create a new invitation. Explicit `resend: true` still renews the existing invitation. Cancellation occurs before the new invitation's capacity and team checks, matching upstream.

Invitation lookup requires a session owned by the recipient, a pending unexpired invitation, and an inviter who still belongs to the organization. Set `require_email_verification_on_invitation: true` to require email verification for lookup, acceptance, and rejection. The default matches upstream's built-in opaque IDs; the bundled stores generate UUIDs. Applications with predictable invitation IDs must enable this option. Listing a user's invitations always requires a verified session email.

## RBAC (Role-Based Access Control)

### Default Roles

| Role | Organization | Member | Invitation | Team | Access control (`ac`) | API key |
|------|-------------|--------|------------|------|-----------------------|---------|
| **owner** | update, delete | create, update, delete | create, cancel | create, update, delete | create, read, update, delete | — |
| **admin** | update | create, update, delete | create, cancel | create, update, delete | create, read, update, delete | — |
| **member** | — | — | — | — | read | — |

The `apikey` resource governs organization-owned keys from the [API Key plugin](/docs/plugins/api-key#named-configurations-and-organization-owned-keys). No default role grants API key actions. The API Key plugin allows the creator role (`creator_role`, `"owner"` by default) implicitly; other roles need an explicit grant. Organization permission checks use the role's statements, including checks made by the creator.

Deleting an organization does not revoke its API keys, matching Better Auth 1.7.6. Applications that require revocation must delete those keys explicitly.

### Custom Roles

Configure static roles with custom permissions. A nonempty `roles` map replaces the default permission definitions:

```rust
use better_auth::plugins::organization::{OrganizationConfig, RolePermissions};
use std::collections::HashMap;

let mut roles = HashMap::new();
roles.insert("editor".to_string(), RolePermissions {
    organization: vec!["read".to_string()],
    member: vec!["read".to_string()],
    invitation: vec![],
    api_key: vec!["read".to_string(), "create".to_string()],
    ..Default::default()
});

let config = OrganizationConfig {
    roles,
    ..Default::default()
};

let auth = BetterAuth::<AppAuthSchema>::new(auth_config)
    .store(store)
    .plugin(OrganizationPlugin::with_config(config))
    .build()
    .await?;
```

### Resources and Actions

**Resources**: `organization`, `member`, `invitation`, `team`, `ac`, `apikey`, and application resource names configured through `RolePermissions.additional`.

**Actions**: `create`, `read`, `update`, `delete`, `cancel`

### Teams

```rust
use better_auth::plugins::organization::OrganizationTeamsConfig;

let plugin = OrganizationPlugin::new().teams(OrganizationTeamsConfig {
    enabled: true,
    maximum_teams: Some(10),
    maximum_members_per_team: Some(50),
    ..Default::default()
});
```

Teams are disabled by default. When enabled, organization creation creates a default team with the organization's name and adds the creator. Set `default_team: false` to disable that behavior. Set `allow_removing_all_teams: true` to allow deletion of the last team. Both numeric limits default to `None`.

Team members must also belong to the organization. Adding an existing team member returns the existing membership, including when the team is full. The store reserves capacity atomically for concurrent additions. A session's `activeTeamId` identifies its selected team. Team selection checks organization membership and team membership; deleting the selected team is rejected until the caller clears or changes the selection.

### Dynamic roles

Enable persisted roles and provide access-control statements:

```rust
use std::collections::HashMap;

let plugin = OrganizationPlugin::new()
    .dynamic_access_control(true)
    .access_control(HashMap::from([
        ("organization".into(), vec!["update".into(), "delete".into()]),
        ("member".into(), vec!["create".into(), "update".into(), "delete".into()]),
        ("invitation".into(), vec!["create".into(), "cancel".into()]),
        ("team".into(), vec!["create".into(), "update".into(), "delete".into()]),
        ("ac".into(), vec!["create".into(), "read".into(), "update".into(), "delete".into()]),
    ]));
```

Dynamic roles belong to one organization. Creating or updating permissions requires the corresponding `ac` action and every permission being granted. Resource names must exist in `ac`. Missing `ac` produces `MISSING_AC_INSTANCE` for create and update requests. The default `member` role can list and read roles, but cannot create, update, or delete them.

Created and renamed role names are converted to lowercase. Role lookup uses the supplied name or ID. A role assigned to a member cannot be deleted. Renaming a role does not rewrite existing member role strings, matching upstream. For composite member roles, one assigned role must authorize the complete permission request.

Generate the organization schema with `better-auth-rs generate --plugins organization`. The schema includes the team, team membership, and organization role tables, plus `active_team_id` on sessions and `team_id` on invitations. Apply application-owned migrations to existing databases before enabling these features.

## Errors

| Status | Condition |
|--------|-----------|
| 400 | Invalid slug format or missing required fields |
| 403 | Insufficient permissions for the operation, or `EMAIL_VERIFICATION_REQUIRED_FOR_INVITATION` when listing invitations with an unverified email |
| 404 | Organization, member, or invitation not found |
| 409 | Slug already taken or user already a member |
