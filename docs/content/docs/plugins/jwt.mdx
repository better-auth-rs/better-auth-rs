---
title: JWT
description: Sign session tokens with persisted asymmetric keys and expose public JWKS.
---

Register `JwtPlugin::new()`. `GET /jwks` returns public signing keys. Authenticated `GET /token` returns `{ "token": "..." }`. A successful `GET /get-session` also sets the `set-auth-jwt` response header and exposes that header through CORS.

The default algorithm is Ed25519 (`EdDSA`). Select `Rs256`, `Ps256`, `Es256`, or `Es512` with `.algorithm(...)`. These algorithms use RSA PKCS#1, RSA PSS, P-256, and P-521 respectively. RSA keys default to 2048 bits; `.modulus_length(3072)` changes the primary RSA key size. The store persists keys through `JwksStore`; private JWKs are encrypted with the authentication secret. Public discovery never returns private key parameters.

Session tokens contain the user fields, the user ID in `sub`, the issue time in `iat`, and a fifteen-minute `exp`. The issuer and audience default to the configured base URL. Override these values with `.issuer(...)`, `.audience(...)`, and `.expiration_time(chrono::Duration::minutes(5))`.

`.rotation_interval(chrono::Duration::days(30))` enables signing key rotation. `.grace_period(...)` controls how long expired public keys remain discoverable; the default is thirty days. Choose a grace period that covers the lifetime of issued tokens. `.jwks_path("/keys")` changes the discovery route. `.disable_setting_jwt_header(true)` suppresses the session response header.

Trusted server code may call `sign` with an application JSON payload. `sign_with_options` accepts `JwtSigningOptions` with an optional `key_id`, `algorithm`, and protected `header`. A pinned key must exist, remain live, and match the requested algorithm. `.key_pair_configs(vec![JwtKeyPairConfig::new(JwtAlgorithm::Ps256)])` permits lazy provisioning for an additional algorithm. An unpinned request prefers the primary algorithm. `create_key_pair` explicitly provisions a key. Concurrent first requests may provision multiple valid keys, as in upstream.

`.define_payload(...)` and `.get_subject(...)` accept asynchronous callbacks. Each callback receives the complete serialized `{ user, session }` object. The payload callback replaces the default user claims. The subject callback overrides `user.id`. The plugin applies default `iat` before subject selection and preserves a supplied `iat`. Both `/token` and the session response header use these callbacks.

`.remote_url(...)` disables local JWKS discovery. Pair the URL with `.custom_sign(...)` to delegate signing. The callback receives defaulted claims and `JwtSigningOptions`; the callback must set `alg` and `kid`, preserve required protected headers, and honor key overrides. Publish the corresponding public keys at the remote URL. `remote_url` alone does not fetch keys or replace the signing store.

`verify(token, issuer_override, context)` is the server-only equivalent of upstream `verifyJWT`; no HTTP verification route is registered. Valid tokens return `Some(claims)`. Invalid signatures, claims, subjects, and unknown keys return `None`. Store failures propagate. Verification reads adapter keys even when `remote_url` is configured, matching `better-auth@1.7.6`. Applications that need remote verification must use a verifier with the remote JWKS.

To sign session cookie caches with plugin keys, enable `SessionConfig.cookie_cache` with `CookieCacheStrategy::Jwt` and register `JwtPlugin::new().session_cookie_cache(true)`. This requires locally managed keys and rejects custom signing callbacks. Core uses the `SessionCookieSigner` runtime interface without depending on the API crate.

Cache tokens use `typ: better-auth.session-cache+jwt`, audience `better-auth:session-cache`, and the configured base URL as issuer. These values are independent of ordinary token issuer and audience configuration. The cache binds `sub` to the cached user ID and `sid` to the cached session token. Cache reads also require the signed session cookie, matching token, cache version, and unexpired session and cache lifetimes. Ordinary JWTs cannot serve as cache cookies. Authoritative session reads bypass the cache.

Public JWKS discovery excludes keys beyond the configured grace period. Local verification continues to use persisted keys, including expired signing keys, as upstream does. Keep published keys available for the lifetime of tokens verified remotely. The compatibility profiles cover default EdDSA, RS256, ES256, ES512, 3072-bit PS256, callbacks and key overrides, remote JWKS rotation, and asymmetric cache round trips and negative cases.
