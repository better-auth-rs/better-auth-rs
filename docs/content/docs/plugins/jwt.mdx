---
title: JWT
description: Sign session tokens with persisted asymmetric keys and expose public JWKS.
---

Register `JwtPlugin::new()`. `GET /jwks` returns public signing keys. Authenticated `GET /token` returns `{ "token": "..." }`.

Database key lists apply `advanced.database.default_find_many_limit` before expiration filtering and newest-key selection. A zero limit or a page containing only expired keys causes signing to create a new key. Custom `get_jwks` callbacks supply their complete keyset without this database limit.

`GET /get-session` signs the endpoint session snapshot and exposes `set-auth-jwt` through CORS. The snapshot is independent of the response body. Better Auth 1.7.6 retains an expired session in endpoint context, so a null expired-session response can still carry a newly signed JWT. A revoked session has no snapshot and emits no JWT. Do not use this header as proof that the session response authenticated the request. `.disable_setting_jwt_header(true)` disables the header.

The default algorithm is Ed25519 (`EdDSA`). Select `Rs256`, `Ps256`, `Es256`, or `Es512` with `.algorithm(...)`. These algorithms use RSA PKCS#1, RSA PSS, P-256, and P-521 respectively. RSA keys default to 2048 bits; `.modulus_length(3072)` changes the primary RSA key size. The store persists keys through `JwksStore`; private JWKs are encrypted with the authentication secret. Public discovery never returns private key parameters.

`JwtPluginConfig.algorithm` uses `Option<JwtAlgorithm>` to retain an omitted configuration. Ordinary key generation still defaults to EdDSA. Cookie verification can use the token's algorithm when both the stored key and configuration omit that value. Remote JWKS configuration requires an explicit algorithm; the `.algorithm(...)` builder retains its ordinary argument.

Session tokens contain the user fields, the user ID in `sub`, the issue time in `iat`, and a fifteen-minute `exp`. The issuer and audience default to the configured base URL. Override these values with `.issuer(...)`, `.audience(...)`, and `.expiration_time(chrono::Duration::minutes(5))`.

Audience configuration preserves a single string or an array: `.audience("service-a".into())` and `.audience(vec!["service-a".into(), "service-b".into()].into())` produce the corresponding `aud` claim. Verification requires at least one matching recipient; an empty configured array accepts no token.

`expiration_time` accepts a relative `chrono::Duration`, an absolute `chrono::DateTime<Utc>`, or an absolute `i64` NumericDate in seconds. Use `JwtExpiration::At(serde_json::Number)` for fractional absolute seconds. Absolute dates discard subsecond precision, matching upstream Date values; relative durations round to the nearest second with ties toward positive infinity. An explicit payload `exp` overrides the configured default.

`.rotation_interval(chrono::Duration::days(30))` enables signing key rotation. `.grace_period(...)` controls how long expired public keys remain discoverable; the default is thirty days. Choose a grace period that covers the lifetime of issued tokens. `.jwks_path("/keys")` changes the discovery route. `.disable_setting_jwt_header(true)` suppresses the session response header.

Trusted server code may call `sign` with an application JSON payload. `sign_with_options` accepts `JwtSigningOptions` with an optional `key_id`, `algorithm`, and protected `header`. A pinned key must exist, remain live, and match the requested algorithm. `.key_pair_configs(vec![JwtKeyPairConfig::new(JwtAlgorithm::Ps256)])` permits lazy provisioning for an additional algorithm. An unpinned request prefers the primary algorithm. `create_key_pair` explicitly provisions a key and returns `AuthResult<Option<Jwk>>`. Concurrent first requests may provision multiple valid keys, as in upstream.

JWT configuration guards, missing or mismatched signing keys, expired pinned keys, decryption failures, and empty discovery results retain the upstream `BetterAuthError` class and message. A mismatch rereads the stored algorithm for its message and preserves unpaired UTF-16 surrogates. Getter and string-conversion failures propagate their original thrown value. Error construction does not undo an adapter write that already completed.

`auth.jwt()?` binds native operations to the registered configuration. Signing and verification run endpoint before/after hooks, validation, and spans. Before context patches can change payload and signing option groups before the handler selects keys and claims. Typed signing methods decode a string only after endpoint hooks complete. `sign_value` and `sign_value_with_options` retain native payload leaves and the original custom signer result through the same validation and hook pipeline. Key-pair provisioning remains a direct helper and skips endpoint hooks. `endpoint.jwt()?` also retains the active transaction. `.with_request(NativeRequest { request, headers })` supplies Request and headers independently for dynamic URL resolution and adapter callbacks. Context-only `JwtPlugin` helpers create native calls without borrowing an ambient request. Use `sign_in_endpoint`, `verify_in_endpoint`, or `create_key_pair_in_endpoint` for an explicit endpoint context.

Native endpoint headers use lowercase names in callback context. `Cookie` and `cookie` both authenticate a supplied session. Calling `/token` through `call_endpoint` requires `EndpointInput.headers`: omission returns `400 VALIDATION_ERROR`; an empty collection returns `401 UNAUTHORIZED`.

`sign_with_overrides(payload, JwtCallOverrides { ... })` replaces supplied `jwt`, `jwks`, or `adapter` groups for one call. Omitted groups retain registration defaults. Supplied groups start from their own defaults; fields do not merge with the registered group. An empty adapter restores default persistence for that call. Changes do not mutate the registered plugin. Changing key encryption for one call can leave stored keys incompatible with the registered encryption policy, matching upstream.

`sign_value_with_overrides(payload, overrides)` accepts native `FieldValue` inputs through the same endpoint. The outer merge retains nested group handles, undefined properties, accessors, and callable identity. A hook that replaces a group or removes a callback also removes the old callback. Signing reads default claim options even when the payload already supplies the corresponding claims. Key selection and creation read options at their business boundary; custom signing does not decode unrelated key settings.

`JwtPlugin::callbacks(JwtCallbacks::<AppSchema>::default().get_jwks(...).create_jwk(...))` overrides reads and writes independently. Each asynchronous callback borrows `EndpointContext`, including body, request, headers, session, runtime, and active transaction. `get_jwks` returning `None` represents an absent keyset. Discovery reads the adapter again after creating the first key and fails if that read is empty. The create callback receives the generated `created_at` and returns `Option<Jwk>`. Discovery rereads storage after a null create result. Signing consumes the returned key and propagates the missing `privateKey` error at that boundary. The default JWT adapter assigns the persistence timestamp before calling the store. Direct `JwksStore::create_jwk` calls preserve the supplied `created_at` on Memory and SQL.

Use `get_jwks_native` and `create_jwk_native` when an adapter returns native `FieldValue` handles. The keyring retains array methods, record accessors, missing and null values, and object identity through selection, signing, verification, and discovery. The existing typed callbacks feed the same keyring after converting typed records. Public `create_key_pair` methods convert their results only at the typed return boundary. Native callback results do not undergo another adapter projection.

Use `create_jwk_value` to receive generated key material as a native `FieldValue` before any `CreateJwk` conversion. Typed adapter callbacks retain the active borrowed `EndpointContext` through shared host-bound functions. Registration creates one native adapter group; subsequent reads retain that group's receiver and callback identities.

Use `JwtPlugin::native_callbacks::<AppSchema>(adapter)` to register an original native adapter value without enumerating or converting it. For an explicit endpoint call, attach the original context with `EndpointContext::with_native_root(value)`, then use `sign_value_in_endpoint`, `verify_in_endpoint`, or `create_key_pair_in_endpoint`. Native `getJwks` receives `[root]`; native `createJwk` receives `[data, root]`. Both retain the original adapter as their receiver and await synchronous or asynchronous `FieldFunction` callbacks. `OwnedEndpointContext` retains the same root handle, including subsequent object mutations. Explicit undefined, null, and primitive roots pass through unchanged.

The explicit root does not project or synchronize typed endpoint fields. Automatic HTTP, cookie-cache, and `JwtApi` dispatch do not yet construct a complete native dispatcher context. A native adapter callback without an explicit root returns a configuration error before invocation; a typed callback continues to receive its borrowed Rust context. Full JavaScript Promise values, callback reflection, and scheduling remain unsupported.

Custom `JwksStore` implementations may override `get_jwk_value` and `list_jwk_values` to return native logical output handles. The defaults wrap the existing complete record projection, and Secondary forwards native handles without reconstructing records. These methods do not bypass field policies or change Memory live reads, SQL snapshots, or transaction boundaries. The typed `get_jwk` and `list_jwks` conveniences materialize values from this same boundary.

Custom plugins may register JWK adapter fields with `ModelFields::register_model_fields(EntityRole::Jwk, fields)`. Register replacements after the JWT plugin. A replacement replaces the complete declaration at its existing position, including defaults, transforms, references, and physical mapping. Native fields and extensions use the same input and output policies. A logical `id` declaration sets the field position; the adapter owns its policy as described under [model IDs](/docs/concepts/database#model-ids).

`CreateJwk` retains ordinary Rust inputs. `CreateJwk.additional_fields` accepts declared logical application values, and `Jwk.additional_fields` contains their output projection. Native `Jwk` fields use `SchemaValue<T>` to preserve omitted, null, and cross-type values. `Jwk.field_order` preserves declared property presence and order through typed records; complete struct literals must initialize this metadata. `Jwk` does not implement `Serialize`, keeping private signing material outside automatic JSON responses. Use `JwksStore` record methods for complete `FieldMap` creation, lookup, update, deletion, and listing. Output errors propagate after direct persistence; enclosing transactions retain their rollback boundary. SeaORM reads a SQL snapshot before output conversion, while Memory reads each field when its output phase starts. Generate matching columns with `jwks.additionalFields`; applications own database migrations.

JWT consumers apply their own key-selection, JSON parsing, and cryptographic requirements after adapter conversion. Configured field transforms do not bypass signature verification. Verification rejects private JWK material in the projected public key field. The default key writer omits optional expiration and curve values when absent so declarations can supply defaults. The `create_jwk` and `create_jwk_native` conveniences convert generated material to `CreateJwk` at their callback boundary. The public JWKS route builds discovery data from the public key field and does not serialize the private key field or additional fields.

Algorithm selection and expiration filtering run in separate passes. Each getter runs at the corresponding business read, including repeated reads in short-circuit expressions. Built-in filters produce candidate arrays and retain the selected record handle. Regular verification parses `publicKey` before reading `alg`; session cookie verification reads `alg` first and rejects a falsey algorithm before parsing the public key. Native access errors reach each verifier's error logger with their original identity.

`.define_payload(...)` and `.get_subject(...)` retain their asynchronous JSON convenience interfaces. Use `.define_payload_native(...)` and `.get_subject_native(...)` to receive the same `NativeSessionData` root as a `FieldValue`. Native callbacks retain accessors, undefined properties, child identities, and mutations made by earlier callbacks. The payload callback runs before the first clock sample; its enumerable fields replace the initial `iat`. The subject callback runs after the spread. Only null and undefined subjects fall back to the current `user.id`; false, zero, and empty strings remain values. Both `/token` and the session response header use this path.

`.remote_url(...)` disables local JWKS discovery. Pair the URL with `.custom_sign(...)` to delegate signing. The callback receives defaulted claims and `JwtSigningOptions`; the callback must set `alg` and `kid`, preserve required protected headers, and honor key overrides. Publish the corresponding public keys at the remote URL. `remote_url` alone does not fetch keys or replace the signing store.

`auth.jwt()?.verify(token, issuer_override)` returns `Some(claims)` for valid tokens and `None` for invalid signatures, rejected claims, unknown keys, and adapter errors. Signing and discovery propagate adapter errors. Verification preserves upstream subject and audience checks, including truthy non-string subjects. Applications must validate application-specific claim shapes. Verification reads adapter keys even when `remote_url` is configured. Applications that need remote verification must use a verifier with the remote JWKS.

Local signing clones native claims after resolving the signing key, before applying JOSE claim setters. Enumerable function values fail with `AuthError::DataClone` without invoking `toJSON`. Native Date claims reach the NumericDate setters before JSON conversion; negative NumericDates remain valid signing input, while truthy subjects and token IDs must be strings. Falsy subject, token ID, issue time, and not-before values remain in the payload. NumericDate duration strings use JOSE syntax. The final encoder rejects non-finite numeric `iat`, `nbf`, and `exp` claims and serializes the payload before the protected header. Signing a token does not establish that verification will accept the token.

The `.custom_sign(...)` callback retains its `serde_json::Map` and `JwtSigningOptions` convenience interface. `.custom_sign_native(...)` receives three `FieldValue` arguments: defaulted claims, the optional protected header, and key selection. An omitted header remains undefined. Key selection owns `signingKeyId` and `signingAlgorithm` even when both values are undefined. Native callbacks return a `FieldValue` without narrowing; the token route retains that value, and the session header performs HTTP string conversion and validation. Both callback interfaces skip local JOSE cloning and key resolution. Direct `JwtPluginConfig` and `JwtTokenOptions` callback fields use the native aliases; existing builders provide the explicit JSON conversion boundary.

To sign session cookie caches with plugin keys, enable `SessionConfig.cookie_cache` with `CookieCacheStrategy::Jwt` and register `JwtPlugin::new().session_cookie_cache(true)`. This requires locally managed keys and rejects custom signing callbacks. Core uses the `SessionCookieSigner<S>` runtime interface without depending on the API crate.

Cache tokens use `typ: better-auth.session-cache+jwt`, audience `better-auth:session-cache`, and the configured base URL as issuer. These values are independent of ordinary token issuer and audience configuration. The cache binds `sub` to the cached user ID and `sid` to the cached session token. Cache reads also require the signed session cookie, matching token, cache version, and unexpired session and cache lifetimes. Ordinary JWTs cannot serve as cache cookies. Authoritative session reads bypass the cache.

Cache signing resolves the local signing key, reads the original session token, and clones the resulting payload before setting claims. The subject setter then reads the original user ID and requires a string. A Date does not become an accepted subject through JSON serialization. A missing or undefined ID fails after key reads or creation. The failure preserves prior key writes unless the active transaction rolls back.

Public JWKS discovery excludes keys beyond the configured grace period. Local verification continues to use persisted keys, including expired signing keys, as upstream does. Keep published keys available for the lifetime of tokens verified remotely. The compatibility profiles cover default EdDSA, RS256, ES256, ES512, 3072-bit PS256, callbacks and key overrides, remote JWKS rotation, and asymmetric cache round trips and negative cases.

`SessionCookieSigner<S>::sign` receives a native `FieldMap` and `SessionCookieContext<S>`, including the request, effective configuration, and active transaction. Custom signers must keep native values until their clone or serialization boundary. `verify` continues to return decoded JSON claims. During transactional signup, signing keys are read or created through the same transaction as the session. A rollback removes new keys with the other database writes; the cookie writer remains inside the transaction.

Custom `SessionCookieSigner::sign` implementations receive `expires_in: f64` seconds so cache lifetimes retain fractional precision. The shared `utils::jwe::encode` lifetime argument also accepts `f64`; integer callers use literals such as `300.0`. Neither change alters verification requirements.
