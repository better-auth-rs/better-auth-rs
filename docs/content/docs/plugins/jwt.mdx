---
title: JWT
description: Sign session tokens with persisted asymmetric keys and expose public JWKS.
---

Register `JwtPlugin::new()`. `GET /jwks` returns public signing keys. Authenticated `GET /token` returns `{ "token": "..." }`.

Database key lists apply `advanced.database.default_find_many_limit` before expiration filtering and newest-key selection. A zero limit or a page containing only expired keys causes signing to create a new key. Custom `get_jwks` callbacks supply their complete keyset without this database limit.

`GET /get-session` signs the endpoint session snapshot and exposes `set-auth-jwt` through CORS. The snapshot is independent of the response body. Better Auth 1.7.6 retains an expired session in endpoint context, so a null expired-session response can still carry a newly signed JWT. A revoked session has no snapshot and emits no JWT. Do not use this header as proof that the session response authenticated the request. `.disable_setting_jwt_header(true)` disables the header.

The default algorithm is Ed25519 (`EdDSA`). Select `Rs256`, `Ps256`, `Es256`, or `Es512` with `.algorithm(...)`. These algorithms use RSA PKCS#1, RSA PSS, P-256, and P-521 respectively. RSA keys default to 2048 bits; `.modulus_length(3072)` changes the primary RSA key size. The store persists keys through `JwksStore`; private JWKs are encrypted with the authentication secret. Public discovery never returns private key parameters.

`JwtPluginConfig.algorithm` uses `Option<JwtAlgorithm>` to retain an omitted configuration. Ordinary key generation still defaults to EdDSA. Cookie verification can use the token's algorithm when both the stored key and configuration omit that value. Remote JWKS configuration requires an explicit algorithm; the `.algorithm(...)` builder retains its ordinary argument.

Session tokens contain the user fields, the user ID in `sub`, the issue time in `iat`, and a fifteen-minute `exp`. The issuer and audience default to the configured base URL. Override these values with `.issuer(...)`, `.audience(...)`, and `.expiration_time(chrono::Duration::minutes(5))`.

Audience configuration preserves a single string or an array: `.audience("service-a".into())` and `.audience(vec!["service-a".into(), "service-b".into()].into())` produce the corresponding `aud` claim. Verification requires at least one matching recipient; an empty configured array accepts no token.

`expiration_time` accepts a relative `chrono::Duration`, an absolute `chrono::DateTime<Utc>`, or an absolute `i64` NumericDate in seconds. Use `JwtExpiration::At(serde_json::Number)` for fractional absolute seconds. Absolute dates discard subsecond precision, matching upstream Date values; relative durations round to the nearest second with ties toward positive infinity. An explicit payload `exp` overrides the configured default.

`.rotation_interval(chrono::Duration::days(30))` enables signing key rotation. `.grace_period(...)` controls how long expired public keys remain discoverable; the default is thirty days. Choose a grace period that covers the lifetime of issued tokens. `.jwks_path("/keys")` changes the discovery route. `.disable_setting_jwt_header(true)` suppresses the session response header.

Trusted server code may call `sign` with an application JSON payload. `sign_with_options` accepts `JwtSigningOptions` with an optional `key_id`, `algorithm`, and protected `header`. A pinned key must exist, remain live, and match the requested algorithm. `.key_pair_configs(vec![JwtKeyPairConfig::new(JwtAlgorithm::Ps256)])` permits lazy provisioning for an additional algorithm. An unpinned request prefers the primary algorithm. `create_key_pair` explicitly provisions a key and returns `AuthResult<Option<Jwk>>`. Concurrent first requests may provision multiple valid keys, as in upstream.

`auth.jwt()?` binds native operations to the registered configuration. Signing and verification run endpoint before/after hooks, validation, and spans. Before context patches can change payload and signing option groups before the handler selects keys and claims. Hook response replacements must retain the typed result shape. Key-pair provisioning remains a direct helper and skips endpoint hooks. `endpoint.jwt()?` also retains the active transaction. `.with_request(NativeRequest { request, headers })` supplies Request and headers independently for dynamic URL resolution and adapter callbacks. Context-only `JwtPlugin` helpers create native calls without borrowing an ambient request. Use `sign_in_endpoint`, `verify_in_endpoint`, or `create_key_pair_in_endpoint` for an explicit endpoint context.

Native endpoint headers use lowercase names in callback context. `Cookie` and `cookie` both authenticate a supplied session. Calling `/token` through `call_endpoint` requires `EndpointInput.headers`: omission returns `400 VALIDATION_ERROR`; an empty collection returns `401 UNAUTHORIZED`.

`sign_with_overrides(payload, JwtCallOverrides { ... })` replaces supplied `jwt`, `jwks`, or `adapter` groups for one call. Omitted groups retain registration defaults. Supplied groups start from their own defaults; fields do not merge with the registered group. An empty adapter restores default persistence for that call. Changes do not mutate the registered plugin. Changing key encryption for one call can leave stored keys incompatible with the registered encryption policy, matching upstream.

`JwtPlugin::callbacks(JwtCallbacks::<AppSchema>::default().get_jwks(...).create_jwk(...))` overrides reads and writes independently. Each asynchronous callback borrows `EndpointContext`, including body, request, headers, session, runtime, and active transaction. `get_jwks` returning `None` represents an absent keyset. Discovery reads the adapter again after creating the first key and fails if that read is empty. The create callback receives the generated `created_at` and returns `Option<Jwk>`. Discovery rereads storage after a null create result. Signing consumes the returned key and propagates the missing `privateKey` error at that boundary. The default JWT adapter assigns the persistence timestamp before calling the store. Direct `JwksStore::create_jwk` calls preserve the supplied `created_at` on Memory and SQL.

Custom plugins may register JWK adapter fields with `AuthInitContext::register_model_fields(EntityRole::Jwk, fields)`. Register replacements after the JWT plugin. A replacement replaces the complete declaration at its existing position, including defaults, transforms, references, and physical mapping. Native fields and extensions use the same input and output policies. A logical `id` declaration sets the field position; the adapter owns its policy as described under [model IDs](/docs/concepts/database#model-ids).

`CreateJwk` retains ordinary Rust inputs. `CreateJwk.additional_fields` accepts declared logical application values, and `Jwk.additional_fields` contains their output projection. Native `Jwk` fields use `SchemaValue<T>` to preserve omitted, null, and cross-type values. Use `JwksStore` record methods for complete `FieldMap` creation, lookup, update, deletion, and listing. Output errors propagate after direct persistence; enclosing transactions retain their rollback boundary. SeaORM reads a SQL snapshot before output conversion, while Memory reads each field when its output phase starts. Generate matching columns with `jwks.additionalFields`; applications own database migrations.

JWT consumers apply their own key-selection, JSON parsing, and cryptographic requirements after adapter conversion. Configured field transforms do not bypass signature verification. Verification rejects private JWK material in the projected public key field. The default key writer omits optional expiration and curve values when absent so declarations can supply defaults. Custom create callbacks retain the typed `CreateJwk` input contract. The public JWKS route builds discovery data from the public key field and does not serialize the private key field or additional fields.

`.define_payload(...)` and `.get_subject(...)` accept asynchronous callbacks. Each callback receives the complete serialized `{ user, session }` object. The payload callback replaces the default user claims. The subject callback overrides `user.id`. The plugin applies default `iat` before subject selection and preserves a supplied `iat`. Both `/token` and the session response header use these callbacks.

`.remote_url(...)` disables local JWKS discovery. Pair the URL with `.custom_sign(...)` to delegate signing. The callback receives defaulted claims and `JwtSigningOptions`; the callback must set `alg` and `kid`, preserve required protected headers, and honor key overrides. Publish the corresponding public keys at the remote URL. `remote_url` alone does not fetch keys or replace the signing store.

`auth.jwt()?.verify(token, issuer_override)` returns `Some(claims)` for valid tokens and `None` for invalid signatures, rejected claims, unknown keys, and adapter errors. Signing and discovery propagate adapter errors. Verification preserves upstream subject and audience checks, including truthy non-string subjects. Applications must validate application-specific claim shapes. Verification reads adapter keys even when `remote_url` is configured. Applications that need remote verification must use a verifier with the remote JWKS.

Local signing follows the JOSE claim setters: negative NumericDates remain valid signing input, while truthy subjects and token IDs must be strings. Falsy subject, token ID, issue time, and not-before values remain in the payload. NumericDate duration strings use JOSE syntax. Signing a token does not establish that verification will accept the token.

To sign session cookie caches with plugin keys, enable `SessionConfig.cookie_cache` with `CookieCacheStrategy::Jwt` and register `JwtPlugin::new().session_cookie_cache(true)`. This requires locally managed keys and rejects custom signing callbacks. Core uses the `SessionCookieSigner<S>` runtime interface without depending on the API crate.

Cache tokens use `typ: better-auth.session-cache+jwt`, audience `better-auth:session-cache`, and the configured base URL as issuer. These values are independent of ordinary token issuer and audience configuration. The cache binds `sub` to the cached user ID and `sid` to the cached session token. Cache reads also require the signed session cookie, matching token, cache version, and unexpired session and cache lifetimes. Ordinary JWTs cannot serve as cache cookies. Authoritative session reads bypass the cache.

Cache signing resolves the local signing key before validating the required string user ID. A missing or undefined ID fails after key reads or creation. The failure preserves prior key writes unless the active transaction rolls back.

Public JWKS discovery excludes keys beyond the configured grace period. Local verification continues to use persisted keys, including expired signing keys, as upstream does. Keep published keys available for the lifetime of tokens verified remotely. The compatibility profiles cover default EdDSA, RS256, ES256, ES512, 3072-bit PS256, callbacks and key overrides, remote JWKS rotation, and asymmetric cache round trips and negative cases.

The signer receives `SessionCookieContext<S>` for signing and verification, including the request, effective configuration, and active transaction. During transactional signup, signing keys are read or created through the same transaction as the session. A rollback removes new keys with the other database writes; the cookie writer remains inside the transaction.

Custom `SessionCookieSigner::sign` implementations receive `expires_in: f64` seconds so cache lifetimes retain fractional precision. The shared `utils::jwe::encode` lifetime argument also accepts `f64`; integer callers use literals such as `300.0`. Neither change alters verification requirements.
