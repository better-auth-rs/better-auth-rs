title: Passkey
description: WebAuthn / FIDO2 passwordless authentication with passkeys.

The `PasskeyPlugin` enables passwordless authentication using the WebAuthn standard. Users can register passkeys (biometric, security keys, etc.) and use them to sign in without a password.

Passkey lists, registration exclusions and authentication allow-lists use the database query order and `advanced.database.default_find_many_limit`. The plugin does not add a creation-time sort.

## Setup

This example assumes you've already defined `AppAuthSchema`. If you want a complete setup from entity definitions through Axum mounting, start with the [Axum integration guide](/docs/integrations/axum).

For a new application-owned schema, generate and bind the Passkey model:

```sh
better-auth-rs generate --plugins passkey --output src/auth_schema.rs
```

```rust,ignore
let store = store.with_plugin_schema::<auth_schema::AppPluginSchema>();
```

```rust
use better_auth::plugins::PasskeyPlugin;

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(
        PasskeyPlugin::new()
            .rp_id("example.com")
            .rp_name("My Application")
            .origin("https://example.com")
    )
    .build()
    .await?;
```

### Storage modes

Fresh generated models use `PasskeyStorage::Native`: the 11 upstream columns contain the credential state, and createdAt is nullable. The private adapter reconstructs the WebauthnCore credential from the standard COSE public key, credential ID, counter, and transport hints. Registration verifies the full response before storage. Authentication verifies the challenge, origin, RP ID, signature, and counter before session creation. Authentication validates backup flags from the signed assertion independently of stored display fields.

Options generation reads credential IDs and transports without decoding stored public keys. Descriptor IDs must be strings. The plugin removes `=` characters and rejects characters outside the base64url alphabet, matching upstream option generation. Empty IDs and incomplete base64 groups retain the upstream options behavior. This acceptance does not establish that a credential can authenticate.

Transport strings split on commas and preserve empty components and UTF-16 code units. HTTP options omit the transports property for null or omitted stored values. Other transport types reject options generation.

Add `--passkey-legacy-schema` when regenerating an existing Legacy schema. Bundled models and models without `#[auth(role = "passkey", native_passkey)]` retain `PasskeyStorage::Legacy`, including the opaque credential and updatedAt columns. Legacy store methods preserve arbitrary opaque strings exactly. Authentication requires the existing valid credential envelope; an envelope decoding error never selects Native mode.

The store reports its mode through `passkey_storage()`. Custom stores and transactions default to Legacy and must explicitly report Native when using standard storage. Direct store callers use these types from `better_auth::prelude`:

| Operation | Native input | Legacy input |
| --- | --- | --- |
| `CreatePasskey.credential` | `PasskeyCredentialState::Native` | `PasskeyCredentialState::Legacy(value)`; `String::into()` and `&str::into()` also select Legacy |
| `update_passkey_authentication` | `UpdatePasskeyAuthentication::Native { counter }` | `UpdatePasskeyAuthentication::Legacy { credential, counter, backed_up, device_type }` |

The selected input mode must match the store mode. A mismatch returns a configuration error. Native authentication updates only the counter; Legacy retains its envelope and metadata update contract. The plugin selects the mode automatically.

Every native field in `Passkey` and `PasskeyView` uses `SchemaValue<T>`. The default schema represents its optional dates and Legacy extension columns as follows:

| `Passkey` field | Type | Native representation |
| --- | --- | --- |
| `credential` | `SchemaValue<String>` | `Undefined` |
| `updated_at` | `SchemaValue<FieldDate>` | `Undefined` |
| `created_at` | `SchemaValue<Option<FieldDate>>` | `Typed(Some(date))` or `Typed(None)` for a stored null |

The corresponding `AuthPasskey` getters borrow these values. Replacement declarations and output transforms can retain another type as `Dynamic(FieldValue)`. Use `.field_value()` to inspect the runtime value or `.typed()?` when a caller requires the default Rust type. `PasskeyView.created_at` retains omission or null and serializes dates as UTC millisecond strings. The HTTP view does not expose credential or updatedAt.

Applications own migration from Legacy to Native. Regeneration does not alter existing tables or convert opaque envelopes. Review column removal, nullable createdAt, server INTEGER counters, and nonunique credentialID indexes before binding the new model. Fresh MySQL has no automatic userId physical foreign key or database cascade; Rust reference conversion and owner/session checks remain unchanged. Explicit mappings retain precedence. See [database schema mapping](/docs/concepts/database#map-plugin-tables-and-columns) for backend types and migration boundaries.

### Configuration

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `rp_id` | `String` | `base_url` host | Relying Party ID (your domain) |
| `rp_name` | `String` | `AuthConfig.app_name` | Relying Party display name |
| `origin` | `PasskeyOrigins` | request `Origin` header | Expected origin, or an array of allowed origins |
| `authenticator_selection` | `AuthenticatorSelection` | resident key and user verification `Preferred` | Browser registration preferences |
| `web_authn_challenge_cookie` | `String` | `"better-auth-passkey"` | Challenge cookie suffix; the configured cookie prefix still applies |
| `registration` | `PasskeyRegistrationOptions` | requires a fresh session | Identity resolver, verification hook and registration extensions |
| `authentication` | `PasskeyAuthenticationOptions` | no hook or extensions | Verification hook and authentication extensions |
| `challenge_ttl_secs` | `i64` | `300` (5 min) | Challenge expiration in seconds |

The `origin` builder accepts a string or `Vec<String>`. Each response must match one allowed origin and the configured RP ID. Generation uses the application's base URL when no RP ID is configured.

`authenticator_selection` controls browser preferences. The `authenticatorAttachment` query parameter overrides the configured attachment. Registration and authentication require user presence, but do not require UV, including when the browser preference is `Required`. Challenge, origin, RP ID, signature and counter checks still apply. Each verification attempt consumes its challenge before cryptographic verification and application hooks.

### Registration and authentication callbacks

The callback types are exported from `better_auth::plugins::passkey`:

- `PasskeyUserResolver::resolve` receives the request and optional `context` query value. It returns `PasskeyRegistrationUser` with an ID, account name and optional display name.
- `PasskeyRegistrationHook::after_verification` receives the verified registration, resolved user, client response and saved context. It can override the target user ID and the passkey name. A nonempty client name takes precedence over the hook name. Both names are trimmed.
- `PasskeyAuthenticationHook::after_verification` receives the verified assertion before the adapter updates its counter or creates a session. A rejected hook leaves the stored counter unchanged.
- `PasskeyExtensionsResolver::extensions` supplies asynchronous extension input. `PasskeyExtensions::Static` accepts a JSON object directly. Registration always includes `credProps: true`; authentication includes extensions only when configured.

Each callback receives a `PasskeyEndpoint` with the request, parsed body, global configuration, application extensions, plugin metadata and a typed user adapter. The user adapter supports lookup by ID or email, creation, update and deletion. These methods use the active transaction during registration. The callback interface does not expose the upstream arbitrary-model adapter.

Application API errors retain their status and body. Ordinary errors in registration verification become `FAILED_TO_VERIFY_REGISTRATION`; ordinary authentication-hook errors become `AUTHENTICATION_FAILED`.

### Passkey-first registration

Set `registration.require_session` to `false` and supply `resolve_user` to start registration without a session. An existing session takes precedence over the resolver. The application must establish which account the registration flow may use; the optional client `context` string is not proof of account ownership.

Send `createSession: true` to `/passkey/verify-registration` to create a session after registration. The registration hook may create the user through `ctx.users` and return that user's ID. The hook, user lookup, passkey insertion and session creation run in one adapter transaction. A failure rolls back database writes, while the consumed challenge remains consumed. The response includes the passkey fields, `session` and `user`, and sets the session cookie. Without `createSession`, callback writes retain the upstream nontransactional behavior.

With the default `require_session: true`, both registration endpoints require a fresh session. The default freshness window is 24 hours. Set `AuthConfig.session.fresh_age` to zero to disable the freshness check.

### Adapter field policies

Register native replacement declarations and application fields through `AuthInitContext::register_model_fields(EntityRole::Passkey, UserConfig)`. Register the plugin that supplies overrides after `PasskeyPlugin`. The shared `ModelFields` merge replaces each complete declaration and preserves upstream field order. Defaults, references, input and output transforms, and column mappings apply to every declared field through the same record and patch conversion. The adapter retains control of `id`.

Use ordinary `CreatePasskey` and `UpdatePasskey` inputs for typed callers. Native runtime fields use `SchemaValue<T>` and retain missing, null, and cross-type values until a consumer requires a specific representation. Public views preserve those values until serialization. The `create_passkey_record`, `get_passkey_record`, and `update_passkey_record` methods accept or return logical `FieldMap` records through the same policies. These methods do not add undeclared Legacy credential fields.

Creation, both lookups, lists, name updates, and authentication updates use the shared field policies. Memory reads each physical field when its output phase starts, so later fields observe writes performed by earlier callbacks. SQL reads supported driver values into a query snapshot before output transforms and runtime record construction. Input errors prevent persistence. Output errors propagate after the completed write. Authentication retains the selected Native or Legacy credential representation and existing ownership checks.

Generate matching columns with `passkey.additionalFields` and `passkey.fields`, then register the corresponding runtime policies. Replacements retain their schema positions. Shared physical columns keep the first position and the last declaration's attributes. Legacy-only credential and update timestamp columns remain internal unless explicitly declared. Applications own migrations for changed columns. Adapter policies do not replace HTTP validators or WebAuthn protocol validation.

## How It Works

### Registration Flow

1. Client calls `GET /passkey/generate-register-options` to get WebAuthn creation options
2. Client uses the browser's `navigator.credentials.create()` API with the options
3. Client sends the credential response to `POST /passkey/verify-registration`
4. Server validates the WebAuthn registration response and stores the passkey

### Authentication Flow

1. Client calls `GET /passkey/generate-authenticate-options` to get assertion options
2. Client uses the browser's `navigator.credentials.get()` API with the options
3. Client sends the assertion response to `POST /passkey/verify-authentication`
4. Server validates the assertion, looks up the passkey, and creates a session

## API Endpoints

The Passkey plugin exposes 7 endpoints. For full request/response details, see the [OpenAPI Reference](/docs/reference/openapi/passkey).

| Endpoint | Method | Description |
|----------|--------|-------------|
| `/passkey/generate-register-options` | GET | Get WebAuthn creation options |
| `/passkey/verify-registration` | POST | Verify and store a new passkey |
| `/passkey/generate-authenticate-options` | GET | Get WebAuthn assertion options |
| `/passkey/verify-authentication` | POST | Verify passkey and create session |
| `/passkey/list-user-passkeys` | GET | List all passkeys for the user |
| `/passkey/delete-passkey` | POST | Delete a passkey |
| `/passkey/update-passkey` | POST | Update passkey name |

## Client-Side Integration

### Registration Example

```javascript
// 1. Get registration options from the server
const optionsRes = await fetch('/auth/passkey/generate-register-options', {
  headers: { 'Authorization': `Bearer ${sessionToken}` }
});
const options = await optionsRes.json();

// 2. Create credential using the browser API
const credential = await navigator.credentials.create({ publicKey: options });

// 3. Send the response back to the server
const verifyRes = await fetch('/auth/passkey/verify-registration', {
  method: 'POST',
  headers: {
    'Authorization': `Bearer ${sessionToken}`,
    'Content-Type': 'application/json'
  },
  body: JSON.stringify({
    response: credential,
    name: 'My Device'
  })
});
```

### Authentication Example

```javascript
// 1. Get authentication options
const optionsRes = await fetch('/auth/passkey/generate-authenticate-options', {
  method: 'GET'
});
const options = await optionsRes.json();

// 2. Get assertion using the browser API
const assertion = await navigator.credentials.get({ publicKey: options });

// 3. Verify with the server
const verifyRes = await fetch('/auth/passkey/verify-authentication', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ response: assertion })
});
const { session } = await verifyRes.json();
```

## Errors

| Status | Condition |
|--------|-----------|
| 400 | Invalid or missing WebAuthn response data |
| 400 | Invalid or expired challenge |
| 401 | Not authenticated (for registration/list/delete) |
| 401 | Credential not found during authentication, or registration targets another session user |
| 403 | Session is not fresh |
| 404 | Credential not found during management |
| 500 | Registration verification or an ordinary registration callback failed |

POST body schemas run before session middleware. Registration and update names use ECMAScript whitespace trimming. Endpoint hooks retain the original name and Request bytes; verification and persistence use the validated value. Unknown body keys are removed from handler input.
