---
title: Sign-In with Ethereum
description: Verify signed Ethereum messages and persist wallet ownership across chains.
---

Generate the schema with `--plugins siwe` and migrate the generated `walletAddress` table before enabling the plugin. Explicit model and field mappings can retain existing physical names. Register the server domain, a nonce generator, and a signature verifier.

```rust
use better_auth::plugins::SiwePlugin;

let plugin = SiwePlugin::new(
    "wallet.example.com",
    || async { Ok(generate_nonce()) },
    |proof| async move {
        verifier.verify(&proof.message, &proof.signature, &proof.address, proof.chain_id).await
    },
);
```

The required verifier must authenticate the signature. Use a maintained Ethereum library or a wallet verification service. The callback receives the original message and signature, the EIP-55 address, the chain ID, and the upstream CACAO context. The plugin does not assume that all wallets use externally owned accounts; the callback may also verify contract signatures.

`POST /siwe/nonce` and `/siwe/get-nonce` issue a persisted nonce. The generator must return 8–250 alphanumeric characters. `POST /siwe/verify` consumes that nonce before checking the domain, address, positive chain ID, validity window, and signature. A rejected proof cannot reuse the consumed nonce.

Sequential sign-ins reuse a wallet's existing user across chains. Each new chain creates a wallet record and a SIWE account. `ens_lookup` may supply the user's name and avatar. `email_domain_name` changes the generated email domain.

`WalletAddress.user_id` uses `SchemaValue<String>` to preserve the adapter's native owner value. Use `user_id.typed()?` for a projected string. Memory Serial mode stores a numeric owner reference and returns its canonical string; for example, input `"001"` stores `1` and returns `"1"`. `CreateWalletAddress.user_id` still accepts a `String`.

Custom plugins can register Wallet adapter fields with `AuthInitContext::register_model_fields(EntityRole::WalletAddress, fields)`. Direct store callers supply declared logical values in `CreateWalletAddress.additional_fields` and read the projected values from `WalletAddress.additional_fields`. Defaults and input transforms run before insertion. Output transforms run after insertion or lookup; an output error leaves the completed direct insert in storage. Generate application columns with `walletAddress.additionalFields` and `--plugins siwe`, then apply an application-owned migration. Native wallet fields and their mapped columns remain reserved.

The SIWE flow supplies an empty additional-field map, so registered defaults can supply application values. The flow retains its native user binding and response fields. Secondary forwards Wallet create/get calls. Applications can call the same methods through `AuthTransaction`; a propagated output error rolls back that enclosing transaction. This capability does not change the SIWE flow's transaction boundary. Ordinary Memory/SQLite display-field contracts verify commit and output-error rollback, including Rust Secondary forwarding.

Fresh CLI Wallet schemas use native column names and an INTEGER chainId column. Generated PostgreSQL/MySQL models use `i32` storage and return the existing public `i64` chain ID; bundled and SQLite Rust models retain `i64`. The generated MySQL Wallet table has no physical userId foreign key or database cascade, matching the pinned catalog; Rust reference conversion and owner checks remain in place. Applications own migrations from existing tables. See [schema mapping](/docs/concepts/database#map-plugin-tables-and-columns) for backend types and the separate catalog acceptance boundary.

As in Better Auth 1.7.6, wallet registration has no unique wallet constraint or atomic registration transaction. Concurrent first sign-ins for the same wallet can race. The email reservation below protects email claims; it does not lock wallet registration.

`anonymous(false)` requires an email in verification requests. An existing email account is never linked based only on a wallet signature: the new wallet receives a placeholder email instead. A database reservation prevents simultaneous wallets from claiming the same new email.

If an email reservation cannot be stored, the plugin logs the failure and uses the wallet placeholder email. Reservation cleanup failures are logged without invalidating the completed user creation, matching upstream behavior.

Nonce requests accept an omitted body or an empty object. Both schemas reject unknown fields. Verification validates all fields before authentication and requires an original Request, including for native calls. Native callers must pass that Request explicitly. With `anonymous(false)`, the email-required refinement runs after valid field types, including when another field fails a length constraint.
