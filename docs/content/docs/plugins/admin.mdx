title: Admin
description: User management, banning, impersonation, and role management for administrators.

The `AdminPlugin` provides administrative endpoints for user management. Route access is permission-based and follows the TypeScript Better Auth admin plugin behavior. The built-in `admin` role includes user email updates; impersonating another administrator requires a separate grant or `allow_impersonating_admins`. The built-in `user` role has no administrator permissions.

## Setup

These examples assume you've already defined `AppAuthSchema`. If you want a complete setup from entity definitions through Axum mounting, start with the [Axum integration guide](/docs/integrations/axum).

```rust
use better_auth::plugins::AdminPlugin;

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(AdminPlugin::new())
    .build()
    .await?;
```

### Configuration

```rust
use better_auth::plugins::admin::AdminConfig;

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(
        AdminPlugin::new()
            .default_role("user")
            .admin_roles(vec!["admin".to_string()])
            .admin_user_ids(vec!["bootstrap-admin-id".to_string()])
            .default_ban_reason("No reason".to_string())
            .default_ban_expires_in(86400.0)
            .allow_impersonating_admins(false)
    )
    .build()
    .await?;
```

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `default_role` | `String` | `"user"` | Default role for new users and role-less permission checks |
| `admin_roles` | `Option<Vec<String>>` | `None` uses `["admin"]` | Explicit administrator roles must exist in the configured role map; an empty list identifies no administrator roles |
| `admin_user_ids` | `Option<Vec<String>>` | `None` | User IDs that always bypass admin permission checks |
| `roles` | `Option<HashMap<String, RolePermissions>>` | built-in `admin` / `user` when unset | Custom permission definitions replace the defaults, including an explicitly empty map |
| `default_ban_reason` | `Option<String>` | `None` | Default reason used by `/admin/ban-user` |
| `default_ban_expires_in` | `Option<f64>` | `None` | Default ban duration in seconds, including fractions; zero means no configured expiry |
| `impersonation_session_duration` | `Option<f64>` | `None` | Impersonation lifetime in seconds, including fractions; omission or zero uses one hour |
| `banned_user_message` | `BannedUserMessage` | upstream default text | Fixed text or an asynchronous callback that receives the stored user |
| `allow_impersonating_admins` | `bool` | `false` | Allow administrator targets without a `user:impersonate-admins` grant |

The `.roles(map)` and `.admin_roles(roles)` builders accept the map and list directly. Use `None` in an `AdminConfig` literal to retain omission. Custom administrator role names are checked when the plugin initializes.

A nonzero `banExpiresIn` request value takes precedence over `default_ban_expires_in`. A zero request value uses the configured default. Both expiry configurations preserve millisecond date precision, so a value of `1.5` represents 1500 milliseconds. NaN has the same default behavior as zero.

The ordinary SQLite contracts cover omission, zero, fractional seconds, request precedence, stored dates, and issuance Cookie attributes. They do not establish equivalent error timing for non-finite or out-of-range dates, or behavior at ban and session expiry boundaries.

```rust
use better_auth::plugins::admin::{AdminPlugin, BannedUserMessage};

let plugin = AdminPlugin::new().banned_user_message(BannedUserMessage::callback(|user| {
    Box::pin(async move {
        Ok(format!("Account unavailable: {}", user.email.as_deref().unwrap_or_default()))
    })
}));
```

The callback receives stored application fields, including fields with `returned: false`. Expired bans are cleared before session creation without calling the callback. The login response retains its original user snapshot; subsequent user reads show the cleared ban. A callback error prevents session creation; typed API errors preserve their public status and body, while ordinary errors produce an empty HTTP 500 response and remain errors in native calls.

## API Endpoints

The Admin plugin exposes 15 endpoints. For full request/response details, see the [OpenAPI Reference](/docs/reference/openapi/admin).

### User Management

| Endpoint | Method | Description |
|----------|--------|-------------|
| `/admin/get-user` | GET | Fetch one user by id |
| `/admin/create-user` | POST | Create a new user |
| `/admin/update-user` | POST | Update a user |
| `/admin/list-users` | GET | List users with pagination, search, and filtering |
| `/admin/set-role` | POST | Set a user's role |
| `/admin/set-user-password` | POST | Reset a user's password |
| `/admin/remove-user` | POST | Permanently delete a user |

`/admin/create-user` creates a credential account only when a non-empty password is provided. Omitting the password creates a passwordless user, matching the upstream TypeScript behavior.

Creating a user with an explicit role also requires `user:set-role`. Supplying `banned`, `banReason`, or `banExpires` during creation or update requires `user:ban`. Updating `email` or `emailVerified` requires `user:set-email`. These checks apply when a field is present, including explicit null or false values. `/admin/update-user` rejects a `password` field; use `/admin/set-user-password` instead.

When a before-update database hook cancels `/admin/update-user`, the endpoint preserves the stored user and skips after-update hooks. The response is HTTP 200 with JSON `null`; a native endpoint call also returns a null body. A callback error remains an error. Successful updates retain the user response and configured output policies.

Trusted server code can provision a user without a session:

```rust
use better_auth::plugins::admin::CreateAdminUser;

let result = auth.admin()?.create_user(&CreateAdminUser {
    email: "new-user@example.com".into(),
    name: "New user".into(),
    password: None,
    role: None,
    data: None,
}, None).await?;
```

Passing `None` for headers selects requestless server provisioning. Passing any headers, including an empty map, requires an authenticated session and the corresponding permissions. Creation uses the registered admission policy and database hooks and does not create a session.

With a dynamic base URL, supplied host headers resolve the runtime before authentication. Requestless provisioning requires a configured fallback; resolution failure prevents user creation.

### Ban Management

| Endpoint | Method | Description |
|----------|--------|-------------|
| `/admin/ban-user` | POST | Ban a user (optional reason and duration) |
| `/admin/unban-user` | POST | Unban a user |

An explicit `banReason: null` or `banExpires: null` clears that field. Updating only `banned: false` preserves the reason and expiration; `/admin/unban-user` clears both. Store callers express these updates through `UpdateUser` using `None` to preserve a field and `Some(None)` to clear it.

An update with `banned: true` revokes the user's sessions after the update operation returns, including a cancelled `/admin/update-user` operation. An after-hook error leaves the completed user update in place and prevents session revocation. Self-banning is rejected. The dedicated role, ban, and unban endpoints still use strict store operations; their cancellation response alignment remains separate work.

### Impersonation

| Endpoint | Method | Description |
|----------|--------|-------------|
| `/admin/impersonate-user` | POST | Create a session as another user |
| `/admin/stop-impersonating` | POST | End impersonation, return to admin session |

### Session Management

| Endpoint | Method | Description |
|----------|--------|-------------|
| `/admin/list-user-sessions` | POST | List all sessions for a user |
| `/admin/revoke-user-session` | POST | Revoke a single session |
| `/admin/revoke-user-sessions` | POST | Revoke all sessions for a user |

### Permissions

| Endpoint | Method | Description |
|----------|--------|-------------|
| `/admin/has-permission` | POST | Check if current user has a permission |

## Errors

| Status | Condition |
|--------|-----------|
| 401 | Not authenticated |
| 403 | Current user lacks the required admin permission |
| 404 | Target user not found |
| 400 | Validation or admin-plugin bad request error |

User listing transforms only the selected page. A successful list read then performs a separate count with the same filters and without pagination or output transforms. Instrumentation emits separate `findMany` and `count` spans for these logical adapter operations. If a page output transform fails, the Admin endpoint returns its existing empty-result error shape and does not run the count.

## Endpoint input

Admin body schemas run before authentication and permissions. Before and after endpoint hooks retain the original body; handlers and database hooks receive the validated projection. Unknown top-level keys are removed. The `data` object keeps its entries.

Admin user IDs accept JavaScript string coercion, including numbers and arrays. A missing required ID remains a validation error. Only `set-user-password` rejects an empty ID; that route also rejects an empty password. The route creates a credential account when the target has none. Ban durations accept fractional seconds. A zero duration selects the configured default, and an empty reason selects the configured reason.

`has-permission` requires exactly one of `permission` and `permissions` at the schema boundary. The handler accepts only `permissions`, matching Better Auth 1.7.6. A requestless native call can check an explicit role or user ID. Supplied headers or a Request require an authenticated session, whose identity takes precedence over the body.
