title: Two-Factor Authentication
description: TOTP, OTP, and backup codes for two-factor authentication.

The `TwoFactorPlugin` adds two-factor authentication (2FA) to your application. It supports TOTP (authenticator apps), OTP (email-based one-time passwords), and backup codes for recovery.

## Setup

These examples assume you've already defined `AppAuthSchema`. If you want a complete setup from entity definitions through Axum mounting, start with the [Axum integration guide](/docs/integrations/axum).

```rust
use better_auth::plugins::TwoFactorPlugin;

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(TwoFactorPlugin::new())
    .build()
    .await?;
```

### Configuration

```rust
use better_auth::plugins::two_factor::TwoFactorConfig;
use std::sync::Arc;

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(
        TwoFactorPlugin::with_config(TwoFactorConfig {
            issuer: Some("My App".to_string()),
            skip_verification_on_enable: false,
            two_factor_cookie_max_age: 600.0,
            trust_device_max_age: 30.0 * 24.0 * 60.0 * 60.0,
            totp_period: 30.0,
            totp_digits: 6,
            send_otp: None,
            account_lockout: Default::default(),
            ..Default::default()
        })
    )
    .build()
    .await?;
```

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `issuer` | `Option<String>` | `None` | Issuer name shown in authenticator apps. Falls back to `app_name`. |
| `skip_verification_on_enable` | `bool` | `false` | Marks the user as 2FA-enabled immediately during enrollment. |
| `two_factor_cookie_max_age` | `f64` | `600.0` | Lifetime of the pending 2FA cookie in seconds, including fractions. |
| `trust_device_max_age` | `f64` | `2592000.0` | Lifetime of the trusted-device cookie in seconds, including fractions. |
| `totp_period` | `f64` | `30.0` | TOTP time step in seconds; generation, verification, and URI lookup use 30 seconds for zero or NaN |
| `totp_digits` | `usize` | `6` | Number of digits in TOTP code |
| `send_otp` | `Option<Arc<dyn SendTwoFactorOtp>>` | `None` | Callback used by `/two-factor/send-otp`. |
| `account_lockout` | `AccountLockout` | Enabled, 10 failures, 900 seconds | Shared failure budget across sign-in factors and challenges. |
| `allow_passwordless` | `bool` | `false` | Make management passwords optional for accounts without a credential password. Credential accounts still require their password. |
| `totp_disabled` | `bool` | `false` | Disable TOTP enrollment, verification, URI lookup, and server-only generation. OTP and backup-code flows remain available. |
| `totp_allow_passwordless` | `Option<bool>` | `None` | Override the global policy for TOTP URI lookup. |
| `otp_digits` | `usize` | `6` | Delivered OTP length. |
| `otp_period` | `chrono::Duration` | Three minutes | Delivered OTP lifetime. Zero selects the upstream default. |
| `otp_allowed_attempts` | `usize` | `5` | Failed attempts before the next verification consumes the exhausted OTP. Zero selects five. |
| `otp_storage` | `TwoFactorOtpStorage` | `Plain` | Plaintext, SHA-256 hash, shared symmetric encryption, custom async hashing, or custom async encryption. |
| `backup_code_options` | `BackupCodeOptions` | Ten codes, ten characters, encrypted | Configure amount, length, custom generation, storage, and passwordless regeneration. |

`BackupCodeOptions::storage` accepts `Plain`, `Encrypted`, or `Custom(Arc<dyn TwoFactorCipher>)`. The custom cipher receives the serialized JSON array. Generated codes contain a separator after the first five characters; `length` counts random characters, and zero `amount` produces no codes. A custom generator returns the complete list. Redeeming a duplicated custom code removes every matching entry.

`TwoFactorOtpStorage::Hashed` stores the unpadded base64url SHA-256 digest. `CustomHash` accepts an asynchronous callback; `CustomEncryption` and custom backup storage call `TwoFactorCipher::encrypt_native` and `decrypt_native`. Their defaults bridge the existing string methods; override the native methods when a field policy or callback returns another runtime type. The default encrypted TOTP secret and backup codes use the shared upstream-compatible symmetric format. Codec failures propagate, and OTP verification consumes the proof before decoding.

The server-only `TwoFactorPlugin::generate_totp(secret)` returns a code using the configured digits and period. No public `/totp/generate` route is registered. The enrollment `issuer` applies to enrollment URIs; the later URI lookup uses `app_name`, matching upstream's separate TOTP option scope.

Use `TwoFactorPlugin::callbacks(TwoFactorCallbacks::<AppAuthSchema>::default().send(...))` for delivery callbacks that need the endpoint context. The callback receives the user, OTP, and `EndpointContext`, including validated input, original request, typed store, and any session already resolved by the endpoint. A pending sign-in challenge has no completed session. This callback takes precedence over `custom_send_otp` and can be configured without a legacy sender.

The sender factory returns `AuthResult<Option<BackgroundFuture>>` after OTP persistence. Factory errors propagate immediately. `Ok(None)` schedules no work. `Ok(Some(task))` uses the configured background handler or awaits delivery. Retain callback data and `endpoint.to_owned()` when the task needs them. Asynchronous delivery failures produce one `Failed to send two-factor OTP` error log and retain the successful response. A background handler failure is logged separately as `Failed to run background task:` and does not cancel delivery.

## Storage

Generate a fresh upstream schema with `better-auth-rs generate --plugins two-factor` and bind the generated `AppPluginSchema`. Native storage has seven columns and no creation or update timestamps. `--two-factor-legacy-schema` preserves the earlier generated schema, including timestamps, userId uniqueness, and non-null verification fields. Bundled and unmarked application models use `TwoFactorStorage::Legacy`; marked models use `TwoFactorStorage::Native`. Existing tables require an application-owned migration before changing storage mode.

All native TwoFactor fields retain omitted, null, and dynamic values through `SchemaValue<T>`. `verified` uses `SchemaValue<Option<bool>>`, `failed_verification_count` uses `SchemaValue<Option<f64>>`, and `locked_until` uses `SchemaValue<Option<FieldDate>>`. Native models omit timestamps unless declared; Legacy models retain their timestamp envelope. `AuthTwoFactor` getters expose these values. Ordinary creation and update inputs retain their string and Boolean fields. Use `.typed()?` for typed application reads, or `.field_value()` when implementing native consumption.

Memory TwoFactor records use the Native shape and omit undeclared timestamps. `TwoFactor`, `CreateTwoFactor`, and `UpdateTwoFactor` expose an `additional_fields` map for declared application fields. Add `additional_fields: Default::default()` to existing creation literals. Register field policies with `AuthInitContext::register_model_fields(EntityRole::TwoFactor, fields)` from an application plugin; use CLI `twoFactor.additionalFields` for matching SQL columns. Runtime registration and schema generation have separate responsibilities. `TwoFactorConfig` does not define an additional-field option.

Declared fields use the shared defaults, update callbacks, storage mappings, and input/output transforms. Successful atomic updates execute output transforms even when the public operation returns only `bool` or `()`. Input failures prevent their write; output failures propagate after persistence. A pure failure-counter increment does not run update callbacks. The threshold increment and lock assignment are separate writes: a failed lock input callback retains the incremented count without setting the lock. Native and additional fields share these policies. Register complete replacements after the TwoFactor plugin; omitted attributes do not survive replacement. A replacement must explicitly retain any required reference conversion. Additional fields do not change the HTTP response shapes.

`UserView.two_factor_enabled` is `Option<bool>` and preserves nullable storage through output projection and session caching. `AuthUser::two_factor_enabled()` remains a Boolean truthiness accessor. Native generated User models use `Option<bool>` and create users with `Some(false)`; updates write the supplied Boolean. Legacy generated User models retain `bool`.

Imported SQL records with a null failure counter retain null after `column + 1`, matching the upstream SQL adapter. These records do not accumulate failures toward account lockout until the counter is set to a number. The native declaration supplies zero during ordinary plugin creation, and successful verification resets the counter to zero. Memory treats a null counter as zero before incrementing. Applications must preserve this adapter distinction when importing records.

## How It Works

### Enrollment Flow

1. User calls `/two-factor/enable` with their password
2. An encrypted TOTP secret is generated and stored
3. Backup codes are generated and stored as encrypted JSON
4. User scans the TOTP URI in their authenticator app
5. `twoFactorEnabled` remains `false` until verification unless `skip_verification_on_enable` is enabled

The enrollment response contains `method: "totp"`, `totpURI`, and `backupCodes`.

Pass `method: "otp"` with the password to enable email/SMS codes when `send_otp` is configured. This method enables 2FA immediately, rotates the session, and returns only `{ "method": "otp" }`. It does not create an authenticator secret or backup codes.

A pending TOTP enrollment can be restarted. Once verified, another enable request returns `TOTP_ALREADY_ENABLED` and preserves the existing secret and backup codes. Disable 2FA before replacing a verified authenticator.

The two cookie lifetime fields preserve an explicit `0.0`. Stored verification dates use millisecond precision; HTTP `Max-Age` uses whole seconds. Cookie attribute overrides follow the shared [cookie configuration](/docs/concepts/cookies) rules and do not change the stored verification lifetime. Integer assignments from earlier alpha APIs must use floating-point literals, such as `600.0`.

`totp_period` accepts fractional seconds, such as `30.5`. Enrollment URIs preserve the configured period, including zero and `NaN`. Code generation, verification, and later URI lookup use 30 seconds for zero or `NaN`, matching Better Auth 1.7.6. Generation and verification use JavaScript Number division and floor. Verification adds each one-step window offset before converting the counter modulo `2^64`. This preserves zero, negative, and large finite counters, including counters from infinite periods. A non-finite counter returns a configuration error. The URI includes the effective digits and period, never the library's internal counter step. Update previous integer assignments to floating-point literals. Fractional periods require an authenticator that supports the same configured period; this API does not establish compatibility with every authenticator.

### Sign-In Flow with 2FA

1. User signs in with email/password as normal
2. Credential sign-in creates a session and runs the user after hook. The Two Factor plugin then checks the issued session. For an untrusted device with 2FA enabled, the plugin clears credential cookies, deletes that session, clears the issued-session snapshot, and creates pending verification records. The response is `{ "twoFactorRedirect": true, "twoFactorMethods": [...] }`, where `twoFactorMethods` lists the factors this user can complete: `"totp"` once a secret is enrolled, `"otp"` when `send_otp` is configured
3. User must verify with one of:
   - **TOTP**: Code from authenticator app
   - **OTP**: Code sent via email
   - **Backup code**: One-time recovery code
4. After successful verification, a session is created

A valid trusted-device proof retains the issued session and rotates the proof. Response replacement by a user after hook does not change the issued-session snapshot. An ordinary after-hook error or a session-deletion error stops challenge creation. Later plugin after hooks observe the final challenge response and no issued session.

When sign-in sets `rememberMe: false`, the completed two-factor session expires after 24 hours and uses a session cookie. Remembered sessions use the configured session lifetime.

## API Endpoints

The 2FA plugin exposes the following endpoints. For full request/response details, see the [OpenAPI Reference](/docs/reference/openapi/two-factor).

| Endpoint | Method | Description |
|----------|--------|-------------|
| `/two-factor/enable` | POST | Enable 2FA (returns TOTP URI and backup codes) |
| `/two-factor/disable` | POST | Disable 2FA (requires password) |
| `/two-factor/get-totp-uri` | POST | Retrieve TOTP URI for enrolled user |
| `/two-factor/verify-totp` | POST | Verify TOTP code during sign-in |
| `/two-factor/send-otp` | POST | Send OTP via email |
| `/two-factor/verify-otp` | POST | Verify email OTP |
| `/two-factor/generate-backup-codes` | POST | Generate new backup codes |
| `/two-factor/verify-backup-code` | POST | Verify a backup code during sign-in |

<Callout type="warn">
Backup codes are shown only once during enrollment or regeneration on the public HTTP surface. Store them securely.
</Callout>

<Callout>
For TS compatibility, Rust keeps backup-code retrieval as a server-only capability. Use `TwoFactorPlugin::view_backup_codes(...)` from trusted server code when you need to read the currently stored codes. There is no public HTTP route for this.
</Callout>

## Security Details

- **TOTP secrets** are encrypted before being stored in the database
- **Backup codes** are stored as encrypted JSON — the plaintext is only returned once during generation
- **OTP codes** are stored as verification records and expire after 3 minutes
- **OTP comparison** uses the original code bytes. Password NFKC normalization does not apply to OTP codes.
- **Password verification** is required to enable/disable 2FA and to regenerate backup codes
- **Used backup codes** are removed with a conditional database update, so concurrent requests cannot reuse a code
- **OTP codes and sign-in challenges** are consumed atomically; an expired latest code also invalidates older codes for the same identifier
- **TOTP and backup-code challenges** allow five failed attempts before the challenge is invalidated
- **Account lockout** blocks sign-in factor verification for 15 minutes after 10 consecutive failures across challenges; successful verification clears the counter. As in Better Auth 1.7.6, the account must have an authenticator record. OTP-only enrollment uses the per-code attempt limit.

`AccountLockout.duration_seconds` accepts `f64` seconds, including fractions, and defaults to `900.0`. Explicit zero is preserved. The deadline clock is read after the first counter increment completes and reaches the threshold, as in Better Auth 1.7.6. Date conversion truncates to JavaScript millisecond precision and returns a configuration error for non-finite or unrepresentable dates. Such an error retains the recorded failure and prevents the lock update. `max_failed_attempts` remains an integer; arbitrary numeric behavior is outside this typed contract.

`TwoFactorStore::record_two_factor_failure` accepts a borrowed, fallible deadline closure. Store implementations must invoke the closure once after the successful increment reaches the threshold, then perform the existing guarded lock update. Store implementations must propagate the original callback error. Replace a fixed deadline argument with `&|| Ok(deadline)` when migrating a direct store caller.

## Request validation and native helpers

Two Factor validates each body before session middleware. Endpoint before/after hooks retain raw input. Handler callbacks receive only schema fields, including `method: "totp"` when enrollment omits `method`. `send-otp` permits an omitted body; explicit `null` is invalid. Global `allow_passwordless`, `totp_allow_passwordless`, and `backup_code_options.allow_passwordless` determine their own password schemas when routes are built.

`auth.two_factor()` binds server-only operations to the registered plugin configuration. `generate_totp(Some(json!({"secret": secret})))` validates the supplied secret and returns a code. `view_backup_codes(Some(json!({"userId": user_id})))` applies upstream ID coercion and reads the stored codes. Pass `None` to preserve an omitted native body. `with_request(NativeRequest { request, headers })` supplies the original native request and headers for dynamic runtime resolution. Both facade methods run shared endpoint hooks, validation and instrumentation. Before responses skip execution, and after responses replace the typed result. Neither helper creates an HTTP route. The direct `TwoFactorPlugin` methods remain available. Both backup-code view methods return `FieldValue`; normal storage produces an array. Falsy decoded backup values reject verification, mixed arrays retain unmatched values, and truthy non-arrays fail at their actual array operation. Codec or array-operation errors restore the consumed challenge attempt.

The server-only facade currently validates input and calls the registered operation directly. Shared endpoint before/after hooks and endpoint spans remain tracked in the alignment backlog.
