title: Device Authorization
description: Register a device through an authenticated browser approval flow.
---

Install `DeviceAuthorizationPlugin` and generate the device-authorization schema. A client requests a code at `POST /device/code`, sends its user to the verification URI, and polls `POST /device/token`. An authenticated user must claim the code through `GET /device` before calling `/device/approve` or `/device/deny`.

```rust
use better_auth::plugins::DeviceAuthorizationPlugin;

let plugin = DeviceAuthorizationPlugin::new()
    .validate_client(|client_id| async move { Ok(client_id == "node-agent") })
    .generate_device_code_with(|| async { Ok(issue_device_code().await?) })
    .generate_user_code_with(|| async { Ok(issue_user_code().await?) });
```

Application generators return `AuthResult<String>`. Each attempt awaits the device-code generator, then the user-code generator, before persistence. A callback error stops the request. Codes may contain up to 191 Unicode scalar values; custom user codes retain their exact case and punctuation. The upstream contract permits an explicitly empty generated code.

The default device-code generator uses ASCII letters and digits. Its default length is 40; configured lengths range from 1 to 191. Custom generators retain their existing string contract.

An omitted or empty `verification_uri` selects `/device`. The complete verification URI replaces the first existing `user_code` query parameter and removes later duplicates, or appends the parameter when absent. Other query pairs retain their order, and the fragment remains unchanged.

The plugin retries a unique-constraint collision at most three times. Each retry generates both codes again. Other persistence errors propagate. Request authorization, applicable client validation, and `on_device_auth_request` run before generation and are not repeated on a collision.

The generator methods now accept asynchronous closures. Change a synchronous closure from `|| value` to `|| async { Ok(value) }`. Keep application-owned admission policy in `validate_client`; a valid device token does not establish machine inventory identity.

All four POST routes validate their bodies before authentication and endpoint middleware. `/device/code` returns OAuth `invalid_request` validation errors. The other routes use `VALIDATION_ERROR`. Without a grant, `client_id` is required. Empty base fields are omitted before callbacks and persistence; issuance requires a client binding after request authorization. Form requests reject repeated nonempty values for these three fields. Endpoint hooks retain the original input.

Every `DeviceCode` native field uses `SchemaValue<T>` to retain omitted fields, null, and replacement values. Use `field_value()` for native values and `typed()` when application logic requires the ordinary Rust type. Device routes consume truthiness, strict equality, numeric comparisons, and Date conversion at the corresponding upstream boundary. Device review responses preserve native values until serialization.

`DeviceAuthorizationPlugin::interval` accepts a `chrono::Duration`. `DeviceCode.polling_interval` uses `SchemaValue<Option<f64>>`; `CreateDeviceCode.polling_interval` accepts optional `f64` milliseconds, so `Duration::microseconds(1500)` retains `1.5` in Memory and SQLite. The issuance response floors both interval and lifetime to whole seconds, as upstream does, including negative fractional configurations. Replace integer field initializers such as `Some(5000)` with `Some(5000.0)`.

A zero polling interval disables the polling-frequency guard, including when the stored `lastPolledAt` is in the future. Expiration, ownership, approval, and single-use consumption checks still apply.

SeaORM models use `Option<better_auth::seaorm::SqlNumber>` with `#[sea_orm(column_type = "Integer", nullable)]`. The generated and bundled initial schemas declare nullable INTEGER, matching the pinned schema. Existing SQLite BIGINT columns can retain integer and fractional values through `SqlNumber`; this change does not automatically narrow existing database columns. PostgreSQL and MySQL parameter behavior for fractional polling intervals in integer columns remains unverified. Enable SeaORM's `sqlx-mysql` feature for MySQL.

Fresh CLI schemas use the native `deviceCode` table and camelCase columns. The two codes have separate unique indexes; userId remains nullable text without a foreign key, including Serial and UUID ID modes. Use `--device-code-legacy-schema` to retain the previous physical schema and reference conversion. Applications own migrations; bundled entities and existing generated files remain unchanged. See [schema mapping](/docs/concepts/database#map-plugin-tables-and-columns) for backend types, index names, and the catalog-only acceptance boundary.


## Request field validation

Configure `DeviceAuthorizationPlugin::request_fields` with `DeviceRequestFields` to validate additional `/device/code` fields. Add fields in order with `DeviceRequestField::new` or `new_async`. A callback receives `Option<serde_json::Value>` and returns `DeviceFieldValidation::Value` or `Issues` through `AuthResult`. `None` preserves omission; `Some(Value::Null)` preserves explicit null. Unknown fields are removed from the validated projection. The original HTTP body remains available to request hooks.

`DeviceRequestIssue` preserves the message, relative path, and validator-specific details. `on_validation_error` receives all issues before the default OAuth `invalid_request` error. An application error propagates unchanged. Native client, user, and scope fields cannot be redefined. Request fields do not authorize the request or become stored fields; configure a grant for authorization and declared adapter policies for persistence.

Route authors can install an async body validator with `AuthRoute::body_validator_async`. Existing `.body_validator(callback)` calls remain unchanged. `better_auth::plugin::BodyValidator` is now a wrapper: replace direct `Arc::new(callback)` construction with `BodyValidator::new(callback)`, and call `validate(&request).await`. Validation runs once before query validation, required headers, and endpoint middleware. Rust does not emulate JavaScript's async-detection probe, repeated callbacks, or task scheduling.

## Grant callbacks

Configure ordinary plugin options and request fields before calling the terminal `DeviceAuthorizationPlugin::grant` builder. `DeviceGrant<S>::new(authorize_request, assert_session_redemption)` requires both callbacks and uses the application's `AuthSchema`. The builder returns an `impl AuthPlugin<S>` through the existing typed callback registration. An unconfigured plugin retains its standalone behavior.

Both callbacks return `DeviceGrantFuture` with `Box::pin(async move { ... })`. They borrow the existing `EndpointContext<S>`, which exposes the validated body, original HTTP request, explicit native headers, and active authentication runtime. Request authorization also receives `&DeviceAuthorizationRequest`; session policy receives `&DeviceCode`. Callback errors propagate unchanged.

Only a configured grant makes the request `client_id` optional. The request callback runs after empty-value and form normalization. It returns `Some(DeviceGrantAuthorization { client_id, additional_fields })` to supply the binding and logical fields to store. That result selects the effective client and does not call `validate_client`. Returning `None` requires a request client and a configured `validate_client` callback that accepts that client. An empty effective client is rejected. `on_device_auth_request` receives the effective client and the normalized request scope.

Use `DeviceGrant::stored_fields(UserConfig)` to declare stored fields. Initialization registers these declarations through `ModelFields`. The configured SQL model must contain the declared columns. Grant declarations cannot redefine native DeviceCode fields, including `scope`; the separate adapter scope policy remains available. Authorization fields pass through existing defaults and transforms. Typed native fields continue to determine the generated codes, client, user, status, expiry, interval, and scope.

The required session policy runs in `/device/token` after ordinary client validation, code lookup, and the existing stored-client comparison. The shared redemption helper runs its polling, expiry, status, user, and atomic-consumption checks afterward. The policy cannot replace those checks or their ownership condition. Configure the policy for the application's intended issuer before enabling grant requests.

`DeviceGrant::verification_context` accepts a synchronous callback returning `AuthResult<Option<FieldMap>>`. The callback runs only after the existing session claim and owner check succeeds. It receives the projected stored row, including the bound user and declared fields. The response merges the additional display fields before its native fields. Native fields retain precedence even when their values are omitted. No callback or a `None` result adds no fields.

These contracts follow pinned 1.7.6 `plugins/device-authorization/routes.mjs:199–244` for issuance, `:436–451` for session policy, and `:528–560` for verification context. `index.mjs:42–64` defines additional-field restrictions and stored schema composition. CI must validate the paired ordinary-flow contracts before runtime parity is claimed. Native verification values retain missing fields, Date values, and object identity until response serialization. JavaScript callback task lifetime and complete legacy Date parsing remain unaligned.

## Grant metadata

Configure grant documentation before calling `DeviceAuthorizationPlugin::grant`. `DeviceGrant::request_error_codes(Vec<String>)` appends codes to the documented `/device/code` `400` error enum, preserving order and duplicate values. The fixed `500` response continues to document only `server_error`.

`DeviceGrant::request_openapi_responses(Map<String, Value>)` supplies additional response objects. The Device plugin's fixed `200`, `400`, and `500` responses replace declarations with those status keys. Other declarations override the OpenAPI generator's default responses for the same status. Response status keys retain JavaScript property ordering.

`DeviceGrant::verification_openapi_properties(Map<String, Value>)` adds documented `/device` verification properties after the native properties. Initialization rejects declarations named `user_code`, `status`, `client_id`, or `scope`. Numeric property names follow JavaScript enumeration order. This metadata does not register stored fields or produce verification values; configure `stored_fields` and `verification_context` for those behaviors.

Schema generation does not execute grant callbacks. Without explicit request-field documentation, the standalone Device document remains unchanged. A configured grant documents `client_id` as optional even when all metadata maps are empty. CI must validate the metadata contract against pinned 1.7.6 before document parity is claimed.

Attach request documentation with `DeviceRequestField::openapi_schema(schema, required)`. Supply a JSON OpenAPI schema for the validator's input. Set `required` from input presence: a field with a default can remain optional even when validation always returns a value. A transformation documents its input type, not its output type. The declaration changes documentation only and does not execute or replace validation.

```rust
let label = DeviceRequestField::new(validate_label)
    .openapi_schema(serde_json::json!({ "type": "string", "minLength": 2 }), true);
let request_fields = DeviceRequestFields::new().field("label", label)?;
```

Annotated fields appear in `/device/code` with or without a grant. Standalone requests retain the required native `client_id`; only a configured grant makes that field optional. Native `client_id`, `user_id`, and `scope` cannot be redefined through `DeviceRequestFields::field`. Replacing an additional field preserves its declaration position and replaces its schema and requiredness. Property keys and required names use JavaScript enumeration order, including numeric field names.

Unannotated validators remain absent from generated request documentation. The library does not infer schemas, defaults, transformations, or requiredness from Rust callbacks. A schema declaration does not add a SQL field, issue a credential, or change client and owner checks. The separate request-schema CI contract compares complete serialized Device operations against pinned 1.7.6 and checks that schema generation calls no validation or grant callback.

## Adapter field policies

Custom plugins can register complete declarations through `AuthInitContext::register_model_fields(EntityRole::DeviceCode, UserConfig)`. Register replacements after the Device plugin. Replacement preserves the original field position and replaces the entire declaration, including its type, references, defaults, mappings, and callbacks. A later native plugin restores its declarations at their existing positions. Grant `stored_fields` retains the upstream restriction to additional fields.

Complete records and update patches use the shared adapter policy. `DeviceCodeStore::{create_device_code_record, get_device_code_record, update_device_code_record}` accepts or returns logical `FieldMap` values. The ordinary typed creation and update methods use the same pipeline. Generate matching physical columns with `deviceCode.additionalFields`, including declarations that replace native fields. Runtime registration does not migrate existing databases.

`DeviceCode` fields preserve dynamic values through `SchemaValue`. `CreateDeviceCode` retains ordinary Rust inputs. `CreateDeviceCode.scope` and `UpdateDeviceCode.scope` distinguish omission with `Default::default()`, explicit null with `None.into()`, and a string with `Some(value).into()`. `UpdateDeviceCode.user_id` accepts `Option<SchemaValue<Option<String>>>`; the outer `None` leaves the field unchanged. `claim_device_code` accepts a native `SchemaValue<String>` user ID. Raw records can express missing, null, and dynamic values for every field.

Create, update, both code lookups, claim, and consumption use the complete output policy. Input failure prevents the write. Output failure propagates after persistence; an enclosing transaction can roll the write back. A failed atomic condition executes no output callback. Memory reads each field from its selected row immediately before that field's output callback. SQL projects the returned database snapshot. Deleted Memory rows retain their consumed snapshot for output projection.

A typed adapter read or write captures the original physical `id`, `deviceCode`, `clientId`, `userId`, and `status` before output callbacks. After projection, the record seals its public bindings. Atomic consumption requires both unchanged public bindings and matching physical bindings. Use the actual adapter-returned record; deserialization and construction from a field map do not supply consumption bindings. Ordinary cloning preserves the bindings. Structured cloning copies the public values and sealed values through one object graph. Bindings are excluded from JSON, public field extraction, and Debug output.

Consumption preserves the ownership condition and approved-status guard. Memory evaluates the ownership condition across every row before deleting a selected row. SQL prepares the ownership expression and physical conditions before executing the guarded statement. MySQL retains the selected row lock and deletes by the locked primary key. Neither adapter reconstructs physical guards from transformed public fields. Ordinary lookup and update parameters retain their declared query conversions.

Memory JSON input conversion, native arrays, Serial reference conversion, and SQL driver conversions retain their backend boundaries. The existing native-replacement fixtures compare complete Memory and SQLite returns, callbacks, errors, key order, and stored values. Server database catalogs and ownership contracts remain separate checks; those checks do not establish complete native-replacement parity on PostgreSQL or MySQL.

## Server-only redemption

Use `better_auth::plugins::device_authorization::redeem_device_code` when an application issues credentials after device approval. Pass an `EndpointContext`, the device code, an authorization callback, and a preparation callback. Both callbacks return `DeviceRedemptionFuture` with `Box::pin(async move { ... })` and borrow the active endpoint. The authorization callback returns `DeviceCodeRedemptionAuthorization { ownership, context }`. The preparation callback receives the code and the authorization context.

The helper authorizes the issuer, enforces the polling interval, updates `lastPolledAt`, checks expiry and approval, prepares issuance, looks up the bound user, and atomically consumes the code. The result contains the actual consumed row, both callback contexts, and the user. A `DeviceCode` with no poll timestamp serializes `lastPolledAt` as null. The current optional timestamp type does not distinguish an omitted JavaScript property from explicit null. The user follows the active schema, retains fields marked `returned: false`, and does not repeat adapter output transforms. Issue application credentials only after the helper succeeds. If the caller uses a transaction, issue credentials only after that transaction commits. Callback errors propagate unchanged. Authorization errors leave the poll timestamp unchanged; preparation errors retain the completed poll update. Polling comparison, timestamp assignment, and the post-update expiry check each read the current time at their own stage.

Set `EndpointContext.transaction` when the caller runs inside an active transaction. The helper uses that transaction for every store operation, including user lookup. `AuthTransaction` exposes the DeviceCode store operations. The default `/device/token` route uses the same helper and creates its session after consumption, using the consumed row's bound user ID.

### Ownership conditions

Use `DeviceCodeOwnership::Where(DeviceCodeWhere)` to add one `AND` condition to consumption. Every condition retains the original ID, device code, client, user, and approved-status bindings. The condition cannot select a different code or replace those bindings. Configured grant callbacks and direct transaction calls use the same consumption path.

`DeviceCodeWhere` accepts native `scope` without registration. Other fields must be declared through a custom plugin or grant. Use the logical name or the configured physical column name. Supported field types are String, Number, Boolean, Date, Enum, StringArray, NumberArray, and Json, without references. String, Json, and Date fields that reference `id` also use the configured ID policy. Use `DeviceCodeOwnership::ClientId` for the native client binding.

For a declared String field named `tenantKey`, return this ownership condition from the redemption authorization callback:

```rust
use better_auth::prelude::{DeviceCodeOwnership, DeviceCodeWhere, WhereMode, WhereOperator};

let ownership = DeviceCodeOwnership::Where(DeviceCodeWhere {
    field: "tenantKey".into(),
    operator: WhereOperator::In,
    value: vec!["fleet".into(), "support".into()].into(),
    mode: WhereMode::Insensitive,
});
```

`DeviceCodeWhere::new("scope", "read")` selects `Eq` and `Sensitive`. The available operators are:

| Rust operator | Upstream operator | Query value |
| --- | --- | --- |
| `Eq`, `Ne` | `eq`, `ne` | A native `FieldValue`, including Date and array objects |
| `Lt`, `Lte`, `Gt`, `Gte` | `lt`, `lte`, `gt`, `gte` | A native operand for the adapter's ordered comparison |
| `In`, `NotIn` | `in`, `not_in` | An array of native candidate values |
| `Contains`, `StartsWith`, `EndsWith` | `contains`, `starts_with`, `ends_with` | An operand for the adapter's pattern or membership operation |

`In` rejects a non-array operand with `Value must be an array` before resolving its field or applying reference and adapter conversion. A valid input array can still become a scalar through Json conversion; that later representation follows the adapter's comparison behavior.

`FieldValue` retains undefined, non-finite numbers, and object identity until the adapter boundary. Memory equality compares Date and array handles; clone a returned value to retain its identity. An explicit Memory transaction copies stored objects with new handles, so a pre-transaction value can differ from a value read inside the transaction. When an empty candidate array reaches Memory or SQLite, `In` never matches and `NotIn` adds no field restriction. PostgreSQL and MySQL reject the empty SQL set with a database syntax error. Json query conversion serializes the candidate array before adapter comparison, so empty-set behavior does not apply. Array and Json fields use the selected adapter's stored representation; accepting a field type does not guarantee that every operator succeeds on that backend.

`WhereMode::Sensitive` retains the adapter's ordinary comparison behavior, including SQL collation. `Insensitive` applies to string equality, membership, and pattern comparisons. The query operand must be a string, or every membership candidate must be a string; a mixed candidate set does not enable case folding. Range operators ignore the mode. SQL pattern operators retain `LIKE` semantics, including `%` and `_` wildcards. Memory string patterns use literal substring, prefix, or suffix matching; Memory `Contains` on an array checks membership. Null handling and database type errors also remain specific to the adapter.

Query conversion does not invoke field input or output callbacks. A Number candidate set of numeric strings converts only when every candidate parses as a number. Matching consumption awaits the consumed row's output callbacks. A query error or a condition that matches no row leaves the stored row intact. Rust preserves `AuthError` and database-driver diagnostics; JavaScript `Error.name` identity is not reproduced.

With Serial ID generation, a reference to `id` uses the shared numeric reference conversion. Query null converts to zero, while stored null remains null. Candidate arrays convert each value independently. Json binding on Memory, SQLite, and MySQL retains the original object, array, Date, or null operand for serialization after reference conversion. SQLite Date binding likewise uses the original top-level Date; dates inside candidate arrays retain numeric reference conversion. Reference declarations do not authorize the caller or change the native DeviceCode user binding.

Custom adapters calling `ModelFields::device_code_ownership_query` must consume its three-item result: the bound condition, field policy, and original operand. Apply adapter-specific Json and Date conversion with that original operand.

The following predicates remain unsupported:

- Reference fields outside String, Json, and Date references to `id`.
- Undeclared fields, other native DeviceCode fields through `Where`, and `OR` or multiple caller-supplied conditions.

The accepted Memory, SQLite, PostgreSQL, and MySQL contracts include 90 ordinary and 23 transaction observations per backend, including Date, non-finite-number, and array-identity cases. Database binding errors and coercion remain specific to each backend. An additional 18 default String-ID reference observations per backend cover logical and physical field names, owner mismatch, every native binding, commit, and rollback. Rust runs each reference observation through both `Where` and `FieldEquals`; CI 37680167423 accepted this addition. CI 37693670658 accepted 30 candidate-set observations per backend with default and Serial IDs, each through `Where` and the corresponding set variant. CI 37695849591 accepted 24 Json/Date reference observations per backend with Serial IDs, all five native guards, commit, and rollback. CI 37699849810 captured 36 default-ID Json/Date observations, including rejection of non-array `In` operands. Rust acceptance for those observations is pending.

The reference contract compares complete Device values, field callbacks, consumed records, rollback restoration, and the original rollback error allocation. Rust also checks that the complete owner view remains unchanged. Raw User, Session, Account, and Verification table snapshots, plus complete Device table enumeration inside the transaction, remain upstream-only observations because the public Rust Store does not expose those reads. MySQL syntax errors retain both complete driver messages in CI. Their SQL excerpts differ because SQLx and mysql2 use different statement forms; the exact excerpts remain unpaired.

The `ClientId`, `FieldEquals`, `FieldIn`, and `FieldNotIn` variants remain available. `FieldEquals` accepts `scope` or a declared String, Number, or Boolean field and a scalar or null operand. `FieldIn` and `FieldNotIn` accept `scope` or declared String or Number fields, with null, string, or number candidates. All three variants accept String references to `id` with the same validation and Serial conversion as `Where`.

## Atomic consumption and transactions

`DeviceCodeStore::consume_device_code(&expected, &DeviceCodeOwnership::ClientId(client_id))` consumes one approved record while retaining the original ID, device code, client, user, and status bindings. The method returns the actual consumed record and awaits its output projection. Scope and poll timestamp changes are included in that result. The method does not replace endpoint authentication, expiry, or polling checks.

`AuthTransaction` includes DeviceCode operations. Memory and SeaORM execute these operations through the active transaction; secondary storage forwards them to that transaction. Memory validates consumed records against the original transaction state before merging any changes. A code created and consumed in the same transaction needs no existing live record. An output error from an ordinary consumption propagates after deletion. An output error propagated out of a transaction aborts that transaction.

For field conditions, Memory checks the field's original value against the live record before transaction commit. A preparation callback can change the field inside its transaction; a concurrent external change rejects the commit even if the new value still belongs to an allowed candidate set. Direct and SQL transaction paths include the field condition in atomic consumption.
