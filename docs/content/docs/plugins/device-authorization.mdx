---
title: Device Authorization
description: Register a device through an authenticated browser approval flow.
---

Install `DeviceAuthorizationPlugin` and generate the device-authorization schema. A client requests a code at `POST /device/code`, sends its user to the verification URI, and polls `POST /device/token`. An authenticated user must claim the code through `GET /device` before calling `/device/approve` or `/device/deny`.

```rust
use better_auth::plugins::DeviceAuthorizationPlugin;

let plugin = DeviceAuthorizationPlugin::new()
    .validate_client(|client_id| async move { Ok(client_id == "node-agent") })
    .generate_device_code_with(|| async { Ok(issue_device_code().await?) })
    .generate_user_code_with(|| async { Ok(issue_user_code().await?) });
```

Application generators return `AuthResult<String>`. Each attempt awaits the device-code generator, then the user-code generator, before persistence. A callback error stops the request. Codes may contain up to 191 Unicode scalar values; custom user codes retain their exact case and punctuation. The upstream contract permits an explicitly empty generated code.

The plugin retries a unique-constraint collision at most three times. Each retry generates both codes again. Other persistence errors propagate. Client validation and `on_device_auth_request` run once before generation.

The generator methods now accept asynchronous closures. Change a synchronous closure from `|| value` to `|| async { Ok(value) }`. Keep application-owned admission policy in `validate_client`; a valid device token does not establish machine inventory identity.

All four POST routes validate their bodies before authentication and endpoint middleware. `/device/code` returns OAuth `invalid_request` validation errors. The other routes use `VALIDATION_ERROR`. Empty `client_id` is rejected; empty `user_id` and `scope` are omitted before callbacks and persistence. Form requests reject repeated nonempty values for these three fields. Endpoint hooks retain the original input.

`DeviceCode.client_id` and `DeviceCode.scope` use `SchemaValue<Option<String>>` so native store reads retain omitted memory fields and SQL null values. Use `json()` to inspect presence and `typed()` for a present nullable string. Device review responses preserve the same distinction.


## Adapter scope policies

Custom plugins can register the ordinary `scope` string field through `AuthInitContext::register_model_fields(EntityRole::DeviceCode, UserConfig)`. Memory and SeaORM consume defaults, `on_update`, and synchronous or asynchronous input/output transforms. Other DeviceCode fields, reference declarations, replacement types, and field aliases are rejected during initialization. The field policy does not replace route validation or authorization decisions.

`CreateDeviceCode.scope` and `UpdateDeviceCode.scope` use `SchemaValue<Option<String>>`. Use `Default::default()` for omission, `None.into()` for explicit null, and `Some(value).into()` for a supplied string. Migrate an old absent create scope to `Default::default()`; append `.into()` to an old supplied `Some(value)`. An omitted update can still receive `on_update`. Explicit null reaches the input transform as null. Memory retains omitted fields, while SQL nullable columns read back as null.

Create, ordinary update, and both code lookups project the returned scope. Conditional update and claim operations also await the successful row's output callback before returning their boolean result. Input failure prevents the write. Output failure propagates after persistence. A condition that matches no row returns false without an output callback. Input callbacks run outside storage locks; the existing atomic write conditions remain part of the write. The public `AuthTransaction` interface does not expose DeviceCode operations, so this slice adds no general DeviceCode transaction API.
