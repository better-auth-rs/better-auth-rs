title: API Key
description: Create, manage, and validate API keys with rate limiting and usage tracking.

The `ApiKeyPlugin` provides API key management with support for rate limiting, usage quotas, expiration, and permissions.

## Setup

These examples assume you've already defined `AppAuthSchema`. If you want a complete setup from entity definitions through Axum mounting, start with the [Axum integration guide](/docs/integrations/axum).

```rust
use better_auth::plugins::ApiKeyPlugin;

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(ApiKeyPlugin::builder().build())
    .build()
    .await?;
```

### Configuration

```rust
use better_auth::plugins::api_key::{ApiKeyConfig, RateLimitDefaults, KeyExpirationConfig};

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(
        ApiKeyPlugin::builder()
            .key_length(64)
            .prefix("sk_".to_string())
            .enable_metadata(true)
            .build()
    )
    .build()
    .await?;
```

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `key_length` | `usize` | `64` | Random characters excluding the prefix; `0` selects the default length of `64`, matching upstream |
| `prefix` | `Option<String>` | `None` | Global prefix for all generated keys |
| `enable_metadata` | `bool` | `false` | Allow storing metadata on keys |
| `require_name` | `bool` | `false` | Require a name when creating keys |
| `default_permissions` | `Option<HashMap<String, Vec<String>>>` | `None` | Permissions assigned when creation omits permissions |
| `api_key_headers` | `Vec<String>` | `["x-api-key"]` | Headers checked when API key sessions are enabled |
| `enable_session_for_api_keys` | `bool` | `false` | Emulate sessions for API-key-authenticated requests |
| `config_id` | `String` | `"default"` | Name of this configuration, stored on every key it creates |
| `references` | `ApiKeyReferences` | `User` | Whether keys belong to the signed-in user or to an organization |

### Expiration Configuration

`KeyExpirationConfig.default_expires_in` uses `Option<f64>` seconds. `None` and `Some(0.0)` create keys without a default expiration; `Some(1.5)` supplies a 1.5-second default. A supplied creation lifetime replaces the default. Updating a key without `expires_in` preserves its existing expiration.

`min_expires_in` and `max_expires_in` use `f64` **days** and constrain supplied creation and update lifetimes. The default bounds remain `1.0` and `365.0`; configure `0.5` and `1.5` to allow half-day through one-and-a-half-day requests. These bounds do not constrain the configured default lifetime. The existing date conversion persists millisecond timestamps.

This changes the three configuration fields from integer types. Update direct struct initializers to floating-point literals, such as `min_expires_in: 0.0` and `default_expires_in: Some(3600.0)`. Key verification, ownership, and usage policies are unchanged.

### Application Callbacks

Each configuration accepts `Arc` implementations of `ApiKeyGenerator`, `ApiKeyGetter`, `ApiKeyValidator`, and `ApiKeyDefaultPermissions`. Register them with `custom_key_generator`, `custom_api_key_getter`, `custom_api_key_validator`, and `default_permissions_callback` respectively. The getter is synchronous; the other callbacks are async.

`ApiKeyDefaultPermissions::permissions` receives `reference_id: &FieldValue`. The callback observes the selected native user or organization reference before storage conversion. Ownership uses strict equality, so a numeric reference differs from the same digits in a string. Native reference queries use `ApiKeyStore::find_api_keys_by_reference_value` and `count_api_keys_by_reference_value`; the `&str` convenience methods call the same implementation. Secondary storage converts the reference only when constructing its cache key.

`CreateApiKey.reference_id` uses `SchemaValue<String>`. Use `"owner".into()` for ordinary IDs and `SchemaValue::from_field(value)` for native references. The selected database declaration and driver can change the stored type: SQLite's default text column returns `7` as `"7"`. Ownership compares that stored value with the session's native User ID. Pure secondary storage preserves the reference's JSON type.

The generator receives the resolved length and prefix. Its result is the complete credential, including any prefix; the plugin then hashes the result and records its starting characters. Dynamic permissions receive the owning user or organization ID and run even when creation supplies explicit permissions. Explicit permissions replace the callback result.

Starting characters use UTF-16 code units, matching JavaScript `substring`. `ApiKeyStart` preserves a surrogate split at the boundary: use `as_utf16()` for exact units and `to_utf8()` for a fallible `String` conversion. Its JSON serialization preserves unpaired surrogates, including secondary-storage round trips. Serialize typed responses directly; `serde_json::Value` cannot represent these strings. Disabling `store_starting_characters` skips prefix extraction.

SQLite model reads match the pinned Bun adapter: each invalid WTF-8 byte becomes U+FFFD, so a split surrogate produces three replacement characters. The stored SQLite byte encoding is not promised to match its nonstandard WTF-8 bytes. PostgreSQL and MySQL use one replacement character per unpaired surrogate, matching the UTF-8 Buffer encoding in [pg](https://github.com/brianc/node-postgres/blob/master/packages/pg-protocol/src/buffer-writer.ts) and [mysql2](https://github.com/sidorares/node-mysql2/blob/master/lib/parsers/string.js). Those driver boundaries are verified by source and a Node Buffer probe; the executable dual-server cases cover SQLite and secondary storage.

`ApiKeyEndpoint` exposes the original request, endpoint headers, path, native body, authentication configuration, runtime extensions, plugin metadata, and API key and organization adapters. Headers can be present without an original request. Its `body` borrows a `FieldValue`. Use `ctx.body.model_property("field")?` to read a property and `strict_equals` to compare object identity. Call `.json()?` only when a JSON representation is required. The session hook retains the endpoint body's missing, undefined, null, and native object values; the getter and validator share the same body handle. Dynamic creation permissions receive the existing validated projection, including route defaults.

Requestless typed Rust methods construct their input from their request DTOs before invoking hooks. Validation and business operations consume the values left by those hooks. The schema preserves native `metadata` references without reading their properties. Creation captures its validated fields before the permissions callback. Replacing a callback body property does not replace the captured value; mutations inside shared metadata and permissions remain visible. Metadata reaches JSON only at the adapter or cache serialization boundary, and permissions are encoded where the endpoint stores them. Verification captures permissions after an explicit configuration's validator; an unscoped validator runs after that capture. Other fields still use strict Rust DTOs after schema validation; strings with unpaired UTF-16 surrogates are not yet supported at that boundary.

Requestless server calls have no HTTP request. Server-only verification has no matcher path; its handler uses `virtual:`, or `/` after session authentication. Callback errors retain their status and response body through `AuthError::from(AuthResponse)`. Ordinary callback failures produce an empty HTTP `500` response; requestless APIs preserve the original error. A getter failure in the hook matcher logs the original error and returns a new `INTERNAL_SERVER_ERROR` API error with the matcher-failure message. A failure in the second getter invocation remains a handler error and preserves the original callback error.

Update wraps adapter and cache write failures in a new `INTERNAL_SERVER_ERROR` API error. The new body contains the thrown value's top-level `message`; the original status, code, and headers are discarded. A failing message getter propagates its own error. Ownership lookup and later metadata migration remain outside this catch. A failed output transform can therefore leave the completed database write persisted.

A configured getter replaces that configuration's header lookup. Returning `None` does not fall back to its headers. Session authentication calls the getter once in the hook matcher and again in the handler. These hooks also run for native creation, update, and verification; a getter can therefore authenticate and consume a credential during a requestless call. Verification then consumes its own credential separately.

Scoped verification calls its validator before lookup and propagates callback errors. Unscoped verification first finds the credential, then calls the owning configuration's validator inside the verification error boundary. Session authentication calls the selected validator before lookup. Validators run before enabled, expiration, permission, and quota checks.

### Storage

A serialized JSON `null` cache entry is a cache miss. Database fallback reloads and caches the stored key when enabled; secondary-only storage rejects the missing credential. Cache hits do not repeat adapter output transforms.

API keys use the database by default. Set `storage: ApiKeyStorage::SecondaryStorage` to use the shared secondary storage. A configuration's `custom_storage` takes precedence over the shared backend. `MemoryCacheAdapter` and the optional `RedisAdapter` implement `SecondaryStorage`; applications implement its async `get`, `set_native`, `delete`, and atomic `get_and_delete` methods. `set_native` receives `FieldValue` keys and values and an optional floating-point TTL in seconds. JSON serialization can produce Undefined, which reaches the backend unchanged. Memory retains that value; Redis rejects non-string values at its encoding boundary. The `set` convenience method accepts string keys, string values, and unsigned TTLs. No TTL means persistent storage.

Native storage bridges may override `invoke_get_native`, `invoke_set_native`, and `invoke_delete_native` to separate invocation errors from returned asynchronous completions. Existing async implementations use the default hooks. The write hook receives `Option<Option<f64>>`: outer `None` omits the TTL argument, while `Some(None)` supplies undefined. API Key calls evaluate each key and start its storage call before evaluating the next key. A later invocation or key-conversion error does not cancel earlier writes. Unowned failures reach the shared terminal reporter; adopted failures retain the existing concurrent collector. Atomic quota and cache-consume APIs keep their separate guarantees.

```rust
use std::sync::Arc;
use better_auth::plugins::api_key::{ApiKeyPlugin, ApiKeyStorage};
use better_auth::store::MemoryCacheAdapter;

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .secondary_storage(Arc::new(MemoryCacheAdapter::new()))
    .plugin(ApiKeyPlugin::builder()
        .storage(ApiKeyStorage::SecondaryStorage)
        .fallback_to_database(true)
        .build())
    .build()
    .await?;
```

`fallback_to_database` keeps database rows authoritative. A cache miss loads the database row and restores both cache indexes. Writes update the database before refreshing the cache. Cache I/O errors propagate; the runtime does not treat an I/O failure as a miss. Verification commits each guarded quota and rate-limit write separately, then updates the timestamp and refreshes the cache. A later database failure preserves earlier committed writes. A cache write failure can therefore follow a successful database mutation. If a database row disappears after a cached ownership lookup, update returns the unchanged cached snapshot, matching the upstream null-update result.

Convert stored keys with `ApiKeyView::try_from_api_key(&key)?`. The view uses the shared native field projection, retains source property order and omission, propagates dynamic read errors, and excludes the stored credential hash.

Register native replacement declarations and application fields through `ModelFields::register_model_fields(EntityRole::ApiKey, UserConfig)`. `ModelFields` merges complete declarations in upstream schema order. A replacement removes the previous default, transform, reference, and mapping unless the replacement declares them. Replacement declarations retain their original positions; new integer property names follow JavaScript enumeration order. The adapter-owned ID policy replaces application ID attributes at the existing ID position.

Complete records and update patches use the same defaults, `on_update`, input transforms, column mappings, and output transforms. Memory stores physical `FieldMap` records and reads each field immediately before its output callback. SQL reads physical values from its query snapshot before constructing the runtime record. Native fields use `SchemaValue<T>` to retain missing, null, and cross-type output values. Output errors propagate after persistence; input errors prevent the write. ID generation and references retain the adapter runtime policy and selected backend conversion.

Database updates preserve `updatedAt` unless the patch supplies a value or the field declaration supplies an update policy. Typed `UpdateApiKey` calls use the same rule as raw record patches. Secondary-only updates and verification usage writes retain their explicit timestamp assignments.

Generate matching columns with `apikey.additionalFields` and `apikey.fields` in the CLI schema configuration. Native replacements use the same declaration path as application fields. When declarations share a physical column, the last declaration supplies the generated column attributes while the first declaration retains its position. Match runtime declarations to the generated schema. Applications own migrations for changed columns; registration does not migrate stored data.

These policies run on actual adapter operations. Secondary-only creation, updates, reads, lists, and usage writes bypass the adapter. Fallback cache hits return the cached projected record without another callback. Fallback misses and database writes use adapter policies before refreshing the cache. Counts and deletes do not project fields.

Ordinary typed create and update inputs remain available. Use `Default::default()` for an omitted `SchemaValue`, `None.into()` for explicit null, and `Some(value).into()` for an optional typed value. Read `.field_value()` for dynamic values or `.typed()?` when a caller requires the declared Rust type. The raw `create_api_key_record`, `get_api_key_record`, and `update_api_key_record` methods accept or return complete logical `FieldMap` records. Typed records preserve field presence and property order in `field_order`; complete struct literals must initialize this metadata. Public views exclude the key hash. The cache codec preserves record order while retaining its existing date conversion and optional-null protocol. Business guards use the upstream operations: only Boolean false disables `enabled` or `rateLimitEnabled`. Permission checks read object properties and array or UTF-16 string indices before calling the selected value's inclusion operation; malformed values retain the upstream validation error path.

Quota guards use the effective field query conversion. Memory atomic increments treat non-number storage as zero and apply the set patch after the increment. SQL uses database arithmetic and lets the increment replace a conflicting set value for the same physical column. Both adapters evaluate input callbacks before the atomic write and output callbacks after persistence. Cache arithmetic retains its separate JavaScript value operations.

Memory numeric comparisons use subtraction. Positive and negative zero, same-sign infinities, and NaN comparisons produce equal ordering. The pinned two-row cases preserve insertion order in both directions. Three or more rows containing NaN and unequal finite values can have non-transitive comparisons; their final order can depend on the JavaScript engine and sorting algorithm.

Memory API Key, User, and Member sorting share a fallible comparator. Strings use ICU 78.3 collation, including raw UTF-16 code units. Nullish values, Numbers, Dates, and Booleans follow the upstream comparison branches. Sorting examines all matching rows before pagination. Binary insertion preserves equal comparisons and has `O(n²)` worst-case data movement. The captured twelve scenarios and two string matrices cover short inputs; longer mixed-type inputs can differ from JavaScriptCore's Powersort merging because their comparisons can be non-transitive. Windows and macOS runtime collation remain unverified.

Cached name sorting uses JavaScript relational conversion. Null and undefined sort first in ascending order and last in descending order. When the comparison relation is consistent, equal values retain their cached order in both directions. Mixed types can produce inconsistent comparisons; nonnumeric string/number pairs and invalid cached dates are unordered. The comparator treats unordered pairs as equal, matching the upstream comparator. The final order of inconsistent inputs can depend on the JavaScript engine and sorting algorithm, so arbitrary-length mixed inputs do not have complete ordering parity.

Cached key sorting uses one local insertion sort for every field to accept non-total comparisons and propagate conversion errors directly. The algorithm makes at most `n * (n - 1) / 2` comparisons, with `O(n²)` worst-case work. Replace this path only after profiling identifies a large-cache sorting bottleneck, and pair the replacement with fresh pinned-upstream observations.

Plain JSON objects use inherited `[object Object]` conversion. An own `toString` property contains a non-callable value and makes conversion fail, including when the object is an array element. An own `valueOf` or an unvisited nested property does not prevent inherited conversion. Cached lists propagate conversion errors without changing stored records. Null/undefined comparator branches and lists that require no comparison do not coerce objects. Callable methods, `Symbol.toPrimitive`, custom prototypes, and getters remain outside the `FieldValue` representation.

A database usage write with a set patch applies the complete field schema before the existing guarded write. A plain quota decrement has no set patch, so it skips input policies and `on_update`. Each successful returned row runs output policies; a condition that matches no row runs none. Callbacks run outside Memory locks. Prepared set fields join the original conditional write, preserving atomic counter expressions. Input errors prevent that write. Output errors preserve the completed write. Earlier successful usage writes remain committed if a later callback fails.

`ApiKeyUsageWrite::Refill.previous` uses `FieldValue`. Direct adapter callers must pass `row.last_refill_at.field_value()`. Memory compares Date object identity; constructing a new Date with equal milliseconds does not match the stored object. SQL compares the persisted value through the column binding. The built-in verification path preserves the observed value automatically.

Without database fallback, the backend stores the full key under `api-key:<hash>` and `api-key:by-id:<id>`. The `api-key:by-ref:<referenceId>` entry stores the owner's key IDs without a TTL. Key entries use the remaining expiration time rounded down to whole seconds; a nonpositive TTL is omitted, matching upstream. Listing ignores entries whose key records have expired. Reference-list mutations are serialized within the process. Quota consumption uses the upstream read/merge/write behavior and does not provide cross-request atomic enforcement. A rate-limit rejection in this mode occurs before the quota write.

Reference lists retain native values through parsing and consumption. Insertions use `SameValueZero`; removals use strict equality, including object identity. Valid non-array JSON reaches the relevant list method, and method errors do not rewrite the reference index. Hash and ID entries retain writes or deletions completed before that error. Native cache methods preserve UTF-16 hash, ID, and reference keys. Custom backends must implement native key reads and deletion to support unpaired code units; the default bridges accept strings.

Cache JSON text uses the shared native parser, including raw and escaped unpaired UTF-16 string values. Reference lists retain nonnumeric array-like lengths and any raw element left by `new Array(length)` when no worker starts. These values pass through sorting, group deduplication, and owner filtering before public projection. Cache records retain property order and use the separate Date revival policy. JSON object keys containing unpaired surrogates remain unsupported by `FieldMap`.

Database fallback invalidates the reference list on writes and rebuilds the list from database rows. Sharing one backend between configurations with and without fallback also shares these indexes, including this upstream invalidation behavior. A list without `configId` groups configurations by storage backend and removes duplicate IDs before configuration and ownership filters. An explicit `configId` preserves duplicate records. Both paths filter before pagination.

Cached list reads and database fallback refills process at most ten keys concurrently. Fractional array-like lengths use the upstream worker count. Each refill retains its two cache writes and reference-index invalidation; the complete index is published only after every key succeeds. Results retain the reference-list or database row order. A failure stops new keys in the affected group from starting; independent groups continue. Cache writes, deletes, and grouped list reads share the same first-error policy. Later callback failures cannot replace the first observed error, and completed writes remain persisted. Rust waits for already-started callbacks before returning that error, while the upstream JavaScript promise rejects before those peers finish. This concurrency boundary does not promise identical JavaScript rejection timing.

Legacy double-stringified metadata is decoded for get, list, update and native verification responses. Get, update and verification await database repair. Lists pass the returned page's repairs to `advanced.background_tasks`, including an empty page when any registered configuration uses the database or database fallback. Without an application handler, the list waits for these repairs. Pure-secondary configurations decode responses without rewriting cache entries; a separate database configuration still enables the list's database repair attempt.

Metadata repair writes only to the database. A missing database row is a successful no-op. Each failed repair logs a warning and leaves the endpoint result unchanged, matching the upstream migration policy. Cache entries retain their original metadata until another operation replaces them. This exception does not suppress other database or cache errors. Custom stores should implement `ApiKeyStore::update_api_key_optional` to return `None` for a missing row; `update_api_key` retains its strict return contract.

`defer_updates` returns secondary-only usage results before writing the updated snapshot. It also defers expiration and exhausted-key deletion. Background failures are logged, matching the upstream policy for these operations. Database quota consumption remains synchronous. Installing the shared backend also enables [secondary session and verification storage](/docs/concepts/secondary-storage). Use the global session and verification configuration to retain database persistence. A configuration-specific `custom_storage` does not install a global backend.

A retained usage task resolves to the complete fresh storage record, including the stored `key` field, or `FieldValue::Null` if the fresh cache read is missing. The application background handler receives that internal record; public verification still returns its sanitized snapshot. Treat retained task values as credential-bearing data. Cleanup and metadata tasks resolve to `FieldValue::Undefined`.

### Named Configurations and Organization-Owned Keys

A plugin instance holds one or more configurations. Each is identified by its `config_id`, and clients select one by sending `configId`. Creation, lookup, update, and deletion use the `"default"` configuration when `configId` is absent. Listing without `configId` includes all registered configurations for the requested owner type. Register additional configurations with `configuration`:

```rust
use better_auth::plugins::api_key::{ApiKeyConfig, ApiKeyReferences};

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(OrganizationPlugin::new())
    .plugin(
        ApiKeyPlugin::builder()
            .prefix("sk_".to_string())
            .build()
            .configuration(ApiKeyConfig {
                config_id: "org".to_string(),
                references: ApiKeyReferences::Organization,
                prefix: Some("org_".to_string()),
                ..Default::default()
            }),
    )
    .build()
    .await?;
```

When a configuration sets `references: ApiKeyReferences::Organization`, its keys belong to an organization instead of a user:

- `create` and `list` require an `organizationId` (body field or query parameter respectively). `get`, `update`, and `delete` resolve the organization from the key itself.
- The caller must be a member of that organization and hold the matching `apikey` action (`create`, `read`, `update`, or `delete`) in the organization plugin's RBAC. The creator role is allowed every action. The default roles grant none, so applications grant them through custom roles; see [Organization RBAC](/docs/plugins/organization#rbac-role-based-access-control).
- The organization plugin must be registered, or requests fail with `ORGANIZATION_PLUGIN_REQUIRED`.

Every key carries `referenceId` (the owning user or organization id) and `configId` in its response.

## How It Works

### Key Generation

API keys are generated as random alphabetic strings (`[a-zA-Z]`) of the configured length. The key format is:

```
{prefix}{random_alpha_chars}
```

Only the SHA-256 hash of the key is stored in the database. The full key is returned only once during creation and cannot be retrieved later.

### Key Structure

Each API key has:

- **`start`**: First 6 characters of the full key including prefix (for UI identification)
- **`prefix`**: Optional prefix (e.g., `sk_`, `pk_`)
- **`enabled`**: Whether the key is active
- **`remaining`**: Usage quota (decremented on each use, `null` = unlimited)
- **`referenceId`**: Owner of the key: a user id, or an organization id for organization-owned configurations
- **`configId`**: The configuration the key was created under
- **`expiresAt`**: Optional expiration date (set via `expiresIn` in seconds)
- **Rate limiting**: Counter-based rate limits with configurable time window and max requests

## API Endpoints

The API Key plugin exposes 5 client-facing endpoints. All require an authenticated session.

| Endpoint | Method | Description |
|----------|--------|-------------|
| `/api-key/create` | POST | Create a new API key (returns key only once) |
| `/api-key/get` | GET | Get key metadata by ID (query param `id`) |
| `/api-key/list` | GET | List keys for the authenticated user or an organization (paginated) |
| `/api-key/update` | POST | Update key settings (body field `keyId`) |
| `/api-key/delete` | POST | Delete an API key (body field `keyId`) |

### Listing

`GET /api-key/list` returns a paginated envelope rather than a bare array:

```json
{
  "apiKeys": [ ... ],
  "total": 42,
  "limit": 20,
  "offset": 0
}
```

| Query parameter | Description |
|-----------------|-------------|
| `configId` | Configuration to list keys from; absent lists all registered configurations for the requested owner type |
| `organizationId` | Selects organization-owned keys; omit to list user-owned keys |
| `limit`, `offset` | Page window after storage selection; both fields are omitted when not sent |
| `sortBy` | API key field used for sorting before the adapter limit |
| `sortDirection` | `asc` (default) or `desc` |

Database-backed lists sort before applying `advanced.database.default_find_many_limit`. The public endpoint then deduplicates combined configuration groups, filters those rows, computes `total`, and applies the requested page window. As in Better Auth 1.7.6, five database records with a default limit of two produce `total: 2`. The adapter still performs a separate unrestricted count, and a count failure rejects the request. Secondary-storage cache hits use the complete cached key set; a database fallback caches only the rows returned by that database read.

<Callout type="warn">
The full `key` value is returned only during creation. Store it securely — it cannot be retrieved later.
</Callout>

<Callout type="info">
Fields like `permissions`, `remaining`, `refillAmount`, `refillInterval`, `rateLimitEnabled`, `rateLimitTimeWindow`, and `rateLimitMax` are server-only and cannot be set from HTTP client requests.
</Callout>

## Server-only Operations

The typed `create`, `update`, and `verify` operations resolve requestless runtime options before accessing storage. A dynamic base URL requires a configured fallback for these operations.

Use `auth.api_keys()?` to access the registered plugin and initialized context from trusted Rust code. The accessor returns a configuration error when `ApiKeyPlugin` is not registered.

```rust
use std::collections::HashMap;
use better_auth::plugins::ApiKeyPlugin;
use better_auth::server_api::{
    CreateKeyOptions, UpdateKeyOptions, VerifyKeyOptions,
};

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(ApiKeyPlugin::builder().build())
    .build()
    .await?;
let api_keys = auth.api_keys()?;

let issued = api_keys.create(user_id, CreateKeyOptions {
    name: Some("worker".to_owned()),
    permissions: Some(HashMap::from([
        ("nodes".to_owned(), vec!["heartbeat".to_owned()]),
    ])),
    ..Default::default()
}).await?;

let key = api_keys.verify(&issued.key, VerifyKeyOptions {
    config_id: Some("default".to_owned()),
    permissions: Some(HashMap::from([
        ("nodes".to_owned(), vec!["heartbeat".to_owned()]),
    ])),
}).await?;

api_keys.update(user_id, &key.id, UpdateKeyOptions {
    enabled: Some(false),
    ..Default::default()
}).await?;
```

Creation and update require the acting user's ID as a method argument. Organization configurations also require `organization_id` during creation and check the acting user's organization permissions. Verification requires the key, without a user session. No public HTTP verification endpoint is exposed.

Verification requires every listed action for every requested resource. Pass a `HashMap<String, Vec<String>>`; the upstream endpoint rejects connector objects before quota consumption. Numeric options use `f64` to preserve upstream fractional values.

Use `FieldUpdate::Unchanged`, `FieldUpdate::Clear`, or `FieldUpdate::Set(value)` for nullable updates to `permissions`, `metadata`, and `expires_in`. Other omitted update fields remain unchanged. For example:

```rust
use better_auth::server_api::FieldUpdate;

api_keys.update(user_id, &key.id, UpdateKeyOptions {
    expires_in: FieldUpdate::Clear,
    ..Default::default()
}).await?;
```

The lower-level `ApiKeyPlugin::create_key`, `update_key`, and `verify_api_key` methods remain available for callers that already manage an `AuthContext` and wire request DTOs.

Verification checks configuration, expiration, permissions, quota, and rate limits. A permission mismatch does not consume quota. In database and database-fallback modes, a rate-limit rejection consumes quota before returning `RATE_LIMITED`, matching Better Auth 1.7.6; `details.tryAgainIn` uses milliseconds. Expired keys and exhausted keys without a refill amount are deleted during verification.

`ApiKeyVerificationError` preserves credential rejections (`Validation`), application API errors caught during unscoped verification (`Rejected`), infrastructure failures (`Internal`), and errors outside the verification boundary (`Endpoint`). Use `into_response()` to reproduce the upstream server endpoint's response: caught failures return a `valid: false` envelope, while endpoint failures retain their original status and body. Some upstream rejection messages contain an error-code object instead of a string; `ApiKeyErrorMessage` preserves both forms. The successful result includes `reference_id`, `config_id`, permissions, and updated counters. It omits the plaintext key and stored hash. Construct a typed rejection with `ApiKeyValidationError::new(code)`. The public `code`, `message`, and `details` fields retain the typed rejection. Unscoped verification constructs a native API error when logging the rejection, then retains that error through response rendering. Logger changes to its body, including dynamic values and nested identities, remain visible in `into_response()`; serialization uses the captured body after logging.

Pass `config_id` when a route accepts credentials from one configuration. Without that field, lookup uses the default configuration's hashing setting, then validates against the configuration that issued the key.

### Delete Expired Keys

`delete_all_expired` implements the upstream `deleteAllExpiredApiKeys` server-only endpoint. It runs endpoint hooks and deletes database keys whose non-null `expiresAt` is earlier than the context's wall clock. Each call bypasses the automatic cleanup interval. The endpoint has no HTTP route, requires no user session, and does not delete secondary-storage cache entries.

```rust
use better_auth::server_api::NativeEndpointInput;

let result = auth.api_keys()?.delete_all_expired(NativeEndpointInput::default()).await?;
let success = result.model_property("success")?;
```

Use `NativeEndpointInput` to pass an original request, independently present headers, and native body or query values to endpoint hooks. An original request can resolve a dynamic base URL. The result is the complete `FieldValue`, so hook replacements, undefined properties, and original error objects retain their values and identities.

The default result is `{ success: true, error: null }`. A database failure is logged by the cleanup helper and still returns that result when logging succeeds. If this first Logger call throws, the endpoint logs the Logger error and returns `{ success: false, error }` with the original error object. If the second Logger call throws, the method propagates that error. These catches preserve the upstream policy; a successful response alone does not prove that database deletion succeeded.

Automatic cleanup shares one last-check timestamp across API Key plugin instances in the process, including instances with different databases. Like Better Auth 1.7.6, the cleanup helper skips a check when fewer than 10,000 wall-clock milliseconds have elapsed. Clock rollback also suppresses automatic cleanup until that interval is reached. The explicit endpoint bypasses the interval and refreshes the shared timestamp, including during rollback. The timestamp is published before database work; database and Logger failures do not restore its previous value.

The helper samples the deletion cutoff separately and passes it to `ApiKeyStore::delete_expired_api_keys_before`. Custom stores must implement this explicit-cutoff operation through their expiration field policy. The existing `delete_expired_api_keys` convenience method samples the current clock and delegates to the same operation. Memory live reads, SQL conversion and deletion statements, transactions, and quota updates retain their backend-specific behavior.

### Session Emulation

Enable `enable_session_for_api_keys` to authenticate user-owned keys through the configured headers. The plugin provides a virtual session to protected routes without creating a database session. Its hook answers both GET and POST requests to `/get-session`, matching upstream behavior. Organization-owned keys cannot create user sessions. Session emulation grants access as the key owner; it does not enforce the key’s resource permissions on each route. For scoped machine credentials, keep session emulation disabled and pass the required permissions to server-side verification.

### Numeric Storage

Better Auth accepts fractional quota, refill, and rate-limit values. Rust uses `f64` for those fields and `request_count`. The bundled migration converts existing PostgreSQL columns to double precision and rebuilds SQLite API key tables with real-valued columns, preserving existing keys. Applications that own their migrations must update the corresponding columns and model fields.

### Endpoint input validation

Create, update, and delete use the shared body schema before endpoint authentication. Plugin before hooks receive the raw body. The handler receives the validated body with unknown top-level fields removed. Create defaults `expiresIn` and `remaining` to null before the permissions callback runs. Error messages aggregate invalid fields in the upstream schema order.

Native creation and update preserve the distinction between omitted headers, explicit empty headers, and an original Request. A requestless call may supply its acting `userId`; a call with headers requires a valid session. An original Request forbids supplying `userId` on creation. The typed native API validates numeric constraints and preserves rejection of NaN and infinities before JSON serialization can turn them into null. Server-only verification validates the permissions record before consuming quota.

Creation leaves `permissions` undefined when neither the request nor the plugin supplies permissions. Database declaration defaults can then apply. Pure secondary storage bypasses declaration defaults and omits undefined permissions from cached JSON; the public response reports `permissions: null`. Store callers use `CreateApiKey.permissions: SchemaValue<Option<String>>` to distinguish omission from explicit null and encoded permissions.
