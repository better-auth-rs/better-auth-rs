Better Auth uses a plugin system to compose authentication features. Each plugin registers routes and can customize initialization and request handling. Use [SeaORM hooks](/docs/concepts/hooks) for database lifecycle operations.

## Built-in Plugins

### Core Plugins

| Plugin | Description |
|--------|-------------|
| `EmailPasswordPlugin` | Email/password and username sign-up/sign-in |
| `SessionManagementPlugin` | Session querying, listing, and revocation |
| `PasswordManagementPlugin` | Password reset and change flows |
| `EmailVerificationPlugin` | Email verification via tokens |
| `AccountManagementPlugin` | List and unlink linked accounts |

### Extended Plugins

| Plugin | Description | Docs |
|--------|-------------|------|
| `OAuthPlugin` | Social sign-in via Google, GitHub, Discord, and custom OAuth providers | [OAuth Plugin](/docs/plugins/oauth) |
| `CaptchaPlugin` | HTTP CAPTCHA checks with five providers | [CAPTCHA](/docs/plugins/captcha) |
| `TwoFactorPlugin` | Two-factor authentication with TOTP, OTP, and backup codes | [2FA Plugin](/docs/plugins/two-factor) |
| `OrganizationPlugin` | Multi-tenancy with organizations, members, invitations, and RBAC | [Organization Plugin](/docs/plugins/organization) |
| `AdminPlugin` | User management, banning, impersonation, and role management | [Admin Plugin](/docs/plugins/admin) |
| `ApiKeyPlugin` | API key creation, validation, rate limiting, and usage tracking | [API Key Plugin](/docs/plugins/api-key) |
| `PasskeyPlugin` | WebAuthn / FIDO2 passwordless authentication | [Passkey Plugin](/docs/plugins/passkey) |

## Registering Plugins

Plugins are added via the builder:

These examples assume you've already defined `AppAuthSchema`. If you want a complete setup from entity definitions through Axum mounting, start with the [Axum integration guide](/docs/integrations/axum).

```rust
let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(EmailPasswordPlugin::new().enable_signup(true))
    .plugin(SessionManagementPlugin::new())
    .plugin(PasswordManagementPlugin::new())
    .build()
    .await?;
```

## The AuthPlugin Trait

```rust
#[async_trait]
pub trait AuthPlugin<S: AuthSchema>: Send + Sync + std::any::Any {
    fn name(&self) -> &'static str;
    fn routes(&self) -> Vec<AuthRoute>;

    /// Called during build to initialize plugin state.
    async fn on_init(&self, ctx: &mut AuthInitContext<S>) -> AuthResult<()>;

    /// Called before core endpoints and plugin request handlers.
    async fn before_request(
        &self, req: &AuthRequest, ctx: &AuthContext<S>
    ) -> AuthResult<Option<BeforeRequestAction>>;

    /// Return Some(response) to handle the request, or None to continue.
    async fn on_request(
        &self, req: &AuthRequest, ctx: &AuthContext<S>
    ) -> AuthResult<Option<AuthResponse>>;

    /// Called after the response and session cookies are available.
    async fn after_request(
        &self, req: &AuthRequest, response: &mut AuthResponse, ctx: &AuthContext<S>
    ) -> AuthResult<()>;
}
```

`on_init`, `on_http_request`, `before_request`, and `after_request` have default no-op implementations. Plugins must implement `name`, `routes`, and `on_request`.

`on_http_request(&AuthRequest, &AuthContext<S>) -> AuthResult<Option<AuthResponse>>` runs only for HTTP calls, after rate limiting and before endpoint middleware and validation. Returning a response skips the endpoint and its `before_request` / `after_request` hooks. Native plugin API calls bypass this phase.

`before_request` hooks run for registered endpoints in plugin registration order. `ReplaceBody` replaces the request body and continues the hook chain. `InjectSession` supplies a session for the remaining hooks and route handler. `Respond` skips the endpoint and all after hooks. Unmatched paths and methods return an empty HTTP 404 after `on_http_request`, without endpoint hooks.

| Failure phase | HTTP behavior | Native behavior |
|---------------|---------------|-----------------|
| HTTP request hook or rate limiter | Return the original error to the transport | This phase does not run |
| Before hook | Skip the endpoint and after hooks; serialize API errors; return an empty 500 for ordinary errors | Return the original error |
| Endpoint | Run after hooks for API errors; stop immediately for ordinary errors | Apply the same hook order and preserve the final error |
| After hook | Continue later hooks after an API error; stop with an empty 500 after an ordinary error | Apply the same hook order and preserve the final error |

API errors preserve their public body and explicit response headers. `AuthResponse::is_api_error` distinguishes a returned response from a thrown API error with the same status. Use `replace_json` to replace the returned value while preserving the status and headers; this clears the API-error marker. Use `replace_returned` to supply a complete replacement response. Ordinary HTTP failures discard queued headers. Writes completed before an error remain committed unless the endpoint itself owns a transaction.

For native calls, `error.to_auth_response()` exposes `api_error_headers()` and `captured_headers()` separately. The first collection contains the API error's explicit headers. The second contains headers accumulated in endpoint context. A before-hook API error retains only explicit headers in its HTTP response, while native callers can also inspect the queued context headers. Endpoint and after-hook API errors accumulate cookies and later hook headers in dispatch order.

Call `BetterAuth::call_endpoint(method, path, EndpointInput)` from trusted server code to use the registered endpoint and its hooks. `EndpointInput.headers` distinguishes omitted headers from an explicitly empty collection. Native dispatch bypasses HTTP request hooks, rate limiting, media parsing, and origin checks; endpoint authentication and validation still apply.

For user and session creation or deletion, register `SeaOrmHooks` on `SeaOrmStore`. These hooks receive the active database transaction.

## AuthRoute

Routes are defined with a method, path, and operation ID (used as the OpenAPI `operationId`):

```rust
use better_auth::plugin::AuthRoute;
use better_auth::prelude::HttpMethod;

let routes = vec![
    AuthRoute::post("/my-endpoint", "handle_my_endpoint"),
    AuthRoute::get("/my-query", "handle_my_query"),
];
```

Paths are relative to the auth mount point (e.g., `/auth`).

## AuthContext

Plugins receive an `AuthContext` providing access to shared state:

```rust
pub struct AuthContext<S: AuthSchema> {
    pub config: Arc<AuthConfig>,
    pub database: Arc<dyn AuthStore<S>>,
    pub email_provider: Option<Arc<dyn EmailProvider>>,
    pub metadata: HashMap<String, serde_json::Value>,
}
```

| Method | Description |
|--------|-------------|
| `email_provider()` | Returns the email provider or an error if none configured |
| `set_metadata(key, value)` | Store plugin-specific metadata |
| `get_metadata(key)` | Retrieve plugin-specific metadata |
