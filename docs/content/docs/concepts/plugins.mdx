Better Auth uses a plugin system to compose authentication features. Each plugin registers routes and can customize initialization and request handling. Use [SeaORM hooks](/docs/concepts/hooks) for database lifecycle operations.

## Built-in Plugins

### Core Plugins

| Plugin | Description |
|--------|-------------|
| `EmailPasswordPlugin` | Email/password and username sign-up/sign-in |
| `UsernamePlugin` | Configurable username validation, normalization, availability, and sign-in |
| `SessionManagementPlugin` | Session querying, listing, and revocation |
| `PasswordManagementPlugin` | Password reset and change flows |
| `EmailVerificationPlugin` | Email verification via tokens |
| `AccountManagementPlugin` | List and unlink linked accounts |

### Extended Plugins

| Plugin | Description | Docs |
|--------|-------------|------|
| `OAuthPlugin` | Social sign-in via Google, GitHub, Discord, and custom OAuth providers | [OAuth Plugin](/docs/plugins/oauth) |
| `CaptchaPlugin` | HTTP CAPTCHA checks with five providers | [CAPTCHA](/docs/plugins/captcha) |
| `TwoFactorPlugin` | Two-factor authentication with TOTP, OTP, and backup codes | [2FA Plugin](/docs/plugins/two-factor) |

## Registering Plugins

Plugins are added via the builder:

These examples assume you've already defined `AppAuthSchema`. If you want a complete setup from entity definitions through Axum mounting, start with the [Axum integration guide](/docs/integrations/axum).

```rust
let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(EmailPasswordPlugin::new().enable_signup(true))
    .plugin(SessionManagementPlugin::new())
    .plugin(PasswordManagementPlugin::new())
    .build()
    .await?;
```

## The AuthPlugin Trait

```rust
#[async_trait]
pub trait AuthPlugin<S: AuthSchema>: Send + Sync + std::any::Any {
    fn name(&self) -> &'static str;
    fn routes(&self) -> Vec<AuthRoute>;

    /// Called during build to initialize plugin state.
    async fn on_init(&self, ctx: &mut AuthInitContext<S>) -> AuthResult<()>;

    /// Called before core endpoints and plugin request handlers.
    async fn before_request(
        &self, req: &AuthRequest, ctx: &AuthContext<S>
    ) -> AuthResult<Option<BeforeRequestAction>>;

    /// Return Some(response) to handle the request, or None to continue.
    async fn on_request(
        &self, req: &AuthRequest, ctx: &AuthContext<S>
    ) -> AuthResult<Option<AuthResponse>>;

    /// Inspect the completed HTTP router response.
    async fn on_http_response(
        &self, req: &AuthRequest, response: &mut AuthResponse, ctx: &AuthContext<S>
    ) -> AuthResult<Option<AuthResponse>>;

    /// Called after the response and session cookies are available.
    async fn after_request(
        &self, req: &AuthRequest, response: &mut AuthResponse, ctx: &AuthContext<S>
    ) -> AuthResult<()>;
}
```

`on_init`, `on_http_request`, `on_http_response`, `before_request`, and `after_request` have default no-op implementations. Plugins must implement `name`, `routes`, and `on_request`.

### Register adapter field policies

Call `AuthInitContext::register_model_fields(EntityRole, UserConfig)` during `on_init` to register fields for User, Session, Account, or Verification. Use `better_auth_core::store::schema::EntityRole`. Later plugins replace earlier declarations for the same field. Application declarations retain precedence at the adapter; plugin declarations retain precedence in existing endpoint parsers. `register_user_fields` remains available for user-only registration.

Use `register_model_schema(role, model_name, fields)` when a native declaration also supplies a model name. Omitted or empty names reset the name to the logical model name. Field-only registration resets an earlier name override to the adapter's native table mapping. Native and custom model aliases resolve in one declaration order; logical names always take precedence. Replacing a declaration preserves its first position. Runtime registration does not rename physical tables or create migrations.

Call `AuthInitContext::register_custom_model(name, model_name, fields)` to declare a custom logical model for runtime reference resolution. `model_name` is an optional physical name; omitted or empty names use the logical name. Repeated declarations merge fields and replace the physical name while preserving declaration order. Logical names take precedence over physical aliases. Native logical names are reserved and cannot be registered as custom models. The supported native field policies are listed below. Adapters can read the declarations through `ModelFields::custom_models()`; the application adapter must provide custom operations and migrations. These declarations do not turn OpenAPI metadata into storage configuration or add generic CRUD to the native Store.

Supported non-core registered fields also enter OpenAPI components through their final adapter policies. These policies replace conflicting explicit model metadata. The builder preserves each field's first declaration position relative to other plugins and builtin models, including core fields that mix runtime registration and explicit metadata. Both `register_user_fields` and successful `register_model_fields` calls retain those names for schema generation. Generated field maps apply JavaScript array-index enumeration after declaration order is resolved; ordinary native positions and policy precedence remain unchanged. Keep `AuthPlugin::openapi` for unregistered documentation fields, models, and routes; do not repeat registered field declarations. Within one plugin, explicit metadata retains its field order and registered names absent from metadata follow it. Schema generation does not invoke field callbacks or change adapter callback order.

API Key, Passkey, DeviceCode, TwoFactor, JWK, and WalletAddress accept complete native replacement declarations and additional fields through the same `UserConfig` merge. Replacing a field replaces every declaration attribute while preserving its first declaration position. Their native plugins register complete schemas at their initialization position, so a later native plugin restores its declarations without moving earlier fields. Shared record and patch conversion handles defaults, `on_update`, synchronous or asynchronous transforms, physical mappings, and references. Output projection precedes runtime `SchemaValue<T>` construction. Adapter-owned ID conversion runs at its existing schema position and retains runtime policy changes caused by preceding callbacks. Standalone Store calls retain native defaults without plugin initialization.

`UserFieldConfig` preserves `index`, `sortable`, and `bigint`, including omission and explicit false. `UserFieldReference::on_delete` uses the shared `FieldReferenceAction` enum; omission selects `Cascade`. Replacing a declaration clears omitted metadata from the previous declaration. Configure matching CLI schema attributes when generating database columns; runtime registration does not alter existing tables. `FieldValidators` retains input and output validator declarations. Public parsing invokes only the input validator; adapter projection does not execute validators.

DeviceCode also accepts declared additional fields through `DeviceCode.additional_fields`, `CreateDeviceCode.additional_fields`, and `UpdateDeviceCode.additional_fields`. SeaORM maps each declaration to an actual typed column; generate columns with `deviceCode.additionalFields` in the CLI schema configuration. Complete native replacement declarations and shared physical columns follow the same field policies. Create, update, both code lookups, conditional updates, claim, and consumption apply the registered policies. Successful boolean writes await output conversion before returning; an output error propagates after the write. A condition that matches no row runs no output callback. Input transforms run before storage locks, and output transforms run after the stored row is returned. DeviceCode retains sealed physical ownership bindings independently of output values. `AuthTransaction` exposes the same DeviceCode operations.

Passkey create, lookup, list, name update, and authentication update use this shared record boundary. Memory reads each field from the selected row before its output callback; SeaORM projects physical values from the query snapshot. Generate Native or Legacy columns with `passkey.additionalFields`. See [Passkey adapter fields](/docs/plugins/passkey#adapter-field-policies) for raw record APIs, Legacy internal fields, and public input boundaries.

Typed Passkey and API Key creation capture their timestamps before awaiting input policies. The adapter generates the ID at its schema position. Output conversion runs after persistence.

Organization and Team accept the same field policies as `OrganizationConfig::schema`. The Organization plugin's own declaration participates at its registration position. Later declarations replace the complete field policy and retain the field's schema position. A later Organization plugin declaration restores native built-in policies unless its configuration replaces them. SeaORM validates the final policies against the selected typed columns. Organization route validation and visibility still use `OrganizationConfig::schema`.

JWK record CRUD and lists use the shared field boundary through `JwksStore`. Ordinary callers can keep using `CreateJwk`; native runtime fields preserve dynamic values and `Jwk.additional_fields` holds extensions. Memory reads every field from the live selected row; SeaORM retains its query snapshot. Generate matching columns with `jwks.additionalFields`. Custom JWT adapter callback results are not transformed again. JWT key selection and cryptographic consumption remain separate from field conversion, and public JWKS responses do not expose additional fields.

WalletAddress record CRUD and both address lookup forms use the same shared policies through `WalletStore`. Ordinary callers can keep using `CreateWalletAddress`; native selectors use `get_wallet_address_value`. Generate matching columns with `walletAddress.additionalFields`. SIWE consumes the selected native owner and builds response address and chain values from the verified message. `AuthTransaction` exposes WalletStore through the active Memory, SeaORM, or Secondary transaction. A direct output error preserves the completed write; an enclosing transaction can roll back that write.

All six model migrations use shared declaration, mapping, and reference resolution. Application-owned SeaORM table and column attributes remain supported. Registration controls adapter conversion; registration does not install HTTP validators or change route visibility. Synchronous public-input parsing still rejects asynchronous input transforms.

API Key native replacements and additional fields use the same complete record and update patch policies. Runtime values and public views preserve dynamic values; public responses omit the key hash. Generate matching columns with `apikey.additionalFields`. Usage writes with a set patch execute the complete schema; a plain quota decrement skips input policies. Each successful returned row runs output policies. Secondary-only operations and fallback cache hits bypass adapter field policies. Database writes and fallback misses use the adapter; fallback caches retain the projected record. See [API Key storage](/docs/plugins/api-key#storage).

An application plugin can keep a typed repository for its own tables and share the repository through `AuthInitContext::extensions`. Unknown tables do not receive Better Auth field policies or a generic CRUD interface from this registration API.

`on_http_request(&AuthRequest, &AuthContext<S>) -> AuthResult<Option<AuthResponse>>` runs only for HTTP calls, after rate limiting and before endpoint middleware and validation. Returning a response skips the endpoint and its `before_request` / `after_request` hooks. Native plugin API calls bypass this phase.

`before_request` hooks run for registered endpoints in plugin registration order. `ReplaceBody` replaces the request body and continues the hook chain. `InjectSession` supplies a session for the remaining hooks and route handler. `Respond` skips the endpoint and all after hooks when the response contains an object, array, Date, binary value, Blob, API error, or explicit HTTP response. Primitive native returns continue the hook chain. The endpoint starts with a fresh response-header accumulator when before hooks continue. Unmatched paths and methods return an empty HTTP 404 after `on_http_request`, without endpoint hooks. HTTP response hooks still run.

Use `InjectNativeSession` in a trusted server hook to supply a complete `NativeSessionData`, including native User values and object identities. The dispatcher stores the value in the private request snapshot. HTTP JSON and cookies cannot set that snapshot. Later Session injection replaces the earlier source. Cached and stateless native Session reads can reuse the snapshot; authoritative reads backed by database or secondary storage clear the snapshot and read current storage. Cookie validation remains independent of this trusted hook action.

`on_http_response(&AuthRequest, &mut AuthResponse, &AuthContext<S>) -> AuthResult<Option<AuthResponse>>` runs after HTTP routing, including route misses and body-decoding errors. Hooks run in registration order and may mutate the response. Returning `Some(response)` replaces the response and stops the chain. Disabled paths, early HTTP request responses, and native calls bypass this hook. `WithCallbacks` forwards this hook to its wrapped plugin.

| Failure phase | HTTP behavior | Native behavior |
|---------------|---------------|-----------------|
| HTTP request hook or rate limiter | Return the original error to the transport | This phase does not run |
| Before hook | Skip the endpoint and after hooks; serialize API errors; return an empty 500 for ordinary errors | Return the original error |
| Endpoint | Run after hooks for API errors; stop immediately for ordinary errors | Apply the same hook order and preserve the final error |
| After hook | Continue later hooks after an API error; stop with an empty 500 after an ordinary error | Apply the same hook order and preserve the final error |

API errors preserve their public body and explicit response headers. `AuthResponse::is_api_error` distinguishes a returned response from a thrown API error with the same status. Use `replace_json` to replace the returned value while preserving the status and headers; this clears the API-error marker. Use `replace_returned` to supply a complete replacement response. A native undefined return preserves the current response and merges the returned headers. Ordinary HTTP failures discard queued headers. Writes completed before an error remain committed unless the endpoint itself owns a transaction.

`AuthResponse.body` retains `ResponseBody::Native(FieldValue)`, `Binary(Arc<[u8]>)`, or `Blob(Arc<ResponseBlob>)` until HTTP materialization. Construct these values with `AuthResponse::native`, `binary`, or `blob`. `AuthResponse::json` converts a Serde value to a native `FieldValue` and returns `AuthResult<AuthResponse>`. `text` and `html` construct explicit HTTP responses. `Empty` represents a null HTTP body; `Bytes(Vec<u8>)` represents an explicit or materialized body, including a present body with zero bytes. Binary and Blob clones retain their shared identity.

Use `body.field_value()?` to read native fields and `body.json()?` to observe their JSON representation. Neither observation replaces the native value. Binary and Blob observations return a type error; read their bytes explicitly. `body.bytes()?` and `body.into_bytes()?` produce HTTP body bytes, so native strings produce unquoted text. A replacement changes the current body for later hooks and native callers. `AuthResponse::is_native` identifies a native result; `is_json` checks the effective HTTP MIME type without decoding the body.

Native constructors defer automatic `Content-Type` generation. Endpoint after hooks and native callers see only explicitly supplied headers. `AuthResponse::into_http_response() -> AuthResult<AuthResponse>` materializes bytes and selects the MIME type: nonempty strings use `text/plain`, binary values use `application/octet-stream`, and Blobs use their normalized MIME type or `application/octet-stream`. Other native values use `application/json`, including empty strings. The inferred MIME type replaces an endpoint-supplied value. HTTP response hooks run after materialization and can replace the header. Materialization follows the pinned Bun Response constructor: status 101 and statuses 200–599 are accepted, including present bodies at 204, 205, and 304. Other status values return `AuthError::RangeError`. Native undefined and `Empty` remain null bodies. The HTTP transport applies its own wire restrictions after construction.

`AuthResponse.status` is the effective HTTP status. `native_status()` distinguishes an absent native status property, an own-undefined property, and an explicit status code through `NativeResponseStatus`. Pass `None` to a native constructor for an unset status; an explicit number retains that selection. Use `AuthRequest::set_response_status` or `EndpointContext::set_status` inside the endpoint to select its status. Before and after hooks have separate status contexts. An after-hook replacement retains the endpoint status. `api_error_status()` returns the error's own status before an endpoint override.

The HTTP boundary removes better-call's excluded request and transport headers from the endpoint accumulator, including `Authorization`, `Cookie`, `Host`, and `Content-Length`. Native results retain those accumulator headers. An explicit response also retains its own headers through `AuthResponse::explicit_response_headers()`. HTTP materialization preserves those own headers, then merges the filtered accumulator; safe queued headers overwrite matching own headers, and cookies retain own-before-queued order. Response headers such as `WWW-Authenticate` remain available in both modes.

`AuthRequest::input_field_value()` reads the current endpoint body without JSON conversion. `input_body()` and `body_as_json()` are explicit JSON observations. Native field dispatch preserves values through before-hook merges and schema validation; `BeforeRequestAction::ReplaceBody` introduces replacement JSON bytes. The original HTTP Request retains its transport bytes.

`RequestHookContext.body`, `EndpointContext.body`, and retained endpoint contexts use `FieldValue`. `FieldValue::Undefined` represents an omitted body. Native hooks preserve Date objects, own undefined properties, unpaired UTF-16 string units, and object references. Use `.json()?` when a consumer requires JSON; conversion errors propagate. `EndpointContext::new` and `native` accept native fields, so import an existing JSON value with `FieldValue::from_json(value)?`. `RequestHookContext::from_request` returns `AuthResult` and imports only an already parsed body. `with_request_hook_context` accepts a future that returns `AuthResult` and propagates initialization errors.

For native calls, `error.to_auth_response()` exposes `api_error_headers()` and `captured_headers()` separately. The first collection contains the API error's explicit headers. The second contains headers accumulated in endpoint context. A before-hook API error retains only explicit headers in its HTTP response, while native callers can also inspect the queued context headers. Endpoint and after-hook API errors accumulate cookies and later hook headers in dispatch order.

Call `BetterAuth::call_endpoint(method, path, EndpointInput)` from trusted server code to use the registered endpoint and its hooks. `EndpointInput.headers` distinguishes omitted headers from an explicitly empty collection. Native dispatch bypasses HTTP request hooks, rate limiting, media parsing, and origin checks; endpoint authentication and validation still apply.

For user and session creation or deletion, register `SeaOrmHooks` on `SeaOrmStore`. These hooks receive the active database transaction.

## AuthRoute

Routes are defined with a method, path, and operation ID (used as the OpenAPI `operationId`):

```rust
use better_auth::plugin::AuthRoute;
use better_auth::prelude::HttpMethod;

let routes = vec![
    AuthRoute::post("/my-endpoint", "handle_my_endpoint"),
    AuthRoute::get("/my-query", "handle_my_query"),
];
```

Paths are relative to the auth mount point (e.g., `/auth`).

## AuthContext

Plugins receive an `AuthContext` providing access to shared state:

```rust
pub struct AuthContext<S: AuthSchema> {
    pub config: Arc<AuthConfig>,
    pub database: Arc<dyn AuthStore<S>>,
    pub email_provider: Option<Arc<dyn EmailProvider>>,
    pub metadata: HashMap<String, serde_json::Value>,
}
```

| Method | Description |
|--------|-------------|
| `email_provider()` | Returns the email provider or an error if none configured |
| `set_metadata(key, value)` | Store plugin-specific metadata |
| `get_metadata(key)` | Retrieve plugin-specific metadata |


### Raw and validated endpoint queries

`AuthRequest.query` and native `EndpointInput.query` use `Option<serde_json::Value>`. `None` preserves omitted native input. `Some(Value::Null)` preserves explicit null. HTTP requests use an object, and repeated URL query names become ordered arrays. Bracketed names remain literal names.

Register a pure validator with `AuthRoute::query_validator` when an endpoint has a query schema. The shared dispatcher runs all before hooks before query validation. Endpoint middleware and the handler receive the validated query in a separate request scope. After hooks receive the original query, including unknown fields, even when validation fails. The original HTTP Request URL and body bytes remain available to callbacks.

Native query input is independent of an optional original Request. Supplying an original Request does not import the Request URL query. Use `Some(serde_json::json!({...}))` for explicit native query input.


### Body validation and before-hook input changes

`AuthRoute::body_validator` accepts a cloneable callback that can capture an instance's schema. Register the callback once when constructing the route. The callback receives decoded endpoint input and returns `ValidatedBody`. The result contains the native field projection for callbacks and a typed value for the handler. Read the typed value with `AuthRequest::validated_body`; use `input_field_value` to read the native projection or `input_body` for a JSON observation. The dispatcher validates body before query, after all before hooks and before endpoint middleware. After hooks retain the original endpoint input when validation returns an API error.

The `impl_auth_plugin!` route declaration accepts `body = validator` and `query = validator` after the handler name. These validators use the same shared dispatch boundary as the `AuthRoute` builder methods.

Use `AuthRoute::require_headers(true)` or append `require_headers = true` to the macro route declaration when an endpoint requires headers. The dispatcher checks headers after body and query validation, before endpoint middleware. Native callers must supply `EndpointInput.headers`; an explicitly empty collection satisfies this requirement, while an original Request alone does not. Before and after hooks retain the raw endpoint input when header validation fails.

`BeforeRequestAction::MergeContext` returns an `EndpointInputPatch` for body or query. The dispatcher accumulates these changes and applies them after every before hook completes. Object fields merge recursively, arrays replace previous arrays, and null patch values leave existing input unchanged. Use `ReplaceBody` only when the plugin must replace raw bytes immediately for subsequent hooks. Validated input never changes the original Request bytes.

The shared body boundary currently covers email signup/sign-in, password reset requests and completion, password changes and verification, sign-out, and OAuth callbacks. Other plugin handlers retain their existing parsers until their route schemas are migrated.
