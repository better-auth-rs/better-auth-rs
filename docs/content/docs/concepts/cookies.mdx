Better Auth uses HTTP cookies to persist session tokens in the browser. This page explains how cookies are configured and the security implications of each setting.

Configure names and attributes through `AuthConfig.advanced`; `SessionConfig` controls session lifetime and caching. The former `SessionConfig.cookie_name`, `cookie_secure`, `cookie_http_only`, and `cookie_same_site` fields have been removed. Use a `CookieOverride` entry in `advanced.cookies`, `advanced.use_secure_cookies`, and global or per-cookie attributes instead.

The resolver applies default attributes, `advanced.default_cookie_attributes`, caller attributes, then the logical cookie entry’s attributes from `advanced.cookies`. `cookie_prefix` changes the default `better-auth` prefix. Per-cookie names replace that default name. Secure policy adds `__Secure-` independently of attribute overrides. The policy comes from `use_secure_cookies`, a fixed dynamic protocol, a static URL scheme, or the production environment. A dynamic incoming HTTPS URL does not change the initial cookie policy unless cross-subdomain cookies trigger per-request resolution.

Serialization enforces `Secure` for `__Secure-` and `__Host-` names. A `__Host-` name also forces path `/` and removes the domain. Session issuance replaces the configured token-cookie `Max-Age` with the session lifetime, or omits it for a browser-session login. Cache cookies retain their own effective `Max-Age`.

The shared HTTP writer emits attributes in Better Call order: `Max-Age`, `Domain`, `Path`, `Expires`, `HttpOnly`, `Secure`, `SameSite`, then `Partitioned`. Missing attributes are omitted. Session tokens, OAuth state, application cookies, cache chunks, expiration headers, and LastLogin use this writer.

Set `CookieAttributes.partitioned = Some(true)` for partitioned cookies. The existing global, caller, and named-cookie precedence applies; explicit false replaces an earlier true value. Session cookies, application cookies, cache chunks, expiration headers, and LastLogin cookies retain the resolved attribute. Rust retains the cookie crate’s partitioned policy and always emits `Secure` with `Partitioned`. The Better Call serializer bundled with Better Auth 1.7.6 changes its options object after writing the Secure attribute, so that mutation timing is not reproduced. The normal compatibility contract sets `secure: true`. Telemetry and TestUtils browser-cookie exports omit partitioned metadata, matching their upstream projections.

Set `advanced.cross_sub_domain_cookies = Some(CrossSubDomainConfig { enabled: Some(true), ..Default::default() })` to derive the domain from each resolved URL. An explicit domain stays fixed. Omitted or false `enabled` disables sharing, even when a domain is configured. When sharing is enabled, static initialization without a URL or explicit cross-subdomain domain fails; setting an unrelated cookie attribute domain does not satisfy that requirement. Cache chunks inherit their parent cookie attributes during writing and deletion.

Use `config.auth_cookie("session_token", CookieAttributes::default())` to inspect the resolved name and attributes. Application cookies can use `context.create_auth_cookie` with their logical name and caller attributes.

HTTP serialization checks the effective `Max-Age` before rounding. Values above 34,560,000 seconds, including positive infinity, return an ordinary runtime error. Negative values, negative infinity, and `NaN` omit `Max-Age`; zero emits `Max-Age=0`. Configuration resolution remains infallible because issuance or explicit expiration can replace an attribute before serialization.

Set `CookieAttributes.expires` to an absolute `chrono::DateTime<Utc>` to include `Expires`. The existing global, caller, and per-cookie precedence applies. The writer compares the original millisecond date against the current clock and rejects dates more than 400 days in the future, after checking `Max-Age`. HTTP formatting uses whole seconds. Explicit expiration remains present when `Max-Age` is omitted or changed to zero, including during clearing and chunk cleanup. No `Expires` value is derived from `Max-Age`.

The public issuance and single-cookie clearing helpers return `AuthResult<String>`. `create_session_cookies` and `create_clear_chunked_cookies` return `AuthResult<Vec<String>>`. Propagate those errors with `?`. Session issuance and aggregate clearing publish each completed cookie operation before attempting the next. A later failure retains already queued headers; failed session issuance does not publish `newSession`. The endpoint's existing error policy determines the final HTTP response. `clear_chunked_cookie` and `better_auth_api::plugins::helpers::delete_session_cookies` return `AuthResult<()>` and accept an optional response-header destination for after hooks; omission writes to the request's response scope.

`render_cookie(value, &resolved_cookie)` is the shared checked writer for an already encoded value. `session_cookie_template` returns `AuthResult<cookie::Cookie>` because date conversion can fail; the template does not check the 400-day limit. Configuration resolution also performs no lifetime check. LastLogin applies its callback veto before serialization and preserves explicit expiration while replacing `Max-Age` and `HttpOnly`. LastLogin retains Rust's existing stronger `Secure` and `Path` settings inherited from the original session name's `__Secure-` and `__Host-` prefixes; pinned Better Auth instead inherits unresolved attributes. The final cookie name controls Domain removal. Telemetry exports a configured global expiration as a UTC millisecond string. TestUtils browser-cookie metadata continues to derive expiration from `Max-Age` and ignores the explicit date.

`create_cookie` accepts its lifetime as `f64` seconds. `create_session_like_cookie` and `create_session_cookie_with_max_age` accept `Option<f64>`. Keep fractional seconds when passing a `chrono::Duration` with `as_seconds_f64()`. Session issuance and renewal preserve this precision: 34,560,000 seconds is allowed, 34,560,000.25 seconds returns an error, and 300.75 seconds emits `Max-Age=300`. Browser-session issuance omits `Max-Age` and does not validate the unused persistent lifetime. The stored session deadline remains independent of HTTP cookie rounding.

## Response Cookies

`Headers::get_all("set-cookie")` returns every cookie in response order. Ordinary writes retain repeated names. A client must apply each entry in order, so the final value for a cookie determines the browser state.

Explicit expiration removes earlier entries for the cookie name and its chunks before adding the expiration header. Session revocation and Two Factor challenges use this operation to keep discarded credentials out of response headers. A raw `Max-Age=0` header remains an ordinary write. Custom plugin expiration can call `remove_set_cookie_entries(request, Some(&mut response.headers), name)` from `better_auth_core::utils::cookie_utils` before appending its expiration header.

`delete_session_cookies(request, config, skip_dont_remember, response_headers)` is the shared aggregate operation in `better_auth_core::utils::cookie_utils`, also available through the existing plugin helper. `SessionManager::clear_cookies` uses the same operation. It expires the token and session base first, then the optional account base and its incoming entries, optional OAuth state, incoming session entries, and finally the remember marker unless skipped. Incoming entries retain their first-occurrence order. An incoming base cookie receives another clearing header during that entry phase; this header does not replace the earlier base expiration. Direct cache clearing distinguishes existing-entry cleanup from base expiration: disabling cache cleans only incoming entries, base expiration removes earlier queued family headers and emits only the base, and account cleanup performs both actions in order. The public header constructors keep their separate contracts.

## Default Cookie Settings

By default, Better Auth sets session cookies with the following attributes:

| Attribute | Default | Description |
|-----------|---------|-------------|
| **Name** | `better-auth.session_token` | Cookie name |
| **Path** | `/` | Available on all paths |
| **Secure** | Derived from `base_url` | Enabled for HTTPS, disabled for HTTP |
| **HttpOnly** | `true` | Not accessible via JavaScript |
| **SameSite** | `Lax` | CSRF protection with top-level navigation support |

## Configuration

Configure cookie behavior through `AuthConfig`:

```rust
use better_auth::AuthConfig;
use better_auth::config::SameSite;
use chrono::Duration;

let mut config = AuthConfig::new("your-secret-key-at-least-32-chars");
config.advanced.cookies.get_or_insert_default().entry("session_token".into()).or_default().name = Some("my-app.session".into());
config.advanced.use_secure_cookies = Some(true);
config.advanced.default_cookie_attributes.http_only = Some(true);
config.advanced.default_cookie_attributes.same_site = Some(SameSite::Lax);
config.session.expires_in = Some(Duration::hours(24 * 7)); // 7 days
```

## Cookie Attributes

### Secure

When `true`, the cookie is only sent over HTTPS connections. This prevents session tokens from being transmitted in plaintext.

```rust
config.advanced.use_secure_cookies = Some(true);
```

<Callout type="warn">
Always set `Secure: true` in production. Only disable it for local development over HTTP.
</Callout>

### HttpOnly

When `true`, the cookie cannot be accessed by JavaScript (`document.cookie`). This prevents XSS attacks from stealing session tokens.

```rust
config.advanced.default_cookie_attributes.http_only = Some(true);
```

Always keep this enabled unless you have a specific reason to access the session token from JavaScript.

### SameSite

Controls when the cookie is sent with cross-site requests:

| Value | Behavior |
|-------|----------|
| `Strict` | Cookie only sent for same-site requests. Most secure but may break OAuth redirects. |
| `Lax` | Cookie sent for same-site requests and top-level navigations (GET only). Recommended default. |
| `None` | Cookie sent for all requests. Requires `Secure: true`. Use for cross-origin API access. |

```rust
use better_auth::config::SameSite;

// Recommended for most applications
config.advanced.default_cookie_attributes.same_site = Some(SameSite::Lax);

// For cross-origin API access (requires Secure: true)
config.advanced.default_cookie_attributes.same_site = Some(SameSite::None);
```

### Expiration

Persistent session cookies use `Max-Age` from the configured session lifetime. The HTTP serializer does not derive an `Expires` attribute from `Max-Age`.

```rust
use chrono::Duration;

// Session and cookie expire after 7 days
config.session.expires_in = Some(Duration::hours(24 * 7));
```

## Cookie Format

The session cookie is set via the `Set-Cookie` HTTP header:

```
Set-Cookie: better-auth.session_token=session_abc123.signature; Max-Age=604800; Path=/; HttpOnly; Secure; SameSite=Lax
```

## Cross-Origin Usage

If your frontend and backend are on different origins, you need to:

1. Set `SameSite::None` and `Secure: true` on the cookie
2. Configure CORS to allow credentials:

This example assumes you've already defined `AppAuthSchema`. If you want a complete setup from entity definitions through Axum mounting, start with the [Axum integration guide](/docs/integrations/axum).

```rust
use better_auth::CorsConfig;

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .cors(
        CorsConfig::new()
            .allowed_origin("https://frontend.example.com")
            .allow_credentials(true)
    )
    .build()
    .await?;
```

3. Include credentials in frontend requests:

```javascript
fetch('https://api.example.com/auth/get-session', {
  credentials: 'include' // Send cookies cross-origin
});
```

## Alternative: Bearer Token

Enable Bearer transport for mobile apps or API clients:

```rust
use better_auth::config::BearerConfig;

config.session.bearer = Some(BearerConfig::default());
```

Then send the raw token returned by sign-in or the signed token returned in `set-auth-token`:

```http
Authorization: Bearer session_abc123...
```

A valid Bearer token takes precedence over the signed session cookie. Set `BearerConfig { require_signature: true }` to require a signed Bearer token. Without Bearer configuration, session authentication uses the signed cookie.

Optional [cookie caching](/docs/authentication/sessions#cookie-cache) stores signed or encrypted session data in `better-auth.session_data`. The cache requires the matching session-token cookie.

Cookie attributes accept fractional `max_age` seconds, for example `Some(3600.5)`. The resolver preserves that value through browser-cookie exports and cache issuance. HTTP `Max-Age` is an integer and floors the resolved value. The order remains global defaults, caller attributes, then per-cookie overrides. Session-token issuance supplies its effective session lifetime after the resolved attributes, as upstream does; TestUtils browser exports use the resolved cookie lifetime.

Session and account cache JWT/JWE issuance preserves fractional lifetimes. Authenticated cache reads retain millisecond precision. The existing cryptographic validators, algorithm restrictions, clock tolerance, and session binding checks are unchanged. The JWT dependency still applies its own NumericDate rounding during validation; subsecond expiry-boundary equivalence is not established by the ordinary future-cookie contracts.
