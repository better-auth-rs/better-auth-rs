## User Entity

Authentication reads application-owned user entities through `AuthUser`. Public responses use `UserView` and the active user schema.

| Field | Type | Description |
|-------|------|-------------|
| `id` | `String` | UUID primary key |
| `name` | `Option<String>` | Display name |
| `email` | `Option<String>` | Email address (unique) |
| `emailVerified` | `bool` | Whether email is verified |
| `image` | `Option<String>` | Profile image URL |
| `username` | `Option<String>` | Unique username |
| `displayUsername` | `Option<String>` | Case-preserved display name |
| `role` | `Option<String>` | User role |
| `banned` | `bool` | Whether user is banned |
| `banReason` | `Option<String>` | Ban reason |
| `banExpires` | `Option<DateTime>` | Ban expiration |
| `twoFactorEnabled` | `bool` | 2FA status |
| `metadata` | `serde_json::Value` | Internal application data; not returned by default |
| `createdAt` | `DateTime` | Creation timestamp |
| `updatedAt` | `DateTime` | Last update timestamp |

## Application User Fields

Register application fields in `AuthConfig.user.additional_fields`. Add matching fields to the application-owned user entity and apply a database migration. `AuthEntity` writes these fields in the same insert or update as the core user fields. `field_name` selects the entity's Serde serialization name; the public API continues to use the configuration key.

```rust
use better_auth::config::{UserFieldConfig, UserFieldType};
use serde_json::json;

config.user.additional_fields.insert("department".into(), UserFieldConfig {
    field_type: UserFieldType::String,
    required: Some(true),
    ..Default::default()
});
config.user.additional_fields.insert("internalCode".into(), UserFieldConfig {
    input: false,
    returned: false,
    default_value: Some(json!("unassigned")),
    ..Default::default()
});
```

`required: Some(true)` rejects missing public creation input without a default. `None` and `Some(false)` keep user fields optional; Organization routes use a different creation requirement, described in the [Organization guide](/docs/plugins/organization). Updates leave missing fields unchanged. `input: false` rejects truthy client values; during creation, a configured default replaces supplied values. `returned: false` hides the field from public user responses, session caches, and JWT user claims. Administrator routes can set configured fields without public input restrictions. Application metadata and permissions are not rewritten by user projection.

Use `validator` for synchronous input validation or normalization. The validator returns `AuthResult<Value>`; a failure becomes `VALIDATION_ERROR`. Use `default_value_fn` for dynamic creation defaults. Use `on_update` to produce a value when a database update omits the field. Use `input_transform` and `output_transform` for transformations. Transform callbacks take and return `Option<Value>`: `None` means undefined, while `Some(Value::Null)` means explicit null.

As in the upstream adapter, public input transforms run at both the route and storage boundaries. A validator replaces the route transform, but the storage transform still runs. Missing optional fields reach the storage input transform during creation. Database reads apply output transforms once; cache reads preserve the transformed values. Date fields use RFC 3339 strings and normalize to millisecond UTC timestamps. The entity column types determine storage representation for strings, numbers, booleans, JSON, arrays, and enums. An enum declaration alone does not validate allowed values; configure a validator when validation is required.

Plugin fields are projected from the active plugin schema. Disabling Anonymous, Phone Number, Username, Admin, or Two Factor hides stored plugin fields on database reads. An existing signed session cache preserves its previous plugin fields until expiry or a cache version change, matching upstream. Current `returned: false` restrictions apply even to existing caches. Change `session.cookie_cache.version` when a configuration change must invalidate cached user shapes immediately.

Custom stores must apply `UserConfig::storage_fields` before persistence. Custom endpoints must return `AuthContext::user_view` rather than serialize storage models. `UserView::from` is an unconfigured internal conversion. Generic OAuth and OIDC pass `OAuthProfile.additional_fields` through `UserConfig::parse_provider_input` before persistence. Custom provider integrations must use the same boundary. Raw OAuth provider response data is not mapped user input.

## Account Entity

Accounts represent authentication methods linked to a user (email/password, OAuth providers, etc.):

| Field | Type | Description |
|-------|------|-------------|
| `id` | `String` | UUID primary key |
| `accountId` | `String` | Provider-specific account ID |
| `providerId` | `String` | Provider name (e.g., `"credential"`, `"google"`) |
| `userId` | `String` | Owning user ID |
| `password` | `Option<String>` | Hashed password (for credential accounts) |
| `accessToken` | `Option<String>` | OAuth access token |
| `refreshToken` | `Option<String>` | OAuth refresh token |

## User Management Endpoints

These endpoints are built into the core and don't require a plugin.

### Update User

```http
POST /update-user
Authorization: Bearer <token>
Content-Type: application/json
```

```json
{
  "name": "New Name",
  "image": "https://example.com/photo.jpg",
  "username": "newusername",
  "displayUsername": "NewUsername"
}
```

The body must be a JSON object. HTTP and native endpoints validate the body before checking the session. All fields are optional; an update with no writable fields returns 400. A truthy `email` value is rejected; `null`, `false`, zero and an empty string leave the email unchanged. Use `/change-email` to change the email address.

### Delete User

```http
POST /delete-user
Authorization: Bearer <token>
```

Enable deletion with `UserManagementPlugin::delete_user_enabled(true)`. Without a sender, the endpoint deletes the authenticated user and associated sessions and accounts. A password proves freshness; otherwise, the session must be younger than `session.fresh_age` (24 hours when omitted). Zero disables the freshness check.

Configure `.send_delete_account_verification(Arc<dyn SendDeleteAccountVerification>)` to require email confirmation. The sender receives the complete public `UserView`, URL, token, and original request. The initial response keeps the session active. Sender failures are logged after storing the token. The old `require_delete_verification` boolean is replaced by this explicit sender configuration.

The callback resolves an authoritative session and atomically consumes the confirmation token before checking ownership or calling `before_delete`. Rejected ownership and callback failures do not restore the token. `before_delete` and `after_delete` receive the complete public user and original request. Both errors propagate. Cookie revocation occurs before `after_delete`, so an error after deletion still clears credentials.

### Change Email

```http
POST /change-email
Authorization: Bearer <token>
Content-Type: application/json
```

```json
{
  "newEmail": "new@example.com"
}
```

The endpoint resolves an authoritative session before checking whether email changes are enabled. Verified users require an email verification sender; a confirmation sender alone does not enable the flow. This configuration check runs before the target-email lookup. An existing target email returns `{status: true}` without changing the user, issuing cookies, or sending a message.

For an unverified user, `.update_without_verification(true)` writes the new email and issues the updated session cookie before invoking the optional verification sender. Otherwise, a configured confirmation sender receives the existing user and new email; the verification fallback receives a user snapshot with the new email. `UserInfo` is an alias for the complete `UserView`. Tokens use `EmailVerificationConfig::verification_token_expiry`, which defaults to one hour. Asynchronous delivery failures are logged after any completed write and cookie issuance. A cancelled user-update hook leaves storage unchanged, but this endpoint still issues cookies and sends the requested verification email. Custom stores must implement `UserStore::update_user_optional`; cancellation returns `None`, while storage and callback errors propagate.

## AccountManagementPlugin

Provides endpoints for listing and unlinking accounts.

This example assumes you've already defined `AppAuthSchema`. If you want a complete setup from entity definitions through Axum mounting, start with the [Axum integration guide](/docs/integrations/axum).

```rust
use better_auth::plugins::AccountManagementPlugin;

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(AccountManagementPlugin::new())
    .build()
    .await?;
```

### List Accounts

```http
GET /list-accounts
Authorization: Bearer <token>
```

```json
{
  "accounts": [
    {
      "id": "uuid",
      "accountId": "user@example.com",
      "providerId": "credential",
      "userId": "uuid",
      ...
    }
  ]
}
```

### Unlink Account

```http
POST /unlink-account
Authorization: Bearer <token>
Content-Type: application/json
```

```json
{
  "accountId": "local-account-id"
}
```

Removes the specified provider link. A session older than or equal to the configured freshness window returns `403 SESSION_NOT_FRESH`; the default window is 24 hours, and zero disables the check. The endpoint also rejects removal of the last authentication method unless `allow_unlinking_all` is enabled.


## User admission

Configure `AuthBuilder::validate_user_info(Arc<dyn ValidateUserInfo<S>>)` to implement upstream `user.validateUserInfo`. The callback receives `UserValidationData` and the complete typed `EndpointContext<S>`. Its source identifies the method, operation, provider, and original provider profile. Creation data precedes database hooks and adapter transforms; generated user identifiers are absent.

Return `Ok(None)` to permit the operation or `Ok(Some(UserValidationRejection::new(code).with_description(message)))` to reject it. A rejection returns HTTP 403 with the application code. Callback errors are logged and return `validation_failed` without exposing internal details. Protected email signup returns a synthetic response after a rejection, following the same enumeration protection as an existing email.

The callback runs during user creation by email/password, Email OTP, phone, magic link, anonymous sign-in, admin, and SIWE. OAuth also invokes the callback before implicit account linking, redirect-based account linking, and an existing provider account's token update. Upstream 1.7.6 does not invoke the callback for ordinary returning password login or the direct ID-token `/link-social` branch.

During transactional signup and OAuth creation, use `EndpointContext::transaction` for callback database work. Callback failure rolls back that transaction. Outside a transaction, use `EndpointContext::auth.database`. Raw store operations do not invoke the admission callback; application persistence is separate from authentication admission.
