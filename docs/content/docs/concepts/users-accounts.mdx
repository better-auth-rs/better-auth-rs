## User Entity

Authentication reads application-owned user entities through `AuthUser`. Public responses use `UserView` and the active user schema.

| Field | Type | Description |
|-------|------|-------------|
| `id` | `String` | UUID primary key |
| `name` | `Option<String>` | Display name |
| `email` | `Option<String>` | Email address (unique) |
| `emailVerified` | `bool` | Whether email is verified |
| `image` | `Option<String>` | Profile image URL |
| `username` | `Option<String>` | Unique username |
| `displayUsername` | `Option<String>` | Case-preserved display name |
| `role` | `Option<String>` | User role |
| `banned` | `bool` | Whether user is banned |
| `banReason` | `Option<String>` | Ban reason |
| `banExpires` | `Option<FieldDate>` | Ban expiration |
| `twoFactorEnabled` | `bool` | 2FA status |
| `metadata` | `FieldValue` | Internal application data; not returned by default |
| `createdAt` | `FieldDate` | Creation timestamp |
| `updatedAt` | `FieldDate` | Last update timestamp |

## Application User Fields

Register application fields with `AuthConfig.user.fields_mut()`. The underlying `additional_fields: Option<IndexMap<String, UserFieldConfig>>` preserves omission separately from an explicitly empty map. `fields()` reads either form without allocating; `fields_mut()` creates a configured map. Add matching fields to the application-owned user entity and apply a database migration. `AuthEntity` writes these fields in the same insert or update as the core user fields. `field_name` selects the entity's mapped field name; `AuthEntity` resolves its Rust and Serde aliases to the physical column. The public API continues to use the configuration key.

```rust
use better_auth::config::{UserFieldConfig, UserFieldType};

config.user.fields_mut().insert("department".into(), UserFieldConfig {
    field_type: UserFieldType::String,
    required: Some(true),
    ..Default::default()
});
config.user.fields_mut().insert("internalCode".into(), UserFieldConfig {
    input: Some(false),
    returned: Some(false),
    default_value: Some("unassigned".into()),
    ..Default::default()
});
```

`input` and `returned` accept `Option<bool>`; omission defaults to true through their runtime getters. `required: Some(true)` rejects missing public creation input without a default. `None` and `Some(false)` keep user fields optional; Organization routes use a different creation requirement, described in the [Organization guide](/docs/plugins/organization). Updates leave missing fields unchanged. `input: Some(false)` rejects truthy client values; during creation, a configured default replaces supplied values. `returned: Some(false)` hides the field from public user responses, session caches, and JWT user claims. Administrator routes can set configured fields without public input restrictions. Application metadata and permissions are not rewritten by user projection.

Set `validator: Some(FieldValidators { input: Some(callback), ..Default::default() })` for synchronous input validation or normalization. The callback returns `AuthResult<FieldValue>`; a failure becomes `VALIDATION_ERROR`. `FieldValidators.output` preserves the upstream declaration but is not executed by Better Auth 1.7.6. `None` omits the validator container; `Some(FieldValidators::default())` retains an empty container and permits the route input transform. Use `default_value_fn` for dynamic creation defaults. Use `on_update` to produce a value when a database update omits the field. Both use `UserFieldFactory`, a synchronous callback returning `AuthResult<FieldValue>`; wrap successful values in `Ok`. A factory error propagates before input transforms or storage writes. A failed creation factory does not fall back to the constant default. For a protected field that is present in creation input, parsing retains the default function itself without calling it. Missing input invokes the factory. Use `FieldValue::Function(FieldFunction::from(factory))` to retain a callable value explicitly; `factory` uses the existing `UserFieldFactory` type. Set `transform: Some(FieldTransforms { input, output })` for transformations. `None` omits the container; `Some(FieldTransforms::default())` retains an explicitly empty container. Both callbacks use `UserFieldTransform`. Transform callbacks take and return `FieldValue`: `FieldValue::Undefined` means undefined, and `FieldValue::Null` means explicit null. Dynamic defaults, update callbacks, and adapter binding callbacks use the same runtime value type.

As in the upstream adapter, public input transforms run at both the route and storage boundaries. A validator replaces the route transform, but the storage transform still runs. Missing optional fields reach the storage input transform during creation. Database reads apply output transforms once; cache reads preserve the transformed values. Runtime Date fields use `FieldDate`, which retains milliseconds, object identity, and invalid dates. Convert Chrono dates with `.into()`; import RFC 3339 strings only at a declared JSON or cache date boundary. The entity column types determine storage representation for strings, numbers, booleans, JSON, arrays, and enums. An enum declaration alone does not validate allowed values; configure a validator when validation is required.

Core User, Account, Session, and Verification database lists preserve the selected row order and advance output transforms by schema field across the batch. Each row retains its field order. If a callback fails, that row stops; other rows finish, then the batch returns the first original error. This preserves callbacks that upstream already started before observing the batch error. Rust completes those rows before returning; JavaScript may reject the caller while other rows continue through microtasks. Rust does not emulate that relative timing. Use `UserFieldTransform::new_async` for adapter callbacks that return futures. Public synchronous input parsing rejects an asynchronous transform when no validator replaces the transform.

SeaORM User and Account reads retain the raw SQL query result until `AdapterRecord` output policies finish. Their point reads, list reads, write returns, and selected joins share this boundary. Handwritten models retain `field_column` mappings; a mapping error propagates at the selected field. Existing `record_fields` methods remain available for application-owned typed conversions. Verification still uses its existing typed extraction boundary. `AuthEntity` generates `record_fields`.

`AuthUser` reads `name` and `image` through `AuthRecordFields` without serializing the model. If their serialized keys differ from canonical names, handwritten implementations must override `serialized_field_name`; `AuthEntity` generates that mapping.

Plugin fields are projected from the active plugin schema. Disabling Anonymous, Phone Number, Username, Admin, or Two Factor hides stored plugin fields on database reads. An existing signed session cache preserves its previous plugin fields until expiry or a cache version change, matching upstream. Current `returned: Some(false)` restrictions apply even to existing caches. Change `session.cookie_cache.version` when a configuration change must invalidate cached user shapes immediately.

Public input parsing starts with application declarations, then replaces complete declarations in plugin registration order. Admin, Phone Number, Anonymous, and Two Factor register their native User declarations through this same mechanism. The final declaration controls protection, defaults, validators, and transforms. Email OTP and Phone Number signup parse additional fields before assigning their verified identity fields; those routes exclude reserved request fields from additional-field validation.

Custom stores must apply `UserConfig::storage_fields` before persistence. Custom endpoints must return `AuthContext::user_view` rather than serialize storage models. `UserView::from` is an unconfigured internal conversion. Generic OAuth and OIDC pass `OAuthProfile.additional_fields` through `UserConfig::parse_provider_input` before persistence. Custom provider integrations must use the same boundary. Raw OAuth provider response data is not mapped user input.

### Runtime values and serialization

Use `FieldMap` for record `additional_fields`. Keep schema declarations as `IndexMap<String, UserFieldConfig>`. Use `FieldMap::from_json` or `FieldValue::from_json` at an external JSON input boundary. Use `.json()` or the explicit `field_value::serde` helpers at an output boundary. Propagate conversion errors. `FieldValue` has no blanket Serde implementation because serialization changes runtime values.

`FieldValue` retains undefined properties, nonfinite numbers, Date objects, arrays, objects, and function identity. A regular clone preserves object handles. Transaction snapshots use one `StructuredCloneContext` across all rows to preserve aliases with new handles. `clone_value` and `clone_map` return `AuthResult`; nested functions fail with `AuthError::DataClone`. Public User, Session, and Account output clones enumerable fields before visibility filtering. A hidden function still causes that clone to fail. Synthetic User construction removes hidden fields before its later public clone. Transaction change detection compares JSON text. Native record cloning preserves private fields and field visibility separately from public serialization.

`SchemaValue<T>::from_json` is fallible. Use `SchemaValue::from_field` for runtime values. JSON output omits undefined and function object properties, encodes these array values as null, and converts nonfinite numbers and invalid dates to null. Top-level `json()` and `stringify()` return `None` for undefined and functions. `Utf16String` retains isolated UTF-16 surrogate units; explicit text serialization preserves these units, while `.json()` reports an error when `serde_json::Value` cannot represent the string. Date JSON output covers the complete ECMAScript TimeClip range with millisecond precision and signed six-digit expanded years. `to_datetime` and locale string output still reject valid dates outside Chrono's range. Date string parsing also remains limited to Chrono's range.

Memory writes retain function values until a clone or serialization boundary. A direct write can remain persisted after a later public clone fails. A transaction over an existing function row fails during snapshot cloning before its callback starts. SQL treats a top-level function as an expression callback before driver binding: ordinary scalar results fail before writes. Rust field callbacks do not expose JavaScript source, receiver arguments, custom coercion, or Kysely operation-node results. These boundaries remain unsupported; converting a function to text returns an explicit error.

Organization metadata and role permissions in adapter records are actual stored fields, usually JSON text. Organization creation, update, and role endpoints parse that text at their upstream response boundary. Do not infer storage representation from the `SchemaValue::Typed` or `SchemaValue::Dynamic` variant.

### Memory JSON and arrays

The Memory adapter stores declared JSON objects, arrays, and null as JSON text after input transforms. An existing JSON string remains unchanged. Output transforms receive the stored text before JSON decoding. A valid JSON string therefore returns its decoded value. Declared string arrays and number arrays remain arrays in storage and callbacks.

User snapshot and live projections retain their existing field order and date assignment. Session projections retain their typed rows and batch order. Fields that reference an ID retain their separate reference conversion before JSON output decoding. The public `UserConfig` projection helpers keep their existing adapter-independent behavior; SQL column conversion and secondary-only session caches are separate boundaries.

JSON storage representation does not establish JSON query equality. The query boundary below describes the current support for declared display fields.

### Query Application User Fields

`UserStore::list_users` resolves declared display fields in `ListUsersParams.filter_field` and `sort_by` through their logical name or configured `field_name`. Memory reads the query snapshot's mapped values. SeaORM reads declared non-reference String values from actual model columns. SQLite also reads declared non-native Boolean and Number values without references from their columns; other configured values retain model serialization. SeaORM retains the original model through selection. Both adapters filter, sort, and page before output transforms, then perform a separate unpaged count after output succeeds. Search keeps its existing native-field behavior.

String and enum fields compare stored strings. Number fields accept qualifying numeric strings, and `in` arrays convert only when every element is a qualifying numeric string. Boolean fields convert string values by comparison with `"true"`. Query binding does not run application input transforms. The selected page runs the existing output policies once; count runs no output callbacks. Numeric representation errors propagate through `AuthResult`.

The pinned Memory/SQLite capture, strict Bun comparison, and Rust contract pass seven ordinary scalar queries per backend.

For declared String, Boolean, and Number fields without references, `eq null` matches a missing or null raw value. `ne null` excludes explicit null and retains missing values. Memory preserves this distinction. SeaORM reads String SQL NULL from the column even when serde omits the serialized field; SQLite additionally preserves Boolean false and Boolean/Number SQL NULL in query snapshots. A handwritten `SeaOrmUserModel` must implement its existing `field_column` resolver for configured non-reference String fields and these SQLite Boolean/Number additional fields, including stores constructed directly without schema preflight. `AuthEntity` generates these mappings. Resolver errors propagate without a serialization fallback. Undeclared filter names return `AuthError::Internal` with the original schema error message. Native names and declared native aliases retain their existing query path.

The pinned capture, strict Bun comparison, and Rust Boolean/Number column-query contract pass. Its eight SQLite queries cover logical and mapped false filters, Boolean ordering and paging, and Boolean/Number null equality and inequality. Four Memory controls use an explicit null row. Complete callback values, display presence maps, row order, and fresh totals are compared separately for each backend. Existing scalar, nullable, sort, SQL-output, output-order, and batch-error regressions pass, as do scoped Clippy and workspace formatting. Numeric Boolean predicates, Boolean range operators, other null operators, nonfinite numbers, mixed types, PostgreSQL/MySQL scalar column extraction, and database affinity or collation remain outside this contract.

Adapter-specific Date, JSON, array, and reference query binding and equality remain incomplete. Logical and mapped name resolution does not establish those contracts. Other null comparisons, mixed-type comparisons, empty sort fields, native-field aliases, and database or JavaScript locale collation also remain unresolved. The ordinary Memory/SQLite nullable String and unknown-filter contract passes, including complete display presence/value maps, callback events, original schema errors, and totals. Its display callback records raw undefined separately and returns `"(missing)"` only for that input. A separate SQLite regression passes for `ne null` with `skip_serializing_if = "Option::is_none"`. Generic JavaScript own-undefined versus Rust missing-key output parity remains unresolved.

SeaORM User and Account projection reads native and additional values from raw database columns through the shared reader used by plugin models. SQL NULL and dynamic values reach output callbacks before field decoding. SQLite callbacks receive numeric booleans, JSON and array text, and UTC date text. PostgreSQL and MySQL retain their driver-specific scalar, JSON, and timestamp values. Query-time native joins retain their original database snapshot; fallback joins follow transformed relation values. Existing SQLite String and extra-field captures remain unchanged. The new complete-return, callback-error, and raw native-column contracts require targeted CI acceptance; they do not establish complete cross-database parity.

Custom typed adapters may use `UserView::with_internal_fields_many_for_adapter_using` to supply raw additional-field values through the existing User projector. Pass `user_fields::FieldOutputCapabilities` instead of the former JSON Boolean argument. Its `supports_native_json`, `supports_native_dates`, `supports_arrays`, and `supports_booleans` members describe the adapter's callback values; a false member enables that type's decoder after the callback. The accessor receives the original model, logical field name, and resolved field policy. `Some(Value::Null)` supplies a present null; `None` retains the existing serialized source. Supplied non-reference values bypass callback-value reconstruction and run the application callback once before decoding. References and the serialized source retain the compatibility output path. Propagate accessor errors. The projector does not call the accessor for native fields or already projected UserViews. `UserFieldConfig::adapter_output` accepts a `FieldValue` and returns a `FieldValue`; use `Undefined` for an absent field. Single-row and batch output retain the same field ordering and error propagation. Direct generic `AuthUser` projection reads `AuthRecordFields` and preserves runtime values.

An optional typed JSON column distinguishes SQL NULL (`None`) from the stored JSON literal null (`Some(Value::Null)`). SQLite callbacks receive null for the first state and the text `"null"` for the second state. Typed JSON reconstruction does not preserve arbitrary original whitespace, number spelling, or key byte order; use a text-column representation when the application needs stored text. Generated UTC dates use the existing millisecond ISO serializer. Other Chrono date representations use their inner value's Serde representation and retain the existing post-callback date result or error. Handwritten `time` date types retain their existing serialized source, including its omission rules, because the generic SeaORM conversion produces SQL literals for those variants. PostgreSQL/MySQL raw native-column acceptance, arbitrary handwritten date types, nonfinite database values, and arbitrary joined shapes remain separate acceptance boundaries. The new contract does not establish those behaviors.

Custom adapters that use `better_auth_core::user_query` must pass final `UserConfig` metadata and a raw-record accessor to `apply_list_users_by` and `count_users`. The accessor returns the native query snapshot and a separate map of mapped raw fields. Keep the raw map separate from projected `UserView` fields. Both helpers return `AuthResult`; propagate conversion errors.

`PreparedUserQuery::new(&params, &config.user)` binds a filter once for selection and the later count. SQL adapters must call `validate_sort()` before the database read. The constructor preserves filter errors before sort errors. `select(rows, accessor)` retains each original row, filters before sorting, and validates a nonempty sort declaration only when more than one filtered row remains. This preserves Memory's comparator-based validation: an unknown sort field succeeds for zero or one matching row. SQL rejects the same field for any row count. Declared logical and mapped names remain valid. `count(fresh_rows, accessor)` neither sorts nor projects; stores still read fresh rows after successful output before counting. The existing free functions remain compatible wrappers.

The pinned ordinary Memory/SQLite sort contract passes with complete display values, callback events, result variants, original schema messages, and totals. SQL validation before I/O is established by source placement; the paired contract does not instrument database operations. Its five cases cover unknown display sort fields with zero, one, and two matching rows, logical numeric ordering, and a mapped numeric sort with pagination. Native selector and comparator branches remain unchanged. Empty sort names, plugin schema availability, native aliases, collation, and mixed-type or non-scalar ordering remain separate boundaries.

## Account Entity

Accounts represent authentication methods linked to a user (email/password, OAuth providers, etc.):

| Field | Type | Description |
|-------|------|-------------|
| `id` | `String` | UUID primary key |
| `accountId` | `String` | Provider-specific account ID |
| `providerId` | `String` | Provider name (e.g., `"credential"`, `"google"`) |
| `userId` | `String` | Owning user ID |
| `password` | `Option<String>` | Hashed password (for credential accounts) |
| `accessToken` | `Option<String>` | OAuth access token |
| `refreshToken` | `Option<String>` | OAuth refresh token |

## User Management Endpoints

These endpoints are built into the core and don't require a plugin.

### Update User

```http
POST /update-user
Authorization: Bearer <token>
Content-Type: application/json
```

```json
{
  "name": "New Name",
  "image": "https://example.com/photo.jpg",
  "username": "newusername",
  "displayUsername": "NewUsername"
}
```

The body must be a JSON object. HTTP and native endpoints validate the body before checking the session. All fields are optional; an update with no writable fields returns 400. A truthy `email` value is rejected; `null`, `false`, zero and an empty string leave the email unchanged. Use `/change-email` to change the email address.

### Delete User

```http
POST /delete-user
Authorization: Bearer <token>
```

Enable deletion with `UserManagementPlugin::delete_user_enabled(true)`. Without a sender, the endpoint deletes the authenticated user and associated sessions and accounts. A password proves freshness; otherwise, the session must be younger than `session.fresh_age` (24 hours when omitted). Zero disables the freshness check.

Configure `.send_delete_account_verification(Arc<dyn SendDeleteAccountVerification>)` to require email confirmation. The sender receives the complete public `UserView`, URL, token, and original request when one was supplied. The initial response keeps the session active. Asynchronous sender failures are logged after storing the token. The old `require_delete_verification` boolean is replaced by this explicit sender configuration.

Use `.callbacks(UserManagementCallbacks::<AppAuthSchema>::new().delete_account_verification(callback))` when delivery needs the complete `EndpointContext` or synchronous completion. The callback receives `VerificationEmail`; return `Err` to fail before scheduling, `Ok(None)` to complete synchronously, or `Ok(Some(BackgroundFuture))` to schedule owned delivery. The verification record already exists when the callback runs, including when the callback fails. `config.advanced.background_tasks` controls scheduling; without a handler, the endpoint awaits delivery and logs asynchronous failures.

The callback resolves an authoritative session and atomically consumes the confirmation token before checking ownership or calling `before_delete`. Rejected ownership and callback failures do not restore the token. `before_delete` and `after_delete` receive the complete public user and original request. Both errors propagate. Cookie revocation occurs before `after_delete`, so an error after deletion still clears credentials.

### Change Email

```http
POST /change-email
Authorization: Bearer <token>
Content-Type: application/json
```

```json
{
  "newEmail": "new@example.com"
}
```

`ChangeEmailConfig.enabled` uses `Option<bool>` to preserve omission. `None` disables email changes; direct assignments use `Some(true)` or `Some(false)`. The `.change_email_enabled(bool)` builder keeps its scalar argument.

The endpoint resolves an authoritative session before checking whether email changes are enabled. Verified users require an email verification sender; a confirmation sender alone does not enable the flow. This configuration check runs before the target-email lookup. An existing target email returns `{status: true}` without changing the user, issuing cookies, or sending a message.

For an unverified user, `.update_without_verification(true)` writes the new email and issues the updated session cookie before invoking the optional verification sender. Otherwise, a configured confirmation sender receives the existing user and new email; the verification fallback receives a user snapshot with the new email. `UserInfo` is an alias for the complete `UserView`. Tokens use `EmailVerificationConfig::verification_token_expiry`, which defaults to one hour. Asynchronous delivery failures are logged after any completed write and cookie issuance. A cancelled user-update hook leaves storage unchanged, but this endpoint still issues cookies and sends the requested verification email. Custom stores must implement `UserStore::update_user_optional`; cancellation returns `None`, while storage and callback errors propagate.

For typed confirmation delivery, register `UserManagementCallbacks::change_email_confirmation(callback)`. The callback receives `ChangeEmailConfirmation` and `EndpointContext`, with the same factory return contract as deletion delivery. The callback's user retains the current address; `new_email` contains the requested address. Verification delivery uses `EmailVerificationCallbacks`. All email-change branches use the configured background handler. A synchronous sender error propagates; a non-API error discards the outgoing cookie response but leaves any completed database write intact.

## AccountManagementPlugin

Provides endpoints for listing and unlinking accounts.

This example assumes you've already defined `AppAuthSchema`. If you want a complete setup from entity definitions through Axum mounting, start with the [Axum integration guide](/docs/integrations/axum).

```rust
use better_auth::plugins::AccountManagementPlugin;

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(AccountManagementPlugin::new())
    .build()
    .await?;
```

### List Accounts

```http
GET /list-accounts
Authorization: Bearer <token>
```

```json
{
  "accounts": [
    {
      "id": "uuid",
      "accountId": "user@example.com",
      "providerId": "credential",
      "userId": "uuid",
      ...
    }
  ]
}
```

### Unlink Account

```http
POST /unlink-account
Authorization: Bearer <token>
Content-Type: application/json
```

```json
{
  "accountId": "local-account-id"
}
```

Removes the specified provider link. A session older than or equal to the configured freshness window returns `403 SESSION_NOT_FRESH`; the default window is 24 hours, and zero disables the check. The endpoint also rejects removal of the last authentication method unless `allow_unlinking_all` is enabled.


## User admission

Configure `AuthBuilder::validate_user_info(Arc<dyn ValidateUserInfo<S>>)` to implement upstream `user.validateUserInfo`. The callback receives `UserValidationData` and the complete typed `EndpointContext<S>`. Its source identifies the method, operation, provider, and original provider profile. Creation data precedes database hooks and adapter transforms; generated user identifiers are absent.

Creation input is prepared once before admission. Runtime fields in `CreateUser::additional_fields` replace convenience fields, including core fields. Email normalization runs after these replacements, and an invalid email value fails before admission or database hooks. Admission and database hooks share the prepared values, property order, Date handles, and nested object handles. Subsequent hook patches can replace fields. Preparation retains explicit undefined properties; schema defaults run later at the adapter boundary. Email/password signup assigns `emailVerified: false` after additional input fields, before admission.

Synthetic signup output uses the same complete declarations, with endpoint field policies and adapter declaration order. `UserView::synthetic_output(data, adapter, endpoint)` applies defaults to missing or undefined input without running adapter transforms. A literal undefined default permits the optional null fallback; a default callback that returns undefined retains that result. Signup then applies the endpoint's `returned` flags, including restrictions on `id`.

Custom synthetic callbacks receive only fields declared by the application, selected from the parsed input. Plugin-only defaults are excluded; overlapping application declarations retain the parsed value. The selection preserves own-undefined properties and JavaScript property order. Protected signup constructs the synthetic response inside the transaction. A synthetic factory error rolls back writes made earlier in that transaction.

Return `Ok(None)` to permit the operation or `Ok(Some(UserValidationRejection::new(code).with_description(message)))` to reject it. A rejection returns HTTP 403 with the application code. Callback errors are logged and return `validation_failed` without exposing internal details. Protected email signup returns a synthetic response after a rejection, following the same enumeration protection as an existing email.

Email/password signup preserves explicit API errors from user creation, including server errors and response headers. A non-API error during input preparation or user creation returns `422 FAILED_TO_CREATE_USER`. Account creation and after-commit hooks remain outside that error boundary. An account creation failure rolls back the transaction; an after-commit failure propagates after the records persist.

The callback runs during user creation by email/password, Email OTP, phone, magic link, anonymous sign-in, admin, and SIWE. OAuth also invokes the callback before implicit account linking, redirect-based account linking, and an existing provider account's token update. Upstream 1.7.6 does not invoke the callback for ordinary returning password login or the direct ID-token `/link-social` branch.

During transactional signup and OAuth creation, use `EndpointContext::transaction` for callback database work. Callback failure rolls back that transaction. Outside a transaction, use `EndpointContext::auth.database`. Raw store operations do not invoke the admission callback; application persistence is separate from authentication admission.
