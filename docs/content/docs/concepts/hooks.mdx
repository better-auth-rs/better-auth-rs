---
title: SeaORM Hooks
description: Intercept SeaORM-backed auth operations with lifecycle hooks.
---

SeaORM hooks let you run custom logic before and after auth writes. Use them for validation, auditing, provisioning, or rejecting operations while keeping the public auth runtime separate from your persistence integration.

`ctx.request` contains the matched endpoint template, captured `params`, and parsed `body`. For `/callback/mock`, the hook path is `/callback/:id` and `params["id"]` is `mock`; `AuthRequest.path` retains the actual request path. Body replacements from earlier plugin hooks are visible to database hooks. Direct store calls have no request context. Native APIs can provide a body without setting `is_http`; HTTP response conversion remains the transport's responsibility.

## Setup

These examples assume you've already defined `AppAuthSchema` and a `database: DatabaseConnection`. If you want a complete setup from entity definitions through Axum mounting, start with the [Axum integration guide](/docs/integrations/axum).

```rust
use better_auth::{BetterAuth, database_hooks};
use better_auth::seaorm::{SeaOrmHookContext, SeaOrmHooks, SeaOrmStore};

struct AuditHook;

#[database_hooks]
impl SeaOrmHooks<AppAuthSchema> for AuditHook {
    async fn after_create_user(
        &self,
        user: Option<&better_auth::wire::UserView>,
        _ctx: &SeaOrmHookContext<'_, AppAuthSchema>,
    ) -> better_auth::AuthResult<()> {
        if let Some(user) = user {
            println!("User created: {:?}", user.email);
        }
        Ok(())
    }
}

let store = SeaOrmStore::<AppAuthSchema>::new(config.clone(), database)
    .hook(AuditHook);

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .build()
    .await?;
```

## The `SeaOrmHooks` Trait

Lifecycle methods have default no-op implementations. Override only the callbacks you need. Apply `#[database_hooks]` to the implementation; the attribute supplies both async-trait support and exact callback metadata. Do not add a second `#[async_trait]` attribute.

Instrumentation uses this metadata to skip default callbacks. A manual implementation must implement `hook_metadata` and list its actual callbacks. Plugin hooks use `#[database_hooks("plugin:plugin-id")]` to identify their source.

```rust
#[async_trait]
pub trait SeaOrmHooks<S: AuthSchema>: Send + Sync {
    fn hook_metadata(&self) -> DatabaseHookMetadata;

    async fn before_create_user(
        &self,
        user: &mut FieldMap,
        ctx: &SeaOrmHookContext<'_, S>,
    ) -> AuthResult<DatabaseHookUpdate<FieldMap>>;

    async fn after_create_user(
        &self,
        user: Option<&better_auth::wire::UserView>,
        ctx: &SeaOrmHookContext<'_, S>,
    ) -> AuthResult<()>;

    async fn before_update_user(
        &self,
        id: &better_auth::FieldValue,
        update: &mut FieldMap,
        ctx: &SeaOrmHookContext<'_, S>,
    ) -> AuthResult<DatabaseHookUpdate<FieldMap>>;

    async fn after_update_user(
        &self,
        user: Option<&better_auth::wire::UserView>,
        ctx: &SeaOrmHookContext<'_, S>,
    ) -> AuthResult<()>;

    async fn before_delete_user(
        &self,
        user: &better_auth::wire::UserView,
        ctx: &SeaOrmHookContext<'_, S>,
    ) -> AuthResult<HookControl>;

    async fn after_delete_user(
        &self,
        user: &better_auth::wire::UserView,
        ctx: &SeaOrmHookContext<'_, S>,
    ) -> AuthResult<()>;

    async fn before_create_session(
        &self,
        session: &mut FieldMap,
        ctx: &SeaOrmHookContext<'_, S>,
    ) -> AuthResult<DatabaseHookUpdate<FieldMap>>;

    async fn after_create_session(
        &self,
        session: Option<&better_auth::wire::SessionView>,
        ctx: &SeaOrmHookContext<'_, S>,
    ) -> AuthResult<()>;
}
```

Creation-after hooks receive `Option<&View>` for User, Account, Session, and Verification. A successful database insert can return `None` when MySQL cannot identify the inserted row. The after hooks still run. A before hook that cancels creation does not insert a row or run the writer or after hooks. An output-transform error also skips after hooks; a direct insert remains committed, while an enclosing transaction retains its rollback boundary.

`SeaOrmHooks::before_update_session` receives the native token as `&FieldValue`. Runtime database hooks continue to receive the update object. Use the native token without a string conversion when the Session schema replaces its type.

## Rejecting Operations

Return `HookControl::Cancel` from Account and Verification creation hooks and delete hooks to cancel the write. User creation/update hooks and Session creation/update hooks return `DatabaseHookUpdate::Cancel`. An error stops the operation and propagates to the caller.

Bulk deletion snapshots the matching records, runs every before hook, performs one batch write, then runs after hooks in snapshot order. A before-hook cancellation preserves the complete batch. An after-hook error occurs after the complete write and stops later hooks and queued effects. User deletion applies this sequence to session children, then account children, before the user's own hooks. SQLite foreign-key cascades can remove children whose hooks cancelled their explicit deletion.

Better Auth 1.7.6 catches deletion snapshot-read errors before running hooks. Bulk deletion still attempts its write; single-record deletion treats an unreadable snapshot as a missing record. This catch is limited to the snapshot read. Hook errors and write errors continue to propagate.

Session deletion snapshots apply configured output transforms once and retain fields with `returned: false`. A transform error follows the same snapshot-read boundary. Output transforms, dates, JSON, and reference fields require runtime hydration for typed session snapshots; `AuthEntity` supplies that implementation. Runtime initialization rejects models without that capability. Ordinary scalar fields without an output policy retain their existing typed values.

Atomic verification consumption returns `None` when a before-delete hook cancels. After-delete hooks run after the consumption transaction commits. An after-delete hook error propagates to the caller, but the consumed credential remains deleted.

```rust
#[database_hooks]
impl SeaOrmHooks<AppAuthSchema> for BlockDisposableEmails {
    async fn before_create_user(
        &self,
        user: &mut FieldMap,
        _ctx: &SeaOrmHookContext<'_, AppAuthSchema>,
    ) -> AuthResult<DatabaseHookUpdate<FieldMap>> {
        if user.get("email").and_then(FieldValue::as_str)
            .is_some_and(|email| email.ends_with("@disposable.com"))
        {
            return Ok(DatabaseHookUpdate::Cancel);
        }
        Ok(DatabaseHookUpdate::Continue)
    }
}
```

## Modifying Data

User creation and update hooks receive the complete `FieldMap`, including native replacements, null, and own-undefined properties. `CreateUser` and `UpdateUser` remain convenient caller inputs; their `additional_fields` values override the corresponding native members before hooks. Creation normalizes a non-null email before hooks. Updates lowercase only truthy email values. A non-string value fails only when that string operation runs.

Create hooks receive mutable references. Each update hook receives the original patch and returns `DatabaseHookUpdate::Continue`, `Cancel`, or `Patch(data)`. Returned patches merge in registration order. User and Session preparation share `PreparedRecordWrite`: creation hooks see cumulative changes; update hooks see the original object. The first returned patch detaches property replacement while retaining shallow object identities. A later hook can overwrite fields returned by an earlier hook, but cannot observe the earlier patch through its input. `SessionUpdate` and `VerificationUpdate` provide the corresponding session and verification fields. Nullable fields use `Option<Option<T>>` to distinguish omission from clearing a value.

Session creation hooks receive one complete `FieldMap`, including `token`, `userId`, `expiresAt`, `createdAt`, `updatedAt`, client fields, and configured defaults. Each hook sees prior in-place edits and returned `DatabaseHookUpdate::Patch` values. The first returned patch, including an empty map, detaches later property replacements from the original creation object. Secondary cache keys and TTL use that original object; the cached Session contains the final adapter result. The active-session owner and user lookup retain the original caller user ID. `FieldDate` values are immutable, so JavaScript `Date.setTime` alias mutations are not supported. `CreateSession` remains the caller input type. Native Session getters and views use `SchemaValue` to preserve replacement values without a second overlay. Use `.typed()?` only when the consuming operation requires the default Rust type.

After-update hooks receive `None` when the database matches no row. The store still returns `UserNotFound` for a missing user. If a transaction caller catches that error and commits, the nullable after hook runs in its original queue position. Rollback discards the hook. A cancelled update does not run after-update hooks.

```rust
#[database_hooks]
impl SeaOrmHooks<AppAuthSchema> for NormalizeEmail {
    async fn before_create_user(
        &self,
        user: &mut FieldMap,
        _ctx: &SeaOrmHookContext<'_, AppAuthSchema>,
    ) -> AuthResult<DatabaseHookUpdate<FieldMap>> {
        if let Some(email) = user.get("email").and_then(FieldValue::as_str) {
            let normalized = email.to_lowercase();
            let _ = user.insert("email".into(), normalized.into());
        }
        Ok(DatabaseHookUpdate::Continue)
    }
}
```

## Provisioning After Signup

Use `after_create_user` to provision records after the authentication transaction commits. Before hooks receive the native SeaORM transaction in `ctx.tx` and the same transaction through the typed `ctx.transaction` interface. After hooks receive `ctx.tx == None` and run in write order after commit. Rollback discards queued after hooks. An after-hook error propagates, stops subsequent hooks, and leaves committed authentication data unchanged.

Database hooks and deferred secondary-storage effects share one ordered commit queue. A user's cache refresh follows that update's after hooks and precedes hooks from later writes. `AuthTransaction::queue_after_commit` adds application effects to the same queue. The queue runs under the committing caller's ambient request scope. Database hooks separately receive the request snapshot captured by the write in `ctx.request`. For a synthetic Email OTP endpoint inside signup, the verification after hook receives the OTP request while `current_request_hook_context()` returns signup. Custom effects must capture any explicit request argument they need. Session creation writes its cache entry immediately by default. `create_session_with_deferred_secondary_optional` preserves a null result and runs session after hooks before publishing the cache entry; rollback discards that deferred write. The strict `create_session_with_deferred_secondary` convenience uses the same ordering.

User cache refresh failures go to the authentication instance's logger and preserve the update result, both outside transactions and after commit. A nullable update result still schedules refresh and reports the missing User through that logger. Ordinary database after-hook errors propagate and stop later queue entries. Refresh starts cache reads concurrently; after the first failure returns, already-started peers can still finish their cache writes. Refresh filters active references individually and logs invalid index shapes. Cached Session expiration accepts an ISO date string or epoch milliseconds; refresh preserves the Session payload and writes User fields in schema order.

```rust
use better_auth::{AuthResult, database_hooks};
use better_auth::error::DatabaseError;
use better_auth::seaorm::sea_orm::ConnectionTrait;
use better_auth::seaorm::sea_orm::sea_query::{Alias, Query};
use better_auth::seaorm::{SeaOrmHookContext, SeaOrmHooks, SeaOrmStore};

struct ProvisionWorkspaceHook;

#[database_hooks]
impl SeaOrmHooks<AppAuthSchema> for ProvisionWorkspaceHook {
    async fn after_create_user(
        &self,
        user: Option<&better_auth::wire::UserView>,
        ctx: &SeaOrmHookContext<'_, AppAuthSchema>,
    ) -> AuthResult<()> {
        let Some(user) = user else { return Ok(()) };
        let statement = Query::insert()
            .into_table(Alias::new("app_workspaces"))
            .columns([Alias::new("user_id"), Alias::new("name")])
            .values_panic([user.id.typed()?.clone().into(), "Default Workspace".into()])
            .to_owned();
        let result = ctx.db.execute(&statement).await;
        result.map_err(|error| DatabaseError::Query(error.to_string()))?;
        Ok(())
    }
}

let store = SeaOrmStore::<AppAuthSchema>::new(config.clone(), database)
    .hook(ProvisionWorkspaceHook);
```

## Multiple Hooks

Multiple hooks can be registered. They execute in registration order:

```rust
let store = SeaOrmStore::<AppAuthSchema>::new(config.clone(), database)
    .hook(AuditHook)
    .hook(NormalizeEmail)
    .hook(BlockDisposableEmails);

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .build()
    .await?;
```

If any `before_*` hook returns its cancellation variant or an error, subsequent hooks and the write itself are skipped.

## Plugin hooks and runtime isolation

Plugins register shared `DatabaseHooks<S>` through `AuthInitContext::register_database_hook`. These hooks run before application hooks. The SeaORM bridge preserves both the native transaction and the typed transaction; plugin writes can participate in the same transaction and commit queue.

`AuthInitContext::runtime` returns a weak binding to the final `AuthContext<S>`. Read this binding from callbacks after initialization. The binding includes the final secondary-storage facade and avoids retaining the authentication runtime through its own store hooks. The provided adapters isolate hook registries and field policies when multiple authentication instances share underlying records.

Plugins can declare user fields through `register_user_fields`. Adapter policies merge plugin fields before application fields. Endpoint validation and public filtering merge application fields before plugin fields. Cached users retain the adapter projection and only reapply public filtering.

Use `UserFieldTransform::new(|value| Ok(value))` for a synchronous field callback. Use `UserFieldTransform::new_async(|value| async move { Ok(value) })` for an awaited callback. Both callback forms receive `FieldValue` and resolve to `AuthResult<FieldValue>`. `FieldValue::Undefined` means undefined, and `FieldValue::Null` means null. Preserve native values through callbacks. Use `.json()` only at a JSON boundary; conversion can fail.

Core User, Account, Session, and Verification adapters await input callbacks before binding stored values. The adapters await output callbacks before converting and returning values. Each row keeps schema field order. Async list projections can advance rows independently and retain the original result order. A failed row stops its callbacks; the batch completes other started rows before returning the first observed original error. JavaScript rejection and continuation microtask timing is not reproduced.

Public-input parsing remains synchronous. If parsing reaches an async input callback, Rust returns `AuthError::Config` before starting the callback. An input validator still takes precedence at this boundary; the adapter subsequently awaits the input transform. This is an upstream compatibility exception: upstream public-input parsing does not await a promise returned by its transform. Organization field policies also remain synchronous and return `AuthError::Config` for an async callback. Awaited Organization policies require a separate change to the Memory transaction and capacity boundaries.

## Server-only endpoint dispatch

The typed `EmailOtpApi`, `JwtApi`, and `TwoFactorApi` facades run actual server-only endpoints through the same endpoint dispatcher as HTTP routes. Global before hooks run before plugin before hooks. Context patches apply after the before hooks. Validation projects handler input once. Endpoint API errors continue through after hooks; ordinary errors stop the pipeline. Before responses skip the handler and after hooks. The typed facade decodes the final hook-replaced response into its documented return type.

Server-only endpoints have no HTTP route. Their explicit hook request uses `/`, while `current_request_hook_context().path` is `None`. The handler context uses `Some("virtual:")`; handler completion restores the outer context. Instrumentation uses `/:virtual` and the actual operation ID. A supplied native Request remains available independently of supplied headers. Typed facade return values correspond to upstream native calls with `asResponse: false`.

The shared dispatcher retains immutable plugin and hook data, not an authentication context. Transaction-bound Email OTP and JWT calls retain the caller's borrowed transaction. `JwtApi::create_key_pair` and direct plugin helpers remain helper calls and do not run endpoint hooks.
