---
title: Observability
description: Configure per-instance logging, endpoint tracing, and opt-in telemetry.
---

Logging, tracing, and telemetry have separate controls. Disabling one does not disable the other two.

## Logging

`AuthConfig.logger` configures one authentication instance. The default threshold is `LogLevel::Warn`. Thresholds follow `Debug`, `Info`, `Success`, `Warn`, and `Error` order. Success messages reach a custom sink as `LogLevel::Info`.

```rust
use better_auth::observability::LogLevel;

config.logger.level = Some(LogLevel::Info);
config.logger.disable_colors = Some(true);
```

Set `disabled = Some(true)` to suppress all instance logger output. `disabled` and `level` use `Option` to retain omission. `None` keeps logging enabled at the warning threshold; `Some(false)` and `Some(LogLevel::Warn)` apply the same runtime defaults but remain explicit telemetry options. Set `log` to an `Arc<dyn LogSink>` to receive the level, original message, and argument list. `LogArgument` preserves text, JSON values, and errors without applying format placeholders. The default sink uses Rust `tracing` events. Concurrent authentication instances retain their own logger configuration.

## Tracing

`config.experimental.instrumentation.enabled` defaults to `true`. Install a `tracing` subscriber to collect spans. The `better-auth` target reports the upstream span name through `otel.name` and the instrumentation scope through `otel.scope.name` and `otel.scope.version`.

Endpoint dispatch produces a method-and-route span, a handler span, and spans for matched endpoint hooks. User hook spans precede plugin hook spans for each phase. Unmatched plugin hooks produce no span. Database hook spans identify the logical model; raw database operation spans identify the model's physical table. Input transforms run before a database operation span, and output transforms run after it. A logical update has one operation span even when the adapter reads and then writes a row.

API errors and ordinary errors record an exception and an error status at the boundary that receives the error. Redirect errors record their response status and a successful span status. Instrumentation preserves the original error and does not log response headers.

Use [`#[database_hooks]`](/docs/concepts/hooks) on database hook implementations. The attribute records the callbacks that the implementation actually supplies, so inherited no-op callbacks do not create spans.

## Global endpoint hooks

Register `EndpointHooks<S>` with `BetterAuth::hooks`. `BeforeEndpointHook<S>` returns an optional `BeforeRequestAction`; `AfterEndpointHook<S>` receives the response by mutable reference. Both callbacks are awaited.

A before-hook error stops the endpoint and later hooks. An endpoint API error still reaches after hooks. An after-hook API error replaces the returned error while later after hooks continue. An ordinary error stops the remaining pipeline. These hooks use the same dispatch and response-header rules as plugin hooks.

## Telemetry

Telemetry defaults to disabled. Set `config.telemetry.enabled = true` or `BETTER_AUTH_TELEMETRY=true` to opt in. Configure `config.telemetry.track` with an application-controlled `TelemetryTransport`, or set `BETTER_AUTH_TELEMETRY_ENDPOINT` to an explicit HTTP endpoint. No default remote endpoint is contacted.

A custom transport takes precedence over the HTTP endpoint and debug output. `config.telemetry.debug` prints reports through the default logger instead of using the HTTP transport. The logger threshold still applies. Telemetry is suppressed when `NODE_ENV=test` or a truthy `TEST` environment variable identifies a test process.

The init payload classifies production before CI, then test, then development. Any supported CI marker counts by presence, including an empty value, unless `CI=false`. `TEST` is true when nonempty and not exactly `false`. Classification does not override test suppression. Rust reads these variables at initialization; upstream captures `NODE_ENV` for test suppression at module import, so later environment mutation has a different timing boundary.

The init payload detects deployment vendors from their environment variables in upstream precedence order. A nonempty `npm_config_user_agent` supplies `packageManager`; omission and an empty value omit that field. Runtime metadata identifies Rust. System metadata reports the target platform, architecture, and `isTTY=true` for terminal stdout; piped stdout omits `isTTY`. Rust reports null for system release, CPU count/model/speed, memory, WSL, and Docker because the standard library cannot accurately obtain these values. Node and Bun use upstream’s Node detector and can populate those fields. Browser `navigator.userAgent` detection for Cloudflare Workers has no native Rust equivalent. These are explicit capability differences, not complete system-information parity.

Initialization starts the report before plugin initialization without waiting for a pending transport. The telemetry module reuses its first project identifier across instances. Transport failures are logged through the default logger and do not fail authentication. Application logger callbacks are not used for these transport failures. Report payloads must not contain authentication secrets or request records.

Session `expires_in`, `update_age`, `fresh_age`, and cookie-cache `max_age` report seconds with their configured fractional precision. Whole-second values remain JSON integers. Telemetry retains explicit duration values without truncating subsecond precision. An explicit zero session lifetime reports 0 and resolves to seven days at runtime.

The init report captures options after storage normalization and before plugin initialization. Optional session and account scalar settings, verification cleanup, explicit cookie-cache overrides, cookie attributes, cookie-map presence, cross-subdomain settings, IP tracking/header settings, database query limits, CSRF settings, rate-limit scalars and storage, API error policy, and logger options preserve omission. Email/password, verification, password-reset, and change-email scalar options and callback presence come from configured plugins, including typed callback wrappers. Verification metadata also includes a verifier attached through `EmailPasswordPlugin::with_email_verification` or `OAuthPlugin::with_email_verification`; reporting does not invoke its callbacks. Omitted `auto_sign_in` resolves to true at runtime but reports false in telemetry, matching upstream’s explicit-option coercion. Database hook presence comes from `#[database_hooks]` declarations; plugin-owned hooks do not count as application hooks.

The config projection is partial. User and session additional-field definitions preserve omitted maps, explicitly empty maps, legal field types, optional booleans, aliases, references, constant defaults, and the optional transform container. Function members are omitted during JSON projection; telemetry never invokes field callbacks. CLI-generated schemas retain the original `modelName` and `fields` options for User, Session, Account, and Verification. The initialization report preserves omitted names, omitted mappings, explicitly empty mappings, and explicit default names from that same generation input. `AuthSchema::model_declarations()` defaults to an empty slice for handwritten and derived schemas; resolved SQL names do not imply an input declaration. A generated RateLimit model also retains its explicitly supplied `modelName`; telemetry reads the current SeaORM plugin-model binding, including replacements and secondary-storage wrappers. This declaration is independent of the rate-limit storage selection. Memory adapters retain no model declaration. A separate real-initialization fixture and empty SQLite tables verify omission, explicit defaults, renamed models, and the absence of rate-limit field mappings from telemetry. Additional-field constraint flags and `references.onDelete` remain outside this projection. Rust validators do not carry the original Standard Schema object shape. The raw `getTelemetryAuthConfig` oracle verifies input projection. Separate real-initialization oracles verify complete plugin arrays and session/cache options for stateless, database, and secondary storage. Stateless initialization fills omitted cache settings with enabled=true, strategy=jwe, and the effective session lifetime. Stateful initialization preserves omitted cache fields and resolves runtime defaults through getters. Raw projection alone does not establish every real `init.config` field. The report does not infer supplied options by comparing runtime values with defaults.

ID-generation telemetry preserves `Database` as false, `Serial` as `"serial"`, and `Uuid` as `"uuid"`. Omitted policies and Rust’s explicit `Random` have no configured upstream JSON value. Custom generators remain typed callbacks and are never invoked for metadata; the JSON projection omits functions, as upstream JSON serialization does.

Trusted-origin telemetry omits an unconfigured source, reports the original length of a static list, and reports 1 for Rust’s request-argument resolver. JavaScript zero-argument resolver arity has no distinct Rust configuration form. Trusted-provider static lists preserve empty versus omitted input; dynamic resolvers are omitted from JSON and are not called for metadata. The normal initialization and request phases still resolve configured callbacks.

The `plugins` array contains configured upstream plugin IDs in registration order. Rust wrappers for core email/password, verification, password reset, account, session, user management, and social OAuth options do not contribute IDs. An `OAuthPlugin` with generic providers contributes `generic-oauth` once. Empty and core-only configurations report `[]`, matching real upstream initialization. Custom plugins inherit their runtime name as the ID and may override `AuthPlugin::telemetry_plugin_id`; typed callback wrappers forward that method.

The init config reports `database="adapter"` when the application supplies a store and `database="unknown"` otherwise, matching upstream adapter configuration. `adapter` identifies the actual implementation: `memory` for `EphemeralStore` and `seaorm` for `SeaOrmStore`. Secondary storage preserves the underlying adapter ID. Custom stores may implement `RuntimeStore::adapter_id`; the default is `unknown`. Reading this metadata does not query the database or inspect application records. SeaORM reports its own ID rather than the upstream Kysely ID.

The `socialProviders` array projects configured social providers in registration order. Omitted and empty configurations report `[]`; Generic OAuth contributes only its plugin ID. The projection includes the provider ID, mapper/user-info/verification/refresh callback presence, default-scope and ID-token switches, optional sign-up switches, profile-update policy, prompt, and optional scopes. Metadata reads the original input without running callbacks or serializing credentials. Built-in decoders are runtime defaults and do not appear as configured callbacks. The normal initialization oracle verifies complete social arrays separately from the pure raw-helper fixture.

The verified upstream mapping uses one `OAuthPlugin`, which may contain both social and Generic OAuth providers. Multiple plugin instances retain their separate registration entries in telemetry. Those instances have no unique upstream `socialProviders` object equivalent; telemetry does not merge or deduplicate their runtime configurations.

Email Verification expiry metadata preserves fractional `Duration` seconds. Password reset lifetime metadata preserves omitted values, integer JSON numbers, and fractional seconds from the same `Option<f64>` configuration used by the runtime. Non-finite numeric metadata follows JSON null serialization; the reset runtime resolves NaN to the one-hour default and rejects unrepresentable expiry dates.
