---
title: Account and Verification Fields
description: Configure adapter fields without changing endpoint input schemas.
---

`AuthConfig.account.additional_fields` and `AuthConfig.verification.additional_fields` use `UserFieldConfig`. Configure defaults, update generators, input/output transforms, column mappings, and visibility on these ordered maps. The CLI accepts matching `account.additionalFields` and `verification.additionalFields` definitions through `--schema-config`.

These definitions affect adapter writes and reads. They do not extend account or verification HTTP request schemas. A field that uses a built-in name replaces that built-in field's policy; the adapter retains ownership of `id`.

## Database and Cache Order

Database creation runs the before hooks, defaults and input transforms, the insert, and output transforms. Database hooks receive the resulting projection. An output-transform error happens after the insert. An enclosing database transaction can roll back that insert; a direct write remains stored.

With verification database storage and secondary storage enabled, creation writes the cache after output transforms and before the after hook. Cache failure prevents the after hook. Verification updates first patch the existing cache, then execute database hooks and database field policies. Database failure does not undo that earlier cache update.

Pure secondary verification storage keeps the raw hook input. It does not generate an adapter ID or execute adapter defaults, input transforms, output transforms, or returned-field filtering. A cache miss during an update returns the supplied partial patch without creating a cache record.

`returned: Some(false)` filters account-list output. Internal account reads and trusted database hooks retain these fields. The account-list endpoint always excludes credential fields. `AccountView` serialization also excludes `password`, including account cookie serialization; trusted code can use `internal_fields()` when it needs the password.

Account field projection within owner reads shares the list output scheduler. Synchronous callbacks run by field across the selected rows. Async callbacks advance each row independently; its owner lookup starts after that row's account projection succeeds. Queries retain the stored owner ID, and `AccountOwner::new` validates the relationship after projection. A failed row skips its owner lookup. Other started rows finish before Rust returns the first observed original error, which can be later than JavaScript `Promise.all` rejection.

Custom adapters can use `UserConfig::project_records_then` for storage maps or `project_adapter_records_then` for extracted `AdapterRecord` values. The completion receives the original row index and projected fields. Keep association data captured from storage separate from those fields. Both methods preserve the original result order. Existing list projection methods use the same scheduler without an additional completion operation.

## Application Models and Runtime Views

`AuthSchema::Account` and `AuthSchema::Verification` describe persistence models. Store methods and database hooks return `AccountView` and `VerificationView`. Their fields use `SchemaValue<T>` so a transform can return another type or omit a field without forcing that result back into the database model.

Read `typed()?` only when an operation needs the default type. Use `json()?` to retain replacement values and omission. `SchemaValue::InvalidDate` serializes as JSON null while preserving an invalid date's comparison and cache-expiry behavior. A genuine null and an invalid date can therefore have different effects before serialization.

`AuthEntity` implements `field_column`, `native_json_field`, `apply_fields`, and `record` for Account and Verification models. Rust field names, camelCase logical names, and Serde rename names resolve to the same column. A handwritten model must implement these methods and return an unvalidated runtime projection from `record`; do not deserialize transformed values back into the persistence model.

Custom adapters must return the runtime views from AccountStore and VerificationStore methods. Implement `create_verification_with_writer` to place the runtime cache writer between adapter output and the after hook. A transaction must enqueue the after hook only after that writer succeeds. The default implementation rejects an installed writer rather than changing the write order.

Creation and update inputs use `SchemaValue<T>` too. `Undefined` omits a field, `Typed(None)` supplies null for a nullable field, and `Dynamic` supplies a replacement value. Input `additional_fields` use logical public names; the adapter applies `field_name` once before binding columns.

## Memory Serial References

With `IdGeneration::Serial`, Memory converts declared references to an `id` field after defaults and input transforms. User and Session additional fields, Account fields, and Verification fields accept finite JSON numbers and values that convert to finite numbers. Null remains null. Arrays preserve null entries and convert each non-null value. Output transforms receive the numeric storage values before the adapter formats references as strings.

Account owner and identity queries apply the same declared reference policy. Verification identifier and value queries also apply the policy. Account relationship checks retain the canonical owner captured from storage before output transforms.

Organization reference conversion remains unsupported in Memory. Values that convert to JavaScript `NaN` or infinity also remain unsupported because JSON cannot represent those numbers. Conversion errors propagate without substituting null.
