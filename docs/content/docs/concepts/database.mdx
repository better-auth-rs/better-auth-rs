Better Auth uses your application's SeaORM entities and `DatabaseConnection`
for auth persistence through the `seaorm2` feature on `better-auth`.

The SeaORM integration enables SQLite, PostgreSQL, and MySQL drivers. Use the matching backend when generating entities with the CLI. Driver availability does not establish complete schema or value compatibility with the upstream adapter; the [alignment inventory](https://github.com/better-auth-rs/better-auth-rs/blob/master/docs/upstream-alignment-backlog.md) records the verified contracts.

Organization projection uses the actual database backend for native and configured fields. SQLite `Json` model values restore JSON text before output callbacks; SQL NULL remains null. Native `metadata` and `permission` values follow the same rule across single, batch, and joined reads. A typed `Json` model does not retain the original text's whitespace or byte layout.

Custom callers of `SeaOrmOrganizationModel::record` and `::records` must pass `DbBackend`. `AdapterRecord::map_storage_fields` also requires the backend's `FieldOutputCapabilities`; the adapter owns ID projection.

The supported public path is:

1. Enable the `seaorm2` feature on `better-auth`.
2. Define auth entities in your app with `#[derive(AuthEntity)]` from `better_auth::seaorm`.
3. Register them in an app schema with `#[derive(AuthSchema)]`.
4. Manage auth migrations in your own SeaORM migrator.
5. Build a `SeaOrmStore` from the shared `DatabaseConnection` and pass it to `BetterAuth::<YourSchema>::new(config).store(...)`.

## Setup

Generate `src/auth_schema.rs` with the [quick-start guide](/docs/quick-start) first.

```rust
mod auth_schema;
use auth_schema::{AppAuthSchema, create_auth_tables};
use better_auth::{AuthConfig, BetterAuth};
use better_auth::plugins::EmailPasswordPlugin;
use better_auth::seaorm::{Database, DatabaseConnection, SeaOrmStore};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let database = Database::connect("sqlite::memory:").await?;
    create_auth_tables(&database).await?;
    let auth_database: DatabaseConnection = database.clone();
    let config = AuthConfig::new("your-very-secure-secret-key-at-least-32-chars-long")
        .base_url("http://localhost:3000");
    let store = SeaOrmStore::<AppAuthSchema>::new(config.clone(), auth_database);

    let auth = BetterAuth::<AppAuthSchema>::new(
        config,
    )
    .store(store)
    .plugin(EmailPasswordPlugin::new().enable_signup(true))
    .build()
    .await?;

    // Keep using `database` for your app's own tables and queries.
    println!("plugins: {:?}", auth.plugin_names());
    Ok(())
}
```

## Adapter configuration

Every auth build passes its final configuration, plugin database hooks, and `ModelFields` to `RuntimeStore::with_runtime`. Custom adapters must implement this method. Return a store view that shares stored records, binds the supplied configuration and model fields, and prepends plugin hooks to application hooks. Forward `ModelFields` through adapter wrappers. Pass `ModelFields::default()` when binding a raw adapter without plugin-table policies. Keep configuration and hook lists isolated from the original store and other auth builds.

`advanced.database.default_find_many_limit` preserves an optional numeric value; omission uses 100. Account and database session lists apply the default before output transforms. Bulk-delete hooks receive a limited snapshot, while the write still deletes every matching row. Verification lookup retains its explicit one-row limit, and secondary session lists remain uncapped. Memory follows JavaScript slice behavior; SQLite accepts negative integer limits as unlimited and rejects fractional or non-finite limits.

Organization lists apply the same default before output projection. User organization and team lists preserve the selected membership page's order. Full organization queries independently limit invitations, members and teams, then load the selected members' users. Received invitations select the email's page and project each associated organization before the endpoint keeps pending records; pending records can be expired.

Custom Organization adapters must return `InvitationOrganization` from `InvitationStore::list_user_invitations`. Resolve the organization with the stored foreign key. Role point lookup, filtered role queries and role count have separate store methods. Team and team-member counts remain independent of list pagination. Rust deliberately retains accurate capacity checks instead of reproducing upstream checks that count a capped team page.

Organization adapters also implement `MemberUser` reads and `OrganizationDetailsQuery`/`OrganizationDetails` for full organization responses. The query keeps member and user limits separate. `advanced.database.joins = Some(true)` selects related Organization records before projection: SeaORM uses one typed SQL statement, including all three full-organization child tables, and Memory keeps child row references. The default fallback instead reads each child after its parent projection. Full-organization child arrays remain sequential, followed by the independent user page. No SeaORM `Related` implementation or public generic record API is required.

Fallback joins read each associated record after the parent row's output policies succeed. Memory groups only currently ready parent rows before the associated records' batch projection; a suspended parent does not delay ready peers. SQL preserves its actual asynchronous query boundary. Immediately ready nested Rust futures do not reproduce JavaScript microtask timing, but each row retains field order and the read-after-parent dependency. Session token batches complete the selected User relationship at this boundary and supply `SessionData<JoinValue<UserView>>` to the caller. Received invitations use the same continuation for Organization projection. Secondary session hits keep their cached projections and token-batch reads do not add a database fallback.

Set `advanced.database.joins = Some(true)` to enable SeaORM native Session/User, Account/User, and User/Account joins. Omission and `Some(false)` retain fallback reads. Each native lookup uses one SQL statement with the parent selection and limit inside a subquery. Output callbacks observe the selected child values even when a parent callback changes stored display fields. Application entities need their existing typed column bindings; they do not need a `Related` implementation. A missing child is distinct from a model decoding error, which propagates.

Native session batches project the users of currently ready parent rows together. A suspended parent does not block ready peers. User-to-account children project sequentially in both modes; a child callback error stops later children. The public account-list method retains batch projection. Native SQL account-child limits follow the upstream assembled-array limit: positive fractions truncate, negative values and NaN select no children, and positive infinity retains all children. SQL parent pagination keeps its existing backend rules. These methods do not define an ordering when their SQL query has no explicit order. Secondary cache hits retain their existing behavior; permitted single-session database misses use the inner snapshot method.

Native Memory Session/User, Account/User, and User/Account joins select live child records. The query selects the parent snapshot and child row references together. Child projection reads each field under a short lock before its callback; no lock crosses an await. A callback can update a later display field, and the selected child observes that value without a second lookup. Native Memory child limits count selected distinct rows; fallback lists retain slice semantics, including their different fractional and non-finite behavior. Session predicates retain their existing identity checks. Rust completes already-started peer projections before returning the first original error; an unstarted sequential child does not run after an earlier child fails.

The Memory fallback User→Account aggregate also retains the selected account page as row references. If one child's display callback updates a later child's display field, that later child reads the updated value. The page is selected once, before child callbacks, and each child projects sequentially.

Memory user point reads, user lists, and fallback User associations retain selected row references through output projection. Each field reads its current stored value before its callback, so an awaited name callback can update a later image field. List filtering, sorting, and pagination use the query snapshot; output callbacks do not select a new page. A fallback User→Account parent is live, while a native join parent retains its query snapshot. Write-return and delete-hook projections keep their existing boundaries. Memory User associations preserve the source field presence in both join modes. Declared output policies can still produce fields that were absent in storage.

Custom adapters must implement `UserStore::get_user_with_accounts` and `AccountStore::get_account_owner` for password and OAuth sign-in. `AccountOwner.user` and `UserAccounts.accounts` use `JoinValue::One(Option<T>)` or `JoinValue::Many(Vec<T>)`; import `JoinValue` from `better_auth::store`. Preserve the relationship shape selected by the schema. `UserAccounts::new` replaces only a missing single Account with an empty page. A missing single User identifies an orphaned Account. Account-owner reads reject duplicate parent Account identities after projection; multiple child Users do not count as duplicate parents.

Memory and SeaORM resolve final Account/User references before reading either model, including empty databases and both native and fallback joins. Replacing `account.userId` without `references` removes its built-in reference. The resolver scans the joined model's references in schema order and scans the reverse direction only when the first scan finds none. Unknown models, missing references, and multiple references reject the read before queries or output callbacks. Active logical names take precedence over physical aliases; SeaORM resolves physical aliases against actual Entity table names. Custom adapters can call `UserAccounts::resolve_schema` or `AccountOwner::resolve_schema` with their active `ModelFields` and table matcher.

The resulting `ResolvedJoin` supplies the selected fields and cardinality. Native joins compare captured physical values. Fallback joins query children after parent output and bind the projected source value through the selected target field. Unique references produce a single child; other reverse references can produce arrays. OAuth admission and session issuance use the selected User ID. Email and OAuth sign-in preserve the upstream failure when an Account relationship is a single object instead of an array. Arbitrary custom plugin models and other model pairs remain separate alignment work.

Custom adapters must also implement `AccountStore::get_credential_account`. This point query matches the stored `userId`, `providerId = "credential"`, and `accountId = userId` before applying account output policies. The query does not use `default_find_many_limit`. Keep ordinary account lists capped; do not implement this method by filtering a list page.

## Generate an initial schema

Run the CLI with every plugin that your application registers:

```sh
better-auth-rs generate --plugins two-factor,api-key --output src/auth_schema.rs
```

The CLI generates core entities, plugin fields and tables, unique indexes, and foreign keys. Unknown plugin names fail. Existing output files are preserved unless you pass `--force`.

Call the generated `create_auth_tables(&database).await?` from the application's initial migration. The function creates tables in an empty database and fails when a table already exists. The function does not compare schemas, alter existing tables, or track migration versions. Use your application's versioned SeaORM migrations for later changes, including plugin additions.

The application owns the generated source. The four core entities use `AuthSchema`. Organization tables use `SeaOrmOrganizationSchema`. API keys, device codes, passkeys, two-factor credentials, JWT keys, and wallet addresses use `SeaOrmPluginSchema`. Table and column attributes on the selected models control all store operations, including conditional updates and transactions.

For application-owned entities, bind the four model types with `AuthSchema`:

```rust
#[derive(better_auth::AuthSchema)]
#[auth(
    user = "user::Model",
    session = "session::Model",
    account = "account::Model",
    verification = "verification::Model"
)]
pub struct AppAuthSchema;
```

Each model must implement its corresponding auth entity trait. You may place each binding in a separate `#[auth(...)]` attribute. Each binding must appear exactly once.

Auth responses serialize timestamps as UTC ISO 8601 strings with three fractional digits, matching the upstream JavaScript client. SeaORM User writes on SQLite bind native `createdAt` and `updatedAt` UTC Chrono values in the same format. This intentionally truncates submillisecond precision for those newly written values, including automatically generated update timestamps. Public Rust date types remain unchanged. Other databases and other date fields retain their existing bindings.

The generated SQLite `date` declaration does not itself change parameter encoding. The native User conversion occurs at the existing write-binding boundary after the model resolves each logical column, so physical aliases retain that conversion. Handwritten models that bind strings or other date variants, direct application ActiveModel writes, declared Date extras, and application-authored SQL predicates keep their existing behavior. Existing rows are not rewritten. Native User list/filter/count operations compare decoded UTC instants; truncation can change submillisecond equality or ordering. Mixed historical text and application SQL comparisons require a separate contract.

The accepted two-row User timestamp interchange baseline preserves SQLx's original automatic fractional precision and numeric UTC offset. All four public reads passed for fixed whole-second and millisecond inputs, with raw text unchanged after reading. That actual fixture remains as prior evidence. The revised writer contract retains every observation and assertion and adds explicit raw equality between both writers. Actual recapture and the strict consumer comparison pass with equal raw text and storage classes for both writers. All four public reads preserve the fixed inputs, and reading leaves the raw values unchanged. The accepted prior fixture remains separate. The fixed contract does not establish submillisecond inputs, update timestamps, date predicates, existing migrations, custom-model bindings, or other databases.

## Model IDs

Configure `advanced.database.generate_id` with `Some(IdGeneration::Random)`, `Some(IdGeneration::Uuid)`, `Some(IdGeneration::Serial)`, `Some(IdGeneration::Database)`, or `Some(IdGeneration::Custom(generator))`. Omission uses `Random` through the `generate_id()` getter. Direct policy assignments now require `Some`. `Random` uses 32 alphanumeric characters. For SQL stores, `Serial` requires numeric auto-increment columns and `Database` requires application database defaults. The memory adapter uses its current table length plus one for `Serial`; deletion can therefore produce duplicate IDs. `Database` omits IDs in memory. PostgreSQL `Uuid` uses the database UUID default; SQLite generates UUIDs in Rust. These options do not change existing columns or migrations.

Generate matching entities and an initial migration with `better-auth-rs generate --generate-id serial`, or `--generate-id uuid --database postgres`. The database option accepts `sqlite` (default), `postgres`, and `mysql`, and selects ID and application JSON storage types and fresh catalog defaults. Serial schemas use `i64` IDs and references for SQLite and `i32` for PostgreSQL and MySQL; PostgreSQL uses identity columns, SQLite uses integer primary keys, and MySQL uses auto-increment columns. UUID schemas use native `Uuid` fields and `pg_catalog.gen_random_uuid()` defaults for PostgreSQL; SQLite and MySQL retain text IDs. Use the generated schema with the selected database backend.

`--generate-id database` preserves the upstream text-ID schema without inventing defaults. Add application-owned defaults before using `IdGeneration::Database`, or use an existing numeric or UUID schema with its own defaults. `AuthEntity` derives read the declared ID and user-reference types, parse public string IDs at the model boundary, and leave absent IDs unset. The generator marks additional ID references with `#[auth(reference)]`; use the same attribute on handwritten reference fields.

A custom generator receives the logical model name, such as `user`, `apikey`, or `walletAddress`. Table aliases do not change that name. Return `Ok(None)` to omit the ID, or an error to stop the write. Create-before hooks run before generation. A cancelled hook does not invoke the generator.

User, Session, JWK, and Wallet creation apply each configured field's input transform and adapter binding before advancing to the next schema field. The ID generator runs at the configured `id` position, or after the other fields when `id` is implicit. The adapter replaces configured ID transforms, defaults, and column aliases with its ID policy. A force-allowed supplied ID skips the generator. A field or generator error stops later callbacks and prevents the write. Native fields retain their schema order, and numeric field names use JavaScript property order.

Memory User and Session creation bind the ID and application aliases to the same storage key in schema order. The last defined write wins. Output aliases read the canonical ID, call their output transform with the stored value, and then apply ID string conversion. Memory Serial mode replaces physical ID writes with the current row count plus one and repeats that assignment during insertion.

Session creation removes a caller-supplied `additional_fields.id` before create hooks. A create hook can supply an ID, including an explicit undefined or null value. The adapter applies its current ID defaults and input transform at the ID slot. A caught nested creation failure can retain a forced-ID policy for later fields of an outer update. A failure before adapter input does not change that policy.

Nested adapter operations share the current ID policy. If a nested output replaces the input policy before the outer creation reaches its ID slot, the outer creation omits ID generation. Memory output reads an ID at its field position, so an earlier output callback can change the returned ID. SQL output reads the returned database snapshot. Memory Serial mode still assigns its numeric ID during insertion.

SQL Session updates resolve a supplied ID at its schema position. Under the Serial input policy, `"1e2"` becomes `100`; empty strings and values that convert to `NaN` omit the ID write. Earlier callbacks can replace that input policy through a nested output. Field aliases retain their write order, and MySQL reads the updated row with the final ID or token binding.

```rust
use better_auth::config::IdGeneration;
let mut config = better_auth::AuthConfig::new("your-very-secure-secret-key-at-least-32-chars-long");
config.advanced.database.generate_id = Some(IdGeneration::Uuid);
```

An explicit `CreateUser.id`, `CreateOrganization.id`, `CreateInvitation.id`, or `CreateTeam.id` is a force-allowed ID. UUID mode accepts canonical hyphenated RFC 4122 version 1–5 IDs, including uppercase hexadecimal characters. Simple, braced, URN, and version 7 forms are omitted; the database then applies its default or constraint. `CreateOrganization::new` leaves generation to the store. `WalletStore::create_wallet_address` takes `CreateWalletAddress` without a caller-generated ID.

In `Serial` mode, the SQL adapter applies JavaScript number conversion before ID lookups and core, plugin, and organization reference writes. For example, `"1.6e1"`, `" 16 "`, and `"0x10"` address integer ID `16`. The adapter applies reference conversion after application input transforms and before the persistence model parses the value. Invalid or fractional values still encounter the model or database's numeric constraints. `Database` mode does not enable this conversion. `AuthEntity` supplies declared reference-column metadata through `SeaOrmPluginModel::is_id_reference` and `SeaOrmOrganizationModel::is_id_reference`; manual implementations must identify their ID reference columns. Explicit field policies override that metadata, and ordinary fields retain their input values.

Pure-secondary sessions and API keys use the context generator. The legacy `advanced.generate_id` callback overrides that context operation only. `IdGenerator` returns `Option<String>`: `None` represents upstream `false`, and `Some(value)` represents a string. Pure-secondary sessions use a random ID for `None`; an explicit empty string omits the session ID. Pure-secondary API keys use the upstream truthy fallback for both cases. Pure-secondary verification records have no generated ID. Session tokens and other authentication credentials use separate random generators.

Runtime records use `SchemaValue<String>` for IDs so `Undefined` remains distinct from an empty string. JSON omits absent IDs. Store and database-hook methods return `UserView` and `SessionView`; `AuthSchema::User` and `AuthSchema::Session` remain typed database mappings. Use `id.typed()?` only when the operation requires a present string ID. Use `id.is_undefined()` to inspect omission. Query application entity models directly when an application needs columns outside its configured auth fields.

`Passkey`, `PasskeyView`, and `TwoFactor` also use `SchemaValue<String>` for `user_id`. Their entity traits return `SchemaValue<Cow<'_, str>>`. `CreatePasskey.user_id` and `CreateTwoFactor.user_id` remain `String`. With the default reference declaration, Memory Serial mode stores numeric references, returns canonical string references, and binds owner `"001"` to user `1`.

Passkey `userId` accepts replacement field declarations. A replacement must include `references` to retain the default User reference conversion. TwoFactor uses the same complete replacement rule. API Key `referenceId` uses `SchemaValue<String>` in runtime records and has no default schema reference. An explicit reference declaration enables the shared reference conversion. Ownership checks consume the resulting runtime value.

`TeamMember.user_id` uses `SchemaValue<String>` for the default user reference. Team store inputs remain string references. Memory Serial mode binds membership lookups, user team lists, invitations, and member removal to numeric owners. Public TeamMember records return canonical string owners. Invitation acceptance retains its staged capacity checks and rejects a conflicting membership change before publishing member or session updates.

The opt-in PostgreSQL identity regressions use application-owned integer models. They check `Serial` and `Database` modes, session/account foreign keys, public string IDs, transaction commit and rollback, numeric aliases, and reference conversion after an input transform. A separate text-ID table checks forced UUID omission against a `gen_random_uuid()::text` default. Set `BETTER_AUTH_TEST_POSTGRES_URL` to a test database whose role can create schemas, then run:

```sh
devenv shell -- cargo test --locked --features axum,seaorm2,redis-cache --test legacy_schema_integration_tests live_postgres -- --ignored
```

The tests create and remove isolated schemas. They do not establish upstream driver parity or cover MySQL, native UUID column models, or additional reference columns outside the core account/session mappings.

## Fresh Session representation

SQLite native strings use TEXT and dates use literal `date`. PostgreSQL uses TEXT strings and TIMESTAMPTZ dates. MySQL uses VARCHAR(255) for token, TEXT for IP and user agent, and TIMESTAMP(3) dates. Server schemas give createdAt the native SQL timestamp default; updatedAt and expiresAt have no SQL default. Token uniqueness is inline, and the mapped userId index uses the shared upstream naming rule. The fresh catalog has no independent active column or expiresAt index. Core expiry, cache, and row-existence behavior remain unchanged.

Use `--session-active-column` when application-owned regeneration must retain the Rust independent active state. This flag preserves the previous Session representation and physical defaults on all CLI backends. Existing generated source, handwritten models, bundled entities, and migration history do not change automatically. The flag is a Rust extension, not an upstream option.

The marker rejects native `active` and any field exposing its logical or serialized alias. Configured logical `active`, including an alias to another model column, requires an active-column model. The adapter resolves the configured column first, so a missing mapping retains its original error. Generate declared Session application fields through `session.additionalFields`, then register the corresponding runtime policies. Session projection omits undeclared plugin fields. Declared nulls and explicitly tracked field presence remain intact.

The generated `create_auth_tables` is an initial creation scaffold. Applications own versioned migrations and must preserve historical inactive state on its active-backed model until they explicitly adopt and validate a migration. Changing date affinity with unchanged Chrono bindings does not establish raw timestamp interchangeability.

The core-only Session catalog contract passes the pinned capture, strict Bun comparison, and real generated Rust consumer. For existing entities, derive `AuthEntity` with role `organization`, `member`, `invitation`, `team`, `team_member`, or `organization_role`. Bind the models with `better_auth::seaorm::OrganizationModels<Organization, Member, Invitation, Team, TeamMember, OrganizationRole>`, or implement `SeaOrmOrganizationSchema`. The organization schema is independent of the four core `AuthSchema` model bindings.

`SeaOrmOrganizationModel` separates stored field extraction (`record_fields`) from projected record decoding (`record_from_fields`). Its shared `record` and `records` methods await configured output transforms and accept the adapter's native JSON capability. `AuthEntity` derives both pure methods. Manual model implementations must expose the same canonical and storage aliases, preserve unconfigured typed JSON values, and decode the projected fields without invoking transforms again. Input transforms run once before JSON and reference binding.

Organization `metadata` uses nullable text storage by default, matching the upstream String field. Absent metadata uses SQL NULL. Organization create and update operations encode JSON before storage; their responses decode that text. Raw adapter operations, including test utilities, preserve text without JSON parsing. The text `null` is distinct from SQL NULL.

When migrating a bundled or generated model from `Option<Json>` to `Option<String>`, migrate the database column to nullable text and preserve the stored JSON text, including quotes around JSON strings. Preserve SQL NULL separately. For example, a PostgreSQL migration can use `ALTER TABLE organization ALTER COLUMN metadata TYPE text USING metadata::text`. SQLite applications must rebuild the table with a TEXT column and copy the existing metadata values. Apply migrations before using the new model. Applications with an explicitly declared JSON model may retain `Option<Json>` and the existing native JSON semantics; the adapter continues to support that model contract.

Team membership storage requires nullable `membership_key` with a unique index. The plugin computes this value as unpadded base64url of SHA-256 over the JSON `[teamId, userId]` tuple. Keep the unique `(team_id, user_id)` index to protect existing rows with a NULL membership key. Use the corresponding mapped column names when your schema renames these fields.

## Plugin Fields

`ApiKey`, `Passkey`, `DeviceCode`, `TwoFactor`, `Jwk`, and `WalletAddress` runtime records wrap native fields in `SchemaValue<T>`. Public views preserve exposed fields in these wrappers, except API Key permissions and metadata use `FieldValue` for their decoded values. Plugin-specific Legacy state retains its existing representation.

`Typed(value)` retains the default Rust type. `Dynamic(FieldValue)` retains a replacement value, including null, dates, arrays, objects, and UTF-16 strings. `Undefined` omits the JSON field. For example, `name` uses `SchemaValue<Option<String>>`: `Typed(None)` emits null, while `Typed(Some(value))` emits the string. Output transforms can return other field types without forcing an early string conversion.

Register policies through `AuthInitContext::register_model_fields` for the corresponding `EntityRole`. A later declaration replaces the complete earlier declaration and retains its field position. Register the plugin that supplies overrides after the plugin that supplies the native fields. The shared conversion applies defaults, references, transforms, and physical column mappings. The adapter controls `id`. Typed create and update inputs enter the same conversion as logical `FieldMap` record operations.

Memory stores physical `FieldMap` values and reads each selected field when its output phase starts. Earlier callbacks can therefore change values observed by later fields. SeaORM reads supported SQL driver values into a query snapshot before output transforms and runtime record construction. This path does not first decode the row into the application's typed model.

Direct application queries still use the model's declared Rust types. SQL columns and constraints control accepted writes, and unsupported driver types return errors. The shared runtime representation does not establish compatibility for every handwritten SQL type.

Read `.field_value()` when application code accepts the configured runtime type. Read `.typed()?` when an operation requires the default Rust type. That call rejects dynamic or omitted values instead of coercing them. Plugin consumers retain their own requirements: Passkey authentication decodes the COSE public key and credential ID, then checks the counter's runtime value. Field policies do not replace HTTP validation, ownership checks, or cryptographic verification.

`CreatePasskey.name` and `CreatePasskey.aaguid` use `SchemaValue<Option<String>>`. Use `Default::default()` for omission, `None.into()` for explicit null, and `Some(value).into()` for a string. Input callbacks distinguish omission from null. Memory retains omitted stored fields, while nullable SQL columns read back as null. Existing model definitions and tables do not change automatically. Applications own migrations when a replacement declaration changes physical storage.

Passkey records expose `created_at: SchemaValue<Option<FieldDate>>`, `updated_at: SchemaValue<FieldDate>`, and `credential: SchemaValue<String>`. Native storage omits the Legacy credential and update timestamp columns. Legacy retains those internal values separately from the native schema declarations. `PasskeyView.created_at` uses the same `FieldDate` representation and serializes dates as UTC millisecond strings. The HTTP view omits credential and updatedAt. Direct create and authentication-update inputs must select the store's explicit [storage mode](/docs/plugins/passkey#storage-modes).

`CreateDeviceCode.scope` and `UpdateDeviceCode.scope` use the same omitted/null/string input representation. DeviceCode scope field policies run through the shared adapter conversion, including successful conditional updates and claims. The returned boolean waits for output conversion; failed input conversion performs no write, and failed output conversion propagates after persistence.

API Key creation without a name retains its explicit null default. Database field policies run before fallback-cache population; cache reads preserve the projected omission or null without repeating callbacks. Secondary-only API Key operations continue to bypass database field policies.

`build().await` rejects a plugin when the user or session entity cannot persist its required fields. `AuthEntity` derives this capability list from the model fields.

| Plugin | Required user fields | Required session fields |
| --- | --- | --- |
| Username, enabled with `EmailPasswordPlugin::username(true)` | `username`, `display_username` | None |
| Two-factor | `two_factor_enabled` | None |
| Admin | `role`, `banned`, `ban_reason`, `ban_expires` | `impersonated_by` |
| Organization | None | `active_organization_id` |

For manual `AuthUser` and `AuthSession` implementations, declare `const PLUGIN_FIELDS: &'static [&'static str]` with the supported Rust field names. Declare a field only when the entity getter and store writes support that field. The default empty list supports core fields only.

Manual SeaORM implementations can use `better_auth::seaorm::field_value::from_column` in `AuthRecordFields` to read native dates, arrays, and SQL NULL without serializing the model through JSON. Use `decode_column` for supported typed writes. For nullable non-JSON columns, map `FieldValue::Null` to `None` and decode present values separately. Native SQL array writes are unsupported. Both functions return errors for unsupported conversions; propagate those errors.

Run the application database migrations before starting the server. Capability validation checks Rust entities; capability validation does not inspect database tables or replace migrations.

## Existing Databases

User `name` and `image` values use `SchemaValue<Option<String>>` in `CreateUser`, `UpdateUser`, and `UserView`. `Undefined` omits a field; `Typed(None)` clears it; `Dynamic(value)` retains a non-string record value. Use `Some(value).into()` for a string and `view.name.typed()?` when application code requires the default type. Signup and OAuth endpoints retain their own input schemas.

The runtime view is independent of the physical model. `AuthEntity` reads each field through its Serde name and binds writes through its mapped SeaORM column. Explicit JSON columns retain JSON values. Custom nullable columns retain their database constraints. Default generated user schemas require `name`; migrate existing NULL names before adding a NOT NULL constraint.

Manual `AuthUser` implementations no longer define string-only `name()` or `image()` getters. Implement `serialized_field_name` when the model uses a different Serde name. For example, return `"displayName"` for `"name"` and return the input unchanged for other fields. Leave `name` and `image` unset in `SeaOrmUserModel::new_active` and `apply_update`; the shared record binder writes these fields after applying storage policies.

SQLite rejects a nonempty array that Bun would treat as a replacement for the whole SQL parameter list. The upstream overload can replace the authenticated WHERE identity and update another user. Rust rejects that overload before executing SQL; it does not reproduce the authorization defect.

If your application already has a `users` table with extra fields or non-string primary keys, keep the same public integration story:

1. Reuse your app-owned SeaORM entities.
2. Use `#[derive(AuthEntity)]` for the supported fields, including integer and UUID IDs. Implement the public model traits manually when the application needs custom construction or projection.
3. Keep `sessions`, `accounts`, and `verifications` as app-owned SeaORM entities in the same database.
4. Run your own SeaORM migrations alongside the rest of the application schema.

The canonical worked example is [`examples/postgres_usage.rs`](../../../../examples/postgres_usage.rs), which demonstrates:

- an existing app-owned schema
- numeric user IDs
- seeded legacy users
- additional required app fields on the user table
- Better Auth mounted on top of the same `DatabaseConnection`

See [Account and Verification Fields](/docs/concepts/account-verification-fields) for runtime policies, storage projections, and handwritten adapter migration.

### User field values

User `name` and `image` values preserve omission, null, and raw JSON in `SchemaValue`. Memory retains the values; SQL stores apply the declared column type and database constraints. The default SQL user name is required. Applications with custom nullable models can retain that schema. SQLite JSON columns accept JSON values; non-JSON columns reject arrays and objects. Rust keeps each value bound to its declared column and rejects the upstream Bun driver's parameter-overload behavior. This is an intentional compatibility exception that preserves statement identity conditions.

`SeaOrmUserModel::new_active` and `apply_update` return `AuthResult`. Direct model calls decode supplied `name` and `image` values into the declared column types. Omitted values leave columns unset or unchanged. Incompatible values return serialization errors. `AuthEntity` generates this behavior; handwritten models must implement the same conversion.

Memory string predicates retain type-safe handling of replacement values. Query failures caused by unrelated malformed rows in the upstream adapter are not reproduced.

## User Updates

`UserStore::update_user_by_id_value` and its transaction counterpart accept a `FieldValue` ID and return `None` after cancellation or an unmatched query. Before-hook cancellation skips the query and after hooks. An unmatched query runs `after_update_user(None)`. OAuth profile overrides preserve the selected User or User array when the update returns `None`. The required string-ID `update_user` API still reports cancellation and missing-row errors.

`SeaOrmHooks::before_update_user` now receives `id: &FieldValue`. Update custom hook implementations to use this signature. Read `id.as_str()` when the hook requires a string; preserve other values when forwarding a native selector. Generic `DatabaseHooks::before_update_user` retains its existing arguments. No database migration is required.

## Account Hook Cancellation

`AccountStore::create_account_optional` and `update_account_optional` return `None` when a database hook cancels that account write. Hook errors remain errors, including errors from nested writes. The strict `create_account` and `update_account` methods retain their existing cancellation error behavior. Custom stores with cancellable hooks must implement the optional methods; their default implementations wrap successful strict results in `Some`.

Account schemas permit duplicate `(provider_id, account_id)` pairs, matching upstream storage. `AccountStore::get_account` reads at most two matching records and rejects an ambiguous identity after output projection. Its two-row limit is independent of `advanced.database.default_find_many_limit`. Generated schemas retain the account user index and foreign key. Existing applications that require upstream storage behavior must remove the former composite unique index in an application-owned migration; schema generation does not alter existing databases. Resolve duplicate identities before authentication can select an account.

## JSON field bindings

Custom adapters can use `FieldValue` and `FieldMap` to retain undefined, non-finite numbers, Date objects, arrays, and object identity before serialization. Ordinary clones retain object handles. Use one `StructuredCloneContext` for an entire transaction snapshot to copy identities while preserving aliases across records. Use `strict_equals` for JavaScript strict equality and `same_value_zero` for array membership; Rust `PartialEq` compares structure. Call `json` or `stringify` only at a JSON boundary. Top-level undefined returns `None`, object properties omit undefined, and array elements encode undefined as null. Non-finite numbers and invalid dates serialize as null. Valid dates retain the ECMAScript TimeClip range. Conversion to a Chrono model still requires Chrono's supported range. Built-in callbacks, runtime records, and adapter bindings preserve these native values until an explicit conversion boundary.

Use `utils::json::parse_native_json` for JSON text held in a native value. The shared parser preserves raw and escaped unpaired UTF-16 string values and applies JSON.parse string conversion. JWT keys and API Key cache records and reference lists use this parser. Safe and client JSON parsing retain their own error, pollution-check, and Date-revival policies. Object keys still require valid Unicode because `FieldMap` uses Rust strings; this parser does not establish complete JavaScript object-key parity.

`ApiKeyView::from_api_key_fields` preserves a native record's property order, removes the stored key hash, and applies the public permission policy. The shared record projection keeps source property order separately from field values. JSON and native output read the current typed fields, including later metadata changes. `ApiKeyView::default` supports ordinary typed construction; `field_order` controls projection order without duplicating values. Existing complete struct literals must supply the new field or use `..Default::default()`. Missing fields, explicit nulls, and native properties whose value is Undefined retain their distinctions until JSON serialization.

MySQL runtime Number bindings use numeric SQL tokens generated from ECMAScript number formatting, matching mysql2's query encoding. This preserves MySQL's distinction between exact decimal values and approximate DOUBLE parameters: an INTEGER assignment of `2.5` rounds to `3`. String values remain bound parameters. Database constraints and backend conversion errors still apply; direct application ActiveModel writes retain their own binding behavior.

Fresh PostgreSQL and MySQL OrganizationRole schemas store native `permission` as JSON text in a TEXT column. The generated SeaORM field is `String`; public `OrganizationRole.permission` uses `SchemaValue<FieldValue>`. Native create and update writes encode the final permission value once, and reads parse the stored text before returning the public record. Parse errors propagate. Explicit permission field policies keep their existing transform order and output representation. Physical field renaming alone does not enable a replacement policy.

Regenerating these server schemas changes the stored model field type and uses upstream table and column names unless explicit mappings override them. Existing generated files and databases do not change automatically. Applications that adopt the new schema must migrate their existing JSON permission column to TEXT and review direct model access. Keep the existing JSON or JSONB model until that migration is complete. Bundled models and SQLite generation retain their existing representation; this change does not rewrite migration history, IDs, references, or permission evaluation.

For fresh application JSON declarations without references, `--database sqlite` generates `SqlText` or `Option<SqlText>`. The fully qualified type is `better_auth::seaorm::SqlText`, an alias of the existing scalar-capable `ReferenceId` storage implementation. The alias alone does not declare a reference. PostgreSQL and MySQL continue to generate `Json`; native overrides and reference fields retain their existing types. The CLI also accepts these declarations through `user.additionalFields` and `session.additionalFields`.

Keep the runtime field policy as `UserFieldType::Json`. Omission stays absent, while explicit null becomes JSON text `null`. Objects and arrays become encoded text. Encoded strings, including whitespace and invalid JSON, remain unchanged in storage. Number and Boolean inputs retain SQLite scalar bindings; TEXT affinity produces their stored text. Output callbacks receive stored text before JSON decoding. Invalid encoded text reaches the existing parser, which logs the error and returns null.

The SQLite binding also applies to application-owned TEXT-compatible columns with a declared non-reference JSON policy, including configured native TEXT overrides. A handwritten model must accept the scalar bindings; incompatible types return the existing database type error. `SqlText` supplies that capability. The old ID/reference branch remains unchanged. An explicit typed `Json` column retains its previous representation limits, including the distinction between SQL NULL and encoded JSON null on input; this generator change does not repair every handwritten model.

Regeneration changes the public Rust field type of affected SQLite models. Existing generated files and persisted values do not change automatically. The generated JSON columns already use SQLite TEXT, so this change adds no migration or data rewrite. Review application code that directly accesses those model fields; persisted `SqlText` values use the `Text(String)` variant. The pinned SQLite capture, strict Bun comparison, and generated Organization consumer pass for 11 create/read cases and three update/read cases. The comparison preserves complete callback events, returned display values, and exact stored text or SQL NULL. The CLI generation tests and all 23 library consumers pass; the live PostgreSQL test remains separate.

When a field binding requires JSON text, the adapter uses the shared JavaScript-compatible serializer. The serializer orders array-index property names before other keys and uses JavaScript number formatting. Input policies run before this conversion. Output callbacks receive the stored text, or text reconstructed from a typed JSON value, before the adapter decodes the callback result.

`UserFieldConfig::adapter_input(value, supports_native_json, native_json_field)` returns `AuthResult<Value>`. Custom adapter callers must propagate or handle this result. `storage_fields_for_adapter`, `record_storage_fields_for_adapter`, and `adapter_output` retain their existing fallible signatures. Serialization errors propagate before the corresponding write or output callback; no fallback serializer runs.

This conversion applies where the existing field and adapter flags require text. It does not change reference conversion or native JSON capabilities. Native SQL JSON columns still use the database driver's serialization and normalization. PostgreSQL JSON fields retain native driver parameter encoding: an empty native array stores `{}`, while Date inputs and nonempty arrays can fail database JSON parsing. Declared StringArray and NumberArray fields encode JSON text before binding, including native JSON columns. Text JSON output decoding restores recognized ISO date strings as native Date values after output callbacks. Callback text equivalence does not establish identical raw native-column bytes. Application-owned column types and existing stored values remain unchanged.

## Notes

- Custom stores must report uniqueness conflicts as `DatabaseError::UniqueConstraint`. Device code generation retries only that error, up to three attempts.
- Custom stores expose JSON adapter behavior through `UserStore::supports_native_json`, inherited by `AuthStore`. Return `false` when field callbacks receive JSON text, as with SQLite; return `true` for native JSON, as with PostgreSQL. The secondary storage facade forwards the database capability.
- `AuthEntity` supplies `SeaOrmUserModel::native_json_field` and `SeaOrmSessionModel::native_json_field` from column definitions. Handwritten models must return `true` for serialized application field names backed by JSON columns. This preserves native JSON objects in typed models while the output boundary supplies adapter text to callbacks.
- Better Auth no longer owns a public SeaORM migration path. Auth and app tables should be migrated together by the host application.
- `MemoryCacheAdapter` and the optional asynchronous `RedisAdapter` implement `SecondaryStorage`. Install an adapter with `BetterAuth::secondary_storage` to enable session persistence. `RedisAdapter::clear` clears the selected Redis database.

## Secondary Session and Verification Storage

Install `MemoryCacheAdapter`, `RedisAdapter`, or an application implementation through `BetterAuth::secondary_storage`. The runtime uses the backend for sessions and verification values. Set `session.store_session_in_database` and `verification.store_in_database` to retain database persistence. Session creation writes to secondary storage immediately by default, including inside a database transaction. The cache snapshot reads the user through the active transaction. A later rollback does not undo that cache write, matching upstream. `AuthTransaction::create_session_with_deferred_secondary_optional` delays the cache write until commit, after session after hooks, and preserves a null creation result. Passkey registration uses this mode. The strict `create_session_with_deferred_secondary` convenience remains available. Rollback discards deferred writes.

Direct `SecondaryStore` callers may use `.with_clock(clock)` to control the facade's timestamps, expiration checks, and cache TTL calculations. The default is `Utc::now`. Clones, runtime views, and deferred writers retain the same clock. The underlying database store and secondary backend retain their own clocks; this method does not change their expiration behavior.

`UserView::field_order` retains source field order for serialization and cache writes. When constructing a view manually, use an empty vector for the default order or supply the source keys. `AuthUser::field_order()` defaults to `None` for handwritten models; runtime views expose their preserved order. Visibility filtering still removes hidden or omitted fields without restoring them from the order list.

Session and Verification caches use the shared native JSON boundary. UTF-16 string values, dynamic values, numeric formatting, and property order survive cache writes and reads. Single-record safe parsing revives recognized dates; batch Session reads retain the upstream conditional `JSON.parse` behavior before native date hydration. Malformed cache entries retain each operation's existing miss, skip, or error policy.

When rate limiting selects secondary storage, the adapter must implement `SecondaryStorage::increment(key, ttl_seconds)`. Increment or create the counter atomically and return the new count. Apply the TTL only when creating the counter; later increments must preserve its expiration. Both bundled adapters provide this operation. The default trait method returns a configuration error when rate limiting requires the missing operation.

To run the Redis counter regression, set `REDIS_TEST_URL` to a disposable Redis 7+ instance:

```bash
devenv shell -- cargo test -p better-auth-core --locked --features redis-cache redis_counters_create_atomically_and_preserve_the_initial_expiration -- --ignored
```

Custom transaction adapters must implement `AuthTransaction::clone_handle`. The returned adapter retains the original transaction, including its finalized state. Finalization must not wait for retained handles. SeaORM serializes commit and rollback against individual SQL operations; application callbacks do not hold the connection lock. A retained SQL adapter rejects reads and writes after commit or rollback. The memory adapter retains its isolated rows. Rows installed during commit remain shared; unchanged base rows remain separate. A late memory update can change a shared committed row, but a late create or delete does not become a normal-store operation.

Custom `AuthTransaction` implementations must also implement WalletStore. Execute Wallet creation and both address lookup forms through the same active adapter. Preserve registered field policies and propagate errors to the transaction owner.

The memory adapter follows Better Auth 1.7.6's public-ID transaction merge. Missing or duplicated IDs can cause an update to disappear during commit. Changing an ID can move the row to the end of its table. These behaviors are upstream compatibility constraints; use unique, stable IDs for applications that rely on memory transactions.

Custom transaction adapters must implement `AuthTransaction::delete_verification_by_identifier` through the active adapter. Preserve verification deletion hooks and the existing ordered after-commit rules.

The transaction owner keeps its after-hook queue alive until commit processing finishes. Retained adapters use weak queue references. Rollback, an after-hook error, or completed processing drops unexecuted effects and releases their captured transaction handles. Effects appended while the queue is being drained run in insertion order. Effects appended after processing ends do not restart the queue.

Custom transaction adapters must implement `AuthTransaction::queue_after_commit`. Add each effect to the same ordered queue as database after hooks. Run the queue after commit, discard the queue on rollback, and stop at the first unhandled error. Keep the committing caller's ambient request scope during the drain. Capture each database hook's explicit request argument separately when the write occurs. `after_create_runtime_session` and `after_create_runtime_verification` accept that captured argument for secondary-only writes. A separate cache queue would reorder effects around later database hooks and could skip an earlier cache refresh when a later hook fails.

`SessionCreateWriter::write` receives the original creation object and final fields as `FieldMap`. Pass the projected adapter result when creation returns a record. If creation returns null, pass the hook-modified input without rerunning defaults or transforms. Keep the original object separate because secondary cache routing can consume values from before the hook patch. `VerificationCreateWriter` receives the corresponding final fields through the same nullable-result rule. Immediate Session writers run before after hooks; deferred writers run after those hooks and after transaction commit.

Raw creation methods for API Key, Passkey, DeviceCode, TwoFactor, JWK, and WalletAddress return `AuthResult<Option<FieldMap>>`. Typed `create_*_optional` entry points preserve null results where the caller needs the complete creation lifecycle. Strict typed conveniences return an error when no record is returned; that error does not mean the insert was cancelled. Passkey optional creation retains the selected Native or Legacy storage mode, including private Legacy credential material.

MySQL insert readback uses the transformed supplied ID, connection-local serial ID, declared unique fields in declaration order, then the complete converted input. Unique probing uses the adapter's current declarations, including the adapter-owned ID replacement; an application's replaced ID mapping or unique flag does not survive that replacement. A unique full match returns the row; an ambiguous or absent match returns null. Direct INSERT precedes a separate readback transaction. Readback errors leave a direct insert committed; errors in an explicit outer transaction roll back that transaction. PostgreSQL and SQLite retain their returning-statement behavior.

Adapters used with secondary sessions must implement `SessionStore::update_session_with_writer_by_token_value`. Keep the string convenience method delegated to this native entry point. Run before hooks once, pass the accumulated `SessionUpdate` to the supplied `SessionUpdateWriter`, then perform the database write when `write_database` is true. Run after hooks with the selected nullable result. Do not call a second complete update lifecycle after the cache writer. The four existing update convenience methods retain their original behavior when no secondary backend is installed.

`delete_user_sessions_optional` returns `None` when a before hook cancels the batch and `Some(count)` after a completed write, including `Some(0)`. `UserStore::delete_user_optional` and its transaction counterpart preserve the same cancellation boundary for user deletion. Delete session children first when enabled, then account children, then the user. Child cancellation does not cancel later user deletion. Custom adapters must preserve these results so the secondary facade can decide whether to delete cached sessions; the default capability methods return explicit configuration errors.

`SessionStore::delete_sessions` deletes a token list through one batch lifecycle. `end_sessions` expires only its live rows and preserves database records. Multi-session uses these capabilities instead of repeated single-session deletion. With secondary storage, token deletions start together before the database batch and leave active-session indices unchanged. The first cache error prevents the database batch while pending cache deletions continue. Custom adapters must implement both batch capabilities when these paths are used; default implementations return configuration errors.

`AuthEntity` supplies field mappings for custom session models. Runtime store and hook results use `UserView` and `SessionView`; these records preserve fields from secondary storage without constructing an application entity model. Account and Verification persistence models instead produce `AccountView` and `VerificationView` through their `record` methods; secondary verification storage uses `VerificationView` directly. See [Secondary Storage](/docs/concepts/secondary-storage) for fallback rules and `VerificationIdentifierConfig` migration behavior.

## Runtime schema validation

SeaORM stores backed by SQLite, PostgreSQL or MySQL validate the configured physical tables before HTTP request hooks, native endpoints and outer transactions. PostgreSQL resolves unqualified entity tables through the effective connection search path. MySQL inspects the current database. Enable SeaORM's `sqlx-mysql` feature in the application to connect to MySQL. Initialization logs failures without rejecting the auth context. A disabled HTTP path returns its 404 before validation. Direct adapter CRUD does not run preflight.

The check reports missing tables, missing columns and extra required columns that inserts do not write. It does not validate SQL types, expected nullability, indexes or foreign keys. `AuthError::SchemaCheck` preserves structured `SchemaFinding` values. Configuration errors in entity mappings remain configuration errors.

Set `config.advanced.database.validate_schema = Some(false)` to disable automatic validation. `auth.context().database.schema_validation()` still exposes the explicit check. Adapters without introspection log a warning only when validation is explicitly enabled.

Each auth build has an independent cached verdict. Concurrent calls share one check. Successful checks and schema mismatches remain cached; driver errors can retry. Store clones share only the invalidation revision. After an application migration with actual schema changes, call `store.invalidate_schema_check()`, including after a partially failed migration. Call this on the original SeaORM store or a clone created before building auth. Separately constructed stores need separate invalidation, even if they share a SQLx pool. The adapter does not poll for DDL or automatically detect direct SQL changes. A migration with no changes need not invalidate.

PostgreSQL preflight reads sequence ownership and schema privileges through catalog OIDs. Unrelated schema cleanup does not require name resolution for those rows. The optional PostgreSQL acceptance test verifies migrations, cached results, defaults, serial columns and search-path precedence against a real server. Set `BETTER_AUTH_TEST_POSTGRES_URL` to a test database whose role can create and drop schemas, then run `devenv shell -- cargo test --locked --features axum,seaorm2,redis-cache --test schema_preflight_tests live_postgres_ -- --ignored`. The test removes its isolated schemas after success. If the test fails, inspect and remove its `ba_preflight_` schemas before repeating the test.

`AuthEntity` provides physical core-field mappings automatically. Handwritten models must implement `field_column` for every core and configured field. Use the existing typed `Column` values so `column_name` remains authoritative. If a handwritten `new_active` supplies extra application columns outside field policies, declare only those columns through `extra_insert_columns`:

```rust,ignore
fn extra_insert_columns() -> Vec<Column> {
    vec![Column::TenantId, Column::Locale]
}
```

Leave the default empty list when inserts do not supply extra columns. Do not declare every entity column: an unconfigured required column must still fail preflight.

Custom database adapters can implement `RuntimeStore::schema_check` using `SchemaInspector` and the typed physical `SchemaTable` descriptors. The descriptor supports migration-disabled tables and merges logical models that share a physical table. It does not use OpenAPI documentation as persistence metadata.

Organization member queries supply an explicit user limit. Full organization queries use the static membership limit for the user page. A member without a matching user fails the operation.

`SessionStore::get_session_snapshot` and `get_session_snapshots` return an optional loaded `SessionData<JoinValue<UserView>>`. `None` means the adapter did not load the relationship; `One(None)` means the selected User is missing; `Many` retains every selected User, including an empty page. `into_typed()` requires a singular User and rejects arrays. `SessionManager::resolve_native` preserves arrays; typed `resolve` rejects arrays before refresh or cookie writes. HTTP, typed callback, and cache projections for relationship arrays still require paired coverage.
