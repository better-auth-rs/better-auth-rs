Better Auth uses your application's SeaORM entities and `DatabaseConnection`
for auth persistence through the `seaorm2` feature on `better-auth`.

The supported public path is:

1. Enable the `seaorm2` feature on `better-auth`.
2. Define auth entities in your app with `#[derive(AuthEntity)]` from `better_auth::seaorm`.
3. Register them in an app schema with `#[derive(AuthSchema)]`.
4. Manage auth migrations in your own SeaORM migrator.
5. Build a `SeaOrmStore` from the shared `DatabaseConnection` and pass it to `BetterAuth::<YourSchema>::new(config).store(...)`.

## Setup

Generate `src/auth_schema.rs` with the [quick-start guide](/docs/quick-start) first.

```rust
mod auth_schema;
use auth_schema::{AppAuthSchema, create_auth_tables};
use better_auth::{AuthConfig, BetterAuth};
use better_auth::plugins::EmailPasswordPlugin;
use better_auth::seaorm::{Database, DatabaseConnection, SeaOrmStore};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let database = Database::connect("sqlite::memory:").await?;
    create_auth_tables(&database).await?;
    let auth_database: DatabaseConnection = database.clone();
    let config = AuthConfig::new("your-very-secure-secret-key-at-least-32-chars-long")
        .base_url("http://localhost:3000");
    let store = SeaOrmStore::<AppAuthSchema>::new(config.clone(), auth_database);

    let auth = BetterAuth::<AppAuthSchema>::new(
        config,
    )
    .store(store)
    .plugin(EmailPasswordPlugin::new().enable_signup(true))
    .build()
    .await?;

    // Keep using `database` for your app's own tables and queries.
    println!("plugins: {:?}", auth.plugin_names());
    Ok(())
}
```

## Generate an initial schema

Run the CLI with every plugin that your application registers:

```sh
better-auth-rs generate --plugins two-factor,api-key --output src/auth_schema.rs
```

The CLI generates core entities, plugin fields and tables, unique indexes, and foreign keys. Unknown plugin names fail. Existing output files are preserved unless you pass `--force`.

Call the generated `create_auth_tables(&database).await?` from the application's initial migration. The function creates tables in an empty database and fails when a table already exists. The function does not compare schemas, alter existing tables, or track migration versions. Use your application's versioned SeaORM migrations for later changes, including plugin additions.

The application owns the generated source. The four core entities use `AuthSchema`. Organization tables use `SeaOrmOrganizationSchema`. API keys, device codes, passkeys, two-factor credentials, JWT keys, and wallet addresses use `SeaOrmPluginSchema`. Table and column attributes on the selected models control all store operations, including conditional updates and transactions.

For application-owned entities, bind the four model types with `AuthSchema`:

```rust
#[derive(better_auth::AuthSchema)]
#[auth(
    user = "user::Model",
    session = "session::Model",
    account = "account::Model",
    verification = "verification::Model"
)]
pub struct AppAuthSchema;
```

Each model must implement its corresponding auth entity trait. You may place each binding in a separate `#[auth(...)]` attribute. Each binding must appear exactly once.

Auth responses serialize timestamps as UTC ISO 8601 strings with three fractional digits, matching the upstream JavaScript client. Stored database timestamps retain their original precision.

## Map plugin tables and columns

Use upstream model names in `--schema-config`: `apikey`, `deviceCode`, `passkey`, `twoFactor`, `jwks`, and `walletAddress`. Enable the corresponding plugins when generating the schema. For example:

```json
{
  "apikey": { "modelName": "machine_credentials", "fields": { "key": "credential_hash", "referenceId": "owner_id" } },
  "deviceCode": { "modelName": "device_authorizations", "fields": { "userCode": "activation_code" } },
  "passkey": { "fields": { "credentialID": "credential_id" } },
  "user": { "fields": { "twoFactorEnabled": "otp_enabled" } }
}
```

Bind the generated models when constructing the store:

```rust,ignore
let store = SeaOrmStore::<auth_schema::AppAuthSchema>::new(config, database)
    .with_plugin_schema::<auth_schema::AppPluginSchema>();
```

For existing entities, derive `AuthEntity` with role `api_key`, `device_code`, `passkey`, `two_factor`, `jwk`, or `wallet_address`. Keep the required Rust field names and types; use SeaORM `table_name` and `column_name` attributes for SQL names. Select models with `PluginModels<ApiKey, DeviceCode, Passkey, TwoFactor, Jwk, WalletAddress>`, or implement `SeaOrmPluginSchema`. Omitted `PluginModels` parameters use the bundled models. `with_plugin_schema` and `with_organization_schema` preserve each other's bindings.

The generated migration maps indexes and foreign keys to the selected table and column names. Apply these names in application-owned migrations too. The library's bundled migration only manages bundled tables.

## Organization models

Use `--schema-config` to generate Organization tables with application column names and additional fields:

```sh
better-auth-rs generate --plugins organization --schema-config organization-schema.json --output src/auth_schema.rs
```

```json
{
  "session": {
    "fields": { "activeOrganizationId": "selected_organization" }
  },
  "organization": {
    "modelName": "workspaces",
    "fields": { "slug": "workspace_slug" },
    "additionalFields": {
      "label": { "type": "string", "fieldName": "stored_label", "required": false },
      "tags": { "type": "string[]", "required": false }
    }
  }
}
```

The configuration accepts `organization`, `member`, `invitation`, `team`, `teamMember`, and `organizationRole`. Each model supports `modelName` and `fields` mappings. Core field keys use upstream camelCase names. Rust core fields retain their snake_case names. The `user`, `session`, `account`, and `verification` entries also support table and column mappings, including fields from enabled plugins. Primary key names remain `id`.

All Organization models except `teamMember` support `additionalFields`. Supported types are `string`, `number`, `boolean`, `date`, `json`, `string[]`, `number[]`, and string arrays that define enum values. Array fields use transparent typed JSON wrappers. Enum fields use `String` storage; the CLI does not generate enum validation. For new fields, only `required: true` generates a nonnullable column. Omitted or false `required` generates an `Option` field. New organization role fields always remain nullable because upstream makes these fields optional when constructing the role update endpoint. `unique: true` generates a unique index.

An additional field with a built-in public name, such as `name`, `logo`, or `createdAt`, replaces that field's generated type and nullability. Only `required: true` generates a nonnullable column; organization role fields remain nullable. A built-in override also replaces its `fields` mapping: `fieldName` selects the SQL column and Serde serialization name, and omitting `fieldName` restores the default column. Its `unique` setting replaces the single-column index; necessary composite identity constraints remain. The adapter owns `id`; an additional-field declaration does not change its type, column, or primary key.

Organization records expose replaceable built-in fields as `SchemaValue<T>`. `Typed(T)` contains the default Rust type, `Dynamic(Value)` preserves another JSON type, and `Undefined` omits the field during serialization. Use `.typed()?` when an operation requires the default type and `.json()?` when an application accepts the configured type. Use `.into()` to construct a default value. Output transforms may return `None` to omit a field without removing the stored value. A timestamp replaced with a string retains that string without date normalization.

Organization `updatedAt` is an application field; the bundled store keeps its internal timestamp separate. Team `memberCount` remains the upstream internal counter. Ordinary team responses remove the counter, while full organization queries retain the adapter's projected counter.

The JSON configuration describes storage. The CLI does not generate SQL defaults, validators, transforms, or callback configuration. Additional field runtime metadata may appear in this JSON but does not configure the plugin. Configure the matching public names, types, and `field_name` in `OrganizationConfig.schema` with `UserFieldConfig`. `field_name` accepts the Rust field name or its Serde serialization name; SeaORM's `column_name` attribute controls the SQL column name. For example:

```rust
use better_auth::config::{UserFieldConfig, UserFieldType};
use better_auth::plugins::organization::OrganizationConfig;

let mut organization = OrganizationConfig::default();
organization.schema.organization.additional_fields.insert(
    "label".into(),
    UserFieldConfig {
        field_name: Some("stored_label".into()),
        required: Some(false),
        ..Default::default()
    },
);
organization.schema.organization.additional_fields.insert(
    "tags".into(),
    UserFieldConfig {
        field_type: UserFieldType::StringArray,
        required: Some(false),
        ..Default::default()
    },
);
```

The generated source exports `AppOrganizationSchema`. Select these models when constructing the store:

```rust
let store = SeaOrmStore::<AppAuthSchema>::new(config.clone(), database)
    .with_organization_schema::<auth_schema::AppOrganizationSchema>();
```

For existing entities, derive `AuthEntity` with role `organization`, `member`, `invitation`, `team`, `team_member`, or `organization_role`. Bind the models with `better_auth::seaorm::OrganizationModels<Organization, Member, Invitation, Team, TeamMember, OrganizationRole>`, or implement `SeaOrmOrganizationSchema`. The organization schema is independent of the four core `AuthSchema` model bindings.

Organization `metadata` uses nullable native JSON storage. Preserve SQL NULL for absent metadata and JSON null for an explicit stored JSON null. Existing application migrations must permit NULL in this column. Team membership storage also requires nullable `membership_key` with a unique index. The plugin computes this value as unpadded base64url of SHA-256 over the JSON `[teamId, userId]` tuple. Keep the unique `(team_id, user_id)` index to protect existing rows with a NULL membership key. Use the corresponding mapped column names when your schema renames these fields.

## Plugin Fields

`build().await` rejects a plugin when the user or session entity cannot persist its required fields. `AuthEntity` derives this capability list from the model fields.

| Plugin | Required user fields | Required session fields |
| --- | --- | --- |
| Username, enabled with `EmailPasswordPlugin::username(true)` | `username`, `display_username` | None |
| Two-factor | `two_factor_enabled` | None |
| Admin | `role`, `banned`, `ban_reason`, `ban_expires` | `impersonated_by` |
| Organization | None | `active_organization_id` |

For manual `AuthUser` and `AuthSession` implementations, declare `const PLUGIN_FIELDS: &'static [&'static str]` with the supported Rust field names. Declare a field only when the entity getter and store writes support that field. The default empty list supports core fields only.

Run the application database migrations before starting the server. Capability validation checks Rust entities; capability validation does not inspect database tables or replace migrations.

## Existing Databases

If your application already has a `users` table with extra fields or non-string primary keys, keep the same public integration story:

1. Reuse your app-owned SeaORM entities.
2. Implement the public `AuthUser` / `SeaOrmUserModel` traits manually instead of relying on `#[derive(AuthEntity)]`.
3. Keep `sessions`, `accounts`, and `verifications` as app-owned SeaORM entities in the same database.
4. Run your own SeaORM migrations alongside the rest of the application schema.

The canonical worked example is [`examples/postgres_usage.rs`](../../../../examples/postgres_usage.rs), which demonstrates:

- an existing app-owned schema
- numeric user IDs
- seeded legacy users
- additional required app fields on the user table
- Better Auth mounted on top of the same `DatabaseConnection`

## Account Hook Cancellation

`AccountStore::create_account_optional` and `update_account_optional` return `None` when a database hook cancels that account write. Hook errors remain errors, including errors from nested writes. The strict `create_account` and `update_account` methods retain their existing cancellation error behavior. Custom stores with cancellable hooks must implement the optional methods; their default implementations wrap successful strict results in `Some`.

## Testing

Run `devenv shell -- ./scripts/consumer-check.sh` to generate fresh schemas and test an independent consumer against the public package. The check creates SQLite tables, registers and signs in a user, protects an Axum route, creates an API key, and enables TOTP. A second schema verifies all six Organization model mappings, additional field storage types, partial updates, and organization deletion. A third schema renames every field in all six plugin tables and maps user, session, account, and verification columns. Tests exercise authentication, TOTP, API key quota consumption, device claims, passkey updates, JWT keys, and wallet chain lookup. Database constraint checks cover uniqueness and foreign keys.

Internal behavior tests also use a bundled schema. Dual-server and client SDK compatibility checks compare behavior with the TypeScript reference server.

## Notes

- Custom stores must report uniqueness conflicts as `DatabaseError::UniqueConstraint`. Device code generation retries only that error, up to three attempts.
- Custom stores expose JSON adapter behavior through `UserStore::supports_native_json`, inherited by `AuthStore`. Return `false` when field callbacks receive JSON text, as with SQLite; return `true` for native JSON, as with PostgreSQL. The secondary storage facade forwards the database capability.
- `AuthEntity` supplies `SeaOrmUserModel::native_json_field` and `SeaOrmSessionModel::native_json_field` from column definitions. Handwritten models must return `true` for serialized application field names backed by JSON columns. This preserves native JSON objects in typed models while the output boundary supplies adapter text to callbacks.
- Better Auth no longer owns a public SeaORM migration path. Auth and app tables should be migrated together by the host application.
- `MemoryCacheAdapter` and the optional asynchronous `RedisAdapter` implement `SecondaryStorage`. Install an adapter with `BetterAuth::secondary_storage` to enable session persistence. `RedisAdapter::clear` clears the selected Redis database.

## Secondary Session and Verification Storage

Install `MemoryCacheAdapter`, `RedisAdapter`, or an application implementation through `BetterAuth::secondary_storage`. The runtime uses the backend for sessions and verification values. Set `session.store_session_in_database` and `verification.store_in_database` to retain database persistence. Database transactions publish new session cache entries after commit; rolled-back transactions publish none.

`AuthEntity` generates runtime hydration for custom session and verification models. The application retains typed model fields and does not need to deserialize the user model. Handwritten model implementations must provide the corresponding runtime hydration methods before enabling secondary storage. See [Secondary Storage](/docs/concepts/secondary-storage) for fallback rules and `VerificationIdentifierConfig` migration behavior.
