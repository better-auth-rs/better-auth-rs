Better Auth uses your application's SeaORM entities and `DatabaseConnection`
for auth persistence through the `seaorm2` feature on `better-auth`.

The SeaORM integration enables SQLite, PostgreSQL, and MySQL drivers. Use the matching backend when generating entities with the CLI. Driver availability does not establish complete schema or value compatibility with the upstream adapter; the [alignment inventory](https://github.com/better-auth-rs/better-auth-rs/blob/master/docs/upstream-alignment-backlog.md) records the verified contracts.

The supported public path is:

1. Enable the `seaorm2` feature on `better-auth`.
2. Define auth entities in your app with `#[derive(AuthEntity)]` from `better_auth::seaorm`.
3. Register them in an app schema with `#[derive(AuthSchema)]`.
4. Manage auth migrations in your own SeaORM migrator.
5. Build a `SeaOrmStore` from the shared `DatabaseConnection` and pass it to `BetterAuth::<YourSchema>::new(config).store(...)`.

## Setup

Generate `src/auth_schema.rs` with the [quick-start guide](/docs/quick-start) first.

```rust
mod auth_schema;
use auth_schema::{AppAuthSchema, create_auth_tables};
use better_auth::{AuthConfig, BetterAuth};
use better_auth::plugins::EmailPasswordPlugin;
use better_auth::seaorm::{Database, DatabaseConnection, SeaOrmStore};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let database = Database::connect("sqlite::memory:").await?;
    create_auth_tables(&database).await?;
    let auth_database: DatabaseConnection = database.clone();
    let config = AuthConfig::new("your-very-secure-secret-key-at-least-32-chars-long")
        .base_url("http://localhost:3000");
    let store = SeaOrmStore::<AppAuthSchema>::new(config.clone(), auth_database);

    let auth = BetterAuth::<AppAuthSchema>::new(
        config,
    )
    .store(store)
    .plugin(EmailPasswordPlugin::new().enable_signup(true))
    .build()
    .await?;

    // Keep using `database` for your app's own tables and queries.
    println!("plugins: {:?}", auth.plugin_names());
    Ok(())
}
```

## Adapter configuration

Every auth build passes its final configuration, plugin database hooks, and `ModelFields` to `RuntimeStore::with_runtime`. Custom adapters must implement this method. Return a store view that shares stored records, binds the supplied configuration and model fields, and prepends plugin hooks to application hooks. Forward `ModelFields` through adapter wrappers. Pass `ModelFields::default()` when binding a raw adapter without plugin-table policies. Keep configuration and hook lists isolated from the original store and other auth builds.

`advanced.database.default_find_many_limit` preserves an optional numeric value; omission uses 100. Account and database session lists apply the default before output transforms. Bulk-delete hooks receive a limited snapshot, while the write still deletes every matching row. Verification lookup retains its explicit one-row limit, and secondary session lists remain uncapped. Memory follows JavaScript slice behavior; SQLite accepts negative integer limits as unlimited and rejects fractional or non-finite limits.

Organization lists apply the same default before output projection. User organization and team lists preserve the selected membership page's order. Full organization queries independently limit invitations, members and teams, then load the selected members' users. Received invitations select the email's page and project each associated organization before the endpoint keeps pending records; pending records can be expired.

Custom Organization adapters must return `InvitationOrganization` from `InvitationStore::list_user_invitations`. Resolve the organization with the stored foreign key. Role point lookup, filtered role queries and role count have separate store methods. Team and team-member counts remain independent of list pagination. Rust deliberately retains accurate capacity checks instead of reproducing upstream checks that count a capped team page.

Organization adapters also implement `MemberUser` reads and `OrganizationDetailsQuery`/`OrganizationDetails` for full organization responses. The query keeps member and user limits separate. `advanced.database.joins = Some(true)` selects related Organization records before projection: SeaORM uses one typed SQL statement, including all three full-organization child tables, and Memory keeps child row references. The default fallback instead reads each child after its parent projection. Full-organization child arrays remain sequential, followed by the independent user page. No SeaORM `Related` implementation or public generic record API is required.

Fallback joins read each associated record after the parent row's output policies succeed. Memory groups only currently ready parent rows before the associated records' batch projection; a suspended parent does not delay ready peers. SQL preserves its actual asynchronous query boundary. Immediately ready nested Rust futures do not reproduce JavaScript microtask timing, but each row retains field order and the read-after-parent dependency. Session token batches complete User projection at this boundary and supply `SessionData` to the existing caller. Received invitations use the same continuation for Organization projection. Secondary session hits keep their cached projections and token-batch reads do not add a database fallback.

Set `advanced.database.joins = Some(true)` to enable SeaORM native Session/User, Account/User, and User/Account joins. Omission and `Some(false)` retain fallback reads. Each native lookup uses one SQL statement with the parent selection and limit inside a subquery. Output callbacks observe the selected child values even when a parent callback changes stored display fields. Application entities need their existing typed column bindings; they do not need a `Related` implementation. A missing child is distinct from a model decoding error, which propagates.

Native session batches project the users of currently ready parent rows together. A suspended parent does not block ready peers. User-to-account children project sequentially in both modes; a child callback error stops later children. The public account-list method retains batch projection. Native SQL account-child limits follow the upstream assembled-array limit: positive fractions truncate, negative values and NaN select no children, and positive infinity retains all children. SQL parent pagination keeps its existing backend rules. These methods do not define an ordering when their SQL query has no explicit order. Secondary cache hits retain their existing behavior; permitted single-session database misses use the inner snapshot method.

Native Memory Session/User, Account/User, and User/Account joins select live child records. The query selects the parent snapshot and child row references together. Child projection reads each field under a short lock before its callback; no lock crosses an await. A callback can update a later display field, and the selected child observes that value without a second lookup. Native Memory child limits count selected distinct rows; fallback lists retain slice semantics, including their different fractional and non-finite behavior. Existing stored-identity checks and session predicates remain unchanged. Rust completes already-started peer projections before returning the first original error; an unstarted sequential child does not run after an earlier child fails.

The Memory fallback User→Account aggregate also retains the selected account page as row references. If one child's display callback updates a later child's display field, that later child reads the updated value. The page is selected once, before child callbacks, and each child projects sequentially.

Memory user point reads, user lists, and fallback User associations retain selected row references through output projection. Each field reads its current stored value before its callback, so an awaited name callback can update a later image field. List filtering, sorting, and pagination use the query snapshot; output callbacks do not select a new page. A fallback User→Account parent is live, while a native join parent retains its query snapshot. Write-return and delete-hook projections keep their existing boundaries.

Custom adapters must implement `UserStore::get_user_with_accounts` and `AccountStore::get_account_owner` for password and OAuth sign-in. Capture the canonical stored identity before applying output policies. The first method projects the user, then reads the account page with that stored identity under the default limit. The second method reads up to two accounts, projects each account and its persisted owner, and rejects duplicate account identities. `UserAccounts::new` and `AccountOwner::new` require the captured stored user ID and reject projections that change the relationship. An orphaned account has no joined user. OAuth resolves this join before admission callbacks or token updates, so a failed owner read must not refresh tokens.

Custom adapters must also implement `AccountStore::get_credential_account`. This point query matches the stored `userId`, `providerId = "credential"`, and `accountId = userId` before applying account output policies. The query does not use `default_find_many_limit`. Keep ordinary account lists capped; do not implement this method by filtering a list page.

## Generate an initial schema

Run the CLI with every plugin that your application registers:

```sh
better-auth-rs generate --plugins two-factor,api-key --output src/auth_schema.rs
```

The CLI generates core entities, plugin fields and tables, unique indexes, and foreign keys. Unknown plugin names fail. Existing output files are preserved unless you pass `--force`.

Call the generated `create_auth_tables(&database).await?` from the application's initial migration. The function creates tables in an empty database and fails when a table already exists. The function does not compare schemas, alter existing tables, or track migration versions. Use your application's versioned SeaORM migrations for later changes, including plugin additions.

The application owns the generated source. The four core entities use `AuthSchema`. Organization tables use `SeaOrmOrganizationSchema`. API keys, device codes, passkeys, two-factor credentials, JWT keys, and wallet addresses use `SeaOrmPluginSchema`. Table and column attributes on the selected models control all store operations, including conditional updates and transactions.

For application-owned entities, bind the four model types with `AuthSchema`:

```rust
#[derive(better_auth::AuthSchema)]
#[auth(
    user = "user::Model",
    session = "session::Model",
    account = "account::Model",
    verification = "verification::Model"
)]
pub struct AppAuthSchema;
```

Each model must implement its corresponding auth entity trait. You may place each binding in a separate `#[auth(...)]` attribute. Each binding must appear exactly once.

Auth responses serialize timestamps as UTC ISO 8601 strings with three fractional digits, matching the upstream JavaScript client. SeaORM User writes on SQLite bind native `createdAt` and `updatedAt` UTC Chrono values in the same format. This intentionally truncates submillisecond precision for those newly written values, including automatically generated update timestamps. Public Rust date types remain unchanged. Other databases and other date fields retain their existing bindings.

The generated SQLite `date` declaration does not itself change parameter encoding. The native User conversion occurs at the existing write-binding boundary after the model resolves each logical column, so physical aliases retain that conversion. Handwritten models that bind strings or other date variants, direct application ActiveModel writes, declared Date extras, and application-authored SQL predicates keep their existing behavior. Existing rows are not rewritten. Native User list/filter/count operations compare decoded UTC instants; truncation can change submillisecond equality or ordering. Mixed historical text and application SQL comparisons require a separate contract.

The accepted two-row User timestamp interchange baseline preserves SQLx's original automatic fractional precision and numeric UTC offset. All four public reads passed for fixed whole-second and millisecond inputs, with raw text unchanged after reading. That actual fixture remains as prior evidence. The revised writer contract retains every observation and assertion and adds explicit raw equality between both writers. Actual recapture and the strict consumer comparison pass with equal raw text and storage classes for both writers. All four public reads preserve the fixed inputs, and reading leaves the raw values unchanged. The accepted prior fixture remains separate. The fixed contract does not establish submillisecond inputs, update timestamps, date predicates, existing migrations, custom-model bindings, or other databases.

## Model IDs

Configure `advanced.database.generate_id` with `Some(IdGeneration::Random)`, `Some(IdGeneration::Uuid)`, `Some(IdGeneration::Serial)`, `Some(IdGeneration::Database)`, or `Some(IdGeneration::Custom(generator))`. Omission uses `Random` through the `generate_id()` getter. Direct policy assignments now require `Some`. `Random` uses 32 alphanumeric characters. For SQL stores, `Serial` requires numeric auto-increment columns and `Database` requires application database defaults. The memory adapter uses its current table length plus one for `Serial`; deletion can therefore produce duplicate IDs. `Database` omits IDs in memory. PostgreSQL `Uuid` uses the database UUID default; SQLite generates UUIDs in Rust. These options do not change existing columns or migrations.

Generate matching entities and an initial migration with `better-auth-rs generate --generate-id serial`, or `--generate-id uuid --database postgres`. The database option accepts `sqlite` (default), `postgres`, and `mysql`, and selects ID and application JSON storage types and fresh catalog defaults. Serial schemas use `i64` IDs and references for SQLite and `i32` for PostgreSQL and MySQL; PostgreSQL uses identity columns, SQLite uses integer primary keys, and MySQL uses auto-increment columns. UUID schemas use native `Uuid` fields and `pg_catalog.gen_random_uuid()` defaults for PostgreSQL; SQLite and MySQL retain text IDs. Use the generated schema with the selected database backend.

`--generate-id database` preserves the upstream text-ID schema without inventing defaults. Add application-owned defaults before using `IdGeneration::Database`, or use an existing numeric or UUID schema with its own defaults. `AuthEntity` derives read the declared ID and user-reference types, parse public string IDs at the model boundary, and leave absent IDs unset. The generator marks additional ID references with `#[auth(reference)]`; use the same attribute on handwritten reference fields.

A custom generator receives the logical model name, such as `user`, `apikey`, or `walletAddress`. Table aliases do not change that name. Return `Ok(None)` to omit the ID, or an error to stop the write. Create-before hooks run before generation. A cancelled hook does not invoke the generator.

```rust
use better_auth::config::IdGeneration;
let mut config = better_auth::AuthConfig::new("your-very-secure-secret-key-at-least-32-chars-long");
config.advanced.database.generate_id = Some(IdGeneration::Uuid);
```

An explicit `CreateUser.id`, `CreateOrganization.id`, `CreateInvitation.id`, or `CreateTeam.id` is a force-allowed ID. UUID mode accepts canonical hyphenated RFC 4122 version 1–5 IDs, including uppercase hexadecimal characters. Simple, braced, URN, and version 7 forms are omitted; the database then applies its default or constraint. `CreateOrganization::new` leaves generation to the store. `WalletStore::create_wallet_address` takes `CreateWalletAddress` without a caller-generated ID.

In `Serial` mode, the SQL adapter applies JavaScript number conversion before ID lookups and core, plugin, and organization reference writes. For example, `"1.6e1"`, `" 16 "`, and `"0x10"` address integer ID `16`. The adapter applies reference conversion after application input transforms and before the persistence model parses the value. Invalid or fractional values still encounter the model or database's numeric constraints. `Database` mode does not enable this conversion. `AuthEntity` supplies declared reference-column metadata through `SeaOrmPluginModel::is_id_reference` and `SeaOrmOrganizationModel::is_id_reference`; manual implementations must identify their ID reference columns. Explicit field policies override that metadata, and ordinary fields retain their input values.

Pure-secondary sessions and API keys use the context generator. The legacy `advanced.generate_id` callback overrides that context operation only. `IdGenerator` returns `Option<String>`: `None` represents upstream `false`, and `Some(value)` represents a string. Pure-secondary sessions use a random ID for `None`; an explicit empty string omits the session ID. Pure-secondary API keys use the upstream truthy fallback for both cases. Pure-secondary verification records have no generated ID. Session tokens and other authentication credentials use separate random generators.

Runtime records use `SchemaValue<String>` for IDs so `Undefined` remains distinct from an empty string. JSON omits absent IDs. Store and database-hook methods return `UserView` and `SessionView`; `AuthSchema::User` and `AuthSchema::Session` remain typed database mappings. Use `id.typed()?` only when the operation requires a present string ID. Use `id.is_undefined()` to inspect omission. Query application entity models directly when an application needs columns outside its configured auth fields.

The opt-in PostgreSQL identity regressions use application-owned integer models. They check `Serial` and `Database` modes, session/account foreign keys, public string IDs, transaction commit and rollback, numeric aliases, and reference conversion after an input transform. A separate text-ID table checks forced UUID omission against a `gen_random_uuid()::text` default. Set `BETTER_AUTH_TEST_POSTGRES_URL` to a test database whose role can create schemas, then run:

```sh
devenv shell -- cargo test --locked --features axum,seaorm2,redis-cache --test legacy_schema_integration_tests live_postgres -- --ignored
```

The tests create and remove isolated schemas. They do not establish upstream driver parity or cover MySQL, native UUID column models, or additional reference columns outside the core account/session mappings.

## Fresh SQLite Session representation

New SQLite generation emits `#[auth(role = "session", row_presence)]`. The model omits the Rust `active` extension, uses table `session` and native camelCase columns, and retains the typed Session API. Native strings use TEXT, dates use literal `date`, token uniqueness is inline, and the mapped userId index uses the shared upstream naming rule. The fresh catalog has no independent active column or expiresAt index. Core expiry, cache, and row-existence behavior remain unchanged.

Use `--session-active-column` when application-owned regeneration must retain the Rust independent active state. This flag preserves the previous SQLite Session representation and physical defaults. PostgreSQL and MySQL generation remain active-backed. Existing generated source, handwritten models, bundled entities, and migration history do not change automatically. The flag is a Rust extension, not an upstream option.

`SeaOrmSessionModel::active_column()` now returns `Option<Self::Column>`. Handwritten active-backed implementations must return `Some(the_existing_column)`. The explicit row-presence derive returns `None` and reports `AuthSession::active()` as true; existing expiry checks still apply. Unmarked derives still require the native `active` field. The marker rejects native `active` and any field exposing its logical or serialized alias. Configured logical `active`, including an alias to another model column, requires an active-column model. The adapter resolves the configured column first, so a missing mapping retains its original error. CLI Session additional-field generation remains unsupported.

The generated `create_auth_tables` is an initial creation scaffold. Applications own versioned migrations and must preserve historical inactive state on its active-backed model until they explicitly adopt and validate a migration. The library does not infer historical meaning from arbitrary column names, validate handwritten getter semantics, or automatically reject rebinding to a historical table. Changing date affinity with unchanged Chrono bindings does not establish raw timestamp interchangeability.

## Database rate limits

Select `RateLimitStorageKind::Database` in `RateLimitConfig` to share request counters through the auth store. Generate the table explicitly; `--plugins all` does not enable database rate-limit storage:

```sh
better-auth-rs generate --rate-limit-database --schema-config schema.json --output src/auth_schema.rs
```

The optional `rateLimit` schema entry accepts `modelName` and mappings for `key`, `count`, and `lastRequest`:

```json
{"rateLimit":{"modelName":"request_limits","fields":{"key":"bucket","count":"requests","lastRequest":"requested_at_ms"}}}
```

Bind the generated `AppPluginSchema` through `with_plugin_schema`. The rate-limit model uses a unique string key, `SqlNumber` count stored in an INTEGER column, and an `i64` timestamp in Unix milliseconds. `SqlNumber` preserves fractional counters read from SQLite; comparisons retain the configured floating-point window and maximum without integer conversion.

Custom auth stores implement `RateLimitStore::consume_rate_limit` as one atomic decision and update. Concurrent callers must share the same unique key and conditional counter updates. A denied request must not change the counter or timestamp. The cleanup window belongs to the current request's configured rules; the store must not retain a historical maximum.

The SeaORM adapter prunes old rows only after a successful expired-window reset. Better Auth 1.7.6 logs pruning failures and preserves that successful decision. The adapter follows this specific behavior; counter reads, inserts, and updates still propagate errors. SQLite binds NaN comparisons as SQL NULL and preserves Infinity, matching the upstream database adapter's numerical behavior.

Core field keys use upstream camelCase names. Rust core fields retain their snake_case names. Optional initialization telemetry reads these declarations from the same input used to generate entities and migrations. Omitted mappings remain omitted; `fields: {}` remains an explicit empty map. Existing handwritten and derived schemas use the method’s empty default. Regenerate the schema after changing declaration input. The method does not infer declarations from physical database names.

For database rate limits, the CLI retains an explicit `rateLimit.modelName` on the generated RateLimit model with `#[auth(role = "rate_limit", model_name = "...")]`. `SeaOrmPluginModel::model_declaration()` defaults to `None`; the generated derive supplies the original name. `SeaOrmStore` reports the declaration from its current `P::RateLimit` binding through `RuntimeStore::rate_limit_model_declaration()`. Memory stores do not invent model declarations. Rate-limit field mappings affect generated SQL, but the upstream telemetry projection does not include them.

Account, Verification, and all Organization models except `teamMember` support `additionalFields` in the CLI schema configuration. Supported types are `string`, `number`, `boolean`, `date`, `json`, `string[]`, `number[]`, and string arrays that define enum values. Array fields use transparent typed JSON wrappers. Enum fields use `String` storage; the CLI does not generate enum validation. Omitted or true `required` generates a nonnullable column and field. `required: false` generates a nullable column and an `Option` field. Organization role fields always remain nullable because upstream makes these fields optional when constructing the role update endpoint.

An additional field with a built-in public name, such as `name`, `logo`, or `createdAt`, replaces that field's generated type and nullability. Omitted or true `required` generates a nonnullable column; organization role fields remain nullable. A built-in override also replaces its `fields` mapping: `fieldName` selects the SQL column and Serde serialization name, and omitting `fieldName` restores the default column. Its `unique`, `index`, and `references` settings replace the original single-column indexes and foreign key; necessary composite identity constraints remain. The adapter owns `id`; an additional-field declaration does not change its type, column, or primary key.

Migration attributes use the upstream field configuration:

- `unique: true` creates a unique constraint. `index: true` creates an ordinary index unless `unique` is also true.
- `sortable: true` selects a bounded string column on MySQL. This setting does not create an index.
- `bigint: true` selects `BIGINT` for a `number` field. Generated numeric fields use `SqlNumber`, a transparent `f64` wrapper that reads both integer and floating-point SQL values. Use `f64::from(value)` to access the number. JSON output remains a number. SQLite can store and return fractional values in both `INTEGER` and `BIGINT` columns.
- `references: { "model": "user", "field": "id" }` creates a foreign key. Known logical model and field names resolve through their configured table and column mappings. Unknown model or field names remain literal application table and column names.
- `references.onDelete` accepts `"cascade"`, `"restrict"`, `"no action"`, `"set null"`, and `"set default"`. Omission selects `"cascade"`. Create referenced application tables before calling the initial migration scaffold.

A reference to `id` uses the referenced ID storage type instead of the public field type. The generated string-ID schema uses `ReferenceId` for these fields. This type preserves scalar database bindings during writes and reads the database's text value. Declare matching runtime metadata with `UserFieldConfig { references: Some(UserFieldReference { model: "user".into(), field: "id".into() }), ..Default::default() }`. The adapter applies the application output transform before converting a non-null reference value to a string. JSON and array references to `id` therefore return strings, rather than decoded documents or arrays.

Application-owned user and session models can use the same `ReferenceId` type and runtime metadata. `AuthEntity` resolves Serde field aliases to the corresponding SQL columns. A manually implemented `SeaOrmUserModel` or `SeaOrmSessionModel` must implement `field_column` for configured references; the default implementation reports a configuration error.

The scaffold creates new tables. Constant `defaultValue` values remain adapter defaults and do not become SQL column defaults. With no SQL default, `"set default"` sets a nullable foreign key to SQL `NULL`. Use application-owned versioned migrations to alter existing tables or add database defaults.

Organization records expose replaceable built-in fields as `SchemaValue<T>`. `Typed(T)` contains the default Rust type, `Dynamic(Value)` preserves another JSON type, and `Undefined` omits the field during serialization. Use `.typed()?` when an operation requires the default type and `.json()?` when an application accepts the configured type. Use `.into()` to construct a default value. Output transforms may return `None` to omit a field without removing the stored value. A timestamp replaced with a string retains that string without date normalization.

Organization `updatedAt` is an application field; the bundled store keeps its internal timestamp separate. Team `memberCount` remains the upstream internal counter. Ordinary team responses remove the counter, while full organization queries retain the adapter's projected counter.

The JSON configuration describes storage. The CLI does not generate SQL defaults, validators, transforms, or callback configuration. Additional field runtime metadata may appear in this JSON but does not configure the plugin. Configure the matching public names, types, and `field_name` in `OrganizationConfig.schema` with `UserFieldConfig`. `field_name` accepts the Rust field name or its Serde serialization name; SeaORM's `column_name` attribute controls the SQL column name. ### User field values

User `name` and `image` values preserve omission, null, and raw JSON in `SchemaValue`. Memory retains the values; SQL stores apply the declared column type and database constraints. The default SQL user name is required. Applications with custom nullable models can retain that schema. SQLite JSON columns accept JSON values; non-JSON columns reject arrays and objects. Rust keeps each value bound to its declared column and rejects the upstream Bun driver's parameter-overload behavior. This is an intentional compatibility exception that preserves statement identity conditions.

`SeaOrmUserModel::new_active` and `apply_update` return `AuthResult`. Direct model calls decode supplied `name` and `image` values into the declared column types. Omitted values leave columns unset or unchanged. Incompatible values return serialization errors. `AuthEntity` generates this behavior; handwritten models must implement the same conversion.

Memory string predicates retain type-safe handling of replacement values. Query failures caused by unrelated malformed rows in the upstream adapter are not reproduced.

## Account Hook Cancellation

`AccountStore::create_account_optional` and `update_account_optional` return `None` when a database hook cancels that account write. Hook errors remain errors, including errors from nested writes. The strict `create_account` and `update_account` methods retain their existing cancellation error behavior. Custom stores with cancellable hooks must implement the optional methods; their default implementations wrap successful strict results in `Some`.

Account schemas permit duplicate `(provider_id, account_id)` pairs, matching upstream storage. `AccountStore::get_account` reads at most two matching records and rejects an ambiguous identity after output projection. Its two-row limit is independent of `advanced.database.default_find_many_limit`. Generated schemas retain the account user index and foreign key. Existing applications that require upstream storage behavior must remove the former composite unique index in an application-owned migration; schema generation does not alter existing databases. Resolve duplicate identities before authentication can select an account.

## JSON field bindings

For fresh application JSON declarations without references, `--database sqlite` generates `SqlText` or `Option<SqlText>`. The fully qualified type is `better_auth::seaorm::SqlText`, an alias of the existing scalar-capable `ReferenceId` storage implementation. The alias alone does not declare a reference. PostgreSQL and MySQL continue to generate `Json`; native overrides and reference fields retain their existing types. User and Session additional-field generation remains unsupported.

Keep the runtime field policy as `UserFieldType::Json`. Omission stays absent, while explicit null becomes JSON text `null`. Objects and arrays become encoded text. Encoded strings, including whitespace and invalid JSON, remain unchanged in storage. Number and Boolean inputs retain SQLite scalar bindings; TEXT affinity produces their stored text. Output callbacks receive stored text before JSON decoding. Invalid encoded text reaches the existing parser, which logs the error and returns null.

The SQLite binding also applies to application-owned TEXT-compatible columns with a declared non-reference JSON policy, including configured native TEXT overrides. A handwritten model must accept the scalar bindings; incompatible types return the existing database type error. `SqlText` supplies that capability. The old ID/reference branch remains unchanged. An explicit typed `Json` column retains its previous representation limits, including the distinction between SQL NULL and encoded JSON null on input; this generator change does not repair every handwritten model.

Regeneration changes the public Rust field type of affected SQLite models. Existing generated files and persisted values do not change automatically. The generated JSON columns already use SQLite TEXT, so this change adds no migration or data rewrite. Review application code that directly accesses those model fields; persisted `SqlText` values use the `Text(String)` variant. The pinned SQLite capture, strict Bun comparison, and generated Organization consumer pass for 11 create/read cases and three update/read cases. The comparison preserves complete callback events, returned display values, and exact stored text or SQL NULL. The CLI generation tests and all 23 library consumers pass; the live PostgreSQL test remains separate.

When a field binding requires JSON text, the adapter uses the shared JavaScript-compatible serializer. The serializer orders array-index property names before other keys and uses JavaScript number formatting. Input policies run before this conversion. Output callbacks receive the stored text, or text reconstructed from a typed JSON value, before the adapter decodes the callback result.

`UserFieldConfig::adapter_input(value, supports_native_json, native_json_field)` returns `AuthResult<Value>`. Custom adapter callers must propagate or handle this result. `storage_fields_for_adapter`, `record_storage_fields_for_adapter`, and `adapter_output` retain their existing fallible signatures. Serialization errors propagate before the corresponding write or output callback; no fallback serializer runs.

This conversion applies where the existing field and adapter flags require text. It does not change reference conversion or native JSON capabilities. Native SQL JSON columns still use the database driver's serialization and normalization. Callback text equivalence does not establish identical raw native-column bytes. Application-owned column types and existing stored values remain unchanged.

## Notes

- Custom stores must report uniqueness conflicts as `DatabaseError::UniqueConstraint`. Device code generation retries only that error, up to three attempts.
- Custom stores expose JSON adapter behavior through `UserStore::supports_native_json`, inherited by `AuthStore`. Return `false` when field callbacks receive JSON text, as with SQLite; return `true` for native JSON, as with PostgreSQL. The secondary storage facade forwards the database capability.
- `AuthEntity` supplies `SeaOrmUserModel::native_json_field` and `SeaOrmSessionModel::native_json_field` from column definitions. Handwritten models must return `true` for serialized application field names backed by JSON columns. This preserves native JSON objects in typed models while the output boundary supplies adapter text to callbacks.
- Better Auth no longer owns a public SeaORM migration path. Auth and app tables should be migrated together by the host application.
- `MemoryCacheAdapter` and the optional asynchronous `RedisAdapter` implement `SecondaryStorage`. Install an adapter with `BetterAuth::secondary_storage` to enable session persistence. `RedisAdapter::clear` clears the selected Redis database.

## Secondary Session and Verification Storage

Install `MemoryCacheAdapter`, `RedisAdapter`, or an application implementation through `BetterAuth::secondary_storage`. The runtime uses the backend for sessions and verification values. Set `session.store_session_in_database` and `verification.store_in_database` to retain database persistence. Session creation writes to secondary storage immediately by default, including inside a database transaction. The cache snapshot reads the user through the active transaction. A later rollback does not undo that cache write, matching upstream. `AuthTransaction::create_session_with_deferred_secondary` delays the cache write until commit, after session after hooks; Passkey registration uses this explicit mode. Rollback discards deferred writes.

When rate limiting selects secondary storage, the adapter must implement `SecondaryStorage::increment(key, ttl_seconds)`. Increment or create the counter atomically and return the new count. Apply the TTL only when creating the counter; later increments must preserve its expiration. Both bundled adapters provide this operation. The default trait method returns a configuration error when rate limiting requires the missing operation.

To run the Redis counter regression, set `REDIS_TEST_URL` to a disposable Redis 7+ instance:

```bash
devenv shell -- cargo test -p better-auth-core --locked --features redis-cache redis_counters_create_atomically_and_preserve_the_initial_expiration -- --ignored
```

Custom transaction adapters must implement `AuthTransaction::clone_handle`. The returned adapter retains the original transaction, including its finalized state. Finalization must not wait for retained handles. SeaORM serializes commit and rollback against individual SQL operations; application callbacks do not hold the connection lock. A retained SQL adapter rejects reads and writes after commit or rollback. The memory adapter retains its isolated rows. Rows installed during commit remain shared; unchanged base rows remain separate. A late memory update can change a shared committed row, but a late create or delete does not become a normal-store operation.

Custom `AuthTransaction` implementations must also implement WalletStore. Execute Wallet creation and both address lookup forms through the same active adapter. Preserve registered field policies and propagate errors to the transaction owner.

The memory adapter follows Better Auth 1.7.6's public-ID transaction merge. Missing or duplicated IDs can cause an update to disappear during commit. Changing an ID can move the row to the end of its table. These behaviors are upstream compatibility constraints; use unique, stable IDs for applications that rely on memory transactions.

Custom transaction adapters must implement `AuthTransaction::delete_verification_by_identifier` through the active adapter. Preserve verification deletion hooks and the existing ordered after-commit rules.

The transaction owner keeps its after-hook queue alive until commit processing finishes. Retained adapters use weak queue references. Rollback, an after-hook error, or completed processing drops unexecuted effects and releases their captured transaction handles. Effects appended while the queue is being drained run in insertion order. Effects appended after processing ends do not restart the queue.

Custom transaction adapters must implement `AuthTransaction::queue_after_commit`. Add each effect to the same ordered queue as database after hooks. Run the queue after commit, discard the queue on rollback, and stop at the first unhandled error. Keep the committing caller's ambient request scope during the drain. Capture each database hook's explicit request argument separately when the write occurs. `after_create_runtime_session` and `after_create_runtime_verification` accept that captured argument for secondary-only writes. A separate cache queue would reorder effects around later database hooks and could skip an earlier cache refresh when a later hook fails.

Adapters used with secondary sessions must implement `SessionStore::update_session_with_writer`. Run before hooks once, pass the accumulated `SessionUpdate` to the supplied `SessionUpdateWriter`, then perform the database write when `write_database` is true. Run after hooks with the selected nullable result. Do not call a second complete update lifecycle after the cache writer. The four existing update convenience methods retain their original behavior when no secondary backend is installed.

`delete_user_sessions_optional` returns `None` when a before hook cancels the batch and `Some(count)` after a completed write, including `Some(0)`. `UserStore::delete_user_optional` and its transaction counterpart preserve the same cancellation boundary for user deletion. Delete session children first when enabled, then account children, then the user. Child cancellation does not cancel later user deletion. Custom adapters must preserve these results so the secondary facade can decide whether to delete cached sessions; the default capability methods return explicit configuration errors.

`SessionStore::delete_sessions` deletes a token list through one batch lifecycle. `end_sessions` expires only its live rows and preserves database records. Multi-session uses these capabilities instead of repeated single-session deletion. With secondary storage, token deletions start together before the database batch and leave active-session indices unchanged. The first cache error prevents the database batch while pending cache deletions continue. Custom adapters must implement both batch capabilities when these paths are used; default implementations return configuration errors.

`AuthEntity` supplies field mappings for custom session models. Runtime store and hook results use `UserView` and `SessionView`; these records preserve fields from secondary storage without constructing an application entity model. Account and Verification persistence models instead produce `AccountView` and `VerificationView` through their `record` methods; secondary verification storage uses `VerificationView` directly. See [Secondary Storage](/docs/concepts/secondary-storage) for fallback rules and `VerificationIdentifierConfig` migration behavior.

## Runtime schema validation

SeaORM stores backed by SQLite, PostgreSQL or MySQL validate the configured physical tables before HTTP request hooks, native endpoints and outer transactions. PostgreSQL resolves unqualified entity tables through the effective connection search path. MySQL inspects the current database. Enable SeaORM's `sqlx-mysql` feature in the application to connect to MySQL. Initialization logs failures without rejecting the auth context. A disabled HTTP path returns its 404 before validation. Direct adapter CRUD does not run preflight.

The check reports missing tables, missing columns and extra required columns that inserts do not write. It does not validate SQL types, expected nullability, indexes or foreign keys. `AuthError::SchemaCheck` preserves structured `SchemaFinding` values. Configuration errors in entity mappings remain configuration errors.

Set `config.advanced.database.validate_schema = Some(false)` to disable automatic validation. `auth.context().database.schema_validation()` still exposes the explicit check. Adapters without introspection log a warning only when validation is explicitly enabled.

Each auth build has an independent cached verdict. Concurrent calls share one check. Successful checks and schema mismatches remain cached; driver errors can retry. Store clones share only the invalidation revision. After an application migration with actual schema changes, call `store.invalidate_schema_check()`, including after a partially failed migration. Call this on the original SeaORM store or a clone created before building auth. Separately constructed stores need separate invalidation, even if they share a SQLx pool. The adapter does not poll for DDL or automatically detect direct SQL changes. A migration with no changes need not invalidate.

The optional PostgreSQL acceptance test verifies migrations, cached results, defaults, serial columns and search-path precedence against a real server. Set `BETTER_AUTH_TEST_POSTGRES_URL` to a test database whose role can create and drop schemas, then run `devenv shell -- cargo test --locked --features axum,seaorm2,redis-cache --test schema_preflight_tests live_postgres_ -- --ignored`. The test removes its isolated schemas after success. If the test fails, inspect and remove its `ba_preflight_` schemas before repeating the test.

`AuthEntity` provides physical core-field mappings automatically. Handwritten models must implement `field_column` for every core and configured field. Use the existing typed `Column` values so `column_name` remains authoritative. If a handwritten `new_active` supplies extra application columns outside field policies, declare only those columns through `extra_insert_columns`:

```rust,ignore
fn extra_insert_columns() -> Vec<Column> {
    vec![Column::TenantId, Column::Locale]
}
```

Leave the default empty list when inserts do not supply extra columns. Do not declare every entity column: an unconfigured required column must still fail preflight.

Custom database adapters can implement `RuntimeStore::schema_check` using `SchemaInspector` and the typed physical `SchemaTable` descriptors. The descriptor supports migration-disabled tables and merges logical models that share a physical table. It does not use OpenAPI documentation as persistence metadata.

Organization member queries supply an explicit user limit. Full organization queries use the static membership limit for the user page. A member without a matching user fails the operation.
