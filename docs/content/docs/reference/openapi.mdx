Better Auth RS generates the Better Auth 1.7.6 OpenAPI 3.1.1 document from the authentication instance's configuration. The document includes request bodies, parameters, response metadata, model fields, security schemes, and error responses.

## HTTP reference

Register `OpenApiPlugin` to expose `GET /open-api/generate-schema` and `GET /reference` under your authentication base path:

```rust
use better_auth::plugins::{OpenApiConfig, OpenApiPlugin};

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(EmailPasswordPlugin::new())
    .plugin(OpenApiPlugin::with_config(OpenApiConfig {
        path: "/reference".into(),
        theme: Some("moon".into()),
        nonce: Some("application-csp-nonce".into()),
        ..Default::default()
    }))
    .build()
    .await?;
```

The reference page uses Scalar. `disable_default_reference: true` keeps the reference endpoint registered and makes the endpoint return an empty 404 response. The schema endpoint remains available.

The nonce applies to the two executable scripts. Configure the application's Content Security Policy separately. Treat the theme and nonce as trusted application configuration.

This example assumes an existing `AppAuthSchema` and store. See the [Axum integration guide](/docs/integrations/axum) for a complete application.

## Programmatic access

Generate the document from the initialized authentication instance:

```rust
let spec = auth.openapi_spec()?;
let json = spec.to_json()?;
```

Use `call_endpoint` with `EndpointInput.request` to resolve a dynamic base URL for a native schema request. The HTTP schema and reference endpoints resolve the base URL from each request. Concurrent tenant requests do not change the instance's initial context.

## Document behavior

- Core endpoint metadata is included even when a feature is disabled. The endpoint's handler enforces the feature setting.
- `disabled_paths` removes matching paths from the document.
- Configured plugins contribute their endpoint metadata and logical models. OpenAPI plugin routes and server-only endpoints are omitted.
- `JwtPlugin::jwks_path` changes the documented JWKS path and preserves the complete operation metadata. Add the configured path to `disabled_paths` to omit the operation.
- Physical table and column mappings do not rename logical model or field keys.
- With secondary storage, the Verification component is omitted unless `verification.store_in_database` is true. Plugin metadata and application fields do not override this final model-presence rule. The generated document retains the Session component independently of session persistence.
- With database rate-limit storage, the native RateLimit fields replace a plugin's entire same-name model declaration. The component keeps its first model position. Memory storage retains the plugin declaration.
- Additional field policies control documented properties, required fields, and read-only flags. Schema generation does not call default factories, transforms, or validators.
- User input properties are merged into the signup and update-user request bodies. The model projection and input projection retain their separate policy precedence.

Custom plugins can attach `OpenApiRouteMetadata` with `AuthRoute::openapi`. Fields registered during initialization enter model components automatically. Final registered adapter policies replace explicit `AuthPlugin::openapi().model(...)` metadata for the same non-core model field. Explicit metadata still supplies unregistered fields, models, and routes. Core model and User input precedence remain unchanged. OrganizationRole retains its configured enablement and optional-field rules. Metadata describes the endpoint; the endpoint retains responsibility for input validation.

Generated model fields retain their first declaration position across configured plugins, including core fields registered without duplicate OpenAPI metadata. Ordinary core names retain their native schema positions. Replacing a policy changes its documented value without moving its first position. Within one plugin, explicit model metadata retains its field order; registered names absent from that metadata follow it. The five Organization models retain their existing schema order and optionality rules. This document order does not change adapter callback order.

Generated field maps then use JavaScript property enumeration: array-index names appear first in numeric order, followed by other names in declaration order. Leading-zero names and `4294967295` are ordinary names. Components keep `id` first in their generated `required` array. User request schemas retain their existing required fields before appended additional requirements. Generated property maps preserve this order for native `OpenApiSpec::to_value` consumers as well as HTTP output. Explicitly supplied required arrays and the pretty `to_json` format remain unchanged.

The final component model map uses the same enumeration rule after logical model names are capitalized. Numeric array-index model names appear before ordinary model names, including core models. Leading-zero model names and `4294967295` keep their ordinary insertion positions. Native `OpenApiSpec::components`, `to_value`, and `to_json` retain this order. The OpenAPI plugin's HTTP schema and Scalar page already apply JavaScript ordering during serialization. Model values, capitalization, and replacement precedence do not change.

Response maps use JavaScript property enumeration after endpoint responses replace default error responses. Numeric status codes appear in ascending order. Other keys, such as `default` and `2XX`, retain their declaration order after numeric keys. Native `OpenApiSpec` consumers and serialized documents retain this order.

Endpoint keys within each plugin follow the same enumeration rule before operation IDs are assigned. Numeric array-index keys appear first; other keys retain their declaration order. This order determines documented path insertion and duplicate `operationId` suffixes. Core endpoints remain before plugin endpoints, and configured plugin order remains unchanged. Metadata ordering does not change runtime route dispatch.

For the mapped API Key, DeviceCode, Passkey, JWK, and WalletAddress roles, runtime registration preserves the model's first plugin position. An explicitly empty `Some(IndexMap::new())` field map declares an id-only component when no other declaration supplies fields. `None` does not declare a model. Explicit metadata retains its existing precedence within one plugin. Organization and Team use their existing schema assembly, and OrganizationRole retains its enablement rule.

Direct `OpenApiRegistry::new` callers must pass the resolved `ModelFields` as the final argument. `BetterAuth` also pairs each plugin's metadata with its successful field declarations. A custom initialization driver must drain `AuthInitContext::take_registered_model_field_names` after each successful `on_init` and attach those groups with `OpenApiPluginMetadata::registered_field_names` when it collects that plugin's metadata. Both hidden startup methods now use `Vec<(EntityRole, Vec<String>)>` instead of flat `(EntityRole, String)` pairs. Each group identifies a declared model and its ordered field names, including an empty vector for an explicit empty declaration. These methods carry no policy values; resolved policies still supply field values. Keep metadata collection at its existing initialization stage so metadata errors retain their order.

The docs site consumes `docs/better-auth.json`, which is generated from the Rust docs profile. The runtime document uses the configuration of the serving authentication instance.
