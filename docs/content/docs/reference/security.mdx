Better Auth is designed with security as a core principle. This page documents the security mechanisms built into the framework and best practices for production deployments.

## Password Security

### Hashing Algorithm

The default `ScryptPasswordHasher` matches upstream: NFKC normalization, scrypt with `N=16384`, `r=16`, `p=1`, and a 64-byte derived key. Stored credentials use `salt:hash` with a random hexadecimal salt. `Argon2PasswordHasher` remains available for applications that explicitly select their existing credential format. The default hasher does not fall back to another algorithm.

Add [Have I Been Pwned](/docs/plugins/have-i-been-pwned) to reject compromised passwords before credential writes.

### Password Policies

Configure minimum password requirements:

```rust
let config = AuthConfig::new("secret-key-at-least-32-chars")
    .password_min_length(8);
```

## Session Security

### Token Generation

Session tokens are generated using cryptographically secure random number generators (`OsRng`). Tokens are sufficiently long to prevent brute-force guessing.

### Cookie Configuration

These examples assume you've already defined `AppAuthSchema`. If you want a complete setup from entity definitions through Axum mounting, start with the [Axum integration guide](/docs/integrations/axum).

```rust
use better_auth::AuthConfig;
use better_auth::config::SameSite;

let mut config = AuthConfig::new("secret-key");
config.session.cookie_secure = true;        // HTTPS only
config.session.cookie_http_only = true;     // Not accessible via JavaScript
config.session.cookie_same_site = SameSite::Lax; // CSRF protection
```

| Setting            | Recommended | Description                                        |
| ------------------ | ----------- | -------------------------------------------------- |
| `cookie_secure`    | `true`      | Only send over HTTPS                               |
| `cookie_http_only` | `true`      | Block JavaScript access (prevents XSS token theft) |
| `cookie_same_site` | `Lax`       | Prevents CSRF while allowing top-level navigations |

See [Cookies](/docs/concepts/cookies) for more details.

### Session Expiration

Sessions have a configurable expiration time. Expired sessions are automatically rejected.

```rust
use std::time::Duration;

let config = AuthConfig::new("secret-key")
    .session_expires_in(Duration::from_secs(7 * 24 * 3600)); // 7 days
```

## CSRF Protection

Better Auth follows the upstream Better Auth web model:

- mutating requests that carry cookies must present a trusted `Origin` or `Referer`
- `/sign-up/email` and `/sign-in/email` also use Fetch Metadata headers to block cross-site navigation login attacks on first login
- the frontend SDK works with cookie sessions directly; no custom CSRF token header is required for the standard `better-auth/react` flow

```rust
use better_auth::middleware::CsrfConfig;
use better_auth::{AuthConfig, BetterAuth};

let config = AuthConfig::new(secret)
        .trusted_origins(vec!["https://myapp.com".to_string()]);

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .csrf(CsrfConfig::new().enabled(true))
    .build()
    .await?;
```

Requests from untrusted origins receive a `403 Forbidden` response.
Better Auth also validates callback and redirect targets against `trusted_origins` unless `advanced.disable_origin_check` is enabled.

`advanced.disable_csrf_check` preserves an unset value. With `disable_origin_check = true`, `None` also disables form CSRF checks for upstream compatibility. `Some(false)` retains Fetch Metadata checks against cross-site navigation; `Some(true)` disables those checks explicitly. The `AuthConfig::disable_csrf_check(bool)` builder sets an explicit value.

Matched HTTP endpoints decode JSON before origin checks and endpoint authentication. Email sign-in, email sign-up, OAuth callbacks, and device-code requests also accept URL-encoded forms. CAPTCHA runs before body decoding. Native APIs use typed input and skip this HTTP phase.

The origin check selects a truthy body `callbackURL` before the query value. It reads `redirectTo`, `errorCallbackURL`, and `newUserCallbackURL` only from the body. Selected truthy values must be strings; other JSON types return `400 Bad Request`. The origin check skips `null`, `false`, `0`, and empty strings; endpoint validation still applies.

## CORS

Properly configured CORS prevents unauthorized cross-origin access:

```rust
use better_auth::middleware::CorsConfig;

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .cors(
        CorsConfig::new()
            .allowed_origin("https://myapp.com")
            .allow_credentials(true)
    )
    .build()
    .await?;
```

## Rate Limiting

Rate limiting protects against brute-force attacks. See [Rate Limiting](/docs/concepts/rate-limit) for detailed configuration.

Recommended limits for authentication endpoints:

| Endpoint               | Limit | Window |
| ---------------------- | ----- | ------ |
| `/sign-in/email`       | 10    | 60s    |
| `/sign-up/email`       | 5     | 60s    |
| `/request-password-reset`     | 3     | 300s   |
| `/two-factor/verify-*` | 5     | 60s    |

## OAuth Security

### PKCE

All OAuth flows use PKCE (Proof Key for Code Exchange) with S256 challenge method. This prevents authorization code interception attacks.

### State Parameter

OAuth state is validated on every callback to prevent CSRF attacks. State tokens expire after 10 minutes.

### Token Storage

Set `account.encrypt_oauth_tokens = true` to encrypt stored OAuth access and refresh tokens. Authenticated account token endpoints can return those tokens. ID tokens remain unencrypted, matching upstream. The optional account cookie uses authenticated JWE encryption.

## Two-Factor Authentication

### TOTP

TOTP secrets are stored securely in the database. Codes are time-based with a configurable period (default: 30 seconds).

### Backup Codes

Backup codes use encrypted JSON by default. Configure a hashing or application codec when the application requires a different storage policy. Successful verification consumes the selected code.

### OTP

Email-based OTP codes expire after 5 minutes and are single-use.

## Body Size Limits

Reject oversized request bodies to prevent denial-of-service:

```rust
use better_auth::BodyLimitConfig;

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .body_limit(BodyLimitConfig::new().max_bytes(512 * 1024))
    .build()
    .await?;
```

## Secret Key

The secret key is used for signing and verification. Use a key with these properties:

- At least 32 characters long
- Kept secret and never committed to version control
- Loaded from environment variables in production

```rust
let secret = std::env::var("AUTH_SECRET").expect("AUTH_SECRET must be set");
let config = AuthConfig::new(&secret);
```

### Secret Rotation

Configure `AuthConfig.secrets` with the current encryption key first and retain older keys while records still require them:

```rust
use better_auth::{AuthConfig, config::VersionedSecret};

let config = AuthConfig::new(std::env::var("LEGACY_AUTH_SECRET")?)
    .secrets(vec![
        VersionedSecret::new(2, std::env::var("CURRENT_AUTH_SECRET")?),
        VersionedSecret::new(1, std::env::var("PREVIOUS_AUTH_SECRET")?),
    ]);
```

New symmetric records use `$ba$<version>$` envelopes. Decryption selects the retained key named in the envelope. A retired version fails without trying another key. Bare hexadecimal records require the explicit legacy `secret`. An empty legacy secret disables that migration path.

JWE session and account cookies identify their key by its thumbprint. Readers accept retained keys and the explicit legacy key. An explicit unknown key ID fails; older cookies without a key ID try the retained keys. Cookie purposes remain separate, so an account cookie cannot be decoded as a session cookie.

Signing uses only the current key. Retaining an encryption key does not keep old signed session tokens valid after rotation.

## Production Checklist

- [ ] Set `cookie_secure: true` (requires HTTPS)
- [ ] Set `cookie_http_only: true`
- [ ] Set `cookie_same_site: Lax` or `Strict`
- [ ] Enable CSRF protection with trusted origins
- [ ] Configure rate limiting on all authentication endpoints
- [ ] Use a strong, random secret key (32+ characters)
- [ ] Load secrets from environment variables, not code
- [ ] Set appropriate session expiration times
- [ ] Configure CORS with specific allowed origins
- [ ] Enable body size limits
- [ ] Use HTTPS in production
- [ ] Set up proper `X-Forwarded-For` headers in your reverse proxy
- [ ] Enable email verification for sign-ups
- [ ] Consider enabling 2FA for admin users
